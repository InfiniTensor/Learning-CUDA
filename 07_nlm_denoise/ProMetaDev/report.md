> 国产平台适配：沐曦 MetaX 曦云 C500 + MACA 3.5.3 + OpenCV 4.5.4（见第 9 节，已实测验证，自带测试全部通过）

## 1. 问题描述

深空探测影像在极低照度、短曝光下成像，噪声以随机噪声 + 传感器热噪声为主。普通均值滤波会
把陨石坑边缘和细裂隙一并抹平，过强的局部滤波又会残留颗粒噪声。

非局部均值（NLM）的核心思想：自然图像中存在大量重复或相似的结构，一个像素的真实值可以由
**与它周围 patch 相似的**若干像素加权得到。题目给定的权重为

```
w(p, q) = exp( -max( dist(P_p, P_q) - 2σ², 0 ) / h² )
```

其中 `P_p`、`P_q` 分别是以 `p`、`q` 为中心的两个 patch，`σ` 是噪声强度估计，`h` 是滤波强度。

需要交付一个**可配置、可验证、可分析性能瓶颈**的 GPU NLM 程序：

| 要求 | 本实现 |
|---|---|
| 输入输出 | 灰度/RGB 8 位图像（PNG/JPG/BMP…），输出同格式 |
| 参数文件 | `patch_radius` / `search_radius` / `h` / `sigma`，与题目键名一致 |
| `patch_radius` ≥ 3、`search_radius` ≥ 10 | 支持 `patch_radius` 1~5、`search_radius` 任意 |
| 正确性 | 与**自研 CPU 精确参考**逐像素比对（MAE/PSNR）；另与 OpenCV `fastNlMeansDenoising*` 交叉对照 |
| 性能 | ≥1920×1080 必测，进阶 4K；给出不同参数组合的运行时间、吞吐、加速比 |
| 近似算法 | 提供三档近似开关，并**量化**误差来源 |

### 2.2 规范语义（先定"标准答案"，再写两个实现）

NLM 的公式看着简单，但**边界处理、归一化、候选范围**三处一旦定义模糊，CPU 和 GPU 就会
各写各的、无法判定谁对。因此先在 `include/nlm.h` 里把语义钉死，再让 CPU 参考与 GPU 内核
都实现这一份定义：

```
D(p,q) = Σ_c Σ_{k∈P} ( I_c(clamp(p+k)) - I_c(clamp(q+k)) )²      // 逐通道求和的平方差
w(p,q) = exp( -max( D(p,q)/|P| - 2σ², 0 ) / h² )                 // |P| = nk²·C，含通道数
out(p) = Σ_q w(p,q)·I(q) / Σ_q w(p,q)
```

- 候选 `q` 的搜索范围**裁剪到图像内**（边界像素候选数自然减少）
- patch 读取在边界处按**复制边缘（clamp）**处理，保证 patch 始终完整
- `D` 除以 `|P| = nk²·C` 得到"逐像素逐通道的平均平方差"，因此 `2σ²` 恰好是**纯噪声下该量的期望**

> `|P|` 里的**通道数 C 不能漏**（详见 3.1，这是本项目最严重的一个 bug）。
> 另注：题目把参数写作 `sigma`，本实现中它同时进入 `2σ²` 与 OpenCV 对照，单位与 8 位像素值一致（0-255）。

### 2.3 关键优化：按位移分解 + 可分离盒式求和

**直接做法**：对每个像素 `p`，遍历搜索窗口内每个候选 `q`，每次都重新算一整块 patch 距离。
计算量是 `O(S²·P²)`（`S = 2rs+1`、`P = (2rp+1)²`）。1080p、`rp=3`、`rs=10` 时约
`441 × 49 × 3 ≈ 6.5×10⁴` 次乘加/像素，GPU 上也得上百毫秒。

**本实现**：注意到

```
D(p, p+s) = Σ_{k∈P} G_s(p+k),   G_s(u) = Σ_c ( I_c(clamp(u)) - I_c(clamp(u+s)) )²
```

`G_s` **只与位移 `s` 有关，与 patch 无关**——每个位移只需对全图算一遍 `G_s`（每像素 1 次），
再对 `G_s` 做一次 **P×P 的盒式和**。而盒式求和**可分离**，两次一维累加即可：

```
对每个位移 s=(dx,dy)：
  ① G_s(u)   = Σ_c ( I_c(clamp(u)) - I_c(clamp(u+s)) )²              // 1 次/像素
  ② 水平：H_s(u)  = Σ_j G_s(u + (j·pstep, 0))                        // nk 次/像素
  ③ 垂直：D(p,p+s)= Σ_j H_s(p + (0, j·pstep))                        // nk 次/像素
  ④ w = exp(-max(D/|P| - 2σ², 0)/h²);  num += w·I(clamp(p+s)); den += w
```

计算量降到 `O(S²·(2·nk + 1))`，1080p 上约 `441 × 15 ≈ 6.6×10³` 次/像素——**降了约一个数量级**，
且每一步都是规则访存，非常适合 GPU。**这个改写不改变任何数学结果**：GPU 与 CPU 参考输出
MAE = 0.0000（第 4 节）。

### 2.4 GPU 实现要点

| 点 | 做法 |
|---|---|
| 并行粒度 | **一个线程 = 一个输出像素（含全部通道）**；`block = 32×8 = 256` 线程 |
| 共享内存分块 | 块内共享 `(32+2rp) × (8+2rp)` 的 `G_s` 缓冲 + `(8+2rp) × 32` 的水平累加结果（rp=3 时约 4.4 KB），**带 halo，每个位移只从全局读一次** |
| 边界 | 全局索引 `clamp`（patch 复制边缘）；候选越界则跳过该位移（搜索窗口裁剪） |
| 位移循环 | 放在**内核内部**，`num[]/den` 常驻寄存器，避免每个位移都写回全局内存 |
| 通道 | 逐通道平方差先求和再算权重 → **精确彩色 NLM**（非"三通道独立降噪"近似） |
| 权重 | 默认 `__expf`（硬件加速指数，相对误差 ~1e-6，远小于 1/255 量化步长）；可选查找表 |
| 模板特化 | `patch_radius ∈ {1..5} × 通道数 ∈ {1,3}` 共 10 个实例，`nk` 与 `pstep` 在编译期可知时内层循环可展开 |
| 计时 | `cudaMalloc` 前置不计入；内核后 `cudaDeviceSynchronize()` 再取时间；首次运行先 `warmup()`（8×8 小图）把 PTX JIT 一次性开销移出计时区间 |

### 2.5 三档近似开关（质量-速度权衡）

| 开关 | 含义 | 性质 |
|---|---|---|
| `search_step = k` | 搜索窗口每隔 k 个候选取一个 | **有损**：候选数降到 1/k² |
| `patch_step = k` | patch 每隔 k 个采样点取一个 | **有损**：patch 距离估计方差变大 |
| `use_lut` + `lut_bins` | 用查找表近似 `exp()` | **近无损**：按指数分档，2048 档实测 MAE ≈ 0.06 |

## 3. 优化历程与开发中发现的问题（真实记录）

### 3.1 最严重的 bug：patch 距离归一化漏了通道数

初版在 `inv_patch` 里只除了 patch 采样点数：

```cpp
const float inv_patch = 1.0f / (float)(nk * nk);          // ✗ 漏了通道数 C
```

而 `D` 累加的是 `nk²·C` 个平方差。灰度（C=1）下看不出问题，**彩色（C=3）下标量被放大 3 倍**：

```
纯噪声下 dd ≈ 3·2σ² - 2σ² = 2·2σ² = 1600   (σ=20)
w = exp(-1600/100) = exp(-16) ≈ 1.1e-7     → 除中心候选外全部权重≈0
```

结果是**输出几乎等于输入**（等于没降噪），而灰度自检 MAE=0.0000、PASS——因为 CPU 参考犯
的是**同一个错误**，两者自洽。这是"自检通过但功能没生效"的典型陷阱：**一致性测试无法
发现"两边一起错"**。

定位方式：把 RGB 结果与"不降噪原图"对比，发现 MAE≈0（降噪前后几乎没变），再去检查权重
是否退化。修复后彩色 PSNR 33.7 dB，灰度不受影响。

> 教训：**归一化的分母要数清楚"到底累加了几项"**；以及"GPU==CPU"是必要而非充分条件，
> 还必须有**外部物理意义上的判据**（这里是与无噪真值的 PSNR）。

### 3.2 LUT 误差大得离谱（MAE 3.68）：分档维度错了，而且 `2σ²` 被减了两次

查找表初版按**距离 `d`** 在 `[0, 255²]` 上等分建表。但权重实际是 `exp(-max(d - 2σ²,0)/h²)`，
在指数域 `x = d/h²` 上变化，`h` 较小时（`h=10`，`h²=100`）档宽被放大 100 倍，
一个档内权重能差好几个数量级 → 实测 MAE 3.68。

改为**按指数 `x = d/h²` 在 `[0, 20]` 上等分**后误差仍偏大，继续查发现 **`2σ²` 被减了两次**：
内核里 `dd = max(msd - 2σ², 0)`，而建表时又折算了 `2σ²`，于是查表路径实际算的是
`exp(-max(d - 4σ², 0)/h²)`。修复：**LUT 路径改用未减 `2σ²` 的 `msd` 查表**。
最终 LUT(2048) 相对精确实现 MAE 降到 **0.0621**，PSNR 反而略高（33.74 vs 33.70，属正常抖动）。

### 3.3 `kernel_ms` 被计成 0.24 ms：kernel launch 是异步的

初版在 `<<<>>>` 之后立刻取时间，结果"内核耗时"只有 0.24 ms，而总耗时 45 ms——
差额全被算进了"回传"阶段。原因是 **kernel launch 是异步的**，必须 `cudaDeviceSynchronize()`
之后才能取时间。修复后内核/预处理/回传三段耗时之和与总耗时自洽。

### 3.4 加速比算反了

`st.speedup = st.total_ms / cpu_ms` —— 得到 0.0003 这种"加速比"。改为 `cpu_ms / total_ms`。

### 3.5 显存分配被算进了总耗时（本轮修复）

`cudaMalloc`/`cudaFree` 在 WSL2 下开销可达数十毫秒。原代码注释写着"分配放在计时之前"，
但实际只放在**分段计时 `t0` 之前**，仍在**总计时 `t_all` 之后**，于是 `T_total` 里混进了
一次性分配开销，导致**同一配置在不同运行里相差最多 1.7 倍**（首次分配 vs 复用缓冲区），
数字完全不可比。修复：把 `ensure()` 整体移到 `t_all` 之前。

### 3.6 笔记本 GPU 热降频：不记录时钟的性能数字没有意义

持续压测下本机 GPU 会明显降频：实测 SM 时钟 **2257~2385 MHz（上限 3090 MHz，约 73~77%）**、
温度 86~87 °C。同一份负载在冷态/热稳态下相差可达 2 倍以上。因此：

- `tests/benchmark.sh` 每一次测试前后都打印 `clocks.sm / clocks.max.sm / temperature / power`
- 每个配置**重复 3 次取中位数**（单次采样波动可达 ±50%）
- 报告同时给出**冷态**与**热稳态**两组数据（第 5 节）

### 3.7 其它踩坑

| 问题 | 现象 | 处理 |
|---|---|---|
| 测试脚本自污染 | 近似模式复用了精确模式的输出文件名，把精确结果覆盖掉，后续对比全错 | 各模式写各自的 `*.png`，文件名区分 |
| shell 解析歧义 | 表格里的数值用 `sed` 提取时命中多行 | 报告中改用 `CSV,` 前缀的机器可读行，人读表格与解析解耦 |
| 参数校验缺失 | `patch_radius=0`、`h=-1`、图片不存在等会静默继续或被 `std::stoi` 抛出难懂异常 | 在 `load_params` 显式校验并给出中文错误；`main` 统一 try/catch 返回非零退出码 |
| WSL2 偶发 `CUDA-capable device(s) is/are busy or unavailable` | 连续快速启动多个 CUDA 进程时出现过 1 次，未能复现 | 如实记录；测试脚本中失败即报错，不掩盖 |
| OpenCV 灰度路径几乎不降噪 | 同样 `h=10, σ=25`，OpenCV 灰度结果 PSNR 仅 20.21 dB（≈输入），而我们 36.50 dB | OpenCV 的 `h` 在灰度/彩色路径语义不同（其灰度路径 `h` 未按 σ 缩放）。报告中标注该对照在灰度下**不可直接比较**，不宣称"我们比 OpenCV 好 16 dB" |

两者最终经"四舍五入 + 截断到 0~255"后**每一位都相同**——即整个算法的数值误差都被

| 对比对象 | MAE | PSNR vs 无噪真值 |
|---|---|---|
| 本实现 vs 无噪真值 | 3.7542 | **33.70 dB** |
| OpenCV `fastNlMeansDenoisingColored` vs 无噪真值 | 4.5734 | 31.52 dB |
| 本实现 vs OpenCV（两者输出的差异） | 2.7055 | —（耗时 302.66 ms，本实现 3.45 ms，**87.7×**） |

即**两者对真值的还原能力相当**（33.70 vs 31.52 dB），而输出差异 MAE ≈ 2.71，来源是
patch 权重策略与边界处理不同（OpenCV 内部对权重做了阈值化"快速"近似），**不是数值错误**。

## 5. 性能指标

### 5.1 指标定义

| 指标 | 含义 |
|---|---|
| `T_preprocess` | 主机端 uint8→float 转换 + H2D 拷贝（`cudaMalloc` **不计入**） |
| `T_kernel` | 内核执行时间（`<<<>>>` 后 `cudaDeviceSynchronize()` 才取时间） |
| `T_download` | D2H 拷贝 |
| `T_total` | 上述三段之和（进程内），吞吐 = 像素数 / `T_total` |
| 加速比 | `T_cpu` 或 `T_opencv` ÷ `T_total` |

| 3 | 10 | 20 | 80.63 | 25.7 | 36.40 |

**读法**：

- **耗时几乎由 `search_radius` 决定**（位移数 `O(rs²)`）：`rs` 10→15，耗时 69 → 161 ms（2.3×，
  接近 (31/21)² = 2.18 的理论值）。这也是算法本身的复杂度瓶颈。
- **`patch_radius` 对耗时影响较小**（1→5 仅 57 → 86 ms）：这正是 2.3 节分解带来的好处——
  patch 大小只影响盒式求和的累加次数，不再乘到候选遍历里。质量上 `rp=1→3` 提升明显
  （35.66→38.00 dB），`rp=3→5` 基本饱和（37.87 dB，且因窗口相对变小而略降）。
- **`h` 太小降噪不足、太大过度平滑**：`h=5` 保留噪声（35.66 dB），`h=10` 最优，`h=20` 开始
  抹细节（36.40 dB 且耗时上升，因为更多权重接近 1 后累加不再提前截断）。

### 5.4 质量-速度权衡（1920×1080 RGB，热稳态）

| 模式 | GPU ms | MPix/s | PSNR vs 真值 | 相对精确模式的代价 |
|---|---|---|---|---|
| 精确 (exact) | 74.51 | 27.8 | 38.00 | — |
| `search_step=2` | 40.51 | 51.2 | 35.21 | −2.79 dB，**1.8×** |
| `search_step=3` | 22.91 | 90.5 | 31.90 | −6.10 dB，**3.3×** |
| `patch_step=2` | 61.22 | 33.9 | 31.65 | −6.35 dB，1.2× |
| `LUT(2048)` | 78.42 | 26.4 | 38.03 | **+0.03 dB（近无损）**，0.95× |
| `search_step=2` + LUT | 24.36 | 85.1 | 35.26 | −2.74 dB，**3.1×** |

**结论与工程取舍**：

- **`search_step` 是最划算的旋钮**：`search_step=2` 用 2.79 dB 换 1.8× 加速；再叠 LUT 可到 3.1×。
  在"实时预览"场景（先出图、再精修）非常合适。
- **`patch_step=2` 不划算**：只快 1.2×（patch 不是瓶颈），却掉 6.35 dB，说明"抽稀 patch"比
  "抽稀搜索窗口"更伤质量。**这直接印证了 2.3 节的分解：瓶颈在搜索窗口，不在 patch**。
- **LUT 在本机是"零收益"**（0.95×，甚至略慢）：因为内核对 `__expf` 有硬件加速，
  而查表要额外读全局内存 + 整数转换。**如实记录**：LUT 的价值在于**无 `__expf` 或不支持
  快速指数指令的平台**（如某些国产加速器），在本机保留该开关是为了验证"近无损"的可行性，
  不作为加速手段。

### 5.5 灰度 vs RGB（1920×1080，热稳态）

| 通道 | GPU ms | MPix/s | PSNR | OpenCV ms | 加速比 |
|---|---|---|---|---|---|
| 灰度 (1ch) | 48.93 | 42.4 | 36.50 | 209.69 | 4.3× |
| 彩色 (3ch) | 80.89 | 25.6 | 37.90 | 553.79 | 6.8× |

彩色耗时约为灰度的 1.65 倍（<3 倍）：因为 `G_s` 的平方差是逐通道的（∝C），
而盒式求和、权重、累加这些"与通道无关"的部分只算一遍。

> ⚠️ 灰度行的 OpenCV 对照**不可直接比较**：OpenCV `fastNlMeansDenoising` 的 `h` 在灰度路径
> 未按 σ 缩放，同样的 `h=10` 它几乎不降噪（PSNR 20.21 dB ≈ 含噪输入）。因此这里只给出
> 对方的耗时，不宣称质量优势。

### 5.6 与 CPU 精确参考的对比

CPU 参考实现是**同一份语义的朴素三重循环**（`O(S²·P²)`，OpenMP 32 线程），用于正确性验证。
它比 GPU 慢两个数量级，只在中小图上取样：

| 分辨率 | CPU 参考 ms（32 线程） | GPU 总 ms | **加速比** | GPU vs CPU 参考 MAE | 两者的 PSNR vs 真值 |
|---|---|---|---|---|---|
| 480×270（RGB，rp=3/rs=10/h=10/σ=25） | 480.32 | 3.00 | **160.0×** | **0.0000**（最大差 1） | 33.37 / 33.37 dB |
| 1280×720（同参数） | 3494.39 | 18.46 | **189.3×** | **0.0000**（最大差 1） | 38.67 / 38.67 dB |

两点值得说明：

1. **加速比随规模增大**（160× → 189×）：CPU 端是纯串行化的算力瓶颈，GPU 端在 480×270 时
   grid 只有 510 个 block（36 个 SM 勉强填满两轮），规模不足；
   到 1280×720（3600 blocks）才进入吞吐饱和区（43.2 → 49.9 MPix/s）。这也解释了
   5.2 节里 480×270 档吞吐偏低的原因。
2. **两者的"vs 真值 PSNR"完全相同**（33.37 / 38.67 dB），而逐像素最大差仅 1（8 位量化的一步），
   说明 GPU 版没有为了速度牺牲任何质量——加速完全来自并行与算法分解，而不是近似。

## 7. 局限与未来可继续提升的方向

**当前局限**

1. **国产平台已完成适配**：沐曦 曦云 C500 + MACA 3.5.3（见第 9 节）。
   自带测试全部通过，GPU 与 CPU 参考 `MAE=0.0000`（逐像素一致）。
   本工程原本强依赖 OpenCV（图像读写 + `fastNlMeansDenoising*` 参考），
   沐曦容器里同样通过 `apt` 装了 OpenCV 4.5.4，因此**源码零改动**。
2. **未采集 `ncu` / `nsys` 数据**（题目列为加分项）：本机为 WSL2，不透传 CUPTI
   （此前项目实测 `nsys` 的 CUDA kernel 段为空），且 sm_120 只能 JIT 运行 sm_90 PTX，
   剖析器无法给出有意义的指令级指标。
3. `search_radius` 增大时耗时按 `O(rs²)` 增长（`rs=15` 已是 161 ms），未做搜索窗口的智能裁剪。
4. 未实现多尺度 / 金字塔 NLM、未使用 Tensor Core。

**可继续提升的方向（按预期收益排序）**

1. **按位移并行**：当前一个 block 在内部**串行**遍历 `S²` 个位移（每次都要一次
   `__syncthreads`）。改成"一次启动处理多个位移、块内归约合并"可以把 `T_kernel` 再压
   2~3 倍，`rs` 很大时收益更明显。
2. **uint8 直达 GPU**：现在主机端把 uint8 转 float 后再上传（4 倍带宽 + 单线程转换）。
   若改为上传 uint8、在内核里用 `uchar4` 向量化读取并就地转换，`T_preprocess` 可降约 4 倍
   （4K 下这部分占 `T_total` 的约 23%）。
3. **`__shared__` 中直接存 uint8/半精度**，减少共享内存占用后可以放大 tile，提高 halo 复用率。
4. **搜索窗口自适应**：按局部方差决定 `rs`，平坦区用大窗口、纹理区用小窗口。
5. 结合 `float4`/`__ldg` 进一步优化全局访存模式。
