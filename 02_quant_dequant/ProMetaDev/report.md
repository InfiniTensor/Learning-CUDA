## 1. 问题描述

现代推理引擎使用 MXFP8、NVFP4 等低精度格式压缩权重与激活，但消费级/较老 GPU
既没有 FP8/FP4 Tensor Core，也没有相关转换指令。因此需要在**普通 CUDA GPU** 上，
用**纯软件**的方式完整实现：

1. 读取 FP32/FP16 输入矩阵；
2. 按配置量化为 MXFP8 或 NVFP4，并按真实位宽**打包**存储；
3. 保存低精度数据与缩放因子；
4. 用 CUDA kernel 将低精度数据**反量化**为 FP16/BF16/FP32；
5. 输出误差统计与性能日志。

约束：基础版本不得依赖 Hopper / Blackwell / Ada 及以上架构特性，不得要求硬件原生
支持 FP8/FP4。

## 2. 数值格式、缩放策略、打包布局与反量化公式

### 2.1 元素格式位布局

| 格式 | 符号 | 指数 | 尾数 | 指数偏置 | 可表示幅值 |
|---|---|---|---|---|---|
| E4M3 | 1 | 4 | 3 | 7 | 次正规步长 2⁻⁹，最大 **448** |
| E5M2 | 1 | 5 | 2 | 15 | 次正规步长 2⁻¹⁶，最大 **57344** |
| E2M1 (FP4) | 1 | 2 | 1 | 1 | **{0, 0.5, 1, 1.5, 2, 3, 4, 6}**，最大 **6** |
| E8M0 | — | 8 | — | 127 | **2^(e−127)**，仅表示 2 的整数次幂 |

解码采用位拼接而非查表，例如 E4M3：

```
E == 0 : v = M · 2⁻⁹                       (次正规)
E >= 1 : v = (8 + M) · 2^(E−10)            (由 ((E+120)<<23)|(M<<20) 直接构造 float)
```

### 2.2 缩放策略

**MXFP8（OCP microscaling）**：每 32 个元素共享一个 E8M0 缩放因子（2 的整数次幂）。

```
e        = ceil(log2(amax_block / max_elem))      // max_elem: E4M3=448, E5M2=57344
scale    = 2^e                                     // 以 E8M0 存储（e + 127）
量化      : q = fp8(x / scale)
反量化    : x̂ = fp8_to_f32(q) · scale
```

采用 `ceil(log2(·))` 保证 block 内最大元素**不溢出**，同时最大程度用满元素格式量程。

**NVFP4（两级缩放）**：

```
gmax     = 全张量 amax
s_g      = gmax / (6 · 448)                        // 张量级 FP32 全局缩放
s_b      = fp8_e4m3(amax_block / 6 / s_g)          // block 内 E4M3 局部缩放
scale    = fp8_e4m3_to_f32(s_b) · s_g
量化      : q = fp4(x / scale)                     // 饱和到 ±6
反量化    : x̂ = fp4_to_f32(q) · scale
```

`s_g` 的取值使**最大 block 的局部缩放恰好落满 E4M3 量程**（`gmax/6/s_g = 448`），
两层缩放共同保证动态范围与精度兼顾。

**`scale_mode`**：`tensor` 模式令 `block_size = 元素总数`（整张量一个缩放因子）；
`block` 模式按 `block_size` 切分。二者共用同一套代码路径，仅 block 粒度不同。

**`block_size` 支持范围**：16 / 32 走共享内存优化路径；**其他任意正整数**走通用路径
（先求 block 缩放因子，再逐元素/逐对量化），已实测 64 / 128 与 CPU 参考逐位一致。

### 2.3 舍入

- **nearest**：四舍五入到最近**偶数**（round-half-to-even），与硬件转换语义一致。
  实现上先把尾数归一化到定点区间再做整数舍入：E4M3 归一化到 `[8,16)`、E5M2 到 `[4,8)`，
  进位溢出则指数加一。
- **stochastic**：先取 `floor`，再以概率 `frac(v)` 加一，实现无偏舍入。
  E2M1 无尾数可归一化，改为先在相邻两个可表示幅值间定位，再按线性概率二选一。
  GPU 端用基于元素全局下标的哈希 RNG，保证与 CPU 参考**逐位一致**（同 seed 同下标同随机数）。

### 2.4 打包布局

- **MXFP8**：每个元素 1 字节，直接 `packed[i] = code`。
- **NVFP4**：**每字节 2 个元素**——低 nibble 存偶数下标元素、高 nibble 存奇数下标元素：
  `packed[i>>1] = (code[i] & 0xF) | ((code[i+1] & 0xF) << 4)`。
  量化时每个线程处理**一对** `(2k, 2k+1)` 元素并合并写出同一字节，避免写竞争；
  反量化实现**向量化 packed load**：一次 `uchar4` 读取 4 个打包字节
  （NVFP4 → 8 个元素，MXFP8 → 4 个元素），每个字节只读一次，消除读放大。

### 2.5 压缩率理论值

| 配置 | 有效位宽 | 压缩率 |
|---|---|---|
| MXFP8, block=32 | 8 + 8/32 = 8.25 bit | 32 / 8.25 = **3.879×** |
| MXFP8, tensor | 8 + 8/N ≈ 8 bit | **≈ 4.0×** |
| NVFP4, block=16 | 4 + 8/16 + 32/N ≈ 4.5 bit | 32 / 4.5 = **7.111×** |
| NVFP4, tensor | 4 + 8/N ≈ 4 bit | **≈ 8.0×** |

实测压缩率与理论值完全一致（见 §6）。

## 3. 实现思路

### 3.1 分层结构

```
lowp.h        纯软件编解码（E4M3/E5M2/E2M1/E8M0），__host__ __device__ 共用，
              保证 CPU 参考与 GPU kernel 使用【同一份数值语义】
io.cpp        张量/配置/权重文件读写；host 端 fp16/bf16 亦为软件位运算实现
reference.cpp CPU 标量参考实现（定义“标准答案”）+ fp32 域反量化
kernels.cu    CUDA 量化/反量化 kernel 与流程编排
main.cpp      CLI 与报告输出
tools/cross_check.py  第三方标准实现的独立交叉验证
```

关键设计：**编解码函数在 host 与 device 两端共用同一实现**，从根上消除
“CPU 与 GPU 算法不一致”这一类问题。

### 3.2 量化 kernel（BLOCK 模式，block_size = 16/32）

采用**共享内存分块 + warp shuffle 规约**：

- 一个线程块处理 `TILE = 256 × BS` 个元素（BS=16 时 4096 个，BS=32 时 8192 个）；
- 载入阶段：256 线程按步长合并读取，tile 数据放入 shared memory（越界补 0，不影响 amax）；
- 缩放阶段：每个 warp 用 `__shfl_xor_sync(..., width=BS)` 在 block 内规约出 `amax`，
  仅 lane 0 计算并写出缩放因子；
- 量化阶段：所有线程再次并行遍历 tile，按重算出的 `1/scale` 做缩放与编码；
  NVFP4 路径每个线程处理一对元素、合并写出一个字节。

访存完全合并，规约无 bank conflict。

### 3.3 量化 kernel（TENSOR 模式与通用 block_size）

NVFP4 需要**全张量 amax**，因此采用两遍：

1. `k_reduce_amax`：grid-stride 遍历 + 块内规约 + `atomicMax(float)`（用 `atomicCAS` 实现）；
2. `k_finalize_scales`：单线程 kernel 计算 `s_g` 与 tensor 模式的统一缩放因子；
3. 主量化 kernel 直接读取 device 侧的缩放结果。

整个量化阶段**无任何主机往返**（见 §4.1），避免同步开销。
非 16/32 的 block_size 走通用路径（`k_block_scales_general` + `k_quant_from_scales_*`）。

### 3.4 反量化 kernel

模板化输出类型（`float` / `__half` / `__nv_bfloat16`），按 `uchar4` 向量化读取打包数据，
按 `i / block_size` 取缩放因子。

## 4. 优化历程与开发中发现的问题（真实记录）

### 4.1 性能计时被主机同步污染

**现象**：1M 元素的量化耗时高达 2.04 ms，有效带宽仅 2.58 GB/s，明显不合理。

**原因**：计时区间 `e0 → e1` 内夹入了 `cudaMemcpy(DeviceToHost)`（把缩放信息回读到主机），
该同步拷贝会强制等待整个管线并引入驱动往返延迟。

**修复**：改为在 device 侧计算缩放并让 kernel 直接读取 `ScaleInfo`（传指针而非传值），
主机回读全部移到计时区间之外。

### 4.2 TENSOR 模式下设备端缩放因子未写入

**现象**：`tensor` 模式 6 个用例全部失败，且 MAE ≈ 0.5（正常应 ≈0.01），
误差值与输入的平均绝对值相当 —— 说明反量化结果**几乎全为 0**。

**原因**：`tensor` 模式的缩放字节由 `k_finalize_scales` 算出后只写到了**主机**
`out.scales[0]`，而反量化 kernel 读取的是 **device** 数组 `d.scales`，该数组从未被写入。

**修复**：把该缩放字节同步上传回 device。修复后全部用例通过。

### 4.3 热路径上的软件 libm 调用

**现象**：量化 kernel 明显慢于反量化（35 GB/s vs 280 GB/s）。

**分析**：量化是**指令受限**而非带宽受限。每元素都要做一次软件编码，而最初的实现中
`f32_to_e4m3` 在归一化时调用了 `ldexpf`（软件实现的 2 的幂缩放，开销大）。

**优化**：

- 用**指数域位加法**替代 `ldexpf`：`bits(a) + (k << 23)`。由于归一化后的结果必为正规数，
  该变换与乘法完全等价，且利用无符号模 2³² 加法天然支持负 `k`。
- `e8m0_to_f32` 同样改为位构造 `c << 23`（c∈[1,254] 时指数域恰为 c），
  仅 `c == 0` 这一极端路径保留 `ldexpf` 以防下溢成 0。

**效果**：MXFP8 量化 2.52 ms → 1.91 ms，反量化带宽 220 → 299 GB/s。

### 4.4 host/device libm 一致性隐患（预防性修复）

`mxfp8_scale_exp` 最初用 `ceilf(log2f(r))` 推导共享指数。`log2f` 是多项式近似，
宿主机 glibc 与 CUDA libm 在末位可能不一致，一旦跨过整数边界就会导致
**缩放因子差一倍**，进而使 CPU 与 GPU 结果不一致。

**修复**：改用 `frexpf` 做精确的指数/尾数拆分（无舍入），
`ceil(log2(r))` 由 `m == 0.5 ? e2-1 : e2` 精确得到，host/device 结果完全确定一致。

### 4.5 向量化 packed load 的收益评估（一次“预期落空”的记录）

**动机**：原反量化逐元素访问 `packed[i>>1]`，NVFP4 下每个字节被读两次，理论上存在 2 倍读放大。

**实现**：改为每线程一次 `uchar4` 读 4 字节（NVFP4 → 8 元素，MXFP8 → 4 元素）。

**结果**：实测带宽提升在**噪声范围内**（±10~15%）。原因是打包数据仅 8 MB，
基本驻留 L2，原先的“重复读”实际被缓存吸收，未真正打到显存。

**结论**：该改动的主要价值是**消除读放大、明确满足题目“实现 packed load/store”的要求**，
而非提升实测带宽。这一“负结果”本身也是有用的工程认知。

### 4.6 其他修正

- `cudaEventElapsedTime` 要求 `float*` 而非 `double*`（编译期发现）。
- 自检中把 `-6` 的 E2M1 编码误写为 `0x8F`；E2M1 是 1 符号位 + 3 幅值位，
  正确值为 `0x0F`（编码实现无误，是测试断言写错）。
- MXFP8 的 BLOCK 模式不写 `d.si`，需预先上传默认值（`gscale = 1.0`）。
- 向量化读取允许尾部越界 3 字节，需将打包缓冲区多分配 16 字节。
- **误差指标口径缺陷**：最初 MAE 基于“反量化结果再舍入到输出类型”计算，
  当数值超出输出类型量程时（如 1e30 转 fp16）会得到 `inf`，掩盖真实量化误差。
  现改为**同时报告两个口径**（见 §6）。

## 5. 正确性验证

### 5.1 编解码自检（`lowprec selftest`，15/15 通过）

- E4M3：全部 254 个有限编码“解码→重编码”往返一致；448 边界；上溢饱和；`encode(1.0)=0x38`
- E5M2：全部有限编码往返一致；最大值 57344
- E2M1：幅值表 `{0,.5,1,1.5,2,3,4,6}` 与往返；上溢饱和到 6；符号位；中点取偶
- E8M0：全部指数往返；`decode(127)=1.0`

### 5.2 端到端测试（`tests/run_tests.sh`，**39/39 通过**）

覆盖：3 种数据分布 × 8 组配置、fp16 输入、权重文件重载、第三方交叉验证、
以及边界与鲁棒性用例。**所有用例的 GPU 结果与 CPU 标量参考逐位一致
（mismatch = 0、max_diff = 0）**。

边界与鲁棒性用例（全部通过且逐位一致）：

| 用例 | 说明 |
|---|---|
| 1001000 元素（32/16 均不整除） | 覆盖尾块 padding 路径 |
| 单元素张量 1×1 | 最小规模 |
| 全零张量 | 缩放因子为 0 的边界路径 |
| block_size = 64 / 128 | 非标准粒度，走通用路径 |

### 5.3 第三方标准实现交叉验证（**关键验证**）

**问题**：仅与自研 CPU 参考“逐位一致”并不足以证明编码语义正确——因为两者
共用同一份编解码代码，属于**自洽验证**而非标准符合性验证。

**方法**：新增 `tools/cross_check.py`，**完全独立**地复现编码过程：

- 用程序自己写出的缩放因子，独立计算每个元素的编码；
- E4M3 / E5M2 的舍入使用 **ml_dtypes**（OCP FP8 标准实现）作为参考；
- E2M1 使用标准幅值表 + 最近偶数舍入的独立 numpy 实现；
- 与程序打包的码流**逐字节**比对。

**结果**：8 个用例**全部 100% 一致**，包括 4096×4096 的 1677 万元素：

| 用例 | 缩放因子一致率 | 元素编码一致率 |
|---|---|---|
| MXFP8 E4M3 / block=32 | 32768/32768 | 1048576/1048576 |
| MXFP8 E5M2 / block=32 | 32768/32768 | 1048576/1048576 |
| MXFP8 E4M3 / tensor | 1/1 | 1048576/1048576 |
| NVFP4 E2M1 / block=16 | 65536/65536 | 1048576/1048576 |
| MXFP8 E4M3 / 4096² | 524288/524288 | 16777216/16777216 |
| NVFP4 E2M1 / 4096² | 1048576/1048576 | 16777216/16777216 |
| NVFP4 E2M1 / outlier 分布 | 65536/65536 | 1048576/1048576 |

**结论**：编码语义与第三方标准实现**逐字节一致**，不再只是自洽。

## 6. 误差指标（1024×1024）

指标口径说明（修正后）：

- **纯量化误差**：反量化结果与原始输入在 **fp32 域**比较，不含输出类型舍入与量程限制；
- **端到端误差**：含 fp16/bf16 输出舍入与量程限制（例如 1e30 转 fp16 会溢出为 inf）；
- **NMAE** = Σ|err| / Σ|ref|，与数值尺度无关，可跨张量/跨格式比较；
- **SQNR** = 10·log10(Σref² / Σerr²)。

下表为**纯量化误差**的 MAE / NMAE（fp32 域，与尺度无关的 NMAE 更适合横向比较）：

| 配置 | random(U[-1,1]) | normal(N(0,1)) | outlier(0.1% 大离群值) |
|---|---|---|---|
| MXFP8 block E4M3 | 0.010410 / 0.020827 | 0.017962 / 0.022507 | 0.020881 / 0.022450 |
| MXFP8 block E5M2 | 0.020809 / 0.041631 | 0.035796 / 0.044852 | 0.041633 / 0.044761 |
| MXFP8 tensor E4M3 | 0.010410 / 0.020827 | 0.017962 / 0.022507 | 0.020897 / 0.022468 |
| NVFP4 block | 0.044219 / 0.088466 | 0.071495 / 0.089582 | 0.084061 / 0.090377 |
| NVFP4 tensor | 0.048625 / 0.097280 | 0.112073 / 0.140426 | **0.812354 / 0.873389** |

### block_size 对精度与压缩率的权衡（NVFP4，1001000 元素，normal 分布）

| block_size | 压缩率 | NMAE |
|---|---|---|
| 16（默认） | 7.111× | 0.089590 |
| 64 | 7.758× | 0.101685 |
| tensor | 8.000× | 0.140408 |

块越大 → 缩放因子越少 → 压缩率越高，但动态范围适配变差 → 精度下降。权衡曲线清晰可见。

**分析**：

1. **MXFP8 明显优于 NVFP4**（NMAE 约低 4 倍），符合预期：E4M3 有 3 位尾数，
   而 E2M1 只有 1 位尾数。
2. **E5M2 比 E4M3 差约 2 倍**：E5M2 动态范围大（57344）但尾数少 1 位，
   在数值分布温和的数据上不划算 —— 这正是 MX 推荐 E4M3 的原因。
3. **block 缩放对 NVFP4 至关重要**：outlier 数据下 NVFP4 `tensor` 模式 NMAE 恶化到
   **0.873**（几乎失效：0.1% 的离群值把全局缩放拉爆，绝大多数元素被压到 0），
   而 `block` 模式仍保持 **0.090**，**改善 9.7 倍**。直观说明了 microscaling 的必要性。
4. **MXFP8 对 block/tensor 不敏感**（0.022450 vs 0.022468）：
   FP8 的误差主要来自**尾数精度**而非动态范围，E8M0 全局缩放已足够用。
5. **随机舍入的 MAE 高于最近舍入**（NVFP4 block：0.0885 → 0.1196）：
   这是**预期行为**。随机舍入的价值在于**无偏性**（期望等于真值，适合梯度/累加场景），
   但它引入额外方差，因此逐元素绝对误差指标反而更差。
6. **输出类型量程是独立误差源**：`huge`（全 1e30）张量在 fp16 输出下 max_abs_error = inf，
   但纯量化相对误差仅 **3.0%**（2.997e28 / 1e30），落在 E4M3 理论界 2⁻⁴ = 6.25% 内。
   这正是本次把两个口径分开报告的原因。

## 7. 性能指标（4096×4096 = 16.78M 元素，输入 64 MiB fp32）

| 配置 | 量化 (ms) | 反量化 (ms) | CPU 参考 (ms) | **加速比** | 量化带宽 (GB/s) | 反量化带宽 (GB/s) | 压缩率 |
|---|---|---|---|---|---|---|---|
| MXFP8 block E4M3 →fp16 | 2.41 | 0.182 | 194.4 | **75.1×** | 35.1 | 279.4 | 3.879× |
| MXFP8 tensor E4M3 →fp16 | 2.20 | 0.190 | 183.4 | **76.9×** | 38.2 | 265.0 | 4.000× |
| NVFP4 block →fp16 | 2.24 | 0.285 | 303.2 | **120.0×** | 34.2 | 150.7 | 7.111× |
| NVFP4 block →fp32 | 2.35 | 0.439 | 258.7 | **92.7×** | 32.6 | 174.3 | 7.111× |

> 说明：该 GPU 在 WSL2 下存在明显运行间波动（±10~15%），上表为多次运行的代表值。

**分析**：

1. **总体性能显著超越 CPU 单线程实现**：加速比 **75× ~ 120×**，
   满足题目“总体性能需超越 CPU 同级别实现”的要求。
2. **量化是 ALU 受限、反量化是带宽受限**：
   - 反量化带宽 265 ~ 279 GB/s（MXFP8），接近该类小规模传输的可达水平；
   - 量化带宽仅 ~35 GB/s。原因是**每个元素都要执行一次软件编解码**
     （分支、整数舍入、位域操作约 20~30 条指令），而反量化只需位拼接 + 一次乘法。
     实测 MXFP8 量化约 1.9~2.4 ms 与按指令数（约 7.9 亿条）和 SM 吞吐估算的 2~3 ms
     量级吻合，确认瓶颈在 ALU 而非显存。
3. **NVFP4 量化需多读一遍输入**（用于全张量 amax 规约），是其量化略慢于 MXFP8 的原因。
4. **NVFP4 压缩收益最明显**（7.1×），代价是精度下降 —— 典型的“压缩率 vs 精度”权衡。

## 8. 软件模拟 vs 硬件/库依赖说明

**全部为软件模拟，无任何硬件或第三方库依赖**：

| 组件 | 实现方式 |
|---|---|
| E4M3 / E5M2 编解码 | 纯位运算（指数域构造 float），**不使用** `cuda_fp8.h` 或 `cvt` 指令 |
| E2M1 (FP4) 编解码 | 8 个可表示幅值的阈值比较 / 概率舍入，纯标量代码 |
| E8M0 缩放因子 | 位构造 `c << 23`，纯位运算 |
| 4bit 打包/解包 | 手工 nibble 拼接与拆分，反量化走 `uchar4` 向量化 packed load |
| amax 规约 | `__shfl_xor_sync` + `atomicCAS` 实现的 float `atomicMax` |
| fp16 / bf16 转换 | host 端为软件位运算；device 端仅用 `__float2half` / `__float2bfloat16` 这两个**基础类型转换**（sm_50+ 通用，非新架构特性） |
| 第三方库 | **无**（仅 CUDA Runtime + C++ 标准库） |

编译目标 `sm_90`，**未使用** Hopper 的 WGMMA / TMA，**未使用** Blackwell 的 FP4/FP8
Tensor Core 指令，**未要求**任何 Ampere 以上的架构特性。代码在 sm_70 及以上均可编译运行。

> 注：`ml_dtypes` 仅用于**离线交叉验证**（Python 工具），不参与程序运行时，
> 不构成对 GPU 端实现的依赖。

## 10. 局限与未来可继续提升的方向

**本次环境的实测局限**：

1. **`ncu` / `nsys` 在 WSL2 下无法采集 kernel 数据**。工具本身已安装
   （ncu 2023.2、nsys 2023.2.3），但 ncu 报 `No kernels were profiled`，
   nsys 报告中 CUDA kernel 段为空 —— WSL2 不透传 CUPTI。因此本报告的 ALU/访存
   瓶颈判断来自**指令量与吞吐的理论估算 + 实测时间吻合**，而非 profiler 计数器。
   若要补齐 `ncu`/`nsys` 分析（题目加分项），需在原生 Linux、训练营服务器或 AutoDL 上运行。
2. 国产平台已适配沐曦 曦云 C500（见第 12 节）：自带测试 36/36 通过，
   全部可比较项均为 CPU=GPU **逐位一致**。移植中唯一的数值陷阱是 **必须关闭
   `-use-fast-math`**（否则 nvfp4 block 模式在临界块上出现 1 ULP 级偏差）。

**技术优化方向**：

1. **消除 NVFP4 的全局 amax 前置遍**：改用单遍在线算法（分块局部 amax + 轻量汇总），
   可省去一遍输入读取，预计 NVFP4 量化提升约 20~30%。
2. **融合量化与反量化**：当前为两个独立 kernel、两遍读输入；
   可在同一 kernel 内完成量化并直接产出反量化结果。
3. **反量化进一步提升**：增大向量宽度（`uint2`/`uint4` 一次读 8~16 字节）、
   缩放因子放入 `__constant__` 内存。
4. **量化 kernel 的 ALU 优化**：把 E4M3 编码改为查表（512 项常量表 + 位域拼接），
   减少分支与整数运算。
5. **更精细的缩放策略**：实现 NVFP4 的随机/最优 block 缩放搜索
   （当前为经典 `amax/6` 启发式），或支持 MXFP6、MXINT8 等更多 MX 格式。
6. **真实模型权重验证**：目前使用合成数据（random / normal / outlier），
   建议补一组真实 LLM 权重（如 GPT-2 / Llama 的 `.safetensors` 张量）的量化实验，
   使误差结论更具说服力。
7. **硬件路径加分项**：在支持 FP8/FP4 的 GPU 上增加 `cuda_fp8.h` / Transformer Engine
   路径并与软件模拟做精度/性能对比（作为可选分支，不影响基础验收）。

## 12. 国产平台适配：沐曦（MetaX 曦云 C500 / MACA）

本工程对数值正确性的要求最高（每个配置都要"CPU 参考 vs GPU 逐位一致"），
因此这次适配的最大收获不是"跑起来"，而是**发现了 fast-math 会破坏逐位一致性**。

### 12.1 平台环境与编译方式

| 项目   | 值                                                                                |
| ---- | -------------------------------------------------------------------------------- |
| 加速卡  | 沐曦 曦云 C500（`mx-smi` 2.2.12，KMD 3.8.30）                                           |
| 设备属性 | `warpSize = 64`，104 个 SM，`maxThreadsPerBlock = 1024`，共享内存 64 KB/block，计算能力 `(10,0)` |
| 软件栈  | MACA 3.5.3.20（SDK 3.5.3.307），CUDA 兼容层由 `tools/cu-bridge` 提供                       |
| 编译器  | `mxcc 1.0.0`（`/opt/maca/mxgpu_llvm/bin/mxcc`）                                     |

构建脚本 [`build_maca.sh`](build_maca.sh)：

```bash
mxcc -x maca -offload-arch native --maca-path=/opt/maca \
     -Iinclude -I/opt/maca/tools/cu-bridge/include -L/opt/maca/lib \
     -imacros __macro_mxcc.h -forward-unknown-to-compiler \
     -fgpu-rdc --maca-link -lToolsExt_cu -lruntime_cu -lmcToolsExt \
     -std=c++17 -O3 \
     src/main.cpp src/io.cpp src/metrics.cpp src/reference.cpp src/kernels.cu \
     -o build_maca/lowprec

export LD_LIBRARY_PATH=/opt/maca/lib
BIN=./build_maca/lowprec bash tests/run_tests.sh
```

### 12.2 移植中唯一的数值陷阱：**必须关掉 `-use-fast-math`**

本工程的其它几个选题在沐曦上都开了 `-use-fast-math`（收益 15% 左右），但**本工程不能开**。

**现象**：开启 fast-math 后，`nvfp4_block_*` 配置在 **2048×2048 的 random 数据**上出现：

```
CPU 参考 vs GPU: 存在差异 (mismatch=16, max_diff=0.262)
```

**定位**：

1. 不一致的元素数**恰好是 16，正好等于 NVFP4 的一个 block**（`block_size = 16`）——
   说明是**某一个块的缩放因子**推导出了不同的结果，而不是逐元素误差；
2. 只有 `nvfp4_block`（块级缩放）受影响，`nvfp4_tensor`（张量级缩放）与 `mxfp8_block`
   都是逐位一致；`normal`/`outlier` 分布也一致，只有 `random` 触发；
3. 形状依赖：2048×1024 / 1024×2048 / 1536×1536 全部逐位一致，只有 2048×2048 命中这个临界块。

结论：这是**块缩放推导在临界点上的一处 1 ULP 级舍入差异**，被 `-use-fast-math`
（更快但精度更松的数学函数近似）放大成了可见的不一致。

**修复**：构建时不加 `-use-fast-math`（与 nvcc 默认行为对齐）。改后：

```
CPU 参考 vs GPU: 逐位一致 (mismatch=0, max_diff=0)
PASS=36  FAIL=0   全部通过
```

> 一般的经验：**涉及"逐位一致"验收的数值工程，不要开 fast-math**；
> 只有在做性能基准、且验收标准是误差上界时才适合打开。

### 12.4 性能对照（4096×4096 = 16.78M 元素，输入 64 MiB fp32）

| 配置                    | 平台         | 量化带宽      | 反量化带宽      | 重载反量化   |
| --------------------- | ---------- | --------- | ---------- | ------- |
| MXFP8 block E4M3 →fp16 | NVIDIA 5070 Ti | 35.1 GB/s | 279.4 GB/s | —       |
|                       | **沐曦 C500** | 35.6 GB/s | 272.9 GB/s | 0.21 ms |
| MXFP8 tensor E4M3 →fp16 | NVIDIA 5070 Ti | 38.2 GB/s | 265.0 GB/s | —       |
|                       | **沐曦 C500** | **77.3 GB/s** | 148.5 GB/s | 0.36 ms |
| NVFP4 block →fp16      | NVIDIA 5070 Ti | 34.2 GB/s | 150.7 GB/s | —       |
|                       | **沐曦 C500** | **50.9 GB/s** | **27.5 GB/s** | 1.50 ms |
| NVFP4 block →fp32      | NVIDIA 5070 Ti | 32.6 GB/s | 174.3 GB/s | —       |
|                       | **沐曦 C500** | 50.6 GB/s | **8.1 GB/s** | 9.39 ms |

**读法**：

1. **量化（ALU 受限）在沐曦上更快**：MXFP8 tensor 77.3 vs 38.2 GB/s（约 2×），
   说明该平台的整数/位运算吞吐对这类软件编解码更有利。
2. **反量化（带宽受限）MXFP8 基本持平**（272.9 vs 279.4 GB/s），
   但 **NVFP4 反量化明显偏慢**（fp16：27.5 vs 150.7 GB/s；fp32：8.1 vs 174.3 GB/s）——
   4-bit 解包路径在该平台上效率较差，这是本次适配中**唯一明显落后于英伟达的项**，如实记录。
3. 报告 §7 里的"加速比"列（CPU/GPU）本次未直接对比：它取决于**主机 CPU 单线程性能**，
   沐曦容器的主机 CPU 明显更强（同一用例 CPU 参考 522 ms vs 笔记本的 194 ms），
   两台的 CPU/GPU 比值不可直接相除。
