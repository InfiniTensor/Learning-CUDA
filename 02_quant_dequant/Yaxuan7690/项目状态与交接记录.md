## 4. 关键数字速查

**性能**（8192×8192 = 6710 万元素，正态分布，输出 FP16，`repeat 50 / warmup 15` 取最小值）

| 配置 | 量化 ms | 反量化 ms | 合计 ms |
| --- | --- | --- | --- |
| mxfp8-e4m3 block（单遍融合） | 0.841 | 0.541 | **1.382** |
| mxfp8-e4m3 block + 随机舍入 | 0.945 | 0.522 | 1.466 |
| nvfp4 block（两遍） | 1.474 | 0.452 | **1.926** |
| nvfp4 block + 随机舍入 | 1.711 | 0.461 | 2.172 |
| nvfp4 + 4/6（`mse` 规则，两遍融合） | 1.774 | 0.456 | **2.226** |

- 优化起点（`data/perf_base.csv`）是 **4.731 / 5.902 ms**，共 22 项优化，逐次快照见 `data/perf_step*.csv`。
- 4/6 动态块缩放（`mse` 规则，两遍融合）比标准 NVFP4 重 **+7%~+22%**（规模越大差距越大；表中 8192² 是 1.474 → 1.774 ms，6.8 的同会话 A/B 是 1.450 → 1.774 ms）：代价是每元素要把两个候选各算一遍；换来的是 512² 上 block 相对 MSE 9.08e-3 → **7.56e-3**（−16.7%）。并入前的三遍实现是 2.109 + 0.450 ms；线程映射改成"一个线程负责一整个缩放块"后，量化 kernel 自身 1.371 → 1.054 ms（详见 `总结报告.md` 8.6）。
- **达成率 96%~105%**：用 `tools/bw_ceiling.cu` 造「同读写比例、纯搬运」的对照 kernel 标定出的
  硬件实测上限做分母，而不是拿 448 GB/s 的纸面峰值（详见 `总结报告.md` §6.3）。
- 端到端拆解：预处理（读文件 + H2D）70~100 ms、CUDA 上下文建立 75~110 ms、D2H + 落盘 249 ms、
  退出清理 145 ms；GPU kernel 本身只占 **1.4~2.2 ms**。

**精度与压缩率**（512×512，RNE，输出 FP16）

| 格式（block 缩放） | 压缩率 | 相对 MSE（正态） | 相对 MSE（含异常值） |
| --- | --- | --- | --- |
| mxfp8-e4m3 | 3.879× | 8.76e-4 | 1.03e-3 |
| mxfp8-e5m2 | 3.879× | 2.91e-3 | 2.90e-3 |
| nvfp4 | 7.111× | 9.08e-3 | 3.88e-3 |
| mxfp4 | 7.529× | 1.33e-2 | 1.65e-2 |
| nvfp4 + 4/6（mse 规则） | 7.111× | **7.56e-3**（-16.7%） | **2.44e-2**（-12.1%） |
| nvfp4（per-tensor，对照） | 8.000× | 1.64e-2 | **1.49e-1** |

> 最后一行是本项目最重要的一个结论：**4 bit 格式必须配 block 缩放**——含异常值矩阵上
> per-tensor 的相对 MSE 是 block 的 **38 倍**；而 8 bit 的 E4M3 有 3 位尾数，per-tensor 已够用。

## 5. 国产 GPU 实测：已完成（摩尔线程 MTT S4000）

### 5.1 结果

原本的门槛是租用平台的**国产卡实例无法创建**（只能启动英伟达算力）；2026-09-16 该限制解除，
当天就在摩尔线程 MTT S4000（MUSA 3.1.0）上完成了实测；**2026-09-17 又把补齐 MXFP4 与 4/6 之后的
当前源码在同一台机器上完整复跑了一遍**。下表是复跑结果（括号内是 09-16 首轮的数字）：

**跨平台一致性最强的一条证据是 4/6**：`test_pipeline` 的 `pipeline/scale-rule-4-6` 用例在 MTT S4000 上
打印的数字与英伟达侧**逐位相同** —— 码字差异 1191 / 807 / 1018，`mse` 7.807984e-03 / 7.715453e-03 /
7.428279e-03（`static_6` 基线 8.758412e-03），`static_4` 的 packed 差异 1960 / 2048。这是同一组输入下逐条
码字的对拍，比「断言数相同」强：新版 4/6 kernel（含「一个线程一个块」那次重写）在两个平台上给出完全
相同的量化结果。

> 误差统计量在两台机器之间不是逐位可比的：`normal_512.tensor` 由各自的 `tools/gen_data.py` 现生成
> （两份 md5 不同），所以 `mse` 会有第 5 位有效数字的差异（7.569e-3 vs 7.557e-3）。判据是「同一台
> 机器上 GPU 与独立 CPU 参考逐位一致」，这一条两轮两平台都成立。

| 架构代号 | **`mp_22` 是唯一可用值**（default / mp_21 / mp_10 全部编译失败，mp_31 编过但启动失败；mcc 的合法代号是 `mp_10 / mp_21 / mp_22 / mp_31 / mp_311`） |
| 构建 | 4 个目标顺序编译，**0 告警 0 错误**；`-O3` 下单个目标约 11~13 分钟 —— 新版 4/6 kernel 按 block_size 特化成 4 个实例，源码量比首轮大，首轮全量只要 1 分 9 秒 |
| 测试 | **22 / 292651 / 21532 = 314205 条断言，0 失败**（与英伟达逐项相同；首轮那一版是 22 / 292397 / 15291） |
| 端到端 | 512×512 RNE/FP16：packed 与 scales 逐位相同、反量化与 CPU 参考 0 处不符，量化 **14.07×** / 反量化 **49.74×** CPU；NVFP4+4/6（`mse` 规则）同样逐位相同（首轮 13.49× / 45.93×） |
| 带宽 | 纯读 **673 GB/s**、纯写 **416 GB/s**、混合模式最好 **674 GB/s**（首轮 669 / 403 / 670） |

**过程中抓出三处只有逐位对拍才能发现的数值语义差异**（都出现在设备端；主机侧 x86 参考实现
在两个平台上一致），全部已修，细节见 `总结报告.md` 6.7：

1. **设备端 fp32 除法不是 IEEE 正确舍入的**：`1.0f / x`（与 `__frcp_rn` 逐位相同）12.4% 差
   1 ulp，`a / b` 3.9% 差 ≥2 ulp；只有 `__fdiv_rn` 逐位正确。修法是加 `f32_div_rn()`，
   统一 6 处除法（`nvfp4_global_scale` / `nvfp4_block_scale_f32` / 量化 kernel 的 `q` /
   `ginv` / 两处主机参考实现）。
2. **乘法被收缩进补偿累加器的加法**：mcc 把 `hi + dh*dh` 在 1048576/1048576 个样本上都算成
   `fma(dh,dh,hi)`（nvcc 一次都没有），于是 TwoSum 残差里自动带上乘积舍入残差，源码再显式
   补一次就重复计入，误差恰好等于 Σp1e。修法是用 `mul_rn()` 写这两处平方。
3. **FTZ / 次正规**：`float → bf16` 不能走 `__bfloat162float`（会把 bf16 次正规刷成 0、把
   NaN 规范化）；`1.0f / e8m0_to_f32(0)` 会因分母是次正规数而算出 `+Inf`，`0 * Inf = NaN`
   把全零块量化成 NaN 编码。前者改位模式解码，后者改成按 2 的整数次幂构造倒数。

> 一处存疑（如实记下）：实测纯读 669 GB/s **超过**该卡运行时报出的"纸面峰值" 512.8 GB/s。
> 用墙上时钟复核过事件计时（比值 1.07），所以不是计时问题；更可能是 MUSA 运行时的
> `memoryClockRate` / `memoryBusWidth` 字段不反映真实数据率。因此国产平台这一列只作同机内部
> 相对比较，不与英伟达的绝对值并列。

### 5.5 上机前修掉的一处构建级差异：摩尔线程 MUSA 的运行时命名

§5.2 里那六处差异都是**源码级**的。复查 MUSA 官方文档时又发现第七处，而且是最大的一处，
`platform.hpp` 修不了：

- MUSA 的运行时对象叫 `musaXxx`（`musaMalloc` / `musaMemcpy`，头文件 `musa_runtime.h`），
  低精度类型头也是 `musa_fp16.h`；而本项目源码里以 `cudaXxx` 写成的调用点有 **200 多处**
  （`cudaMemcpy` 48、`cudaMalloc` 31、`cudaFree` 28、`cudaMemcpyDeviceToHost` 35 …）。
- 逐行改名的代价不只是工作量：改完这份源码就不能再直接交给 nvcc 了，而且等于重写一遍要重新验证。

官方对这件事给了**三条**现成的路。`Makefile` 的 `moore` 分支把三条都接好了，
`MUSA_MODE=auto`（默认）按可用性自上而下自动选：

| 模式 | 命令要点 | 可用条件 | 说明 |
| --- | --- | --- | --- |
| `wrapper`（首选） | `mcc -mtgpu -cuda_wrapper … -lcuda2musa` | `libcuda2musa.so` 在 | mcc 的"兼容封装模式"，手册原话是"支持开发人员使用 CUDA API 而不是 MUSA 的"。**本次镜像（MUSA 3.1.0）走这条**，源码一行不改 |
| `mapping` | `mcc -x musa -fplugin=<libMusaMapping.so>` | SDK ≥ 5.2.0 | 编译期 Clang 插件，按映射表重写头文件名与标识符 |
| `plain` | `mcc -mtgpu … -lmusart` | 源码已迁移过 | 先跑 `musify-text --inplace -- src/*.cu tests/*.cu` 改一遍源码 |

`make` 会在编译前打印实际选中的模式，上机第一条日志就能看到：

```
[moore] MUSA_MODE=wrapper, MUSA_ARCH=''
```

四条来自官方手册、已写进注释的注意事项：

1. `.cu` 后缀 mcc 默认不认，必须 `-mtgpu`（或 `-x musa`）才按 MUSA 源文件处理。
2. wrapper 模式要链接 `libcuda2musa.so` 而**不是** `libmusart.so`。若报"未定义引用"，
   先在 `LDFLAGS` 里补 `-lmusart`，再检查 `-l` 的先后顺序。
3. mcc 默认按 `--as-needed` 链接、顺序敏感；必要时用 `-Wl,--no-as-needed` 覆盖。
4. `--offload-arch` 要按卡填代号：MUSA 3.1.0 的有效代号是 `mp_10 / mp_21 / mp_22`，
   且**不传时默认出 mp_21 + mp_22 两个**；官方也没有"卡型号 → 代号"对照表。所以
   `run_domestic.sh` 里加了探测：用与正式构建**完全相同**的模式与库参数，按
   `默认 → mp_21 → mp_22 → …` 逐个编译一个"写 42 再读回来"的极小 kernel 并真的执行一次，
   第一个既编得过又跑得出正确答案的代号就拿来用。

`run_domestic.sh` 一并做的几件事（都为了让租来的每小时更值，且都在日志里留痕）：

- 在探测编译器**之前**先设好 SDK 环境变量（否则 SDK 没进 PATH 会被误报成"工具链没装"）；
- 打印 `mcc --version` / `musa_version_query` / `mthreads-gmi`（或 `mx-smi` / `ixsmi` / `nvidia-smi`）；
- 明确报告这台机器上哪条兼容路可用（`libcuda2musa.so` / Mapping 插件 / `musify-text`）；
- 正式编译前先 `make -n` 干跑一遍 —— Makefile 分支或参数有问题在这一步暴露，不浪费编译时间；
- 最后量一次这台机器的带宽天花板（`make bw` + `build/bw_ceiling`），这是达成率的分母。

## 9. 已知限制（写进报告的"诚实状态"）

- **国产平台只测了摩尔线程这一款**（§5）—— MTT S4000（MUSA 3.1.0）上 314205 条断言全过（22 / 292651 / 21532），
  与英伟达一致；但天数智芯 / 沐曦两条分支仍只是"按官方仓库可用配置写好、带自诊断探针"的状态，
  未在真机跑过。三处数值语义差异里只有"乘法收缩进加法"这一条被证明是 mcc 特有；另两条
  （除法非正确舍入、FTZ 影响 bf16 次正规）**不排除**在别的国产卡上同样存在，换平台时应重新跑
  一遍 `总结报告.md` 6.7 节那三组对拍。
- **国产平台的带宽读数存疑**（§5.1 末尾）：实测纯读超过运行时报出的纸面峰值 1.31×，原因未定，
  该列数值只作同机内部相对比较。
- **硬件 FP8 `cvt` 快路径**（优化 16/19）依赖 sm_89 及以上，是本实现**唯一的架构条件编译**；
  但它是加分项，软件回落路径始终存在且在 `test_formats` 里被逐位验证过。
- **4/6 的融合路径有前置条件**：块大小必须是 2 的幂、块要完整、不是单块平铺
  （即 `block_size ∈ {4,8,16,32}`、`numel % block_size == 0`、`num_blocks > 1`）。不满足时自动
  回落到三遍实现（`k_nvfp4_block_scales_46` + `k_quant_nvfp4`），精度口径完全相同，只是多读
  一遍输入。
- **4/6 融合版的新映射在极小张量上不如旧映射**：它一个线程负责一整个块，所以能用的线程数就是
  块数。`numel / block_size` 远大于 GPU 的驻留线程数（本机 36 SM × 1024）时稳赢，但 256² 这种
  只有 4096 个块的规模填不满机器，实测比三遍路径慢 5 µs（0.0280 vs 0.0232 ms，两者都在 30 µs
  以内、本身由启动延迟主导）。真要覆盖这种规模，可以按块数在两种 kernel 之间二选一，本次没做。
- **4/6 融合版在 block 32 / 随机舍入的实例化上有少量寄存器溢出**：默认配置（block 16 + RNE）
  是 64 寄存器零 spill，block 32 + RNE 约 40 B、block 16 + SR 约 240 B、block 32 + SR 约 1 KB。
  放宽 launch bounds（4 → 3 blocks/SM）可以换回寄存器，代价是占用率；本次没有为它单独调参。
- **本机无 GPU 计数器权限**，ncu 不可用，剖析改用 nsys。
- 几个百分点以内的性能差异在本机上不可区分（跨会话摆动实测 2%~5%：`k_block_amax_pow2_vec4`
  在 0.672~0.691 ms 之间摆动，纯写带宽在 423~443 GB/s 之间摆动，见 `data/out/nvidia_verify_20260918.txt`），
  报告里对这类差异一律不下结论。
- **误差统计量不逐位可复现**（`总结报告.md` 5.1）：`src/metrics.cu` 的归约是"每 block 一次
  `atomicAdd(double)`"，block 之间的完成顺序由调度决定，因此 `accum diff` 这类统计量的末位会在
  1e-16 量级上跳动。它不影响任何断言（门限 1e-13，实测余量约 1000 倍），也不影响量化输出
  （packed / scales 只依赖 max 归约，与顺序无关，实测每次都 `packed_bits_identical = yes`）。
  英伟达与摩尔线程上实测的波动取自同一组取值，属设计固有的行为，不是平台差异。
