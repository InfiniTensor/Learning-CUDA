# 国产平台排查探针（一次性程序，不属于正式代码）

这些是 2026-09-16 在摩尔线程 MTT S4000（MUSA 3.1.0 / mp_22）上定位 `总结报告.md` 6.7.2 那三处
数值语义差异时用到的一次性探针，外加 6.7.6 那处计时存疑的复核程序。

放在这里是为了让报告里的每条结论都能顺着找到"它当时是怎么被测出来的"。它们**不属于**正式代码：
不参与 `make` 构建、不在 `Makefile` 的目标里、也不要求 clang-format。所有探针都只依赖
`musa_runtime.h` —— 把 `musa` 换成 `cuda`、`__mt_bfloat16` 换成 `__nv_bfloat16`，就能在英伟达上
原样复跑同一组对拍。

## 差异 1：设备端 fp32 除法不是 IEEE 正确舍入

| 文件 | 作用 |
| --- | --- |
| `rr.cu` | 在 2²² 个随机 fp32 上比较 `/`、`1.0f / x`、`__frcp_rn`、`__fdiv_rn` 与 x86 主机侧的正确舍入结果 |
| `rr2.cu` | 上一版的加强：过滤掉 NaN / Inf / 0 / 次正规输入，输出逐位 ULP 偏差的直方图 |

结论：`a / b` 有 22.8% 差 1 ulp、3.9% 差 ≥2 ulp；`1.0f / x` 与 `__frcp_rn` 逐位相同、12.4% 差
1 ulp；只有 `__fdiv_rn` 在 4194304 个样本上**全部逐位正确**。

## 差异 2：乘积被收缩进补偿累加器的加法（这条是逐步逼出来的）

| 文件 | 作用 |
| --- | --- |
| `p3.cu` | 先确认 `fmaf` / TwoSum / 精确拆平方在设备端是否符合 IEEE 语义 |
| `p4.cu` | 把 `include/lpq/stats.cuh` 的 `AccumFast` 原样搬到设备上，与逐元素 fp64 累加对拍 |
| `p5.cu` | 逐元素拆开 `AccumFast` 里 d² 的补偿项，看误差出在哪一项 |
| `p6.cu` | 逐线程 vs 逐元素 fp64，两份输出缓冲完全分离（排除互相覆盖的干扰） |
| `p7.cu` | 把 `hi` / `lo` 两条链分开，各自与 fp64 对照 |
| `p8.cu` | 修正项分别累加到普通 fp32 与 `lo` 分量，看哪条路把修正项丢了 |
| `p9.cu` | **定案**：验证 `hi + dh*dh` 是否被收缩成 `fma(dh, dh, hi)` |

结论：mcc 在 1048576 / 1048576 个样本上都做了这个收缩（同一份代码在 nvcc 上只有 4222 个），于是
TwoSum 的残差里自动带上了乘积的舍入残差，源码再显式补一次 `p1e` 就是重复计入，误差恰好等于
Σp1e —— 实测量到的 1.96e-11 / 2.99e-10 与 Σp1e/Σp1、Σp2e/Σp2 完全吻合。

## 架构代号探针

| 文件 | 作用 |

| `arch_probe.cu` | 第一版：用了 `__nv_bfloat16`，在 MUSA 上类型名不对，任何代号都编不过 |

同一版探针输出（`default` 与 `mp_21` 编译失败、`mp_22` 编过并在设备上跑出 42；文件为空 = 编过），
