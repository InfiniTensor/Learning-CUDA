## 2. 格式、缩放、打包与公式

### 2.1 元素格式

所有格式都用**纯位运算**实现，转换函数同时标注 `__host__ __device__`，GPU 与 CPU 共用
同一份代码，从根本上排除"两端公式不一致"。

| 格式 | 符号/指数/尾数 | bias | 最大有限值 | 特殊值 | 用途 |
| --- | --- | --- | --- | --- | --- |
| E2M1 | 1-2-1 | 1 | 6.0 | 无 Inf/NaN | NVFP4 与 MXFP4 的元素 |
| E4M3 | 1-4-3 | 7 | 448.0 | 0x7F/0xFF = NaN，无 Inf | MXFP8 元素 / NVFP4 块缩放 |
| E5M2 | 1-5-2 | 15 | 57344.0 | 有 Inf 与 NaN | MXFP8 可选元素 |
| E8M0 | 8 bit 纯指数 | 127 | 2^127 | 0xFF = NaN | MX 共享缩放因子 |
| FP16 | 1-5-10 | 15 | 65504.0 | 有 Inf/NaN | 反量化输出 |
| BF16 | 1-8-7 | 127 | 3.39e38 | 有 Inf/NaN | 反量化输出 |

转换语义：**就近舍入（RNE，平局取偶）或随机舍入（SR），有限输入一律饱和**
（例如 E4M3 输入 480 → 448，而不是 NaN，即 `cvt.satfinite` 语义）。

### 2.2 MXFP8 与 MXFP4

由 OCP Microscaling Formats v1.0 定义：每 `block_size`（默认 32）个元素共享一个 E8M0
缩放因子（2 的整数次幂）。**MXFP8 与 MXFP4 用完全相同的缩放规则与打包框架，区别只在
元素位宽**：MXFP8 的元素是 8 bit 的 E4M3 / E5M2，MXFP4 的元素是 4 bit 的 E2M1。

```
amax_b     = max(|x_i|)                       i 属于块 b
shared_exp = floor(log2(amax_b)) - emax_elem  emax_elem: E4M3=8, E5M2=15, E2M1=2
shared_exp = clamp(shared_exp, -127, 127)     amax_b = 0 时取 -127
code_b     = clamp(shared_exp + 127, 0, 254)  # E8M0 编码，255 保留为 NaN
scale_b    = 2^(code_b - 127)

量化   : q_i = round_to_elem(x_i / scale_b)
反量化 : x̂_i = elem_to_f32(q_i) * scale_b
```

E8M0 只表示 2 的整数次幂，所以**一个块内所有元素共用同一个指数**，尾数精度全部让给元素格式。

MXFP4 取 `emax_elem = 2`（E2M1 的最大有限值 6.0 落在 [4, 8) 这个 binade），于是同一块数据在
MXFP4 下的 `shared_exp` 比 MXFP8-E4M3 小 1，块内元素落在 `[4, 8)` 的幂次区间；而 E2M1 的最大
有限值只有 6.0，所以当块内 `amax / scale` 落在 (6, 8) —— 也就是该 binade 顶部 25% —— 时，
最大元素会饱和到 6.0。这个比例（25%）比 E4M3 的 12.5%（见 6.1 结论 3）更大，是 MXFP4 相对
MXFP8 更容易在异常值分布上吃饱和的根因。

### 2.3 NVFP4

两级缩放：

```
全局缩放（每张量，FP32）: global_scale = 448 * 6 / amax_tensor
块内缩放（每 16 元素，E4M3）: block_scale_b = e4m3(amax_b * global_scale / 6)

量化   : q_i = e2m1(x_i * global_scale / block_scale_b)
反量化 : x̂_i = e2m1_to_f32(q_i) * block_scale_b / global_scale
```

设计意图：`global_scale` 先把整个张量映射到 E4M3 的表示范围内（`amax_tensor * global_scale
= 448*6 = 2688`，恰好让最大的块缩放到 E4M3 的最大值 448 × 6），再由每个块用 E4M3 记录
自己的相对幅度；元素端则用 E2M1 表示归一化后的值（量程 ±6）。E4M3 的 3 位尾数使得块缩放
因子本身的相对误差约 2^-4，比 E2M1 的 2^-2 精细得多，因此**分层缩放把精度留给了最需要的地方**。

#### 2.3.1 4/6 自适应块缩放（本次补齐）

上面这条 `block_scale_b = e4m3(amax_b * global_scale / 6)` 是一条**只由块内 amax 决定的 AbsMax
规则**，它保证块内最大值恰好落在 E2M1 的 6.0 上。但 E2M1 的格点并不等间距
（0, 0.5, 1, 1.5, 2, 3, 4, 6），当块内元素的分布与格点错开时（高斯分布的小块尤其典型），
把最大值压到 4.0 反而能让**更多**元素离格点更近。于是引入一条**按块二选一**的规则
（Four Over Six，arXiv:2512.02010）：

```
6 候选: bs6 = e4m3(amax_b * global_scale / 6)      # 规范公式, 最大值 -> 6.0
4 候选: bs4 = bs6 * 1.5                            # 最大值 -> 4.0 (再经 E4M3 编码)
两个候选中各量化-反量化整个块一次, 累加目标误差
scales[b] = (err4 < err6) ? code4 : code6          # 平手时保留 6 候选
```

误差口径 `err` 可选 `abs_max` / `mae` / `mse`，对应 `ScaleRule::AbsMax / Mae / Mse`；此外还有
两条不做比较的静态规则：`Static6`（即规范基线）与 `Static4`（恒取 4 候选）。

**一个容易被忽略的细节**：两条「动态」规则必须把 `max_s` 从 448 降到 256。原因是 4 候选要在
6 候选的基础上乘 1.5，而 `448 * 1.5 = 672 > 448` 会溢出 E4M3；所以动态规则改用
`global_scale = 256 * 6 / amax_tensor`。这与上游参考实现 [`fouroversix`](https://github.com/mit-han-lab/fouroversix)（arXiv:2512.02010 的官方代码）的
`448 if static else 256` 一致。等价地：`Static6` 的全局缩放是 `2688 / amax`，
`Static4` 是 `1792 / amax`，两条动态规则是 `1536 / amax`（`tests/test_formats.cu` 里逐条钉死）。

**代价**：每个元素都要把两个候选各量化-反量化一次才能比较，量化阶段因此比标准 NVFP4 重
**+7%（2048²）~ +22%（8192²）**（见 6.8 的逐项分解）。多出来的那一遍输入已经并进量化
kernel 消掉，输入遍数与标准 NVFP4 相同（见 3.3、8.6）。

### 2.4 打包布局

* **MXFP8**：每个元素恰好 1 字节，与元素下标一一对应。
* **NVFP4 / MXFP4**（所有 4 bit 元素格式共用同一条打包规则）：每个字节存 **2 个元素**，**下标为偶数的元素在低半字节**。量化 kernel 每线程
  处理 4 个连续元素，一次写入一个 `uint16`（`c[0] | c[1]<<4 | c[2]<<8 | c[3]<<12`）；
  反量化端一次读出一个 `uint16`。
  两种格式的译码也共用同一个 `fmt_x4_4bit_to_f32()`，`tests/test_formats.cu` 的
  `formats/x4-4bit` 用例把 16⁴ = 65536 个半字节组合与单元素译码逐位对拍过。

文件布局：`128 字节头（magic/version/format/elem_kind/scale_kind/scale_mode/rounding/
num_rows/num_cols/block_size/num_blocks/packed_bytes/scale_bytes/global_scale/seed）|
packed 数据 | scale 数组`。scale 数组的元素类型由 `scale_kind` 决定（E8M0 或 E4M3，均 1 字节）。

### 2.5 舍入

* **RNE**：对尾数做截断 + 平局取偶，实现中统一处理了指数进位、次正规、上溢饱和。
* **SR**：按剩余量成比例随机进位。GPU 端用 `random_at(seed, idx)`（splitmix64，由
  **种子与元素下标哈希**得到，而非流式状态）取低 `drop` 位与余数比较，因此**结果与线程调度
  无关、完全可复现**。

## 3. 实现思路

### 3.1 总体结构

```
读文件 + H2D 拷贝
   ↓
┌─ 量化（GPU，CUDA event 分段计时）────────────────┐
│  MXFP8 block 模式：融合 kernel（1 遍）           │
│  其它配置：amax kernel → scale kernel → quant kernel │
└──────────────────────────────────────────────────┘
   ↓ D2H → 写 <prefix>_lowp.bin
反量化 kernel（GPU）→ 写 <prefix>_dequant.bin
误差统计 kernel（GPU 归约）→ 写 <prefix>_log.txt
   ↓ （可选）CPU 参考实现逐位对拍 + GPU/CPU 加速比
```

### 3.2 Kernel 设计要点

* **向量化访存**：量化/反量化统一按"每线程 4 个连续元素"组织——FP32 输入用 `float4`，
  FP16 输入用 2×`half2`，FP16/BF16 输出把 4 个 16 bit 编码打包成 `uint2` 写回。这样访存
  完全合并，同时 4 是 16/32 的约数，与 block_size 天然对齐。
* **缩放因子查表复用**：一个线程的 4 个元素若落在同一缩放块内（绝大多数情况），只做一次
  scale 查表；跨块时才逐元素查表。
* **块内 amax 归约**：`block_size ≤ 32` 时用 `__shfl_xor_sync`（`width = block_size`）在寄存器内
  完成，不需要共享内存；更大或非 2 的幂的 block_size 走通用的"每 warp 一个块"路径。
* **下标计算**：block_size 为 2 的幂时用移位替代整数除法（`shift >= 0` 走 `i >> shift`）。
* **误差统计**：单 kernel 归约出 `Σ|d|`、`Σd²`、`Σr²`、`Σd`、`max|d|` 五个量，块内共享内存
  树形归约 + 全局 `atomicAdd`/`atomicMax`（`atomicMax` 借助 `__float_as_int`，因误差非负而安全）。
* **边界处理**：所有主 kernel 按 4 元素向量处理主体，尾部（最多 3 个元素）由 0 号线程串行
  收尾，保证任意 `numel` 都正确。

### 3.3 融合 kernel（关键优化）

MXFP8 的缩放因子只依赖**本块内**的 amax，因此"块内 amax → E8M0 → 量化 → 打包"可以在
**一次访存**内完成。融合 kernel 按"每线程 4 元素"映射后，一个缩放块恰好由 `block_size/4`
个相邻线程负责，于是块内归约可以用一次 `__shfl_xor_sync(width = block_size/4)` 在寄存器内
完成：

```cuda
for (int off = lanes_per_block >> 1; off > 0; off >>= 1)
    m = fmaxf(m, __shfl_xor_sync(0xFFFFFFFFu, m, off, lanes_per_block));
```

这消除了三阶段实现中**一次完整的输入重读**以及两个 kernel 的启动开销。注意归约必须在整个
warp 上一致执行，因此放在越界提前 `return` **之前**（越界线程贡献 0）。

该路径的适用范围是 `mxfp8 / mxfp4 + block 模式 + block_size ∈ {4,8,16,32,64,128}` ——
判据就是 `can_fuse()` 里的 `cfg.is_mx()`，即"缩放因子只依赖本块"的格式都能融合。
NVFP4 **不能**这样融合：它的 `global_scale` 依赖**全张量** amax，必须先读完一遍输入才能
定出全局缩放，所以固定为两遍。但 NVFP4 另有一处可以融合的地方 —— 4/6 动态规则的两个候选
取舍：那个判据只需要"块 amax + 全张量缩放"这两个上一遍就已经定稿的输入，因此选择可以并进
量化 kernel 就地完成，输入遍数从 3 回到 2（见 6.8 观察 3 与 8.6）。

**误差统计同样被并进了量化 kernel。** 量化 kernel 手里本来就有原始值 `x` 和刚算出的量化码，
顺手反量化一次就能把 `Σ|d| / Σd² / Σref² / Σd` 与 `max|d|` 累加出来，不必事后再把 268 MB
的 FP32 输入与 134 MB 的反量化结果各读一遍（8192² 下 402 MB，比量化本身还重）。代价是每个
元素多付约 50 条 fp32 指令，收益是整条链路少一次完整的重读——实测净赚 0.4~0.5 ms
（优化 5，见 4.5 节）。两条路径共用同一份累加代码（`include/lpq/stats.cuh`），由模板
`NullSink / FastSink / StrictSink` 在编译期选择：不开统计时 `NullSink` 完全消失，
生成的指令与手工删掉那几行相同。

### 3.4 三份互相独立的实现

正确性不是靠单测自证，而是靠**三份独立实现互相钉死**：

1. **GPU 实现**（`src/*.cu`）：位运算转换 + 向量化 + 并行归约；
2. **CPU 参考实现**（`src/reference.cu`）：刻意避开所有位运算技巧——格式转换用
   "枚举全部可表示幅值 + 二分查找"，`floor(log2())` 用"反复折半计数"，流水线为纯串行标量；
3. **NumPy 实现**（`tools/verify_numpy.py`）：用 `np.searchsorted` 在枚举值表上定位区间，
   显式还原每一步 fp32 运算顺序，直接解析低精度权重文件对拍 packed / scales / 反量化结果。

三者在**所有 RNE 配置下逐位一致**。随机舍入由于两端取随机数的方式不同（GPU 按低位掩码
比较、参考实现按浮点概率比较），只做统计意义下的交叉验证——由测试
`pipeline/stochastic-unbiasedness` 完成。

## 4. 优化历程与开发中发现的问题

### 4.1 优化 1：向量化访存

初版按"每线程 1 个元素"处理，访存无法形成 128 bit 事务。改为每线程 4 个元素（`float4` /
`half2` × 2 / `uint2`）后带宽显著提升，同时天然对齐 block_size。

### 4.2 优化 2：block 模式单遍融合（MXFP8）

见 3.3 节。效果（正态分布、`output_type=fp16`、`scale_mode=block`）：

| 规模 n | 量化 ms（三阶段） | 量化 ms（融合） | 加速比 | 量化带宽 GB/s（前） | 量化带宽 GB/s（后） |
| --- | --- | --- | --- | --- | --- |
| 512 | 0.02582 | 0.006528 | 3.96× | 51.1 | 202.0 |
| 1024 | 0.04224 | 0.016900 | 2.50× | 124.9 | 312.2 |
| 2048 | 0.10910 | 0.040800 | 2.67× | 193.4 | 517.2 |
| 4096 | 0.44730 | 0.171100 | 2.61× | 188.7 | 493.4 |
| 8192 | 1.80900 | 0.783200 | 2.31× | 186.6 | 431.1 |

（融合后 `amax_kernel_ms` 与 `scale_kernel_ms` 在日志中为 0，因为这两个阶段已被并入
量化 kernel，`quantize_total_ms` 即等于 `quantize_kernel_ms`。）

### 4.3 优化 3：误差统计 kernel 摆脱 fp64 ALU 瓶颈（3.1×）

`k_error_stats` 一直是整条链路里最慢的一环（占 GPU 时间 55%~69%，有效带宽只有 123 GB/s）。
真正的原因不在访存而在 ALU：消费级 Blackwell 的 fp64 吞吐只有 fp32 的 **1/64**，而"逐元素
转 fp64 再累加 `Σ|d|` / `Σd²` / `Σr²` / `Σd`"相当于每个元素要付约 300 条 fp32 指令的代价。
SASS 统计显示每 4 个元素有 20 余条走 fp64 通路的指令（`DFMA` + `DADD` + `F2F`），与 3.2 ms
的实测时间严格吻合——这是硬性的吞吐墙。先做的"每线程 4 元素向量化访存"因此几乎没效果
（3.2764 → 3.2728 ms），因为它缓解的是访存而不是 ALU。

解决办法是把累加搬到 fp32，但**必须保证每一项本身算准**，否则相对误差会劣化到 1e-8 量级：

1. `d = test - ref` 用 Knuth TwoSum 拆成精确的两分量 `(dh, dl)`。直接做 fp32 减法在两者
   指数相差较大时（例如 `ref = 3e-3` 而 `dequant = 0.5`）并不精确——仅这一处就会带来
   1e-8 的相对误差（这个 bug 被测试抓住，见 4.5 节第 8 条）；
2. `|d| = |dh| + sign(d)·dl`，`d² = dh² + 2·dh·dl + dl²`，其中 `dh²` 与 `ref²` 用 `fmaf`
   拆成"舍入值 + 精确残差"两分量（否则每次平方都要丢掉一半尾数位）；
3. 主项（`|dh|` / `dh²` / `ref²` / `dh`）走 `(hi, lo)` 补偿累加；量级只有主项 1e-8 的修正项
   （`sign(d)·dl` / `sqe` / `cross` / `rqe` / `dl`）用一个普通 fp32 寄存器攒起来就够——它们
   自身的舍入误差再乘 1e-8，落在 1e-13 以下；
4. 线程间仍在 fp64 上做共享内存树形归约，因此最终统计量仍与 CPU 双精度参考一致。

每元素约 50 条 fp32 指令，约合 **0.8 条 fp64 指令**，kernel 重新变成访存瓶颈。另外把累加器
拆成两组独立实例（每批 8 个元素、各喂 4 个）来遮盖 `(hi, lo)` 补偿链的延迟（SASS 里大量的
`NOP` 说明调度器原本在等依赖）。

原 fp64 路径保留为 `AccumMode::Precise`（命令行 `--metrics-precise`），
`tests/test_pipeline.cu` 会把两条路径与 CPU 双精度串行循环三方对拍。

| 指标（8192×8192） | 优化前 | 优化后 |
| --- | --- | --- |
| `k_error_stats` 单次耗时 | 3.276 ms | **1.043 ms** |
| 有效带宽（402 MB / 耗时） | 123 GB/s | **386 GB/s** |
| 占 GPU 时间（nsys） | 68.9% | **42.7%** |
| 与 Precise 路径的相对差 | — | ≤ 6.7e-16（宽动态范围数据） |

新增测试 `pipeline/error-stats-accum`：用元素指数跨越 2^-24 ~ 2^24 的数据把 Fast / Precise /
CPU 双精度循环三方对拍，实测相对差在 1e-16 量级。

这一步对照运行的原始日志归档在 `data/out/`：`opt3_metrics_precise_log.txt` 与
`opt3_metrics_fast_log.txt`（同为 mxfp8-e4m3/block、8192²，`metrics_kernel_ms` **3.285 → 1.059**，
即本条优化的 3.10×；更早一次只跑 fp64 路径的基线见 `metrics_precise_baseline_log.txt`，3.412 ms）。
表里的 3.276 / 1.043 ms 取自另一次同配置运行，差异属运行间正常抖动。

### 4.4 优化 4：反量化 kernel 的两处 ALU 开销（1.32×）

反量化原本只有 ~300 GB/s（67% 峰值），而它的数据量只有 203 MB。SASS 显示每 4 元素有 130+
条分支指令，是典型的**控制流/标量指令开销压过访存**。两处根因：

1. **`same_block()` 里的 64 bit 整数除法**。判断 4 个连续元素是否落在同一个缩放块时用的是
   `i0 / block_size == (i0 + 3) / block_size`，而 `block_size` 是运行时值——GPU 上一次
   64 bit 整数除法要展开成二十来条指令。改为统一走 `block_index()`（`block_size` 是 2 的幂
   时退化成移位），并且只在首尾两个元素的块号不相等时才逐元素查表。
2. **fp16/bf16 输出编码**。通用实现 `f32_bits_to_fmt_mag<>` 要同时覆盖"次正规规格化（一个
   `while` 循环）+ 上溢饱和 + NaN 传播"，每个元素十几条指令、若干分支。但只要**结果本身落在
   目标格式的有限可表示范围内，硬件转换指令的 RNE 结果与它逐位相同**（两者都是"舍入到
   11 / 8 bit 有效位、ties-to-even"，次正规的进位规则也一致）。因此 `OutTraits` 改成先用
   一条硬件 `cvt` 指令，只有在需要饱和 / NaN 传播的极少数输入上才回退到通用实现。

第 2 条的正确性不是靠推理担保的：`tests/test_formats.cu` 新增 `formats/fast-encode`，
用「全指数域采样 + 全空间随机位模式 + 关键边界值」共 **10 097 216** 个 fp32 编码逐一比对
快速路径与通用实现，**0 处不一致**（在 `-arch=native` 与 `-arch=compute_75` 下都通过）。

| 指标（8192×8192） | 优化前 | 优化后 |
| --- | --- | --- |
| 反量化（MXFP8 block） | 0.671 ms / 303 GB/s | **0.514 ms / 396 GB/s** |
| 反量化（NVFP4 block） | 0.675 ms / 255 GB/s | **0.452 ms / 380 GB/s** |

### 4.5 优化 5：把误差统计融进量化 kernel（1.21× / 1.15×）

**动机**：误差统计原本是独立 kernel，要把 FP32 原始输入（268 MB）和反量化结果（134 MB）
再各读一遍并**逐元素转 fp64 累加**。它一度占 GPU 时间的 55%~69%，是最重的一环；即使
优化 3 把它从 3.28 ms 拉到 1.04 ms，它仍然是**单次访存最大的一遍**。

**做法**：量化 kernel 里已经同时存在 `x[i]` 与刚算出的量化码，反量化只是一次查表 + 一次
乘法，于是把统计直接挂在量化 kernel 的内层循环末尾。工程上有三个要点：

1. **共用累加器**。把 `AccumFast / AccumPrecise` 与归约「汇点」抽到 `include/lpq/stats.cuh`，
   独立 metrics kernel 与融合路径用的是**同一份代码**——两条路径对同一组输入给出逐位相同
   的结果（`pipeline/fused-stats` 断言相对差 ≤ 1e-13，实测 1e-16）。
2. **编译期分流**。`NullSink`（不开统计）/ `FastSink` / `StrictSink` 三个 `Sink` 由
   `dispatch_sink_out()` 的 3×3 泛型 lambda 展开成具体 kernel。不开统计时 `NullSink::add`
   是空函数、`if constexpr` 让整个收尾也消失，因此**未开启统计的量化 kernel 与优化前的
   版本逐指令相同**（实测 0.7855 ms vs 0.7846 ms，差异在噪声内）。
3. **收尾用 warp shuffle**。第一级归约在 warp 内用 `__shfl_xor_sync` 做完，共享内存只需
   8 个 warp 的部分和（288 B）而不是 9 KB，屏障也从 9 次降到 1 次——在量化 kernel 里，
   收尾的共享内存与屏障会明显压低常驻 block 数，代价比归约本身大得多。
   另外收尾的**归约树全程走 fp32 的双分量 (hi, lo)**（每级仍是精确的 TwoSum），只有
   每个 block 最后的 4 次 `atomicAdd(double)` 落在 fp64：消费级 Blackwell 的 fp64 吞吐
   只有 fp32 的 1/64，把 25 次 warp 归约放在 fp64 里每个线程要多付约 1300 条 fp32 指令。

**测量**（MXFP8 / 8192²，`scripts/perf_probe.py`，repeat 30）：

| 方案 | 量化 ms | 误差统计 ms | 合计 ms |
| --- | --- | --- | --- |
| 融合前（独立 metrics kernel） | 0.785 | 1.043 | 2.337 |
| 融合后 | 1.310 | 0（已并入量化） | **1.932** |
| 仅累加、不做收尾归约（对照） | 1.008 | — | — |
| `NullSink`（`--no-fuse-stats`，对照） | 0.786 | 1.043 | 2.337 |

即：累加本身约 +0.22 ms、收尾归约约 +0.09 ms，合计 +0.31 ms，换掉 1.04 ms 的重读，
**净赚约 0.73 ms**。融合后的 NVFP4 同理（3.058 → 2.658 ms）。

### 4.6 优化 6：给量化 kernel 一个寄存器预算（1.16×）

融合之后出现了一个反直觉的现象：量化 kernel 变慢得比"多算的那些指令"更多（1.31 ms vs
预计的 1.01 ms），而**它的访存模式没有变**。用 `-Xptxas -v` 一看就明白了：`NullSink`
版本只要 44 个寄存器，而 `FastSink` 版本要 58 个——累加器本身要常驻 `hi[4] + lo[4] + m`
（9 个），再加上内层循环的工作集，ptxas 就跨过了 4 blocks/SM 的台阶（64K 寄存器 / 256 线程）。
常驻 block 从 5 掉到 4 之后，访存延迟盖不住，算力也就发不出去。

于是做两件事：

1. **把修正项并进 `lo`**。`AccumFast` 原本用 4 个独立的 `cs[4]` 寄存器攒 `|d|`/`d²` 的
   低阶修正，现在直接补进 `lo`——`lo` 本身就是 1e-7 量级的低分量，再叠 1e-8 的修正不改变
   量级，却省下 4 个常驻寄存器。
2. **给 kernel 一个明确的占用率目标**：`__launch_bounds__(kThreads, 6)`（每 SM 至少 6 个
   block）。ptxas 于是把预算压到 40 个寄存器，三个热点 kernel（`FastSink` 的 mxfp8 /
   nvfp4 / 融合版）在 sm_120 上**零 spill**。

| MXFP8 量化阶段 | ms |
| --- | --- |
| 融合后（默认寄存器分配） | 1.310 |
| `-maxrregcount=56` | 1.174 |
| `-maxrregcount=48` | 1.103 |
| **`__launch_bounds__(256, 6)`（改用，源码级）** | **1.078** |

这一步还顺带改掉了收尾归约里的一处结构性问题（fp64 → fp32 双分量树），单独测量只值约
2%，但它的收益是"少占 8 个寄存器 + 不再依赖 fp64"，属于顺手做对的事，不是这一节的主要收益。

**优化 5 + 优化 6 合并效果**：MXFP8 2.337 → **1.668 ms（1.40×）**，
NVFP4 3.058 → **2.608 ms（1.17×）**。

### 4.7 开发中发现并修复的问题

跨实现逐位对拍的价值在于：**它把"看起来对"的实现逼出真 bug**。下面这些都被三实现对拍或
边界测试抓出来并修复：

1. **NVFP4 打包掩码抹掉了符号位**。拼接 4 bit 编码时只保留了幅值掩码，负数被写成正数。
2. **参考实现的二分查找缺少 0 候选**。小于最小可表示幅值的输入被错误地舍入到"最小非零值"
   而不是 0（例如 E2M1 的 0.0076 应为 0，却被量成 0.5）。
3. **反量化的乘法结合顺序不一致**。GPU 写成 `q * (block_scale * global_scale_inv)`，
   参考实现写成 `(q * block_scale) * global_scale_inv`；在 fp32 输出下产生 ULP 级差异。
   统一为前者的结合顺序后逐位一致。
4. **FP32 → BF16 的次正规处理缺失**。BF16 次正规可一直延伸到 2^-133，原实现未做尾数归一化
   就直接取高位，导致小值区间错误。
5. **`f32_from_half_bits` 的 FP16 次正规指数字段算错 2**。归一化循环的初值处理不当，
   使得部分 FP16 次正规读出来的值偏大 4 倍。
6. **`k_block_amax_pow2` 漏掉了 `block_size < 32` 时的部分块**。`__shfl_xor_sync` 用
   `width = block_size` 时，每个子组各有一位组长持有结果；原实现只在 `lane == 0` 时更新
   全张量 amax，于是当 block_size < 32 时一个 warp 里第 2..(32/block_size) 个子块被漏掉，
   **NVFP4 的全局缩放随之错误**。
7. **单块平铺路径没有写出全张量 amax**。当 amax 阶段走"整张量一个 tile"的分支
   （per-tensor，或 block 模式下 `num_blocks == 1`）时，结果直接落在 `block_amax[0]`，
   `d_tensor_amax` 从未被写过，NVFP4 的全局缩放退化成 1.0。
8. **`|d|` 的补偿项把 `dl` 的符号写反了**。4.3 节的 `|d| = |dh| + sign(d)·dl` 一开始写成
   `|dh| + copysignf(dl, dh)`——而 `copysignf(dl, dh)` 取的是 `dl` 的**幅值**配上 `dh` 的
   符号，这里要的却是"`dl` 保留自身的符号、整体再乘 `dh` 的符号"。它让 `Σ|d|` 偏了约
   3e-10 相对量级：绝对值很小，但足以让 1e-12 的判据失败。定位方式是**把同一套算式在
   numpy 里用 `float32` 逐位复现**，一次就分辨出是算法错而不是 kernel 实现错。
9. **误差统计的 `same_block` 式块号判断在反量化里成为性能陷阱**（见 4.4 节第 1 条）：
   功能完全正确，但在每个元素都要调用一次时，64 bit 整数除法把 kernel 拖成了 ALU 受限。
   这类"正确但昂贵"的问题只有靠 SASS 统计 + 逐次计时快照才能发现。
10. **融合统计与独立 metrics kernel 差 1 ulp —— 元凶是编译器的 FFMA 收缩**（优化 5 引入，
    由新加的 `pipeline/fused-stats` 抓出）。两者本应逐位一致，但 `nvfp4/tensor` 一例在
    1e5 个元素里约有 150 个差 1 ulp（相对 3.5e-8），量级不大却足以让 1e-13 的判据报警。
    定位过程：先确认 packed / scales / 反量化输出都逐位相同（即数据没问题），再单独写一个
    kernel 复刻同一个表达式并把它**写进显存**——结果与独立 kernel 逐位相同，说明差异来自
    上下文而不是算式。真正的原因是：独立 kernel 里的 `test` 是从显存读回来的（舍入已经定死），
    而融合 kernel 里的同一个乘积是**就地**交给 `d = test - ref` 的，nvcc 默认
    `-fmad=true`，会把这两步收缩成一条 FFMA——少做了一次舍入。
    用 `-fmad=false` 复编译后差异立刻消失，根因坐实。
    修复不是加编译选项，而是把不变量钉进源码：所有喂给累加器的 `decoded * scale`
    一律走 `mul_rn()`（`__fmul_rn`，明确禁止融合），见 4.5 节。
    这类"同一份算式在两个上下文里舍入不同"的问题，只有逐位对拍才抓得住。

### 4.8 工程环境问题

* **源码编码（补齐 MXFP4 时定位到根因，比原先的判断深一层）**：源码是 UTF-8 无 BOM，且允许中文
  注释 / 字符串。原先只知道要加 `-Xcompiler /utf-8`（否则 MSVC 按本地代码页 GBK 解释非 ASCII
  字节），但这次在中文 Windows（ACP = 936）上写新测试时撞见一个更隐蔽的坑：**`nvcc` 自己的 C++
  前端 `cudafe++`（EDG 6.6）也按系统 ANSI 代码页读源码**，而 `-Xcompiler /utf-8` 只作用于主机
  编译器 cl.exe，管不到它。于是 UTF-8 的汉字被按 GBK 双字节**错位切分**，剩下的孤立首字节会把
  字符串的收尾引号当成自己的尾字节吃掉，报 `error: missing closing quote`（并且在前端眼里整个
  字符串从未闭合，后面还会连带报一串 `expected a ")"`）。
  这个报错**与汉字内容无关，只与本行之前出现过多少字节有关**：在字符串末尾多打一个空格就可能
  "修好"，换一组字又坏掉 —— 极易误诊成"nvcc 不支持中文"。定位手段是用最小探针二分：单字符
  `"应"` 必失败，而同一个字符串后面补一个 `x` 就通过（字节数变了、错位就对不齐了）。
  根治办法是让前端也按 UTF-8 解码，而且必须与 `/utf-8` **同时**给出：

  ```bash
  nvcc ... -Xcudafe --unicode_source_kind=UTF-8 -Xcompiler /utf-8 ...
  ```

  只给 `/utf-8` 会踩上面那个错位坑；只给 `-Xcudafe --unicode_source_kind=UTF-8` 会换成另一个错
  （前端按系统代码页输出预处理结果，汉字表示不了，报 `invalid multibyte character sequence`）。
  两条已加进 `Makefile`（Windows 分支）与 `scripts/build.ps1`；Linux 那几条前端（clang++ /
  mcc / mxcc）不需要。
* **含中文的 `argv` 路径**：Windows 下 `argv` 按 ANSI 代码页编码，若把含中文的绝对路径传进
  程序，日志里会出现 GBK 字节、破坏日志的 UTF-8 一致性。实验脚本因此统一改用相对路径传参
  （解析端也做了 UTF-8 → GBK 的回退）。
* **nsys 与中文工作目录**：nsys 的 protobuf 序列化不接受非 UTF-8 的 `working_directory`，
  中文路径下直接报 `invalid UTF-8 data` / `bad conversion`。解决办法是把可执行文件与数据
  复制到纯 ASCII 目录后再剖析。

| `perf_step20.csv` | **1.382** | **1.926** | 优化 21：宿主侧文件 IO（不改 kernel 时间）；优化 22：融合统计块数上限分路径标定 |

> 因此本报告对小于 3% 的差异一律不下结论（优化 18 的负收益是 1.1%，但它在同一会话内做了

> 合计落在 1.911~1.937 ms，`perf_step20.csv` 是其中最后一次——所以这张表里个位数的百分比

### 4.10 优化 7 ~ 19 摘要

> 优化 1~6 的详细过程见 4.1~4.6，开发中修复的问题见 4.7。以下是其后的要点。

**优化 7~15：逐元素的 ALU 与控制流开销收敛。** 编码/译码函数原本按"正常 / 次正规 / Inf /
NaN / 零"分成多条分支，每个元素都要走一次 BSSY/BSYNC；改成"谓词化 + 末尾一条 SEL"后分支
全部消失（`include/lpq/formats.hpp` 里有详细注释）。同一时期还做了：把 `fmt_to_f32` 的
指数拼接从带 `while` 规格化循环改成位拼接、`clz32` 取代循环、把误差统计里与 CPU 参考实现
对拍的乘法统一成 `mul_rn` 以保证逐位一致。逐次快照见 `perf_step8..15`（MXFP8 1.590 → 1.374，
NVFP4 2.437 → 2.110 ms）。这一段是"多项小优化叠加"，没有单一的决定性改动。

**优化 16：硬件 FP8 编码路径（加分项）。** `cvt.rn.satfinite.{e4m3,e5m2}x2.f32` 一条指令
编码两个 fp32，取代软件路径。用 `tools/verify_fp8_hw_encode.cu` 对**全部 2³² 个 fp32 位模式**穷举验证：
所有有限值逐位一致，唯一差异是 e4m3 的 NaN 符号位与 e5m2 的 Inf 码（两者都不参与数值比较）。
该路径由 `#if LPQ_HW_FP8X2`（`__CUDA_ARCH__ >= 890`）保护，关闭时自动回落软件路径。
另外顺手确认了一个**否定结论**：Blackwell 的 `cvt.*.e2m1x2.f32` 在 ptxas 12.9 上对
sm_120 / 120a / 121a / 103a / 101a / 100a / 120f 一律报
`Instruction 'cvt with .e2m1x2' not supported on .target`，所以 NVFP4 只能走软件编码器。

**优化 17：E2M1 专用 RNE 编码器。** 通用路径要维护 64 bit 有效数字与大量位运算；E2M1 只有
16 个码字，可以直接在 fp32 位模式上做：一次 32 bit 加法同时完成"加半个 ulp + 进位 + 取尾数
低位"，再把指数字段线性映射成 4 bit 码。`tools/verify_e2m1_rne.cu` 对 **2³² 个位模式穷举**，0 处不一致。
这是单点收益最大的一项：NVFP4 量化从 0.9498 降到 0.7332 ms（+29%，其中还包含优化 16 的贡献）。

**优化 18：NVFP4 三合一融合（负收益，已回滚）。** 把"块 amax + 块缩放 + 量化"并进一个
kernel，可以省掉 16.7 MB 块 amax 的写出与读回，看起来是稳赚。实测却是**净变慢**：

| 方案 | amax | 块缩放 | 量化 | 合计 |
| --- | --- | --- | --- | --- |
| 分离（现方案） | 0.693 | 0.045 | 0.734 | **1.472 ms** |
| 三合一（优化 18） | 0.663 | 0.007 | 0.819 | 1.489 ms |

原因是：融合 kernel 里每个 lane 都要对自己那 4 个元素做一次 warp 归约并**独立算出块缩放**
（冗余 4 倍），而分离方案里这些工作落在 `k_nvfp4_block_scales`——它**每线程处理一整块**，
把 log₂(block) 倍的归约与编码完全摊销掉了，量化 kernel 因此退化成纯流式（0.734 ms，
达到纯读上限的 100%）。合计差 17 µs，分离方案胜出，于是回滚；这次实验的记录保留在
`data/perf_step17.csv`（源码已回滚，见 4.9 的快照表）。

> 同期的另一条**排除性实验**：把融合 kernel 里的 shuffle 归约整段去掉（结果错误，只测时间），
> MXFP8 量化耗时从 0.8643 变成 0.8640 ms——**这条路径上的 shuffle 不是瓶颈**。这条结论只对
> MXFP8 成立：它的归约只有 log₂(block/4) 步、且 kernel 已经贴着纯读上限，省掉归约自然不快。
> 到了 8.6 的 4/6 kernel 情况正好相反——那里每个 4 元素向量要发 4×L×2 条 shuffle，去掉归约
> 实测能快 18%。

**优化 19：硬件 FP8 译码路径。** `cvt.rn.f16x2.{e4m3,e5m2}x2` + `cvt.f32.f16` 两条指令取代
十几条整数拆分 + `exp2i` 的软件译码。e4m3/e5m2 的全部有限值都能被 fp16 精确表示，因此
**逐位等价**（`tools/verify_fp8_hw_decode.cu` 对全部 256 个编码核对）。在访存受限的核里收益 < 1%（落在测量
噪声内），但在块缩放热点（优化 18 的融合路径）上实测有 1.2%——保留它是因为它严格更少指令、
且与优化 16 的编码路径对称。

### 4.11 优化 20：随机舍入不再用 splitmix64

**问题。** 随机舍入原先每个元素调一次 `mix64`（splitmix64 终混），即**两次 64 bit 乘法**加
多次 64 bit 移位/异或。翻回编码函数就能看到这笔钱花得冤枉：判定式是 `q = q0 + (r < rem)`，
而 `rem = sig & ((1<<drop)-1)` 恒小于 2²⁴（`sig` 只有 24 bit），**所以真正被用到的只有 rnd
的低 24 位**——64 bit 混合是在为用不到的高位付钱。

**改法。** 换成 murmur3 fmix32 风格的 32 位混合（3 次 32 bit 乘法）。归因用"把随机数换成
一个平凡哈希"的极限实验做了隔离：随机数原本占掉 mxfp8 量化 +0.175 ms，换 fmix32 后只剩
+0.065 ms，余下的是通用软件舍入路径与硬件 `cvt` RNE 路径的固有差距。

| 配置（8192²，fp16 输出） | 优化前量化 | 优化后量化 | 提升 |
| --- | --- | --- | --- |
| mxfp8-e4m3 block，随机舍入 | 1.060 ms | 0.931 ms | **−12.1%** |
| nvfp4 block，随机舍入 | 1.855 ms | 1.717 ms | **−7.4%** |
| （对照）mxfp8-e4m3 block，RNE | 0.864 ms | 0.864 ms | 不变 |
| （对照）nvfp4 block，RNE | 1.458 ms | 1.490 ms | 漂移范围内 |

**正确性论证。**
1. `include/lpq/common.hpp` 的注释给出了"只用低 24 位"的推导；
2. 新哈希的下标高位也参与混合，因此 numel ≥ 2³² 时不会与低位下标混叠；
3. `tests/test_pipeline.cu` 的 `pipeline/stochastic-rounding`（落点必须在 RNE 相邻编码上、
   并且确实产生了差异）与 `pipeline/stochastic-unbiasedness`（|bias_rne| / max|bias_sr| 需
   相差 50 倍以上）继续通过；
4. **随机舍入本来就没有"逐位复现某条随机序列"的判据**——测试只约束"±1 ulp"与"期望无偏"
   两条统计性质。

**这是一处会改变输出比特的改动**（同一 seed 下与旧版不同，统计性质不变）。配套地，CPU 参考
实现的 `table_quantize` 改为由低 32 位构造 [0,1) 均匀分布（原来是取高 53 位，那是 splitmix64
时代的口径）。`data/cpu_compare.csv` 里 GPU/CPU 的"逐位一致"对随机舍入一栏本来就是 `no`：
CPU 参考用"表格插值 + 概率 p"的公式，GPU 用"有效数字余数"的公式，两者**概率等价但不是同一
组随机实现**，这正是 6.4 要专门说明的一点。
### 4.12 优化 21：宿主侧的整块文件读写（预处理快 5 倍）

**问题。** 到优化 20 为止，报告里的数字全是 GPU kernel 的：8192² 下两条链路合计 1.39 / 1.93 ms。
但把整个进程的墙钟时间拆开（在 `src/main.cu` 里临时插桩）后发现，GPU 只占其中很小一部分：

| 阶段 | 优化前 |
| --- | --- |
| 进程启动到 CUDA 上下文可用 | 74 ms |
| 预处理（读 256 MiB + H2D） | **417 ms** |
| GPU 流水线（warmup 15 + repeat 50 = 65 轮） | 107 ms |
| D2H + 写 `_lowp.bin`（69 MB） | 82 ms |
| D2H + 写 `_dequant.bin`（134 MB） | 167 ms |
| 写日志 + 进程退出清理 | 145 ms |
| **合计** | **约 620 ms** |

也就是说：**「读一个 256 MiB 的输入」这一件事，比整条 GPU 链路还贵 100 倍。**

**定位。** 单独写了一个最小程序（`build/_io.cpp`，临时用，已删）逐项计时，问题出在 MSVC 的
iostream 上——同一块盘、同样已进页缓存，CRT 的 `fread/fwrite` 快 4 倍：

| 路径 | 读 256 MiB | 写 134 MiB |
| --- | --- | --- |
| `std::ifstream` / `std::ofstream` | 162 ms（1.66 GB/s） | 120 ms（1.17 GB/s） |
| CRT `fread` / `fwrite` | **39 ms（6.88 GB/s）** | **81 ms（1.73 GB/s）** |

另有几处重复搬运：`read_tensor_file` 先把整个文件读进临时 `vector`，再 `assign` 进
`HostTensor`（256 MiB 拷两遍，外加一次 `vector` 的零初始化）；`write_lowp_file` 又把
header + packed + scales 拼成第三个 69 MB 的大 buffer。

**改法**（`src/lowp_tensor.cu` 重写，入口签名不变）：

* 加一层平台相关的整块读写 `FileReader` / `FileWriter`：Windows 走
  `_wfopen`（UTF-8 路径 → UTF-16）+ `fread/fwrite`，其它平台仍走 iostream，Linux/Makefile
  路径的行为与之前一致；
* 张量文件改成「先读文件头解析 shape/dtype → 算出数据偏移 → `seek` 过去直接
  读进 `HostTensor::data`」，只剩一遍；lowp 文件同样改成头/packed/scales 三段直读；
* 写侧改成头/packed/scales 三段顺序写出，不再先拼一个大 buffer；
* 顺带补了 `LowpHeader` 里 `packed_bytes < 0` / `scale_bytes < 0` 的合法性检查
  （原来是 `(size_t)` 强转后比大小，负值会被当成天文数字）。

**计时口径。** 首次触碰 CUDA 时要建上下文（实测 74~110 ms），这是驱动的一次性开销，不属于
「预处理」。现在它被单独记为 `cuda_context_init_ms`（从进程启动计到 `cudaFree(nullptr)`
唤醒运行时为止），`preprocess_ms` 只剩下「读文件 + H2D 拷贝」。**日志里两个数都给，
不藏账。**

**效果：`preprocess_ms` 417 ms → 70~100 ms（约 5 倍），端到端 620 ms → 537~573 ms。**
正确性上这是一次纯 IO 改写：改动前后 `_lowp.bin` 与 `_dequant.bin` 的 SHA256
**完全一致**，三套测试全部通过。

> 端到端剩下的三块（D2H + 落盘 249 ms、上下文建立 75~110 ms、退出时驱动清理 145 ms）都在
> 磁盘与驱动里，程序侧没有可改的余地。

### 4.13 优化 22：融合统计的块数上限按路径分开标定

**背景。** 优化 5 把误差统计融进量化 kernel 后，收尾（warp 内两分量树形归约 + 每 block
4 次 fp64 `atomicAdd`）是**按 block 数收费**的：8192² 下若放开到 65536 个 block，
`4 × 65536` 次 `atomicAdd(double)` 全撞在同 4 个地址上被硬件串行化，量化 kernel 直接从
0.78 ms 涨到 1.93 ms。所以当时把带统计的块数上限压到 `kStatsMaxBlocks = 2048`，
用网格跨步循环把 65536 块的工作摊到 2048 块上。

**重新标定。** 上限压低省了收尾，却牺牲了访存并行度；随着优化 16/17/20 把每元素
的指令数降下来，这个平衡点已经移动了。把上限做成可覆盖的宏后扫了一遍（每个点 50 次取最小，两轮取 min）：

| 统计块数上限 | MXFP8 RNE 量化 | MXFP8 SR 量化 | NVFP4 RNE 量化 | NVFP4 SR 量化 |
| --- | --- | --- | --- | --- |
| 2048 | 0.870 | **0.928** | **0.733** | **0.978** |
| 4096 | 0.858 | 0.943 | 0.741 | 0.998 |
| 8192 | **0.847** | 0.977 | — | — |
| 32768 | 1.024 | — | — | — |
| 65536 | 1.927 | — | — | — |

（8192²，ms）

**结论是一条与注册器压力相关的规律**：MXFP8 的 RNE 路径每线程注册器最少、驻留
block 最多，上限提到 8192 反而更快（−2.7%）；而随机舍入多一份随机数运算、NVFP4
每元素多一次除法与 4 bit 打包，两者的驻留块数更低，上限一放宽就亏。因此按路径分开：

```c
LPQ_STATS_MAX_BLOCKS     8192   // MXFP8 RNE
LPQ_STATS_MAX_BLOCKS_SR  2048   // 随机舍入路径
LPQ_STATS_MAX_BLOCKS_NV  2048   // NVFP4（两种舍入都用）
```

`src/quantize.cu` 的注释里保留了完整扫描数据，三个宏都能用 `-D` 覆盖重扫。

**关于「是否引入回归」**：三个宏里只有第一个相对旧值（2048）有变化，即 MXFP8 RNE
量化 0.868 → 0.849 ms（−2.2%）；其余三条路径的取值与优化 5 以来的行为完全一致，
所以这次标定对任何配置都不引入回归。`perf_step20.csv` 与 `perf_step19.csv` 的逐路径对比是
MXFP8 RNE −0.7% / MXFP8 SR +1.5% / NVFP4 RNE +0.01% / NVFP4 SR −0.3%：MXFP8 SR 的 +1.5%
落在 4.9 说的环境漂移里，同会话的扫描（上表）显示该路径在 2048 与 4096 两个上限下都是
0.928~0.943 ms，没有变化。

* **融合统计与独立统计的一致性**（`pipeline/fused-stats`，优化 5 新加，本次扩充）：15 种配置
  （四种格式 × tensor/block 缩放 × fp16/bf16/fp32 输出 × 含异常值分布，另含三条 4/6 规则）下，逐步验证
  packed、scales、反量化输出**逐位相同**，且融合统计与独立 metrics kernel 的四个统计量
  相对差 ≤ 1e-13（实测 1e-16 量级）。这条断言正是 4.7 节第 10 条那个 FFMA 收缩 bug 的
  捕获者。
* **4/6 逐规则对拍**（`pipeline/scale-rule-4-6`，本次新加）：static_6 / static_4 / abs_max / mae / mse 五条规则 × 3 种分布，块缩放因子与 packed 码字全部与独立参考实现逐位一致；并断言动态规则确实改写了块缩放因子、MSE 不劣于 static_6、且各自改善对应指标。

**随机舍入无偏性的决定性检验**：构造一个"绝大多数元素取同一个落在量化区间内部的值"的
张量，同时把 amax 抬高以固定缩放因子。此时 RNE 对同一个值总是朝同一侧舍入，每次运行的
平均误差都是同一个非零偏置；SR 每次在相邻两个格点间独立随机选择，平均误差期望为 0。

| 格式 | RNE 偏置绝对值 | SR 单次最大偏置绝对值 | RNE/SR |
| --- | --- | --- | --- |
| mxfp8-e4m3 | 2.499959e-02 | 5.150e-04 | **49×** |
| mxfp8-e5m2 | 9.999850e-02 | 1.225e-03 | **82×** |
| mxfp4 | 3.999939e-01 | 3.937e-03 | **102×** |
| nvfp4 | 2.666626e-01 | 3.215e-03 | **83×** |
即 SR 的单次偏置比 RNE 小 1.5～2 个数量级，且 32 次试验的平均偏置进一步小一个数量级，
与"SR 无偏、RNE 有偏"的理论一致。（RNE 那一列是确定值；SR 那一列每次运行有 ~5% 抖动，
因为随机舍入的抽样本身随机，这也符合 5.1 的说明。）
与"SR 无偏、RNE 有偏"的理论一致。

### 5.1 统计量的运行间非确定性

上面这些测试打印的误差统计量（`accum diff`、`fused-stats` 那几行）**不逐位可复现**：同一个
二进制、同一份固定输入（`pipeline/error-stats-accum` 的输入由 `tests/test_pipeline.cu` 里写死的
种子 `0x2545F4914F6CDD1D` 生成），连跑几次，末位会跳：

| 运行 | MTT S4000：fast vs precise 的 mae | MTT S4000：precise vs cpu 的 mae | RTX 5060 Ti：fast vs precise 的 mae | RTX 5060 Ti：precise vs cpu 的 mae |
| --- | --- | --- | --- | --- |
| 1 | 0.000e+00 | 8.468e-13 | 1.303e-16 | 8.472e-13 |
| 2 | 2.607e-16 | 8.472e-13 | 2.607e-16 | 8.468e-13 |
| 3 | 0.000e+00 | 8.471e-13 | 1.303e-16 | 8.471e-13 |

原因在 `src/metrics.cu` 的归约方式：**每个 block 一次 `atomicAdd(double)`**（该文件顶部注释里
写明了这个取舍），block 之间的完成顺序由硬件调度决定，而浮点加法不满足结合律，于是每次运行的
求和顺序不同。这是设计取舍得来的、**与平台无关**的行为：两台机器上出现的取值来自**同一个离散
集合**（`fast vs precise` 的 mae 只取 {0, 1.303e-16, 2.607e-16, 5.213e-16}），不是某张卡
"算得不准"。

影响面很窄，可以放心：

* **断言全部稳定通过**。三条统计断言的门限是 1e-13，实测在 1e-16 量级，即使取到波动的最坏值
  也还有约 1000 倍余量；断言全过这件事不受它影响（当前英伟达上合计 314205 条）。
* **量化输出本身逐位确定**。packed 位与 scales 只依赖 amax，而 max 归约与顺序无关，所以端到端
  实验每次都报 `packed_bits_identical = yes`、`dequant_bit_mismatch_count = 0`。
* 因此两份不同时间跑出来的日志在**数值列最后 1～2 位**上有差异属于正常现象，不是平台差异、
  也不是回归。

要彻底消除它，需要改成确定性归约（两级：先把每 block 的部分和写入数组，再做一趟固定顺序的
归约），代价是一次额外的 kernel 与一趟显存往返。本项目没有做这个改动：误差统计是给开发者看的
分析工具、不是被提交的计算结果，为一个只影响第 16 位有效数字的展示值付这份代价不划算。

| outlier | nvfp4 | block | 3.536 | 0.08407 | 2.78e-2 | **3.88e-3** |
| outlier | mxfp4 | block | 15.87 | 0.1148 | 0.1178 | 1.648e-2 |
| outlier | mxfp4 | tensor | 15.74 | 0.8037 | 1.060 | 1.482e-1 |

**结论 1 —— 缩放粒度对 4 bit 格式是决定性的，对 8 bit 格式则不是。**
NVFP4 只有 2 位尾数，块内元素必须紧贴本块 amax 归一化才能保住精度：含异常值矩阵上
per-tensor 的相对 MSE 为 1.49e-1，block-wise 为 3.88e-3，**改善约 38 倍**。
MXFP8 的 E4M3 有 3 位尾数、相对精度本身较好，一个全局指数已足以应付异常值：
tensor 7.17e-4 与 block 1.03e-3 处于同一量级，block 甚至略差——来源是块间指数的抖动，
以及结论 3 要讲的顶部饱和。在平稳分布上两者差别同样很小（normal：7.07e-4 vs 8.76e-4，
per-tensor 略优）。**工程含义：4 bit 格式必须配 block 缩放；8 bit 格式在对 scale 元数据
开销敏感时可以直接用 per-tensor 缩放。**

> 附注：随机分布（uniform[-1,1]）下 MXFP8 的 tensor 与 block 结果**逐位相同**，原因是
> 均匀分布的每个块 amax 都落在同一 binade（`amax < 1.0` 恒成立），于是 `floor(log2(amax))`
> 对 8192 个块给出同一个指数——这也从侧面验证了共享指数的计算是自洽的。

**结论 2 —— 元素格式的尾数位比缩放粒度更值钱。** 同为 block 缩放，MXFP8-E4M3 的相对 MSE
只有 MXFP8-E5M2 的 30%（8.76e-4 vs 2.91e-3），因为 E4M3 有 3 位尾数而 E5M2 只有 2 位。
而 NVFP4 用一半的位宽把相对 MSE 做到 9.08e-3，代价是相对 MSE 比 MXFP8-E4M3 高约 10 倍、
压缩率高约 1.8 倍——**典型的"精度换压缩率"折中曲线**。

**结论 3 —— 观察到 MX 共享指数的一个固有现象（饱和）**。OCP 规定的共享指数是
`floor(log2(amax)) - emax`，因此 `amax / scale ∈ [2^emax, 2^(emax+1))`；而 E4M3 的有限
最大值是 448 < 512，于是**当块内 amax 落在其 binade 的顶部 12.5%（0.875, 1.0）区间时，
最大元素会饱和到 448**。这解释了 6.1 节表格中"normal 分布下 block 的 max abs err（0.4942）
反而大于 tensor（0.2414）"的反直觉现象：某个块 amax ≈ 3.99，其缩放因子为 2^-7，3.99/2^-7
= 510.7 > 448，饱和后只会得到 3.5，误差 0.49。这是规范化公式的已知副作用（饱和转换是
`cvt.satfinite` 语义），而非实现错误——但确实提示了 8.2 节的一个改进方向。

**结论 4（本次补齐 MXFP4 后的新对照）—— 同为 4 bit，MXFP4 的共享指数比 NVFP4 的分层缩放更粗。**
MXFP4 与 NVFP4 的**元素**完全相同（都是 E2M1、都占 4 bit），差别全在缩放语义上：MXFP4 用
E8M0 的 2 的整数次幂做块缩放，NVFP4 用 E4M3（3 位尾数）+ FP32 全局缩放。实测（normal 分布，
block 模式）相对 MSE 为 **1.328e-2 vs 9.078e-3**，MXFP4 差约 46%；含异常值的 outlier 分布上
差距拉大到 **1.648e-2 vs 3.880e-3**，差约 4.2 倍 —— 因为 E8M0 只能表达 2 的幂，块内 amax 落在
binade 顶部时无法像 E4M3 那样"退而求其次"，只能吃饱和。作为交换，MXFP4 的元数据更轻：
每 32 元素 1 字节 scale（0.25 bit/元素）vs NVFP4 每 16 元素 1 字节（0.5 bit/元素），
压缩率 7.529× vs 7.111×。**工程含义：MXFP4 适合"元数据开销敏感、且数据分布平缓"的场景，
NVFP4 适合对精度要求更高（尤其是长尾/异常值）的场景。**

> 附注：MXFP4 的 tensor 与 block 在随机分布下**逐位相同**，原因与 MXFP8 完全一致（见上一条附注）
> —— 均匀分布的每个块 amax 都落在同一 binade，`shared_exp` 对全部块给出同一个值。这也是
> E8M0 语义正确性的又一个侧面证据。

| mxfp8-e4m3 block + 随机舍入 | **1** | 0.945 | 0.522 | 0 | 1.466 |
| nvfp4 block（两遍） | 2 | 1.474 | 0.452 | 0 | 1.926 |

NVFP4 的量化列由三个 kernel 构成（amax 0.689 + 块缩放 0.044 + 量化 0.740 ms，nsys 单独
计时见 6.5）。作为对比，优化 6 结束时这两行是 **1.668 / 2.608 ms**，即端到端 1.21× / 1.35×。

**带宽账按实际显存流量算**（每个 kernel 真正读写的字节数，而不是「输入只计一次」的口径）：

| 阶段 | 实际流量 | 带宽 |
| --- | --- | --- |
| NVFP4 块 amax（读 268 + 写 17 MB） | 285 MB | 413 GB/s |
| NVFP4 块缩放（读 17 + 写 4 MB） | 21 MB | 477 GB/s（几乎全命中 L2） |
| NVFP4 量化（读 273 + 写 34 MB） | 306 MB | 413 GB/s |
| MXFP8 量化（读 268 + 写 69 MB） | 338 MB | 402 GB/s |
| MXFP8 反量化（读 69 + 写 134 MB） | 203 MB | 375 GB/s |
| NVFP4 反量化（读 38 + 写 134 MB） | 172 MB | 380 GB/s |

**「到顶了没有」——用同样读写比例的纯搬运做标定。** 拿纸面峰值（448 GB/s）去比会低估实现
质量，因为这张卡在读写混合下本来就拿不到标称带宽；拿「输入只计一次」的口径去比，又会让
NVFP4 的读数超过物理上限。更严格的做法是给每个阶段造一个**只做同样字节搬运、不做任何计算**
的对照 kernel（`tools/bw_ceiling.cu`：每条线程的访存宽度、每元素读写的字节数都与真实 kernel
逐项对齐），量出该 (读, 写) 组合下硬件真正能跑到的带宽，再让真实 kernel 去比：

| 阶段 | 每元素读 / 写 | 对照 kernel 上限 | 真实 kernel | 达成率 |
| --- | --- | --- | --- | --- |
| NVFP4 块 amax | 4 B / 0.25 B | 0.660 ms（431 GB/s） | 0.689 ms | **96%** |
| MXFP8 量化（含融合统计） | 4 B / 1 B | 0.820 ms（409 GB/s） | 0.841 ms | 98% |
| MXFP8 量化（关掉统计） | 4 B / 1 B | 0.820 ms | 0.779 ms | **105%** |
| NVFP4 量化 | 4 B / 0.5 B | 0.712 ms（425 GB/s） | 0.740 ms | 96% |
| MXFP8 反量化 | 1 B / 2 B | 0.534 ms（377 GB/s） | 0.541 ms | **99%** |
| NVFP4 反量化 | 0.5 B / 2 B | 0.457 ms（366 GB/s） | 0.452 ms | **101%** |

其中「关掉统计」一行是同一个 kernel 只换一个编译期汇点类型（见 4.10）：它**比对照 kernel 还
快 5%**，说明量化 kernel 本身的访存已经没有任何余地；打开统计后掉到 98%，也就是融合进来的
误差统计只花掉约 8% 的量化 kernel 时间（0.779 → 0.841 ms）——而这笔代价换来的是省掉一个
1.05 ms 的独立 metrics kernel（优化 5），是明确的净赚。

同一张表还解释了两件事：反量化两行**接近或略超 100%**，因为它读得少、写得多，而真实 kernel
的写比对照更集中（每线程 4 个 half 落成一条 8 B store）；而全部对照 kernel 的带宽都落在
366~431 GB/s，与同一台机器上**纯读 423 GB/s、纯写 423~443 GB/s**（`build/bw_ceiling.exe` 的第 1
行与第 7 行；纯写这一项跨会话会在 423~443 之间摆动，`data/out/nvidia_verify_20260918.txt` 归档了
其中一次完整输出）处在同一量级——**读写混合与换向的开销是 DRAM 的硬性代价，与 kernel 写法无关**。

为确认「混合上限」不是访问方式造成的假象，还拿同一微基准扫过 `__ldcs` / `__stcs` / `__ldg`、
每条线程 1/2/4 个 16 B 段、256/512/1024 线程、常驻块数（36×8 / 36×16）等组合，
**所有读数的离散度都在 ±1.5% 以内**。

**结论：整条链路是访存受限的，每个阶段都达到了「同种字节混合」下硬件实测上限的 96%~105%。**
唯一还看得出结构性差距的是随机舍入：MXFP8 量化 402 → 357 GB/s、NVFP4 量化 413 → 313 GB/s。
原因是随机舍入必须走通用的软件舍入路径，拿不到 RNE 那条硬件 `cvt` 快路径。优化 20 把这一项
的相对代价从 +23%（MXFP8）/ +27%（NVFP4）压到 **+12% / +32%**（都按量化 kernel 本身计：
0.841 → 0.945 ms、0.740 → 0.978 ms）；NVFP4 若改按含 amax 与块缩放的量化总时间计则是 +16%
（1.474 → 1.711 ms）。剩下的差来自舍入逻辑本身；8.1 给出了把它也做成专用编码器的路径。

> 关于"有效带宽"的口径：日志同时给出两个数。`effective_bandwidth_quantize_GBps` 按"输入
> 只计一次"的口径（直观、便于横向比较），`dram_bandwidth_quantize_GBps` 按**实际读取遍数**
> 折算真实显存流量。对 MXFP8 单遍融合路径两者相同；对 NVFP4 两遍路径，前者约 208 GB/s、
> 后者约 390 GB/s——后者才是物理量。**小规模（n ≤ 4096）的读数会被本机 32 MiB 的 L2 抬起，
> 属于测量假象**：n = 8192（输入 256 MiB）时 L2 影响可忽略。

**规模效应**：n = 256 时量化 8 µs、反量化 9~14 µs，两者都在启动开销的量级，n ≤ 2048
时反量化的测量里混着相当比例的同步/启动开销（数字抖动可达 2~3 倍，见 `docs/measurements.md`
表 4/表 5 里 n = 256~2048 的几行）。这有两层原因：一是 kernel 本身只有几十微秒；二是优化 5
之后，融合路径为了让调用方立刻拿到统计量，要在量化阶段末尾做一次 36 字节的 D2H 并同步，
这次同步会清空流水，把随后 kernel 的**启动延迟**暴露进它的计时窗口（约 5~15 µs）。n ≥ 4096
后这个固定开销可以忽略。这也是本报告坚持给出"规模 → 带宽"曲线而不是单一数字的原因。

### 6.4 GPU 与 CPU 同级别实现的对比

程序内置的 `--cpu-check` 会额外运行单线程 CPU 参考实现（查表 + 二分 + 串行流水线），
并给出加速比与逐位对拍结果。

**测量规模的选择**：512×512 时 GPU kernel 只有几微秒，加速比被 kernel 启动开销与测量抖动
主导（同一配置重测可在 45×~156× 之间波动）；退到 2048×2048（419 万元素）GPU kernel 也只有
几十微秒，量化时间的重测抖动仍有 1.8 倍（同一配置两次测得 0.070 ms 与 0.126 ms）。因此这里取
**8192×8192 = 6710 万元素**（与 6.3 节同规模）：量化 kernel 落在 0.85~1.70 ms，CUDA event
计时的相对误差进入 2% 以内，各配置之间的相对次序也才稳定下来
（`python scripts/cpu_compare.py --n 8192 --repeat 50 --warmup 15`，数据见 `data/cpu_compare.csv`）：

| 配置 | CPU 量化 ms | GPU 量化 ms | 量化加速比 | CPU 反量化 ms | GPU 反量化 ms | 反量化加速比 | packed 逐位一致 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| mxfp8-e4m3 block / fp16 / RNE | 2161.71 | 0.8294 | **2606×** | 309.83 | 0.5518 | 562× | 是 |
| mxfp8-e4m3 block / fp16 / SR | 2033.42 | 0.9173 | **2217×** | 301.85 | 0.5376 | 561× | 否（见下） |
| mxfp8-e5m2 block / fp16 / RNE | 1977.68 | 0.8369 | **2363×** | 302.74 | 0.5541 | 546× | 是 |
| mxfp4 block / fp16 / RNE | 1644.27 | 0.7885 | **2085×** | 321.68 | 0.4971 | 647× | 是 |
| nvfp4 block / fp16 / RNE | 1895.58 | 1.4811 | **1280×** | 282.65 | 0.4672 | 605× | 是 |
| nvfp4 block / fp16 / SR | 1669.05 | 1.7032 | **980×** | 280.17 | 0.4441 | 631× | 否（见下） |
| nvfp4 tensor / fp16 / RNE | 1433.60 | 1.3968 | **1026×** | 283.29 | 0.4522 | 626× | 是 |
| nvfp4 tensor / fp32 / RNE | 1423.21 | 1.3934 | **1021×** | 279.47 | 0.8200 | 341× | 是 |

> GPU 侧是流水线内的事件计时，每个 kernel 的启动延迟（约 5~15 µs）与融合路径末尾那次 36 字节
> D2H 同步都还计在里面，所以这一列的绝对值仍然偏保守，加速比是**下限**。
> 各配置之间的相对次序与 6.3 节一致：MXFP8 单遍融合快于 NVFP4 两遍，RNE 快于 SR；
> 最后一行反量化最慢是因为输出类型是 fp32（要写 268 MB 而不是 134 MB）。

**所有 RNE 配置下 `packed_bits_identical = yes`、`dequant_bit_mismatch_count = 0`**，即
在获得 980×~2606×（量化）、341×~647×（反量化）加速的同时，上表每一个「逐位一致 = 是」
的行都与 CPU 参考实现**逐位一致**。SR 配置的 packed 不一致
是设计使然：GPU 端按 `random_at(seed, idx)` 的低位掩码进位，参考端按浮点概率进位，
两者用的是不同的随机数方案，因此只在**统计意义**下可比（由
`pipeline/stochastic-unbiasedness` 验证无偏性），这一点在 `include/lpq/reference.hpp`
的注释中已明确说明。

### 6.5 nsys 剖析

用 Nsight Systems 抓取 8192×8192 的完整流水线（每个配置 1 次预热 + 5 次正式运行；
kernel 名与调用次数直接取自报告的 `CUPTI_ACTIVITY_KIND_KERNEL` 表；原始记录与统计文本见
`docs/profile/`）。

**MXFP8（单遍融合路径）**

| Kernel | 单次耗时 | 占 GPU 时间 |
| --- | --- | --- |
| `k_quant_mxfp8_block_fused<float, FmtE4M3, FastSink<__half>>` | 0.847 ms | 61.8% |
| `k_dequant_mxfp8<__half, FmtE4M3>` | 0.524 ms | 38.2% |

**NVFP4（两遍路径）**

| Kernel | 单次耗时 | 占 GPU 时间 |
| --- | --- | --- |
| `k_quant_nvfp4<float, __half, FastSink<__half>, false>` | 0.746 ms | 38.6% |
| `k_block_amax_pow2_vec4<float>` | 0.687 ms | 35.5% |
| `k_dequant_nvfp4<__half>` | 0.446 ms | 23.1% |
| `k_nvfp4_block_scales` | 0.052 ms | 2.7% |
| `k_nvfp4_global_scale` | 0.0009 ms | 0.0% |

**分析：**

1. **nsys 的 kernel 时间与程序内部 CUDA event 计时互相印证**：NVFP4 量化
   0.687 + 0.052 + 0.0009 + 0.746 = **1.486 ms**，与 6.3 节同一快照日志里的 `quantize_total_ms`
   （1.474 ms）相差 0.8%；MXFP8 融合量化 nsys 0.847 ms 与事件计时的 0.841 ms 相差 0.7%。
   这点差额来自 nsys 的插桩开销与 4.9 节记录的那 2~3% 环境漂移。这说明自建计时口径可信，
   不需要额外的计时基础设施。
2. **误差统计 kernel 已经不在列表里**——优化 5 把 `Σ|d|`/`Σd²`/`Σr²`/`Σd` 的累加并进了
   量化 kernel 的收尾（见 4.5）。本报告早期版本里"`k_error_stats` 独占 55%~69% GPU 时间"
   那一节已经完全作废，这也是当年最大的一处瓶颈。
3. **NVFP4 的两遍里，`k_block_amax_pow2_vec4` 占 35.5%**：它读满一遍输入（268 MB）并写出
   16.7 MB 块 amax，合计 285 MB / 0.687 ms = **415 GB/s**，已经是本机纯读实测上限
   （423 GB/s，见 6.3）的 98%。这一遍之所以省不掉，是因为 NVFP4 的 `global_scale` 依赖全张量 amax
   （格式定义决定，见 2.3）；优化 18 试过把它融进量化 kernel，实测更慢（见 4.10）。
4. `k_nvfp4_block_scales` 与 `k_nvfp4_global_scale` 合计只占 2.7%（52 µs + 0.9 µs），说明
   "每线程处理整块"的小 kernel 摊销得很好——这也是优化 18 的融合方案反而失败的原因。
5. 反量化 kernel 的占比（23%~38%）与它的数据量一致，没有异常。
### 6.6 平台适配

`Makefile` 为 `nvidia / iluvatar / moore / metax` 四个平台提供了编译分支（分别使用
`nvcc / clang++ / mcc / mxcc`，参数对齐官方 `Learning-CUDA` 仓库中已验证可用的配置）。

**初版结论「源码无需修改」在细查后被推翻了。** 本实现确实不含 `cuda_fp8.h`/`cuda_fp4.h`、
不含 Tensor Core、不含 Hopper/Blackwell 专有语义，但逐行审计后仍找到**六处**平台相关
差异 —— 它们此前散落在源码各处，只在英伟达编译器下「恰好」都能工作：

| # | 差异点 | 原来依赖 | 抽象后 |
| --- | --- | --- | --- |
| 1 | 是否处于设备编译 | `#if defined(__CUDACC__)` | `LPQ_CUDA`（同时认 `__MUSACC__` / `__MACA__`） |
| 2 | 是否处于设备编译遍 | `#if defined(__CUDA_ARCH__)`（2 处） | `LPQ_DEVICE_PASS` |
| 3 | 低精度类型头文件 | 硬编码 `cuda_fp16.h` / `cuda_bf16.h` | `LPQ_FP16_HEADER` / `LPQ_BF16_HEADER` |
| 4 | warp 内交换 | `__shfl_xor_sync`（3 处） | `LPQ_SHFL_XOR` |
| 5 | 浮点原子最大 | `atomicMax((int*)…)`（5 处） | `lpq_atomic_max_f32` |
| 6 | 双精度原子加 | `atomicAdd(double*)`（**4 处，在最热的 kernel 里**） | `lpq_atomic_add_f64` |

第 6 项是复查时最意外的发现：`atomicAdd(double*)` 自 sm_60 起才是硬件指令，更早的架构
由 nvcc 生成 CAS 序列，而部分国产平台根本没有实现它 —— 偏偏它出现在占 GPU 时间
55%~69% 的 `k_error_stats` 里。第 5、6 项都补了 CAS 循环回退，并已在本机实测：加上
回退开关后 `test_portability` 全部通过，且 `test_pipeline` 的随机舍入无偏性数字与原生
实现**逐位一致**（46× / 79× / 91× 完全相同）。第 4 项没有提供自动回退，因为一个正确的
共享内存版本要求三处调用点的线程参与条件完全一致，直接替换宏会在 `k_block_amax_generic`
的提前 `return` 之后造成 `__syncthreads` 分歧；因此 `LPQ_SHFL_XOR` 被设计成唯一改动点。

配套的 `tests/test_portability.cu` 把上述能力拆成七组独立小测试（宏探测、`width` 取
1/2/4/8/16/32 的 warp 交换、两种原子操作、位模式往返、半精度/bf16 转换、`float4` 与
`uint16` 打包访存），逐项报告通过与否，并在失败时直接给出应该添加的 `-D` 开关 ——
避免在按小时计费的租用机器上通过「改一处、重编一次」的方式盲试。`scripts/run_domestic.sh`
把「环境检查 → 编译 → 探针 → 正确性套件 → 小规模端到端实验」串成一条命令，且刻意不在
失败时退出。

**复查时又发现第七处差异，而且是最大的一处 —— 它在构建层，`platform.hpp` 修不了。**
摩尔线程 MUSA 的运行时对象叫 `musaXxx`（`musaMalloc` / `musaMemcpy`，头文件 `musa_runtime.h`），
低精度类型头也是 `musa_fp16.h`；而本项目源码里以 `cudaXxx` 写成的调用点有 200 多处。逐行改名
既费时又容易引入笔误，改完这份源码也不能再直接交给 nvcc，还要重新验证一遍。官方对这件事给了
三条现成的路，`Makefile` 的 `moore` 分支把三条都接好，`MUSA_MODE=auto`（默认）按可用性自动选：

| 模式 | 命令要点 | 可用条件 | 说明 |
| --- | --- | --- | --- |
| `wrapper` | `mcc -mtgpu -cuda_wrapper … -lcuda2musa` | `libcuda2musa.so` 在 | mcc 的"兼容封装模式"，手册原话是"支持开发人员使用 CUDA API 而不是 MUSA 的" |
| `mapping` | `mcc -x musa -fplugin=<libMusaMapping.so>` | SDK ≥ 5.2.0 | 编译期 Clang 插件，按映射表重写头文件名与标识符 |
| `plain` | `mcc -mtgpu … -lmusart` | 源码已迁移过 | 先跑 `musify-text --inplace` 改一遍源码 |

这处差异同样暴露了几个只有读手册才能知道的细节：`.cu` 后缀 mcc 默认不认，必须 `-mtgpu`
（或 `-x musa`）才按 MUSA 源文件处理；wrapper 模式要链接 `libcuda2musa.so` 而**不是**
`libmusart.so`，报"未定义引用"时得先补 `-lmusart` 再看 `-l` 的先后顺序；mcc 默认按
`--as-needed` 链接、顺序敏感；`--offload-arch` 必须按卡填代号，而 MUSA 3.1.0 的有效代号只有
`mp_10 / mp_21 / mp_22`（不传则默认出 mp_21 + mp_22），官方也没有"卡型号 → 代号"对照表。
最后一条是没法靠读文档解决的，所以 `run_domestic.sh` 里加了一段探测：用与正式构建**完全相同**
的模式与库参数，按 `默认 → mp_21 → mp_22 → …` 逐个编译一个"写 42 再读回来"的极小 kernel
并真的执行一次，自动试出可用的代号。

**诚实状态已更新（2026-09-16）：摩尔线程 MTT S4000 上机实测通过。** 6.6 节列的七处差异里，
构建级那处（运行时命名）与能力级那处（原子操作 / warp 交换）都按预期生效；真正卡住的是
**三处数值语义差异** —— 它们既不在编译层也不在 API 层，而是"同一份 C++ 源码在两个平台上
算出不同的浮点数"。下面这一节是实测记录。

#### 6.7.2 三处数值语义差异（本次实测的核心发现）

**(1) 设备端 fp32 除法不是 IEEE 正确舍入的。** 在 2²² 个随机 fp32 上逐位对拍（设备端结果
与 x86 主机侧的 `/` 比较，主机侧的 `/` 是正确舍入的）：

| 写法 | 与正确舍入不一致 | 最大偏差 |
| --- | --- | --- |
| `a / b` | 22.8% 差 1 ulp、**3.9% 差 ≥2 ulp** | >2 ulp |
| `1.0f / x`（与 `__frcp_rn(x)` 逐位相同） | **12.4% 差 1 ulp** | 1 ulp |
| `__fdiv_rn(a, b)` | **0 / 4194304** ✅ | — |

注意第二行：MUSA 的 `__frcp_rn` 与 `1.0f / x` **逐位相同** —— 连按名取义的"正确舍入倒数"
在这张卡上也是近似的。这处差异最早表现为 NVFP4 反量化在 fp32 输出下 97 / 15291 条断言失败，
且失败全落在输出最低位上（`packed` 与 `scales` 逐位相同，只有反量化结果差 1~2 ulp）：
NVFP4 的全局缩放倒数正好把这份偏差带进结果。修法是在 `common.hpp` 里加一个 `f32_div_rn()`
（设备遍走 `__fdiv_rn`、主机遍走 `/`），把两级缩放链路上的 6 处除法全部换过去。

**(2) 乘法会被收缩进后面的加法，把补偿求和的修正项重复计入一次。** `AccumFast` 用
`p1 = dh*dh`、`p1e = fmaf(dh, dh, -p1)` 做"精确拆平方"，再把 `p1` 交给 TwoSum 累加、把
`p1e` 补进低分量。但如果编译器把 `hi + p1` 收缩成 `fma(dh, dh, hi)`，TwoSum 的残差里
**自动**就带上了 `p1e`，下面再显式补一次就是重复计入。实测：

| 编译器 | `(hi + dh*dh)` 与 `fma(dh, dh, hi)` 逐位相同的比例 |
| --- | --- |
| mcc（MTT S4000） | **1048576 / 1048576**（全部收缩） |
| nvcc（RTX 5060 Ti） | 4222 / 1048576（不收缩） |

后果是误差**恰好等于 Σp1e**：实测 `Σp1e / Σp1 = -1.96e-11`、`Σp2e / Σp2 = -2.985e-10`，
与同一份代码在这张卡上量到的相对误差 `1.96e-11` / `2.99e-10` 完全吻合，而在英伟达上是
`1e-14` —— 直接顶掉 `pipeline/error-stats-accum` 那条 1e-13 的判据。修法是用 `mul_rn()`
（`__fmul_rn`）写这两处平方。`mul_rn` 本来就是为同类问题引入的（4.7 节第 10 条），这次只是
把它从"喂给汇点的乘积"推广到"累加器内部的平方"。

**(3) FTZ / 次正规：乘加把次正规结果刷成 0，且关不掉。** 两处受影响：

* `float → bf16` 的位模式编解码不能走 `__bfloat162float` —— 它会把 bf16 次正规输入刷成 0、
  并把 NaN 规范化成 `0x7FC00000`。改成纯移位的位模式解码后，`test_formats` 里 65536 个
  bf16 编码的往返对拍从 2046 处不符降到 0。
* `1.0f / e8m0_to_f32(sc)`：`sc == 0` 时 `e8m0_to_f32(0) = 2^-127` 恰好是次正规数，设备端
  除法把它当 0，`1/2^-127` 算出 `+Inf`，紧接着 `0.0f * Inf = NaN`，全零块被量化成 NaN 编码
  而不是 0。改成按 2 的整数次幂直接构造倒数（`e8m0_rcp`）后根治，顺带把内层循环里的除法
  换成了几条整数指令。

> 这一节的排查过程留了完整的探针档案：`data/domestic_probes/`。每个探针查的是什么、结论是什么，
> 都写在该目录的 `README.md` 里；探针只依赖 `musa_runtime.h`，把 `musa` 换成 `cuda` 就能在英伟达上
> 复跑同一组对拍。`p3`~`p9` 是差异 (2) 的逐步定位过程 —— 从"AccumFast 与 fp64 对不上"一路收到
> "`hi + dh*dh` 被收缩成 `fma`"这一行为止。

| normal | abs_max | 7.973e-3 | -12.14% | +0.64% | **-34.34%** |

| outlier | abs_max | 2.509e-2 | -9.58% | -0.14% | **-0.41%** |
| outlier | mae | 2.463e-2 | -11.23% | **-5.14%** | -0.41% |
| outlier | mse | 2.439e-2 | **-12.10%** | -4.11% | -0.41% |

**观察 1 —— 收益是稳定的，但规则与指标的对应关系必须讲清楚。** 三条动态规则在三种分布上
都把 MSE 拉低了 9.6% ~ 26.5%，而且**各自都改善了自己优化的那个指标**：`mse` 规则给最好的 MSE，
`mae` 规则给最好的 MAE，`abs_max` 规则给最好的 max abs err（normal 分布上 -34.34%）。
这不是"调参调出来的"，而是判据的直接后果：规则在块级别最小化什么，全局就改善什么。

**观察 2 —— 静态取 4 候选是错的，但错得很有意思。** `static_4` 在 random 上居然把 MSE 改善了
19.45%，在 normal / outlier 上却分别恶化 5.69% / 3.13%（同时 max abs err 仍改善 22.07%）。
原因与 2.3.1 的动机一致：均匀分布的块内元素稠密且接近 amax，压到 4.0 让格点间距变小、反而更准；
高斯分布的最大值本身是离群点，把它压到 4.0 等于牺牲了主体的分辨率。**这正是"必须按块自适应
二选一"而不是"全局选一个阈值"的实证依据。**

**观察 3 —— 代价不是"多读一遍"，也不是除法，而是"每元素要算两个候选"。** 动态规则必须把
两个候选都量化-反量化一次才能比较，所以每个元素的算术量天然是标准 NVFP4 的两倍。同一次 A/B
（同会话、同张量）里：2048² 上 0.1054 → **0.1127 ms（+6.9%）**，8192² 上 1.450 → **1.774 ms
（+22.3%）**——规模越大差距越大，因为标准 NVFP4 在 8192² 上已经贴着带宽上限（量化 396 GB/s），
而 4/6 是 ALU 侧受限（324 GB/s）。

原先多出来的那一遍输入已经并进量化 kernel（3.3、8.6），`quantize_input_passes` 与标准 NVFP4
一样是 2。8.6 里的单点探针进一步把 4/6 量化 kernel 的开销拆开：每元素两次"正确舍入的 fp32
除法"只占 **10%**，"每元素要算两个候选"占 19%（算法本身要求，去不掉），而原来的"块内 shuffle
归约"占 18% —— 最后这一项已经通过把线程映射改成"一个线程一个块"消掉，8192² 的量化 kernel
从 1.371 ms 降到 **1.054 ms**（−23%）。

**观察 4 —— 正确性口径没有放松。** 四条规则的 GPU 结果与独立 CPU 参考实现在三种分布上
**逐位一致**（`packed_bits_identical = yes`、`scales_identical = yes`、
`dequant_bit_mismatch_count = 0`），说明"两个候选都真算了一遍"而不是近似/启发式；
`tests/test_pipeline.cu` 的 `pipeline/scale-rule-4-6` 用例进一步把五条规则的码字与块缩放因子
与参考实现逐条对拍。

## 8. 未来可继续提升的地方

### 8.1 把随机舍入也做成"专用编码器"

优化 20 换掉了随机数生成器，但随机舍入仍然走 `f32_bits_to_fmt_mag` 的通用路径：它要维护
24 bit 有效数字，并按 `drop` 做变长移位与掩码（`drop` 可达 63，被迫用 64 bit 运算）。两条
可行的收尾：

* **32 bit 化**：`rem = sig & ((1<<drop)-1)` 恒小于 2²⁴（`sig` 只有 24 bit），所以当
  `drop ≥ 24` 时 `q0 = 0` 且 `rem = sig`；只有 `drop < 24` 的正常值才需要变长掩码。
  把两支都写成 32 bit 即可去掉全部 64 bit 指令。**注意**：`drop > 24` 时不能简单把掩码截断
  到 24 位——`r` 的高位仍参与 `r < rem` 的比较，必须保留原语义（一个精确的写法是
  `(rnd & ((1<<drop)-1)) < rem` 与 `((uint32)rnd < rem && (rnd >> 24) & ((1<<(drop-24))-1) == 0)`
  等价）。
* **E2M1 专用随机编码器**：仿照优化 17 的 `e2m1_mag_rne`，把"加均匀随机数再截断"直接做在
  fp32 位模式上（`b = a + (rnd & 0x3FFFFF)` 后套用同一条码字公式），可把 NVFP4 的随机舍入
  拉回接近 RNE 的速度。`|x| < 1` 的区间要单独处理（目标格点只有 {0, 0.5, 1}）。实现后必须
  像 `tools/verify_e2m1_rne.cu` 那样对 2³² 个位模式穷举对拍——随机舍入只有"±1 ulp"与"无偏"两条判据，
  普通测试**抓不住**编码器里的细微错误。

### 8.2 NVFP4 的"少搬一遍"

NVFP4 的两遍是格式定义决定的（`global_scale` 依赖全张量 amax）。优化 18 已经用实测证明
"把块 amax 融进量化 kernel"是亏的：每 lane 都要冗余做一遍归约，反而不如"每线程处理整块、
摊销 log₂(block) 倍"的独立小 kernel（见 4.10）。剩下真正能减少字节的方向是把第一遍写出的
16.7 MB 块 amax **压窄**（例如存成 e4m3）；但 `global_scale` 在第一遍结束时才知道，这条
路会改变数值结果。**结论：在保持逐位一致与规范公式的前提下，NVFP4 的量化流量已经到顶。**

### 8.3 反量化的缩放因子访存

反量化每 16/32 个元素读 1 字节 scale，属于分散字节读。理论上可以先把 scale 展开成 `half`
数组（一次额外写 2 字节/元素），或让一个 warp 共享一次 scale 读取（`__shfl_sync` 广播）。
**实测结论：不值得做。** 用 2 Byte 读 + 8 Byte 写的微基准测过展开方案，8 元素/线程只有
349.8 GB/s，与现状 349.1 GB/s 没有差别；而反量化现在 375 GB/s，已经接近读写混合的
实际上限（见 6.3）。

### 8.4 误差统计的进一步降本

统计现在融进了量化 kernel 的收尾，其 ALU 成本已经摊薄在访存里（6.3 显示量化 kernel 已经贴着
同读写比例下的实测上限）。若将来输入换成 fp16/bf16（读流量减半、kernel 转为算力受限），统计的
fp32 累加会重新变成瓶颈，届时的手段是**整数定点累加**或 **float + Neumaier 补偿求和**——
`AccumFast` / `AccumPrecise` 两套累加器正是为这条演进预留的接口
（`pipeline/error-stats-accum` 验证两套结果相差 1e-15 量级）。

### 8.6 已落地：把 4/6 的选择并进量化 kernel，线程映射改成一个线程一个块

6.8 已经把代价量化过：动态规则比标准 NVFP4 重 7%~22%。这一节做两件事——消掉多出来的那一遍
输入，以及把"选哪个候选"从跨 lane 归约改成线程内串行。两件都做完了。

**先纠正本节早期版本里的两个判断错误。**

第一，"可以把比较并进块 amax 归约那一遍"**走不通**：块缩放因子 `bs6 / bs4` 要先知道
`global_scale`，而 `global_scale` 依赖**全张量** amax，只有等 amax 那一遍全部跑完才定得下来，
所以两个候选的 E4M3 码字在 amax 那一遍里根本算不出来。

第二，"瓶颈是每元素两次正确舍入的除法"**不成立**。把 4/6 kernel 里的两处 `f32_div_rn` 临时
换成乘法（只测时间，结果故意算错），8192² 上只快了 0.140 ms。同一组单点探针把开销拆开了：

| 探针（只改一处，结果故意算错，只看时间） | 8192² 量化 kernel | 差额 |
| --- | --- | --- |
| 改造前（shuffle 归约版） | 1.371 ms | — |
| 两处 `f32_div_rn` 换成乘法 | 1.229 ms | 10.2% |
| 去掉块内 shuffle 收集 | 1.122 ms | 18.1% |
| 不算第二个候选 | 1.114 ms | 18.7% |

除法只占 10%；"块内归约"与"每元素要算两个候选"各占约 19%。后一条是算法本身要求的（要比较
就得两个都算），前一条是线程映射带来的——也正是这次真正改掉的那个。

**改法：一个线程负责一整个缩放块。** 原来的映射是"每线程 4 个连续元素"，一个块落在
`block_size/4` 个相邻 lane 上，于是块内误差要靠 `4 × L × 2` 条 shuffle 收给组长（block 16 是
32 条），而且只有组长在累加、组内其余 lane 空转。改成"每线程一个块"之后：

* 块内元素本来就在同一个线程的寄存器里，**shuffle 收集整段消失**；
* 每个 lane 都在算自己那个块的判定，没有空转的 lane；
* 输出侧顺带改善：一个块的 4 bit 数据由本线程一次写成 `uint32`（block 16 是 4 字节），不再
  是每线程 2 字节的碎写。

这与 8.2 里优化 18 的结论是同一个道理：归约型的融合会让每个 lane 都做一遍冗余归约，而
"每线程处理一整块"能把那份工作完全摊销掉。区别在于 4/6 的两个候选码字**不需要任何归约**——
它们只依赖上一遍已经定稿的块 amax 与全张量缩放，所以这次不但没有冗余，还省掉了整整一遍输入。

**逐位一致靠的还是累加次序。** 参考实现与独立选择 kernel 都是"块内元素按下标顺序逐个累加"，
而浮点加法与 fma 都不满足结合律，树形归约会选错候选。融合版里的累加次序就是块内下标的自然
顺序（一个线程顺序处理自己那 block_size 个元素），因此不需要任何还原次序的技巧。块内元素数
决定线程的循环长度，必须是编译期常量（否则块内元素会掉进 local memory），所以 `LOG_BLOCK`
是模板参数，按 `block_size = 4 / 8 / 16 / 32` 特化出四个实例；块大小不满足"是 2 的幂、块完整、
`num_blocks > 1`"时回落三遍路径（`can_fuse_nvfp4_46` 判定）。

**实测**（RTX 5060 Ti，min of 4，repeat 20 / warmup 5，4/6 的 `mse` 规则；"三遍"那一列是把
`can_fuse_nvfp4_46()` 强制返回 `false` 后重新编译的对照构建）：

| 规模 | 三遍（独立选择 kernel） | 两遍（并进量化） | 差 |
| --- | --- | --- | --- |
| 256² | **0.02317 ms** | 0.02803 ms | +21.0% |
| 512² | 0.03347 ms | **0.02906 ms** | -13.2% |
| 1024² | 0.06976 ms | **0.04810 ms** | -31.1% |
| 2048² | 0.14979 ms | **0.11677 ms** | -22.0% |
| 4096² | 0.56387 ms | **0.48374 ms** | -14.2% |
| 8192² | 2.09514 ms | **1.78314 ms** | -14.9% |

8192² 是最能说明问题的一档（256 MB 输入，远超这张卡 32 MB 的 L2）：省下的那一遍是实打实的
DRAM 流量，量化 kernel 1.371 → **1.054 ms**（−23%），整段量化 2.109 → **1.774 ms**，输入遍数
3 → 2。6 个规模里 5 个更快；唯一变慢的 256² 是因为那里一共只有 4096 个块（= 4096 个线程），
"一个线程一个块"填不满 36 个 SM，差值在 5 µs 量级（0.0232 vs 0.0280 ms，两者都不到 30 µs，
本身就被启动延迟主导）。换句话说：**这条路径是给大张量准备的**——只要 `numel / block_size`
远大于 SM 数 × 每 SM 驻留线程数，新映射就稳赢。

**剩下的余量在哪。** 并进量化后 8192² 的 `dram_bandwidth_quantize_GBps` 是 324 GB/s，而同样
两遍的标准 NVFP4 是 396 GB/s——4/6 依然不是访存受限，余量在"每元素两个候选"的 ALU 与打包上。
按上面的探针，这一项占 19%，且是算法本身要求的；再往下压只能改写第二个候选的算法（例如证明
某个候选的码字能由另一个精确导出），本次没有做。另外 ptxas 显示默认配置（block 16 + RNE）
零 spill、64 个寄存器，而 block 32 或随机舍入的实例化会有少量寄存器溢出（最多约 1 KB/线程）；
把 launch bounds 从 4 blocks/SM 放宽到 3 可以换回来，代价是占用率，本次没有做。

### 8.7 关于"优化上限"的结论

把 22 项优化的逐次快照（4.9）与 6.3 的两张表放在一起看：本实现已经处在「访存受限、且贴着
这张卡实测可达带宽」的位置。6.3 的第二张表把「可达带宽」从纸面峰值换成了**逐阶段、同读写比例
的对照 kernel 实测值**，两条链路六个阶段的达成率落在 96%~105% 之间——也就是说，除非减少搬运
的字节数，否则这些 kernel 已经没有可挖的空间。

剩下的空间只有三类——**(a) 少搬字节**（需要改变数值语义，8.2）、**(b) 让随机舍入拿到与 RNE
同级的编码器**（8.1，预计还能再拿 5%~10% 的随机舍入配置）、**(c) 换更快的硬件**。6.8 的 4/6
动态规则是唯一一处"主动多搬一遍字节换精度"的地方：它不属于上面三类，而是显式的精度-带宽
折中，多出来的那一遍输入已经在 8.6 里收回去了（并且顺带把量化 kernel 加快了 23%）。此外优化 21 说明了一件事：当 kernel 已经贴着
带宽上限时，**继续榨 GPU 的收益远小于修掉宿主侧的浪费**——
那一项没有改一行 kernel 代码，端到端仍快了约 13%。
