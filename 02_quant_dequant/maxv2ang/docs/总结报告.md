# 选题二总结报告：MXFP8 / NVFP4 低精度格式的软件模拟与反量化

> 2026 夏季 InfiniCamp CUDA 方向训练营 · 选题二
> 交付代码：`include/` + `src/`（库：格式逻辑、GPU 内核与驱动）、`test/`（测试程序）、`Makefile`、`config_*.txt`

---

## 1. 问题描述

大模型推理的瓶颈正在从算力转向内存带宽与容量：FP16 权重让十亿级模型难以部署，业界因此
转向 FP8 / FP4 低比特格式。题目设定的现实约束是：**测试环境拿不到 Hopper、Blackwell
或更新架构的 GPU，手上只有支持常规 CUDA kernel 的卡**。

因此本项目要解决的问题是：在不依赖任何 FP8/FP4 硬件指令的前提下，用软件模拟的方式在
通用 GPU 上还原两种主流低精度格式的完整语义。具体要求拆解为五步：

1. 读取 FP32 / FP16 输入矩阵（行主序张量文件）；
2. 按配置量化为 **MXFP8**（OCP MX 标准）或 **NVFP4**（NVIDIA Blackwell 权重格式），
   并按真实位宽打包（4bit 元素每字节存 2 个）；
3. 保存低精度数据 + 缩放因子；
4. 用 CUDA kernel 反量化为 FP16 / BF16 / FP32；
5. 输出误差统计（最大绝对误差 / MAE / MSE / 压缩率）与性能日志（量化与反量化 kernel
   时间、有效内存带宽 GB/s）。

在此之上还要求支持 `per-tensor` 与 `block-wise` 两种缩放、`nearest`（RNE）与
`stochastic` 两种舍入，并对**随机 / 正态 / 含异常值三种分布矩阵分别输出误差统计**。

## 2. 低精度格式细节

### 2.1 元素格式

| 格式 | 结构（S+E+M） | bias | 最大可表示值 | 特殊值 | 在本项目中的用途 |
|---|---|---|---|---|---|
| E4M3（OCP 变体） | 1+4+3 | 7 | 448 | **仅 NaN**（0x7F / 0xFF），无 Inf | MXFP8 的默认元素格式；同时作 NVFP4 的块缩放载体 |
| E5M2（IEEE-like） | 1+5+2 | 15 | 57344 | Inf + NaN | MXFP8 的可选元素格式（`elem_format` 配置项） |
| E2M1 | 1+2+1 | 1 | 6 | **无**（16 个码点全是数值） | NVFP4 的元素格式 |
| E8M0 | 8 位纯指数 | 127 | 2¹²⁸ | 无保留值 | MXFP8 的块缩放因子 |

三个必须记住的细节：

- **E2M1 的全部正值码点为 {0, 0.5, 1, 1.5, 2, 3, 4, 6}**，动态范围只有 12 倍，且
  normal 最小值为 1.0。单靠它自身无法覆盖真实权重的取值分布——这正是所有 NVFP4/FP4
  方案都必须引入缩放因子的根本原因。
- **E4M3 的高值区间**：0x78–0x7E 是普通数（对应 256…448），**只有 0x7F / 0xFF 是 NaN**，
  没有 Inf。把 0x7E 当特殊值处理会白白损失整个高值区间。
- **E8M0 的数值等于 2^(e−127)**，e ∈ [0, 255] 全区间有效，上界为 2¹²⁸。它只能取 2 的
  幂，这带来一个重要性质：乘一个 E8M0 缩放因子等价于对指数做整数偏移，**乘法开销为零**，
  代价是缩放因子的粒度很粗（见 §2.2）。

### 2.2 MXFP8：OCP MX 标准的块缩放 FP8

缩放策略：每 **32 个连续元素**为一组（与 OCP MX v1.0 规范一致），整组共享**一个**
E8M0 缩放因子。即 block-wise scaling，块大小固定为 32。

```
量化：  m     = max|xᵢ|                        （块内 32 个元素的最大绝对值）
        scale = 2^⌈log2(m / 448)⌉              （保证 m/scale ≤ 448 的最小 2 的幂）
        eᵢ    = clamp( round(xᵢ / scale), E4M3 可表示范围 )

反量化：x̂ᵢ = eᵢ × scale
```

**关键取舍**：因为 scale 被 E8M0 约束为 2 的幂，指数必须**向上取整**（`⌈·⌉`），
这比"浮点 scale 取精确比值"略有保守、误差略大——换来的是缩放因子本身零乘法开销、
且编解码只需位移。这是 OCP MX 标准的刻意设计，不是实现上的偷懒。

### 2.3 NVFP4：两层缩放的 4bit 格式

NVFP4 是 NVIDIA 为 Blackwell 定义的权重格式，其缩放机制与 OCP 的 MXFP4 **完全不同**：
它用 **E2M1 元素 + 每 16 元素一个 E4M3 块缩放 + 每张量一个 FP32 全局缩放**。

```
量化：  s_global = amax / (448 × 6)                             （amax 为全张量最大绝对值）
        s_block  = E4M3_encode( ⌈amax_block / (s_global × 6)⌉ ) （块内 amax，向上取整到 E4M3 码点）
        qᵢ       = clamp( round(wᵢ / (s_global × s_block)), −6, +6 )

反量化：ŵᵢ = qᵢ × s_block × s_global                            （乘法顺序固定，见 §4.2 问题 2）
```

**两层设计的动机**：E2M1 的动态范围只有 12 倍（0.5 → 6），单层缩放无法同时照顾
"块内的局部数值差异"和"整个张量的取值范围"。E4M3 块缩放负责捕捉局部差异，FP32 全局
缩放负责把整体范围对齐、并保证 s_block 落在 E4M3 的可表示范围内（故分母取 448×6）。
`448×6` 这个常数的含义是"块缩放上限 × 元素上限"：

- 元素最大 6，除以 s_global 后要能被 E4M3 表示，故 s_block 的上限对应 amax_block/(s_global×6)；
- 取 s_global = amax/(448×6) 可保证当某块 amax_block = amax 时，该比值恰为 448，
  即 E4M3 的最大可表示值——既不浪费码点也不会溢出。

### 2.4 缩放策略总览与对比

| 格式 | 缩放层次 | 缩放因子格式 | 块大小 | 每元素缩放开销 |
|---|---|---|---|---|
| MXFP8 | 单层块缩放 | E8M0（8 bit，2 的幂） | 32 | 8/32 = 0.25 bit |
| NVFP4 | 两层：块 + 全局 | E4M3（8 bit）+ FP32（32 bit，整张量一个） | 16 | 8/16 + 32/N ≈ 0.5 bit |

`per-tensor` 模式是二者的退化情形（MXFP8 用单个 E8M0、NVFP4 只用 s_global），
代码中由 `scale_mode` 配置项切换，用于做 §5.1 的对照实验。

### 2.5 打包布局（题目硬性要求）

- **4bit 元素逐对打包**：`字节 = [元素₀ 占低 4 bit | 元素₁ 占高 4 bit]`。
  题目明确禁止"一个字节存一个 4bit 元素"的浪费写法，本实现严格遵守。
- **NVFP4**：每 16 个元素 → 8 字节 packed 元素数据 + 1 字节 E4M3 块缩放；
  每张量末尾再附 4 字节 FP32 全局缩放。
- **MXFP8**：每 32 个元素 → 32 字节元素数据 + 1 字节 E8M0 块缩放。

### 2.6 反量化公式汇总

| 格式 | 反量化公式 | 查表还是计算 |
|---|---|---|
| MXFP8（E4M3 元素） | `x̂ᵢ = e4m3_table[eᵢ] × 2^(scaleᵢ−127)` | 元素查 256 项表；缩放是位移 |
| MXFP8（E5M2 元素） | `x̂ᵢ = e5m2_table[eᵢ] × 2^(scaleᵢ−127)` | 同上 |
| NVFP4 | `ŵᵢ = e2m1_table[qᵢ] × s_block(块) × s_global` | 元素查 16 项表；两次乘法 |

解码表放在 `__constant__` 内存中（`include/quant_tables.h`），由生成脚本从同一份格式
定义自动产出，**保证表与格式语义同源、不会被手改漂移**。

### 2.7 文件格式

- **张量文件（输入与反量化输出同格式）**：header = rows / cols（各 int64 小端）
  + dtype（固定 4 字节 char，取值 `fp32` / `fp16` / `bf16`），其后为行主序、小端的数据区；
- **量化参数文件**：`KEY = VALUE` 文本，包含题目要求的 6 个键，另可选支持
  `elem_format`（`e4m3`/`e5m2`）与 `seed`（stochastic 舍入的随机种子）；
- **低精度权重文件（LPW1）**：header + packed data + scale 数组 + 全局 scale；
- **metrics.json / metrics.log**：最大绝对误差 / MAE / MSE / 压缩率 / 量化与反量化
  kernel 时间 / 有效带宽 GB/s / 自检结果。

## 3. 实现思路

### 3.1 总体架构：单一 CUDA 程序，主机端与设备端共用一份格式逻辑

```
include/quant_format.h   格式语义（编解码 / 缩放指数 / 舍入 / FP16·BF16 转换）
        │  全部 __host__ __device__，header-only —— 设备编译唯一需要看到的头文件
        ├──► 设备端：被 src/quant_gpu.cu 的 7 个 kernel 调用
        └──► 主机端：被 src/quant_io.cu 的主机参考实现调用（= 逐字节对拍的基准）
                 两者共用同一份舍入语义，因此可以逐字节比对

include/quant_tables.h   常量表（主机副本 + __constant__ 设备副本）
include/quant_io.h       ──► src/quant_io.cu    主机侧：配置 / 文件 I/O / 主机参考 / 指标
include/quant_gpu.h      ──► src/quant_gpu.cu   设备侧：7 个 kernel + 驱动 + run_one

库（include/ + src/）不含 main、不含命令行、不产出可执行文件；
test/test_all.cpp 是唯一编译成可执行文件的地方。
```

**设计动机**：低精度格式的实现极易出现隐蔽错位——次正规数、舍入边界、指数偏移、
4bit 打包的高低半字节顺序，任何一处写错都会表现为"结果看起来差不多，但就是不对"。
把格式语义收敛到**一份** host/device 共享的头文件里，从结构上就消除了"两处逻辑各自
漂移"的可能；而同一份代码编译出的主机版本，恰好又充当设备端输出的对拍基准——
**正确性标准因此从"抽查若干样例"升级为"字节级等价"**。

### 3.2 CUDA kernel 设计（共 7 个）

| Kernel | 设计要点 |
|---|---|
| `k_amax` | 全局最大绝对值归约：对非负 double 的**位模式**做 `atomicMax(unsigned long long)`（利用 IEEE754 正数位模式保序的性质，绕开原子操作不支持浮点的问题） |
| `k_mxfp8_quant_block` | 每 warp 负责一个 32 元素块：`__shfl_xor_sync` 归约出块内 amax → 算 E8M0 → 逐元素编码 |
| `k_mxfp8_quant_tensor` | per-tensor 模式：单个 E8M0 缩放，逐元素编码 |
| `k_nvfp4_quant_block` | 每 half-warp 负责一个 16 元素块：两层缩放 + shuffle 完成 4bit 配对打包 |
| `k_nvfp4_quant_tensor` | per-tensor 模式：单个全局缩放，每线程 2 元素打包成 1 字节 |
| `k_mxfp8_dequant` | 逐元素：查 E4M3/E5M2 表 × E8M0 指数偏移 → 转为输出类型 |
| `k_nvfp4_dequant` | 逐元素：解包 4bit → 查 E2M1 表 × s_block × s_global |

**通用手段**：grid-stride 循环（支持任意规模矩阵）、256 线程/块（块数封顶 SM 数 × 16，
由 grid-stride 兜底）、缩放因子与解码表走 `__constant__` 与 `__ldg`、cudaEvent 计时并
支持 `--repeat N` 取 N 次最小值以消除调度抖动。

**四步循环，把"两遍法"合并进一个 kernel**：块的 amax 需要先归约、再量化，朴素做法要
扫两遍内存。本实现把 32 个元素正好放进一个 warp 的寄存器（16 元素放进一个 half-warp），
用 shuffle 归约出块内 amax，归约后所有 lane 都持有相同的 amax，于是**第二遍不再读内存，
直接在自己寄存器里完成编码与打包**。

**对拍校验默认开启**（`run_one` 的 `verify=true`）：每次运行都把 GPU 量化/反量化的输出字节与主机端基准逐字节
对比，不一致时以非零退出码失败。这条约定是后续所有性能优化的安全网——每改一版 kernel
必须先过它（闭环流程见 §7 开头）。

### 3.3 架构合规

题目要求不依赖新硬件特性。本实现只使用 **sm_35 即已存在**的原语：

- grid-stride 循环、`__shfl_xor_sync` warp 内 shuffle、`atomicMax(unsigned long long)`、
  `__constant__` 查表、cudaEvent 计时；
- **无** cp.async / async barrier（Ampere+）、**无** FP8/FP4 Tensor Core、
  **无** bf16 硬件转换路径（bf16 的转换由位运算软件实现）；
- 默认编译目标 `-arch=sm_75`（T4），`ARCH=` 变量可切 sm_80 / sm_86 / sm_89。

**关于使用 `double` 的说明**：格式逻辑中的 `frexp` 与若干中间量用 `double`，
为的是让主机端与设备端在同一套舍入规则下完全一致（见 §4.2 问题 1）。这类 kernel 的
算术强度极低（每元素只有查表与几次乘法），`double` 运算不构成瓶颈。

*实测佐证*：§5.3 实测的有效带宽（128–140 GB/s）远低于 RTX 5090 的理论峰值
（1792 GB/s），说明 kernel 远未跑到算力或带宽的极限；在这种利用率下 `double` 的
额外乘法更不可能是瓶颈。**但这一条仍未经 profiler 证实**，属于从带宽数字反推的结论。

### 3.4 三个关键设计决定

**（1）编解码用"查表 + 二分"，而不是"位运算"。**

格式的舍入逻辑实现为：在"正数幅值表"上做二分查找 + 平局取偶码点（码点低 3 位即尾数，
码点偶等价于尾数偶，正好就是 RNE 的语义）。这条路径**不含位运算特有的边界分支**，
主机端与设备端共用同一份表与同一段查找代码，因此按构造逐位一致。代价是查表比纯位运算
略慢，但本项目是访存受限型，这个代价可以接受。解码/编码表由脚本自动生成，
从机制上杜绝手改漂移。

**（2）对拍的粒度分级：文件字节全等，统计量给极小容差。**

量化权重与反量化输出的字节要求**完全相等**——格式语义是确定性的，没有任何理由放宽；
而 `metrics.json` 里的误差指标（MAE / MSE / RMSE）因浮点求和累加顺序不同，允许
**1e-12 的相对误差**。这个分级是有意设计的：**能被固定的东西必须字节级钉死；天然带
浮点求和不确定性的统计量，则给一个远小于任何真实错误的容差**。用一个宽松的误差阈值去
卡"对不对"，正是本报告反复强调要避免的做法。

**（3）零第三方依赖。**

CUDA 版只依赖 CUDA Toolkit ≥ 11（需要 C++17），自测用自研的极简断言，不引入任何测试
框架。这样交付物是自包含的：在只有 nvcc 的服务器上 `make` 即可构建与自测，
不需要先搭一套测试环境。

### 4.2 开发中发现并解决的问题

**问题 1：E8M0 指数用 `log2` 算，在幂次边界上差 1。**

- *现象*：MXFP8 的块缩放在少数块上差一个 2 的幂，导致该块全部元素的误差翻倍。
- *根因*：`log2` 是**近似**实现，在 2 的幂附近（如恰好等于 1.0、2.0）会因舍入误差返回
  0.9999… 或 1.0000…1，向上取整后就会差 1。
- *解决*：改用 `frexp`。`frexp(x, &e)` 是精确的位运算，直接给出 `x = m × 2^e` 的指数
  `e`（对一切正数成立 `floor(log2 x) = e_frexp − 1`），不存在近似误差。
- *教训*：在"逐字节一致"这个标准下，**任何数学库近似函数都是嫌疑对象**。

**问题 2：反量化的乘法顺序不固定，产生 1 ULP 的差异。**

- *现象*：NVFP4 反量化结果"几乎一样"，但在最后 1 个 ULP 上与基准不同，字节对拍失败。
- *根因*：浮点乘法**不满足结合律**。`(q × s_block) × s_global` 与
  `q × (s_block × s_global)` 在实数意义上等价，在浮点下不一定等价。
- *解决*：把顺序**写死为 `(v × s_b) × gs`**（先块缩放、后全局缩放），设备端与主机端
  两处保持同一顺序。这是 NVFP4 一层里最容易忽略的一致性要求。
- *教训*：跨实现比对时，**表达式的结合顺序与表达式本身同等重要**。

**问题 3：`__shfl_xor_sync` 不支持 `uint8_t`。**

- *现象*：NVFP4 块量化里想用 shuffle 直接搬运打包好的 4bit 字节，编译不过。
- *根因*：CUDA 的 warp shuffle 内建函数只支持 32 位（及 64 位）整型与浮点类型，
  没有 8 位重载。
- *解决*：打包后的字节经 `uint32_t` 中转再 shuffle，落盘前截回 8 位。
- *教训*：CUDA 内建函数的类型覆盖面比想象中窄；遇到"看起来显而易见"的写法编译不过，
  先怀疑是不是类型重载不存在。

**问题 4：`__constant__` 解码表用 `NAN` / `INFINITY` 字面量初始化。**

- *现象*：解码表（E4M3/E5M2 的 256 项）里有几个特殊值码点用 `NAN` / `INFINITY` 填充，
  而 `__constant__` 的静态初始化对常量表达式的要求较严，个别 nvcc 版本可能拒收。
- *现状*：保留原写法作为待验证项，并预置了降级预案——若真机上被拒，把对应项改成 `0.0`
  即可，**不影响正确性**：E4M3 的 NaN 码点（0x7F / 0xFF）只会出现在输入本来就含 NaN
  的情形，正常权重路径永远解码不到它们；唯一受影响的是自测里那两条特殊值断言。
- *教训*：对"不确定能否编译过"的点，先准备好**可一行修好的降级预案**，
  而不是等上机时手忙脚乱。

**问题 5：聚合初始化触发 `missing-field-initializers` warning。**

- *现象*：用 `-Wall -Wextra` 编译时报出 3 处结构体初始化字段缺失。
- *解决*：补齐字段初始化，全项目清零 warning（题目对"代码整理"有明确要求）。
- *教训*：warning 清零要**在整理阶段集中做并复跑验证**——改初始化与格式化都可能顺手
  引入语义变化，改完必须重跑自测确认。

**问题 6：`stochastic` 舍入如何做到可复现、可对拍。**

- *问题*：`stochastic` 舍入天生使用随机数。若用无状态下发的随机数发生器，同一份输入
  两次运行结果不同，GPU 与主机端也无法比对，这条路径就完全无法回归测试。
- *解决*：设计**逐元素确定性 RNG**——`splitmix64(seed, idx)`，把元素的全局下标也参与
  散列。于是固定 `seed` 下每个元素都得到确定的随机数，设备端与主机端可以逐字节对拍，
  同时随机舍入本身的无偏统计性质不受影响。
- *价值*：这一设计让"随机舍入"这条**最难验证的路径变得可回归测试**。

**问题 7：量化时误用"编码前的浮点缩放因子"。**

- *现象*：量化时若拿计算出来的**浮点**缩放因子去除元素，而落盘存的是它**编码之后**的
  值，两边就不一致——反量化回来乘的是编码后的缩放因子，于是"存盘的权重数据"与
  "报告里统计的误差"对不上。
- *根因*：**缩放因子自己也是被量化的对象**。E8M0 只能取 2 的幂、E4M3 只有有限码点，
  编码必然引入误差；必须先量化缩放因子，再用**量化后的**缩放因子去量化数据。
- *解决*：统一用 `decode(encode(scale))` 的结果参与后续量化，设备端与主机端一致。
- *教训*：这是低精度实现里最容易漏掉的一步——**缩放因子的量化误差会被乘以每一个元素**。

**问题 8：amax = 0 的块（含全零矩阵）除零产生 NaN。**

- *现象*：全零矩阵或全零块使 `amax = 0`，计算缩放因子时出现 0/0；一旦产生 NaN，
  会通过后续运算污染整个张量。
- *解决*：显式特判，分母兜底为 `1.0`，使全零块产出全零结果而非 NaN；同时在读入处对
  NaN / Inf 输入显式报错，**不让非法输入静默传播**。

**问题 9：尾部块越界（元素数不是块大小的整数倍）。**

- *现象*：矩阵不被块大小整除时，最后一个块会读到数组末尾之外。
- *解决*：显式处理尾部块（按剩余元素数归约与编码）；并且**故意用非整块尺寸（257×131）
  的输入跑对拍**——把测试矩阵从"好看的整块尺寸"扩展到不对齐的尺寸，否则这条路径
  永远不会被测到。

**问题 10：计时口径。**

- *现象 a*：kernel 计时忘了同步（`cudaDeviceSynchronize()`），测到的是 kernel
  **launch** 的耗时而不是执行耗时，数字小得离谱还不报错。
- *现象 b*：计时把 H2D 拷贝与首次启动开销算了进去，有效带宽数字很难看。
- *解决*：明确区分两个口径——**仅 kernel 本体**用 `cudaEvent` 前后夹住（先 warmup
  一次再计时，`--repeat N` 取最小值），**端到端**时间另外单独报。§5.3 报的是前者。
- *附带约束*：测量规模不能太小。1024×1024（输入 4 MiB）若再缩小，数据会整体落进 L2，
  测出的"有效带宽"会虚高到**超过 DRAM 理论峰值**——那种数字是自欺欺人。

### 4.3 已有的性能取向的设计决定

| 决定 | 理由 |
|---|---|
| grid-stride 循环 + 256 线程/块 | 支持任意规模矩阵；256 线程在 T4 上占用率与寄存器压力平衡合理（本项目实测显卡为 RTX 5090，同样适用） |
| 解码表与缩放因子走 `__constant__` / `__ldg` | 表被所有线程反复读取，常量内存有广播优化；`__ldg` 走只读数据缓存 |
| warp / half-warp 负责一个块，从寄存器直接打包 | 32 / 16 个元素正好放进一个 warp / half-warp 的寄存器，归约与编码在一次访存内完成（见 §3.2） |
| `--repeat N` 取 N 次**最小值** | 消除调度抖动与冷启动影响，比取平均更接近 kernel 的真实能力 |
| amax 用位模式 `atomicMax` | 原子操作只支持整型；非负浮点数的 IEEE754 位模式与数值大小同序，故可安全按 ULL 比较 |
| bf16 转换用位运算实现 | 无硬件 bf16 路径时的软件模拟，符合"不依赖新架构特性"的约束 |

### 4.4 发现了但尚未实施的优化

开发期通过代码分析定位到 4 项优化机会（输入向量化、反量化每线程 2 元素、
缩放因子预取 shared memory、amax 串行链重叠）。当时判断需要 **ncu 证据**才能确定
优先级。

**上机后的实测数据修正了这个判断**：真正被数据直接指向的是 **amax 串行链**
（因为它把 `quantize_ms` 拉高一倍），而向量化类优化的依据是"实测有效带宽远低于
理论峰值、远未饱和"这一间接推论。

**5 项的完整说明、具体改法、预期收益与未做原因见 §7。**

## 5. 实验结果与分析

**测试条件**：矩阵规模 1024×1024 FP32（N = 1,048,576 个元素），三种分布——
随机 U[0,1)、正态 N(0,1)、含异常值（N(0,1) 基础上 0.5% 的元素 ×100）。
实测环境为 **NVIDIA GeForce RTX 5090（sm_120，170 SM）**。

精度类指标在主机端计算产出。**数值与 GPU 版完全相同**——§5.4 的逐字节对拍证明
设备端产出的量化权重与反量化张量字节级等同于主机端实现，因此误差/压缩率必然一致。
（§5.1 末尾的随机舍入对比、以及 §5.4 的覆盖矩阵是本次上机新增的实测结果。）

### 5.1 误差指标（三种矩阵分开统计）

**MXFP8（E4M3 元素，block = 32，nearest，输出 FP16）**

| 矩阵 | 最大绝对误差 | MAE | RMSE |
|---|---|---|---|
| 随机 U[0,1) | 0.0312 | 0.0104 | 0.0136 |
| 正态 N(0,1) | 0.246 | 0.0180 | 0.0266 |
| 含异常值 | 15.93 | 0.0272 | 0.191 |

**NVFP4（E2M1 元素，block = 16，nearest，输出 FP16）**

| 矩阵 | 最大绝对误差 | MAE | RMSE |
|---|---|---|---|
| 随机 U[0,1) | 0.167 | 0.0469 | 0.0614 |
| 正态 N(0,1) | 0.670 | 0.0762 | 0.100 |
| 含异常值 | 35.95 | 0.141 | 0.484 |

**格式间对比**：同分布下 NVFP4 的误差约为 MXFP8 的 3–5 倍。根因是位宽的本质代价——
E2M1 只有 8 个正数码点，而 E4M3 有 127 个。这个精度代价换来的是约 2 倍的压缩率（§5.2），
是典型的"精度 ↔ 容量"权衡。

**关于 outlier 矩阵的 max_abs 偏大**：这是**预期行为**而非缺陷。异常值幅值在 100 以上
（经 ×100 放大），绝对误差 15.9 相对于 300 的幅值约为 5%，相对误差并不高。真正会被
异常值毒害的是 **per-tensor 缩放**，见下表。

**block-wise vs per-tensor（含异常值矩阵，本项目最关键的对照实验）**

| 格式 | 缩放模式 | MAE | RMSE |
|---|---|---|---|
| NVFP4 | block（每 16 元素） | **0.141** | 0.484 |
| NVFP4 | per-tensor | 0.844 | 1.310 |
| MXFP8 | block（每 32 元素） | 0.0272 | 0.191 |
| MXFP8 | per-tensor | 0.0311 | 0.191 |

**分析**：NVFP4 上 block 缩放把 MAE 降低了约 **6 倍**。机理很清晰：per-tensor 模式下，
一个幅值约 300 的异常值把整张量的全局缩放因子撑大，于是其余 N(0,1) 量级的元素全被
压进 1–2 个码点，量化台阶变得极粗；而 block 缩放下，异常值只影响它所在的那个 16 元素
块，其余块不受牵连。**这正是 NVFP4 采用两层缩放、MX 标准采用块缩放的现实动机**——
LLM 的激活与权重中异常值普遍存在，per-tensor 缩放会被单个 outlier 击穿。

MXFP8 上两种模式的差距要小得多（0.0272 vs 0.0311）。原因有二：E4M3 本身的动态范围
远大于 E2M1，抗 outlier 能力天然更强；且 E8M0 的"2 的幂"约束已经引入了固定量的保守性，
部分掩盖了 block 缩放本应带来的收益。

**随机舍入 vs 就近舍入（实测，256×256，其余配置相同）**

| 格式 / 分布 | RNE MAE | SR MAE | 比值 | RNE RMSE | SR RMSE |
|---|---|---|---|---|---|
| MXFP8 / random | 0.01041 | 0.01390 | 1.33× | 0.01364 | 0.01932 |
| MXFP8 / normal | 0.01794 | 0.02399 | 1.34× | 0.02652 | 0.03759 |
| MXFP8 / outlier | 0.02712 | 0.03592 | 1.32× | 0.19203 | 0.26165 |
| NVFP4 / random | 0.04681 | 0.06310 | 1.35× | 0.06134 | 0.08819 |
| NVFP4 / normal | 0.07579 | 0.10357 | 1.37× | 0.09975 | 0.14990 |
| NVFP4 / outlier | 0.13654 | 0.20227 | 1.48× | 0.45932 | 1.05369 |

**6 组全部一致：随机舍入的 MAE 比就近舍入高 1.32–1.48 倍。** 这不是实现缺陷，
而是随机舍入的固有性质——**它用"单元素精度"换"统计无偏"**：RNE 总是取最近的码点，
单元素误差最小；SR 在相邻两个码点间按距离概率取值，单元素误差的方差更大，但
期望误差为零。SR 的价值在于**累加场景**（大量权重求和时误差不会系统性偏置），
不在于单元素的误差指标。§5.1 的误差表用的是 RNE，也正是因为这个原因——报告误差
指标时应取单元素精度最优的舍入模式。

（这一对比是本次上机才量出来的；此前只验证了 SR 在格式层的无偏性锚点，
没有端到端的误差对照。）

### 5.2 压缩率

| 格式 | 每元素实际位数（含缩放因子摊薄） | 压缩率（相对 FP32 输入） |
|---|---|---|
| MXFP8（block = 32） | 8 + 8/32 = **8.25 bit** | **3.88×** |
| NVFP4（block = 16） | 4 + 8/16 + 32/N ≈ **4.5 bit** | **7.11×** |

> 压缩率的基准是**输入 dtype**：上表为 FP32 输入。若输入本身是 FP16，基准降到 16 bit，
> 压缩率相应减半（MXFP8 1.94×、NVFP4 3.56×）——这是"相对你手上的原始精度压缩了多少"，
> 而不是相对某个固定基准。

**一个容易误解的点**：块缩放开销是**每元素恒定**的，不随 N 摊薄——只有整张量共享的
那 1 个 FP32 全局缩放会随 N → 0。因此 NVFP4 在块大小 16 时，无论 N 多大都是 4.5
bit/元素，**永远达不到理论上的 8×**。

要进一步提高压缩率只能加大块：块 32 → 4.25 bit（7.53×）、块 256 → 4.03 bit（7.94×）。
代价是块内动态范围变大、误差上升。压缩率与精度此消彼长，而代码已支持任意 `block_size`，
跑三组即可画出权衡曲线（见 §7 第 5 项）。

## 6. 明确说明：哪些是软件模拟，哪些依赖特定 GPU

**本实现是纯粹的软件模拟，不依赖任何 FP8/FP4 硬件特性。**

- **全部格式语义均由软件实现**：E4M3 / E5M2 / E2M1 / E8M0 的编码与解码、4bit 配对打包
  与解包、块缩放与全局缩放的计算、反量化——没有一处调用硬件 FP8/FP4 指令。
- **FP4 的实际运算路径**：解包 4bit 索引 → 查常数表得到浮点值 → 反量化到 FP16/BF16/FP32
  → 之后的一切都退化为**普通浮点运算**。也就是说，即使把结果送去参与矩阵乘法，
  走的也是标准的 FP16/BF16/FP32 通路，**不需要 Tensor Core 的 FP4 支持**。
- **所用 CUDA 原语的下限是 sm_35**（Kepler）：grid-stride 循环、warp shuffle、
  `atomicMax(unsigned long long)`、`__constant__` 查表、cudaEvent 计时。
  没有使用任何 Ampere 及以上的特性（cp.async、async barrier 等），
  也没有使用 bf16 的硬件转换路径。默认编译目标是 `-arch=sm_75`（T4）。
- **不需要的特殊硬件**：不需要 Hopper / Blackwell / 更新的架构，不需要 FP8 或 FP4
  Tensor Core，不需要任何新的 ISA 扩展。

## 7. 未来可继续提升的地方

**本节说明的是"已知该做什么、为什么没做、怎么做、预期多少"**——下面 5 项在本次
交付中**均未实施**，逐项写清现状与依据。每项的实施都遵循同一个闭环：
`make test`（正确性，逐字节对拍 + 性能）→ ncu 复测 Memory Throughput。
**正确性挂了就回退，正确性优先于性能。**

**为什么没有实施**（共性原因，逐项另有补充）：

1. **缺少 profiler 证据**。nsys/ncu 数据因容器 profiling 权限未能采集，
   所有瓶颈归因都只能从实测带宽反推，不足以支撑"改哪里、改多少"的判断；
2. **改动有回归风险**。格式语义是逐字节对拍锁死的（§5.4，43+18 组全过），
   任何 kernel 改动都必须重新上机验证；
3. **本次交付的范围**已满足题目全部必做项——优化属于"锦上添花"，且需要额外的
   GPU 机时。

### 7.1 优化项（按优先级排序）

**第 1 项：amax → 全局 scale 串行链重叠**

- *现状*：未实施。这条链在 `src/quant_gpu.cu` 的 `quantize_gpu` 里：
  `run_amax()` 内是 `cudaMemset` → launch `k_amax` → `cudaMemcpy`(D2H, 8 B) → 主机
  读回 amax → 算出 gs（还要一次 H2D 传回）。全程同步等待。
- *具体改法*：① 用 `cudaMemcpyAsync` + pinned memory 让 D2H 与后续准备重叠；
  ② 进阶：把 gs 的计算搬进设备端（第二趟 kernel 以 gs 为参数，或用一个小的
  device-side 归约），彻底去掉 D2H + 同步；③ nsys 时间线上可直接看到这段空隙。
- *预期收益*：**潜在最大**——这条链是纯串行等待（launch → 同步 → 主机往返 → 再
  launch），重叠掉大部分即可见效；改法也最直接。但需先量出它占多少。
- *为何未做*：需要 nsys 时间线定位空隙大小；改动涉及同步语义，必须重跑对拍验证。

**第 2 项：量化 kernel 的输入向量化**　〔访存量最大的一块〕

- *现状*：未实施。四个量化 kernel 目前都是每线程读 1 个 `float`（4 B）。
- *具体改法*：改为 `float4`（128 bit）读 4 个再在寄存器内拆分。**注意难点**：
  block 模式下块边界与 warp lane 是绑定的（MXFP8 一个 warp 管一个 32 元素块，
  NVFP4 一个 half-warp 管一个 16 元素块），改成 float4 后 lane↔元素的映射要重新
  推导，shuffle 归约的粒度跟着变——这不是机械替换。
- *预期收益*：输入读取是量化路径访存的大头（4 MiB / 5.03 MiB），DRAM request 数
  可降至 1/4，指令数同步下降。在有效带宽远低于理论峰值的前提下**确有空间**。
- *为何未做*：映射关系改动有回归风险；缺 profiler 证据确认收益方向。

**第 3 项：反量化 kernel 每线程处理 2 个元素**

- *现状*：未实施。`k_mxfp8_dequant` / `k_nvfp4_dequant` 都是每线程 1 个元素。
- *具体改法*：一个线程解包一个 packed 字节、一次写出两个输出（4bit 对正好在一个
  字节里），配合 `uint2`/`ushort2` 向量化写出。
- *预期收益*：读指令数减半；同时消除"相邻线程读同一 packed 字节"的冗余。
- *为何未做*：同上。

**第 4 项：缩放因子预取进 shared memory**

- *现状*：`__ldg` 已用；shared memory 预取未做。
- *预期收益*：**低**。NVFP4 每 256 个线程才触碰 16 个 scale 字节，命中率本来就高；
  MXFP8 每 32 元素 1 字节同理。属"做也无害、但不解痒"的加分项。
- *为何未做*：性价比最低，排在最后。

**第 5 项：块大小 16/32/64 的误差–压缩率权衡实验**　〔唯一不改代码的一项〕

- *现状*：未做。代码已支持任意 `block_size`（`Config::block_size` 一路传到 kernel）。
- *具体改法*：加两个配置文件，跑 `{16, 32, 64} × {MXFP8, NVFP4}` 共 6 组，
  记录 MAE / 压缩率 / 有效带宽。
- *预期收益*：直接补强 §5.2——目前表中只有"块 16 → 4.5 bit、块 32 → 4.25 bit"
  的**理论**换算，缺实测的误差随块大小上升的曲线。
- *为何未做*：**这是成本最低的一项（不需要改代码）**，仅因需要额外的 GPU 机时
  而未跑。建议作为下一次上机的首选。

## 8. 构建与复现

### 8.1 构建与测试（CUDA ≥ 11，C++17，无第三方依赖）

**一行命令跑完全套**（在有 GPU 的机器上，工程根目录执行）：

```bash
make test          # 自测 → 性能档 → 覆盖档 → 边界尺寸 → nsys/ncu（可用时自动跑）
make test-fast     # 同上但跳过 nsys/ncu，只出正确性与性能数据
```

测试分两档：**性能档**（1024×1024 fp32→fp16，与 CPU 基线同规模，出 §5.3 的表）与
**覆盖档**（256×256，把题目要求的输入 dtype × 输出类型 × 舍入 × 格式 × 分布全遍历，
每组都逐字节对拍）。

`-arch` 由 Makefile 按 GPU 计算能力自动探测，不需要手动指定；需要强制时用
`make test ARCH="-arch=sm_86"`。

**测试逻辑全部由 C++ 实现**（`test/test_all.cpp`，调用 `include/quant_gpu.h` /
`src/quant_gpu.cu` 里那份库实现）；shell（`test/run.sh`）只做一件事——包装
nsys / ncu 这两个 NVIDIA 外部分析工具。说明见 `test/README.md`。

工程分成两层：

- `include/` + `src/` 是**库**：格式逻辑、GPU 内核与驱动。**不含 main、不含命令行、
  不产出可执行文件**；
- `test/test_all.cpp` 是**测试主程序**，本工程唯一编译成可执行文件的地方。

需要单独调参时：

```bash
./test/test_all --outdir my_out --repeat 10   # 直接跑测试程序
bash test/run.sh                              # 只跑 nsys / ncu
```

每个（格式 × 输入）组合在 `test/out/<格式>/<输入名>/` 下产出：`weights.bin`
（低精度权重：packed data + scale 数组 + LPW1 header）、`dequant.bin`（反量化输出，
与输入张量同格式）、`metrics.json` / `metrics.log`（误差、压缩率、kernel 时间、
有效带宽、对拍结果）。

### 8.2 ncu / nsys

被 profile 的对象就是测试程序本身（它跑完整套流程，时间线里包含全部 kernel）：

```bash
nsys profile -o prof --stats=true ./test/test_all --outdir test/out/nsys/run
ncu --set basic -k regex:k_nvfp4_dequant --launch-skip 1 --launch-count 1 \
    --csv ./test/test_all --outdir test/out/ncu/run
```

这两条已由 `test/run.sh` 封装，一般直接 `make test` 即可。

### 8.3 已知注意事项

1. `quant_tables.h` 的 `__constant__` 数组用 `NAN`/`INFINITY` 字面量初始化——若个别
   nvcc 版本不接受，把解码表对应项改为 `0.0` 即可（解码路径永远到不了 NaN 码点，
   只影响自测中的两条特殊值断言）。见 §4.2 问题 4。
2. 首次运行较慢：CUDA context 初始化 + JIT（若已装 sm_75 对应的 cubin 则无 JIT）。
3. `--repeat N` 的计时取 N 次**最小值**；若报告需要用中位数，`metrics.json` 中已保留
   每次计时，改统计字段即可，无需改 kernel。
