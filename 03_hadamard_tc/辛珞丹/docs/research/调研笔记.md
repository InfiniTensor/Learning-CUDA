# Hadamard 变换加速实现 —— 调研笔记

> 选题 3「Hadamard 变换的 CUDA 加速实现与优化」前置调研。
> 文献列表见文末，标题与摘要都是对着 arXiv 原页核对过的。

---

## 1. 为什么要在量化前做 Hadamard 变换

低比特量化的主要敌人是激活/权重中的离群值（outlier）。均匀量化（INT4/FP8）的
量化台阶是等距的，少数幅值极大的通道会撑大整个张量的动态范围，使得其余绝大多数
元素的有效比特数骤减。Hadamard 矩阵 `H`（元素仅取 ±1、正交）对张量做正交旋转
`x → Hx`，把某个维度上的极端能量"摊"到全部维度上，从而压平分布、缩小动态范围。

关键在于这个旋转必须是免费或近乎免费的：

* QuaRot（arXiv 2404.00456）把旋转注入 LLM 的残差流、FFN 激活、注意力机制和 KV
  cache，实现全 4-bit 端到端量化（LLaMa2-70B WikiText-2 困惑度仅 +0.47）。
* SpinQuant（arXiv 2405.16406）指出不同旋转矩阵的量化效果差异可达 13 个 zero-shot
  点，于是把旋转矩阵变成可学习参数；LLaMA-3 8B 上相对 QuaRot 把精度差距缩小 45.1%。
* FlatQuant（arXiv 2410.09426）观察到 Hadamard 变换后分布仍然"陡峭且分散"，改用
  可学习的 Kronecker 仿射变换，并把全部操作融合进单个 kernel，得到 2.3x prefill /
  1.7x decode 加速。

HadaCore（arXiv 2412.08832）对这种"旋转开销"给出了非常具体的量化：以 Llama-2 7B 为例，
如果旋转用 FP16/BF16 的普通 matmul 实现，线性层计算量会膨胀到原 FP16 模型的 110%
（假设 INT8 是 FP16 的一半代价），即旋转把量化省下的收益全部吃掉。这正是必须用
Fast Walsh–Hadamard Transform（FWHT） 而不是稠密矩阵乘的理由。

FWHT 的核心事实：`H_d` 是 Sylvester 递推构造的 2 的幂阶矩阵，
`H_{ab} = H_a ⊗ H_b`（Kronecker 积），因此

* 计算复杂度从 `O(d²)` 降到 `O(d log d)`（每行只需 `(d/2)·log2(d)` 个蝶形加减）；
* 矩阵本身不需要存储在内存里，省掉 matmul 的访存瓶颈。

## 2. 主流实现路线

### 2.1 路线 A：经典寄存器/共享内存 FWHT（非 Tensor Core）

代表实现是 Tri Dao 的 `fast_hadamard_transform`（github.com/Dao-AILab/fast-hadamard-transform，
也是选题要求的正确性参考）。

* 一个 thread block 负责一行；`dim ≤ 256` 时只用一个 warp（`dim/32 ≤ 8` 个元素/线程），
  `dim > 256` 时多个 warp 合作。
* 低位的 butterfly 在寄存器内完成，高位的 butterfly 通过共享内存交换完成
  （warp 内用 `__shfl_xor_sync`，跨 warp 用 smem）。
* 特点：无数据重排以外的额外开销，访存完全合并（每线程连续 8 个 half = 一次 128-bit 访问）。

瓶颈：

1. `dim` 小时一个 warp 只处理一行，block 内线程数过少（例如 `dim = 64` 时每行只要 2 个
   线程），占用率很低。
2. `dim > 256` 之后出现 `__syncthreads()` 和共享内存往返，扩展性变差。
3. 完全用 FP16/BF16 ALU 做，2 元素/指令；在算力富裕、带宽吃紧的现代 GPU 上，
   ALU 并不是瓶颈（见第 3 节）。

### 2.2 路线 B：Tensor Core 化（HadaCore）

HadaCore 的核心结论是：不能把 FWHT 简单地"矩阵乘化"。

对 `d` 阶变换，稠密 matmul 每行需要 `d²` 次 MAC，而 FWHT 只需要 `(d/2)·log2(d)` 个蝶形，
二者的执行/运算比为

```
d² / ((d/2)·log2 d) = 2d / log2 d      →  d = 256 时为 64×
```

即"用 MMA 做非结构化矩阵会浪费 64 倍的执行槽位"。Tensor Core 唯一能利用的结构是
块对角（block-diagonal）结构。

HadaCore 的做法（原文第 3 节）：

1. base case = 16 阶 Hadamard，用 2 条 `mma.m16n8k16` 完成（一条 mma 覆盖 16 个
   输出中的 8 个）。原文指出这一步比四次 `2×2` 蝶形多用 2x 的浮点运算，但
   Tensor Core 的 FLOPS 约为 ~8x，且能把外层迭代次数减少 4 次（减少同步）。
2. d ≤ 256：把 `1×256` 的行重排成 `16×16`，先对每组连续 16 个元素做 H16，
   转置后再做一次 H16（此时作用在相隔 16 的元素上），再转置回来 —— 即 `H_16 ⊗ H_16`。
3. d > 256：把 `1×n` 看成 `(n/256)×256`，对每个 256 分片做上面的变换；然后
   在共享内存中转置成 `256×(n/256)`，再做一次 `(n/256)` 阶变换，最后转置回来。
   即 `H_n = (H_{n/256} ⊗ I_256)·(I_{n/256} ⊗ H_256)`。
4. 非 16 次幂尺寸：分解 `d = 2^m · 16^n (0 < m < 4)`，最后一层用一个"`2^m` 阶
   Hadamard 沿对角线铺开"的 `16×16` 矩阵代替完整 H16。
5. 转置读取是不合并访存，作者用 warp shuffle 解决（`512/1024/2048` 直接在寄存器
   布局上 shuffle；`≥4096` 先把所有 chunk 读进寄存器再 shuffle）。

结果与瓶颈：
* A100 相对参考实现 1.1–1.4x（峰值 3.5x），H100 1.0–1.3x（峰值 3.6x）—— 注意这远
  不是"数量级"的收益。
* 作者自述瓶颈：`512` 是最小的需要跨 256 分片同步的尺寸，因而开销与所有 `> 256` 的
  尺寸相当；`≥8K` 时为了合并访存需要每个 warp 处理 8/16/32 个 chunk，牺牲了并行度；
  共享内存的数据重排（layout conversion）比参考实现更贵，因为它必须服从 Tensor
  Core 的寄存器布局。
* 一个很有价值的工程发现：原地变换（in-place）。16M 元素的 FP16 张量（如 4096×4096）
  约占 32MB，与 A100/H100/L40S 的 L2（40/50/48MB）同级；若是 out-of-place，输入和
  输出会把对方的 cache line 挤出去。改成原地后，参考实现在某些尺寸下甚至超过了
  memcpy 下界。

### 2.3 路线 C：与量化/矩阵乘算子融合（co-design）

这是近年最活跃的方向，核心思想是旋转 + 量化 + 后续算子做成一个 kernel，
让旋转在片上完成、结果直接以低比特写回：

* SAW-INT4（arXiv 2604.19157，KV-cache 4-bit 量化）结论非常直白：
  在真实 serving 约束（paged memory、规整访存、fused attention）下，
  "token-wise INT4 + 块对角 Hadamard 旋转"就是精度/效率最优解，
  更复杂的向量量化/Hessian 感知量化只带来边际收益；作者实现了融合 rotation-quantization
  kernel 直接嵌入 paged KV-cache 布局，端到端零可观测开销。
  这说明"融合"是让旋转真正免费的关键，也说明块对角（而非完整）Hadamard 已经足够。
* AdaHOP（arXiv 2604.02525）指出 Hadamard 旋转的效果取决于其方向是否与离群值
  的结构（按行 / 按列 / 无）对齐；据此自适应地选择 Inner Hadamard Transform 或把
  离群行/列抽出到高精度通路，配合融合的 Triton kernel 在 MXFP4 训练下达到 BF16 质量、
  最高 1.46x 端到端加速。
* OSCAR（arXiv 2605.17757）针对 INT2 KV-cache 指出"朴素 Hadamard 旋转与 attention
  实际消费的协方差结构不对齐"，改为离线估计 attention-aware 协方差来导出自适应旋转，
  并把 INT2 attention kernel 与 paged serving 融合。
* Hadamard quantizer（arXiv 2306.11987，4-bit Transformer 训练）最早把 Hadamard
  量化器用于前向激活以抑制离群值，其 prototype 线性算子比 FP16 快 2.2x。
* 结构化 WHT 替代 attention 输出投影（arXiv 2603.08343）把 WHT + 对角仿射用作
  参数自由的输出投影，在等效训练预算下 loss 低于稠密基线，收益随模型/批次/序列长度
  单调增长 —— 说明 Hadamard 变换本身也在从"量化辅助"变成"结构算子"。

### 2.4 路线 D：存内 / 近存加速（非 GPU 路线）

这一路线的出发点不同：Hadamard 矩阵元素只有 ±1，乘法退化为加减，非常适合在
存内计算阵列中"免费"实现。

* HTMA-Net（arXiv 2509.23103）把 Hadamard Transform 与免乘法（multiplication-avoiding）
  的 SRAM 存内计算结合：用 Hybrid Hadamard 变换层替换 ResNet 中的部分卷积，其内部
  卷积通过存内免乘法操作实现，在 CIFAR-10/100、Tiny ImageNet 上消除了最多 52% 的
  乘法且精度可比。
* 这类工作的价值在于能效（避免数据搬运和乘法），而不是绝对吞吐；它依赖特定
  模拟/存内器件（SRAM/RRAM 阵列），与本项目的 NVIDIA GPU 软件路线是互补而非竞争关系。
  对 GPU 侧的直接启示只有一条：±1 结构意味着加减就够了，任何引入真正乘法的
  Hadamard 实现（例如把 H 当成普通矩阵做 FP16 matmul）都是不划算的。

## 3. 性能瓶颈归纳

把上面几条路线放在一起，可以对 Hadamard 变换的瓶颈给出统一判断：

1. 算术强度极低 → 本质上是一个带宽受限算子。
   每处理 1 个元素需要 `0.5·log2(d)` 次加减，而（FP16 输入 + FP16 输出）的访存量是
   4 字节。`d = 256` 时约 4 次 ALU 操作 / 4 字节，即 ~1 op/byte。
   在 400–500 GB/s 级别带宽、~20 TFLOP/s 级别 ALU 的消费级 GPU 上，算力根本不是瓶颈。
   推论：Tensor Core 的 8x 算力优势无法转化为端到端收益，这与 HadaCore 只有
   1.0–1.4x 的实测加速比完全一致。
2. 数据重排（layout conversion）常常比计算更贵。
   Tensor Core 的 A/B/C fragment 布局和"块对角"算法所需的元素位置不一致，
   必须通过转置/共享内存/shuffle 重新排布。HadaCore 明确把"共享内存数据重排"列为
   其主要开销来源。
3. 块对角结构决定了共享内存的 bank 冲突。
   当某个 radix-16 分片的步长 `s` 是 64 个 half（= 128 字节 = 正好一个 32-bank
   交错周期）的整数倍时，同一 warp 内不同线程的 gather 会落到同一个 bank，
   共享内存吞吐被串行化。
4. 小 `dim` 的占用率陷阱。 `dim = 64` 时"一块一行"只用到 2 个线程；
   必须改成"一个 warp/block 处理多行"才能打满。
5. L2 容量效应。 张量尺寸在 L2 容量附近时，out-of-place 的输入/输出互相驱逐；
   原地（in-place）变换可以让有效带宽翻倍，甚至超过 memcpy 下界。
6. 同步。 `dim > 256` 的跨 chunk 阶段必然引入 block 级同步，且同步次数随
   `log16(d)` 增长。

## 4. 对本项目的启示（转化为优化设计）

| 调研结论 | 本项目的对应设计 |
|---|---|
| 带宽受限，算力非瓶颈 | 主算子走"寄存器 + warp shuffle"路线，目标是**打满实测 D2D 带宽**；Tensor Core 作为对照实验保留 |
| 小 dim 占用率陷阱 | `rows_per_block` 让每个 block ≥ 128 线程，`dim = 64` 时一个 block 处理 16 行 |
| 数据重排比计算贵 | 主线实现**完全不使用共享内存**（零 bank 冲突、零 `__syncthreads`） |
| ±1 结构 -> 加减即可 | 每对元素用一条 `HFMA2` + 一条 `PRMT` 完成蝶形（4 条指令 / 2 个元素） |
| 打包 2 元素/寄存器 | FP16/BF16 原生 `__half2/__bfloat162` 累加，ALU 与 shuffle 指令数各减半 |
| 转义到低比特可以省访存 | 融合量化：变换结果**不落回 DRAM**，直接以 FP8/INT4 写回 |
| 大 dim 需要分治 | `dim > 1024` 走两级（寄存器 chunk + 共享内存跨 chunk）分治路径，且支持原地 |
| L2 容量效应 | 两个 kernel 都满足原地（`x == y`）语义，并提供原地基准 |
| Tensor Core 需要块对角结构 | TC 路径按 `H_d = H_16^{⊗L} ⊗ H_{2^r}` 分解成块对角 radix-16 阶段，用 `mma.m16n8k16` 实现 |

### 4.1 事后回看：第 3 节那六条瓶颈判断，后来验证得怎么样

这份调研是在动手之前做的，所以第 3 节的六条本质上都是推断。做完之后逐条对过账
（实测见 `总结报告.md`，跨平台的对照见 `docs/国产平台适配.md` 第 9 节）：

| 第 3 节的判断 | 实测结果 |
|---|---|
| 算术强度极低，本质是带宽受限算子 | ✅ 证实。ncu：DRAM 吞吐 87–93%、SM 吞吐 20–24%（报告 8.4）；Tensor Core 在显存受限区与寄存器路径打平（0.99–1.02x） |
| 数据重排常常比计算更贵 | ✅ 证实。TC 路径的 L1/TEX 吞吐比寄存器路径高 30%，这笔开销真实存在，只是被 DRAM 瓶颈掩盖（报告 8.4） |
| 块对角结构决定共享内存 bank 冲突 | ✅ 证实。两级共享内存路径用位分离索引后，dim 一直到 16384 仍贴住 memcpy 屋顶（报告 7.4） |
| 小 dim 的占用率陷阱 | ✅ 证实，而且是本项目收益最大的一条：dim=64 只改启动几何就有 6.7x（报告 7.5） |
| L2 容量效应 | ✅ 证实，但窗口比预想的窄——只有工作集正好等于 L2 容量时才成立（2.12–2.18x，报告 7.8） |
| 同步 | ✅ 证实。寄存器主线干脆完全不用共享内存，把这条从设计里消掉了 |

一条补充的教训：瓶颈清单准，不等于结论可以外推。同一份代码换到国产卡上，
"算力不是瓶颈"仍然成立，但"所以一定打满带宽"不成立——那边只跑到实测屋顶的
47–89%，访存喂不喂得满还要看网格与分块。性能结论必须按平台重量。
