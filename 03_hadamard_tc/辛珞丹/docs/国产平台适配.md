## 1. 先看依赖清单：这个算子到底需要什么硬件能力

搞清楚"要移植什么"，比讨论"移植到哪"更重要。本实现用到的设备侧能力可以分成三层，
按必要性排序：

| 层次 | 能力 | 用在 | 缺少它会怎样 |
|---|---|---|---|
| **L1 必需** | 打包 2 lane 的加减（`__hfma2` / bf16 对应指令） | `kernel_reg` 蝶形 | 退化为标量加减，指令数 ×2，但在带宽受限区间**不影响**吞吐（见第 4 节） |
| **L1 必需** | 32 lane 内的任意 lane 交换（`__shfl_xor_sync`） | `kernel_reg` 跨 lane 蝶形 | 必须改用共享内存交换，多一次 smem 往返 + 一次 `__syncthreads` |
| **L1 必需** | 128-bit 向量化全局访存 | 所有内核 | 访存事务数 ×8，在大 `dim` 上会掉到 DRAM 带宽的一半以下 |
| L2 可选 | 共享内存 + 块内同步 | `kernel_smem`（`dim > 1024`） | 大 `dim` 无法处理（但 LLM 的 `head_dim` 实测都在 64–256，不受影响） |
| L3 可选 | `mma.m16n8k16`（fp16/bf16 → fp32） | `kernel_tc` | 只是没有对照实验，主线功能不受影响 |
| L3 可选 | E4M3 硬件 `cvt`（sm_89+） | `kernel_quant` | 自动退回软件编解码，速度略降、结果不变 |

关键结论：L1 就是"一半精度的加减 + lane 间通信 + 向量化访存"，这是任何向量加速器
都具备的能力；真正需要矩阵部件的 L3 反而是可选的。

### 1.1 已经实测过的两条可移植性性质

这两条不是推测，是本机跑出来的，见 `docs/portability_sm80.log`：

1. 不依赖新指令。 用 `-arch=sm_80`（没有 sm_89 的 FP8 `cvt`，也没有 sm_120 的
   任何新东西）重新编译，在 sm_120 设备上跑完整测试套件：`test_correctness` 560 项、
   `test_fusion` 132 项、`test_fp8` 2 项，以及 `test_graph` 158 项、
   `test_gemm` 124 项——合计 976 项全部通过（`docs/portability_sm80.log` [2][5]；
   其中 [3][4] 记的是中间轮次的 156/157 与 85 项，测试文件随后扩充到 158/124 项，
   结论不变）。
2. 硬件专有路径有等价的软件回退，且被验证过。 `test_fp8` 在 sm_80 构建下明确报
   `hw encoder built: no (software fallback)`，走到 `common.cuh::float_to_e4m3_rne`，
   与硬件指令的结果一致。（更正：那一版的这行提示是在主机端判断 `__CUDA_ARCH__` 的，在任何
   架构上都会打印 no；sm_80 的结论本身不受影响——sm_80 < sm_89，设备端本来就没有硬件 `cvt`。
   收尾复核时已改为从设备端读取，sm_89 / sm_120 上会正确报 yes，此时 `test_fp8` 做的是
   「硬件 vs 软件」逐位比对。）

另外 `-arch=sm_75` 编译失败，原因是类型层需要 sm_80 的原生 bf16 算术。这条限制来
自 bf16 输入格式本身，不是来自算法；如果目标平台只支持 fp16，把 bf16 从
`ElemTraits` 里摘掉即可。

## 2. CUDA → 各平台的 API 映射

| 能力 | CUDA | 昇腾 AscendC / CANN | 寒武纪 BANG C | 海光 DCU | 摩尔线程 MUSA |
|---|---|---|---|---|---|
| 核函数 | `__global__` | `__global__ __aicore__` | `__global__` | `hipLaunchKernel` | `musaLaunchKernel`（源码级兼容 CUDA） |
| 打包 2 lane 加减 | `__hfma2(a, b, c)` | `vadd`/`vsub`/`vmul` on `half` 向量，或 `Add`/`Mul` 高阶 API | `__bang_add` / `__bang_sub` on `half2` | `__hfma2`（HIP 同名） | `__hfma2` |
| lane 间交换 | `__shfl_xor_sync(m, v, off)` | `AscendC::Shuffle` / `GatherMask`（UB 内数据重排） | `__shfl_xor_sync` | `__shfl_xor_sync` | `__shfl_xor_sync` |
| 128-bit 访存 | `float4` / `uint4` | `GlobalTensor<half, 8>` 定长向量搬运 | `__ldg` + 向量类型 | `float4` | `float4` |
| 片上暂存 | `__shared__` | Unified Buffer（UB）/ L1 | NRAM / WRAM | LDS | `__shared__` |
| 块内同步 | `__syncthreads()` | `AscendC::SyncAll` / 流水同步 | `__syncthreads()` | `__syncthreads()` | `__syncthreads()` |
| 16×16×16 矩阵乘 | `mma.m16n8k16` | Cube 单元 `Mmad`（原生 16×16×16 fp16） | 张量指令 | MFMA | `musa_mma` |
| FP8 E4M3 | `cvt.rn.satfinite.e4m3x2.f32` | 昇腾 910B 支持 hif8/e4m3 | 软件 | 软件/HIP 库 | 软件 |
| INT4 | 纯软件（本实现） | 纯软件 | 纯软件 | 纯软件 | 纯软件 |

海光和摩尔线程是源码级兼容路线：本项目的 `kernel_reg.cuh` / `kernel_smem.cuh`
去掉 CUDA 专有头文件后基本可以直接编译，工作量最小。昇腾和寒武纪需要把
"一个线程处理若干元素"的 SIMT 写法改写成"一条向量指令处理一整块"的
SIMD/向量流水写法，改动最大，但算法分解（蝶形按二进制位分段）完全不变。

## 3. 各平台落地要点

### 3.1 昇腾（Ascend 910B / Atlas）

* 分解方式不用改：`kernel_reg` 的"低位在寄存器内、高位跨 lane 交换"在昇腾上变成
  "低位在 UB 内做向量加减、高位用 `GatherMask` 做 UB 内重排"。
* Cube 路线反而比 CUDA 更自然：Ascend 的 Cube 单元原生就是 16×16×16，
  而 HadaCore 与本项目 `kernel_tc` 的 base case 正好是 16 阶 Hadamard。
  `H_16` 可以由 `popcount` 奇偶在 UB 里堆出一个常量矩阵，一次 `Mmad` 就是一层
  radix-16。`dim = 256` 时 `H_256 = H_16 ⊗ H_16`，两层 Cube 即可。
* 注意：昇腾的算子开发习惯是"一次算子处理一个 tile"，而本项目的 kernel 是
  "一行一个 block"。移植时应改成按 tile 切分，把 `rows_per_block` 语义换成 tile 大小。
* 好处：Cube 是 16×16×16 的立方体，`dim` 不是 16 的幂时的残余 `H_{2^r}`
  （`r = log2(dim) mod 4`）仍要落回向量单元，这一点与本项目 `kernel_tc.cuh` 的处理一致。

### 3.2 寒武纪（MLU）

* BANG C 提供 `__bang_add` / `__bang_sub` 的 half2 版本与 `__shfl_xor_sync`，
  `kernel_reg` 可以近乎逐行对应。
* NRAM 容量有限：`kernel_smem` 的共享 tile 策略需要按 NRAM 大小重新选 `CHUNK`。
  好在 LLM 的 `head_dim` 集中在 64–256，这条路径通常用不到。

### 3.3 海光 DCU（HIP）

* 最省事：`hipify-perl` 转换后基本可直接编译，`__shfl_xor_sync` / `__hfma2` /
  `__syncthreads` 全部同名同语义。
* 唯一需要检查的是 `mma.m16n8k16` 的 fragment 布局，海光走 MFMA，需要重写
  `kernel_tc.cuh` 的 gather/scatter 索引。
* Wavefront 是 64 而不是 32，`kernel_reg.cuh` 里所有与 32 相关的常量
  （`kSmemLogTPR = 5`、`default_log_tpr`）都要跟着改。

### 3.4 摩尔线程 MUSA

* 源码级兼容，`musify` 之后基本可直接编译；MUSA 提供 `__hfma2` 与 `__shfl_xor_sync`。

## 4. 哪些设计天生对国产加速器友好

这一节是本文档最实在的部分：本实现里有几个设计选择，恰好绕开了国产加速器常见的短板。

1. 主路径完全没有乘法，也没有 shared memory。
   `kernel_reg` 每条蝶形只有一次打包加减（`±1` 结构），且零 `__shared__`、
   零 `__syncthreads`。国产加速器的 UB/NRAM 容量普遍小于 NVIDIA 的 shared memory，
   而占满 LLM 实际 `head_dim`（64–256）的这条主路径根本不用片上暂存。
2. 算力不是瓶颈，所以向量单元弱也能打满带宽。
   实测（第 7.2 / 7.3 节）：本算子在 DRAM 受限区间达到实测 memcpy 带宽的 99–100%，
   而 Tensor Core 路径与之完全打平。也就是说这个算子对"每条指令能算多少"不敏感，
   对"能不能把访存喂满"敏感。这对向量宽度和主频都不占优的国产卡是好消息。
3. 原地变换（in-place）对显存小的机型直接有效。
   一体机 / 国产卡常见的显存配置下，工作集更容易落在 L2 容量附近——而实测表明，
   正是在这个边界上原地变换能带来 2.12–2.18x（见 `docs/结果表格.md` 第 7 节）。
   国产卡的 L2 通常更小，这个收益的窗口会落在更小的 `dim` 上，反而更容易命中。
4. 低比特输出直接融合掉一次 DRAM 往返。
   融合 FP8/INT4 实测 2.38x–5.09x（第 7.7 节）。对显存带宽紧张的机型，这是
   最直接的一条收益。
5. `dim` 不是 16 的幂也支持。 本实现按 `d = 2^r · 16^L` 分解，最后用
   `H_{2^r}` 残余蝶形收尾，不要求 `head_dim` 是 16 的倍数。

## 5. 存内 / 近存计算路线（对应调研笔记第 2.4 节）

HTMA-Net（arXiv 2509.23103）证明 `±1` 的 Hadamard 变换可以在存内计算阵列里
完全不做乘法：蝶形的 `a+b` / `a-b` 正好是交叉阵列的两种读方式。本实现与该路线
共享同一个性质——整个变换里没有一次真正的乘法。

落到工程上的建议：

* 存内阵列适合承担低位的、块内的蝶形（数据不需要离开阵列）；高位的跨块交换
  仍然要靠数字逻辑或片上总线，这部分与本项目的 `kernel_smem` 两级分治同构。
* 量化环节应当紧贴变换做在阵列输出端（本项目的融合量化就是这个思路的片上版本）。

## 6. 移植后的验证策略

算法无关、平台无关的验证方法本项目已经具备，可以直接复用：

1. 金标准：`tests/test_util.h` 里的 double 精度 CPU FWHT 实现。它不依赖任何
   加速器 API，任何平台上都能跑，且比 `fast_hadamard_transform` 更严格。
2. 验收标准：`tools/check_against_ref.py` 直接按选题书写的阈值判定
   （FP16 < 1e-2、BF16 < 5e-2）。移植后把 `--bin` 换成目标平台的可执行文件即可。
3. 性能口径：屋顶必须实测，而且要在同一个会话里测。`--mode roof`
   用和变换内核同一批执行资源（网格跨步、128 位访存）去量拷贝 / 只读 / 只写 /
   L2 驻留四个屋顶。不要用驱动报的理论带宽：在 MTT S4000 上它算出 512.8 GB/s，
   而实测拷贝是 671–688 GB/s——拿它当分母会让内核"跑到理论值的 116%"。
   也不要跨会话比较绝对值：同一台 NVIDIA 机器两次会话的实测搬运带宽差过 25%
   （总结报告 7.15.11）。
4. 原地语义：`tests/test_correctness.cu` 里的 `test_inplace` 检查原地与
   非原地结果逐位一致，这是移植到显存紧张平台时最容易被打破的性质。

## 7. 要不要租国产加速卡服务器：当时说"不必"，实测推翻了

### 7.1 当时的推理（原文保留）

选题书原文：

> 4. 平台适配：默认需在英伟达平台上支持。每在一款国产平台上支持，额外加分。

当时的判断有三条：

1. 它是加分项，不是验收项。 基础验收要求"英伟达平台上支持" + 精度阈值 +
   加速比表格 + Nsight 分析，本实现全部满足。
2. 租卡解决不了开发链路问题。 昇腾 / CANN 与寒武纪 / BANG 是"主机 + 驱动 +
   设备"三件套，算子要用 Ascend C / BANG C 重写；当时手上是 Windows 消费级平台
   （连 ncu 的计数器权限都没有），远程租卡只能拿到"算力"，拿不到可迭代的闭环。
3. 加分以"测试全部通过"为前提，而把 900 多项检查、融合量化、原地变换、Tensor
   Core 对照在另一套编程模型上重做一遍，在剩余时间里的期望收益低于把已有工作做扎实。

因此当时写的是：不租卡。

### 7.2 实测结果（推翻）

后来租了一台（AutoDL 上的 MTT S4000，¥1.96/时），结论是：第 3 条错得最厉害。

* "重做一遍"没有想象中贵。 摩尔线程是源码级兼容路线：一份
  `include/fhwt/backend.cuh`（55 条 `cuda*` → `musa*` 映射 + 2 个类型别名，每条都在
  MUSA 3.1 头文件里核过）之后，`mcc` 直接编译同一份 `.cu`，不需要任何源码改写。
  移植本身两个小时内完成，781 项回归全绿。
* "拿不到可迭代的闭环"也是错的。 远程容器里 `mcc` + `python3` + `torch_musa`
  齐全，构建一次 1–2 分钟，测试全套 3 分钟，迭代速度和本地没有区别。
* 最有价值的是第 3 条的反面：换一个平台，才发现自己代码里有一个 UB。
  `kernel_gemm.cuh` 里一处严格别名违规（把 `uint4` 局部变量按 `__half*` 读）
  在 nvcc 下恰好正确，在 mcc 下被优化成读陈旧数据，`k=128` 的 fp16 融合 GEMM
  因此产出 `inf`（详见总结报告 5.9）。这类问题不换编译器就永远看不见，
  而它本来会在某天以"莫名其妙的数值错误"的形式出现在别人的卡上。

### 7.3 实测还推翻了三条性能结论

| 在 NVIDIA 上成立 | 在 MTT S4000 上 | 原因 |
|---|---|---|
| 内核打到实测带宽的 99–100% | 只有 **47–89%**（rows ≥ 65536） | 该卡中等规模还没喂满访存；rpb 是最有效的旋钮 |
| 原地变换 **2.12–2.18x** | **1.10–1.17x**，窗口很窄 | L2 倍率 4.4x（同口径纯拷贝 5.2–5.5x）→ 2.0x，容量 32 → 24 MiB |
| CUDA Graph 是"剩下的唯一优化"（小规模 5–29x） | **单节点图重放 0.09–0.39x** | 图重放固定开销 ~0.24 ms；应改成"多节点录一张图" |
| 融合旋转进 GEMM 1.02–11.0x | **0.97–1.03x** | 该卡手写 SIMT GEMM 全程算力受限（258–295 GFLOP/s） |

这些差异不是"移植的瑕疵"，而是平台画像。 一份只在一种卡上做过实验的报告，
无法知道上面任何一条。

### 7.4 现在的结论

* 对"加分项"这件事：国产平台适配已经从"设计级方案 + 推断"变成实测完成
  （781 项回归、全量性能表、图实验、融合实验），并且附上了一份平台差异清单
  （总结报告 7.15.2）与一份该平台上还能怎么优化的清单（7.15.10）。
* 对"要不要租卡"这件事：要，但要挑兼容路线。源码级兼容的两家（摩尔线程 MUSA、
  海光 DCU/HIP）值得租，成本是每小时个位数人民币，收益是"换编译器暴露 UB" +
  "拿到跨平台结论"；昇腾 / 寒武纪那种需要重写算子的路线，才是真正贵的。
* 对读这份文档的人：如果你要在这个项目上继续做国产适配，先读总结报告 7.15.2
  那张差异化表——它列出了从 warp 宽度（128 vs 32）、共享内存容量、有没有
  `mma.sync`、图 API 完整度、一直到每次发射的主机代价（~15–20 µs vs 2–5 µs）的全部
  实测差异。表里每一行都对应一个具体的适配决定。

## 8. 适配过程（实测记录）

### 8.1 迁移方式：在包含层映射，而不是改写源码

厂商的迁移路径是 `musify-text` 这类源码改写：把 `cudaMalloc` 改写成 `musaMalloc`、
把 `cuda_runtime.h` 改写成 `musa_runtime.h`。它能把东西跑起来，代价是仓库本身不再
可编译——每次构建前都得先改写一遍，构建用的源码与仓库里的源码不是同一份
（本项目在移植初期就是这样做的，一次同步就把改写结果覆盖掉了，见 8.3）。

改用包含层映射之后：

```cpp
// include/fhwt/backend.cuh
#if defined(__MUSACC__)
#include <musa_runtime.h>
#include <musa_fp16.h>
#include <musa_bf16.h>
#define cudaMalloc               musaMalloc
#define cudaStream_t             musaStream_t
...                                   // 共 55 条，逐条核对过存在性
using __nv_bfloat16  = __mt_bfloat16; // 唯一一处"换个名字的另一个类型"
using __nv_bfloat162 = __mt_bfloat162;
#else
#include <cuda_runtime.h>
#include <cuda_fp16.h>
#include <cuda_bf16.h>
#endif
```

MUSA 安装里不存在任何 `cuda*` 标识符——头文件、类型、函数都没有——所以这 55 条
映射是必需的，不是偷懒。好处是 `nvcc` 与 `mcc` 编译的是同一份源码。

构建与实验脚本：

```bash
bash scripts/build_musa.sh all              # → build/fhwt, build/test_*.exe
bash scripts/run_experiments_musa.sh --build # → data/musa/*（与 CUDA 的 data/ 分开）
python3 tools/analyze_musa.py --data data/musa --out docs/结果表格_MUSA.md
```

### 8.2 需要在行为层面（而非拼写层面）处理的六处

1. Tensor Core 路径：MUSA 工具链下没有 `mma.sync.m16n8k16`（`mma.h` 在，但没有这
   条指令），`kernel_tc.cuh` 整个编译为空桩，`--kernel tc` 显式报错并给提示，
   `test_correctness` 的 TC 段按平台跳过——不静默出错。
2. `musaGraphInstantiate` 是 5 参旧签名（CUDA 12 是 3 参），且 MUSA 3.1 把
   `musaGraphUpload` 注释掉了，exec 只能由首次发射惰性装载。
3. `musaGraphGetEdges` 对所有图都返回 `not supported`（驱动级 `muGraphGetEdges`
   也一样），所以测试里的边查询类断言降级为"跳过并打印"。
4. 从捕获参数重建 kernel node 会被拒（`invalid device function`），
   `GraphSequence` 的 fork/join 因此回退到 child-graph 路由——而这条路在同一块卡上
   重放代价极高（总结报告 7.15.8）。
5. bf16 打包算术：`mp_22` 上 packed bf16 内建不可用（`__hfma2` 会落到内联汇编报
   寄存器约束错），`types.cuh` 用 fp32 展开实现；结果正确，指令数翻倍。
   另外 `__byte_perm` 也没有，用移位对替代。
6. 默认流和自建流之间没有隐式同步：测试里一处 `cudaMemset(z, 0, bytes)`（默认流）
   后面紧跟着在 `cudaStreamCreate` 建出来的 `cache.stream()` 上重放图，在 CUDA 上靠
   legacy 流的隐式同步成立，在 MUSA 上 memset 会落到重放之后，`z` 读回来全是 0
   （逐元素位模式诊断、修法与复跑记录见总结报告 7.15.15）。把清零点改到同一条流上即
   解决；库本身从不使用默认流，受影响的只有测试写法，但这说明迁移时不能把 NULL 流
   当成隐式同步点。

### 8.3 一个教训：改写式迁移会污染工作副本

移植初期用的是 `musify-text --inplace`，它把 `src/*.cu` 里的 `cuda*` 就地改成 `musa*`。
后来把本地仓库的源码同步上去，那份被改写的可编译版本就被覆盖了，`mcc` 立刻报
`cuda_bf16.h not found`。这件事本身就是"改写式迁移"的缺陷演示：仓库里的源码不再
等于能编译的源码。8.1 的方案消除了这个问题。

## 9. 第 1–6 节里哪些推断被实测证实 / 推翻了

写这份文档时手上只有一块 NVIDIA 卡，所以第 1–6 节是设计级分析 + 明确标注的推断。
移植完成之后逐条对照：

| 第 1–6 节的判断 | 实测 | 结论 |
|---|---|---|
| 能力分三层，**L1（半精度加减 + lane 通信 + 向量访存）是必需的，L3 矩阵部件是可选的** | MUSA 上没有 `mma.sync`，781 项检查照样全绿；TC 段只影响 195 项对照实验 | ✅ 证实。**"矩阵部件可选"是本项目最重要的移植性质** |
| `kernel_reg` / `kernel_smem` 在源码级兼容路线下"基本可以直接编译，工作量最小" | 实际改动：1 个映射头 + 6 处行为差异（第 6 处见 8.2）；半天内 781 项全绿 | ✅ 证实（但"直接编译"略乐观：55 条名字映射是必须的） |
| **算力不是瓶颈，向量单元弱也能打满带宽** | MUSA 上内核只到实测屋顶的 **47–89%**（rows ≥ 65536），中等规模只有 49% | ⚠️ 部分推翻。**"算力不是瓶颈"对，但"因此一定打满带宽"不对**——访存喂不喂得满还取决于网格/分块，得按平台重扫 |
| 原地变换在 L2 边界上值 **2.1x**，国产卡 L2 更小、"收益窗口落在更小的 dim 上，反而更容易命中" | MUSA：**1.10–1.17x**，窗口极窄（L2 倍率 2.0x vs 4.4x（同口径纯拷贝 5.2–5.5x），容量 24 vs 32 MiB） | ❌ 推翻。窗口小 ≠ 更容易命中：**收益 = L2 倍率 × 命中比例，两个因子都更小** |
| 低比特融合"对显存带宽紧张的机型是最直接的收益" | MUSA：**1.65x / 2.63x**（dim=256；dim=64 达 **5.33x / 6.11x**；NVIDIA 上 2.38–5.09x） | ⚠️ 部分推翻。融合省的是流量，**收益上限被融合进去的那一步本身的效率卡住**——MUSA 上量化内核一度只有屋顶的 17–27%，7.15.14 优化一轮后为 14–42%，仍未贴顶 |
| 存内 / 近存路线与本实现"共享没有一次真正乘法"的性质 | 未做硬件验证 | ➖ 未测（保持为设计级观察） |
| 验证策略（double 精度 CPU 金标准、按选题书阈值判定、占实测量级表达）可以直接复用 | 直接复用，781 项全绿；性能口径改成"占实测屋顶" | ✅ 证实，且屋顶口径被证明**必须**实测（驱动理论值低于实测值） |
| **第 7 节：不必租卡** | 租了，两小时移植完成，并且**因此发现并修掉一个真实 UB** | ❌ 推翻，见第 7 节 |

一句话总结：设计级分析把"需要什么能力"讲对了（所以移植才快），
但把"有了这些能力就能跑多快"讲错了——性能结论必须按平台重量，不能从另一块卡上搬。
