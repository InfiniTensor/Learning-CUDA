Node-level profile of `--mode loop`: the four submission strategies
==================================================================

    nsys profile --force-overwrite true --cuda-event-trace=false \
        --cuda-graph-trace=node -o p_nodes_all \
        -- .\build\fhwt.exe --mode loop --rows 512 --dims 128 \
           --layers 8 --iters 20 --reps 3

and the same command again with `--serial-entry`, saved as `p_nodes_sr`.  Both
`.nsys-rep` files are in this directory.  RTX 5060 Ti / sm_120 / CUDA 12.9 /
Windows.

WHY `--cuda-graph-trace=node`
---------------------------
nsys traces a CUDA Graph as ONE opaque record by default.  `loop_forkjoin.txt`
was captured that way, which is why it only ever contains 184 kernel records --
strategy A's.  With the default granularity C and D are invisible; every number
below comes from the node-level capture.

1. The kernels are identical in every strategy
---------------------------------------------
Both runs: 2016 kernel records, one kernel type, median 992 ns; multi-root min 896
/ max 2080 ns, single-root min 832 / max 3488 ns (raw summaries at the bottom).
So a fork/join graph's kernels cost the same as a linear chain's, and any C-vs-D
difference is host-side.

2. Host side: `cudaGraphLaunch`, split by how the call was produced
-----------------------------------------------------------------
The mode runs A, B, C, D in that order, `--reps` times, after 1 correctness probe
and 2 warm-up rounds.  Classifying every `cudaGraphLaunch` by how many GPU kernels
share its correlation id recovers the boundaries, and the last 120 8-node replays
are exactly C (first 60, three reps of 20) then D (last 60).

3. What it says
---------------
C is the internal control: it never calls `add_parallel()`, so `--serial-entry`
cannot touch it, and it lands on p50 9.9-10.2 us in the multi-root run and
9.8-10.0 us in the single-root run -- the same, as it must be.

D with 8 roots: p50 35.5 / 58.3 / 35.0 us (worst 295 us).
D with 1 root:  p50 11.7 / 12.0 / 11.6 us (worst 58.5 us).
Same nodes, same kernels (section 1), same driver, same stream -- the only
difference is whether the graph has 8 roots or 1, and the launch cost differs by
3.0x.

This is what made the forked strategy lose in `data/loop.csv`.  It is not the
fork/join shape and not `cudaGraphAddChildGraphNode` (section 5.8 replaced every
node with a real kernel node and the numbers did not move); it is the number of
root nodes, which is a property of the caller's step list.

Note also that D's degradation is not constant: 35.5 us p50 over the first 20
replays, 58.3 us over the second.  The single-root column stays flat (11.7 -> 12.0).
