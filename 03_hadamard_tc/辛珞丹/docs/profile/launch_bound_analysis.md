# 发射受限分析：内核时长 vs. 内核之间的空隙

> 由 `tools/gap_analysis.py` 从 `nsys stats --force-export=true` 导出的
> sqlite 生成（`CUPTI_ACTIVITY_KIND_KERNEL` / `CUPTI_ACTIVITY_KIND_RUNTIME`
> 按 correlationId 对齐）。对应总结报告 8.5 节。

每个用例是一个进程：`--warmup` + `--iters` 次完全相同的启动。

| 用例 | 内核数 | 内核中位时长 µs | 内核合计 ms | 窗口 ms | GPU 忙占比 | 间隔中位 µs | 间隔均值 µs | 间隔最大 µs | API 中位 µs | API 最大 µs | 入队等待中位 µs |
|---|---|---|---|---|---|---|---|---|---|---|---|
| `small_iters20` | 70 | 2.59 | 0.187 | 2.314 | **8.1%** | 1.54 | 30.82 | 595.8 | 6.66 | 13716.3 | 671 |
| `small_iters2000` | 2050 | 2.59 | 5.869 | 81.958 | **7.2%** | 1.54 | 37.13 | 3413.1 | 8.11 | 18216.2 | 27635 |

读法：`间隔中位` 贴着 1.5 µs（下一条命令已经在驱动里）而 `间隔均值` 接近 30 µs，说明间隔分布是双峰的——均值被少量几百微秒的提交停顿支配。`GPU 忙占比` 就是内核合计时长与窗口的比值：这个值低于 10% 时，cudaEvent 计时窗口量到的是提交路径而不是内核。

`API 中位/最大` 是 `cudaLaunchKernel` **调用本身**在 CPU 上的耗时：中位 6–8 µs，远大于内核的 2.6 µs；最大十几毫秒的离群值是首次触碰新分配显存的那一次，属于一次性噪声。

`入队等待中位` 是 `内核开始 - API 调用开始`，也就是主机抢跑的程度。它不是 API 开销：`iters` 越大这个值越大，说明主机把整段 burst 早早排进队列，然后被 GPU 侧的消费速度卡住——瓶颈不在 CPU 发得不够快。
