# 数据索引：每个实验产物是什么、怎么跑出来的、用在哪一节

`data/` 是 NVIDIA RTX 5060 Ti（sm_120，CUDA 12.9）的实测输出，`data/musa/` 是摩尔线程
MTT S4000（MUSA 3.1，`--offload-arch=mp_22`）的实测输出。两个目录分开存放、永不互相
覆盖，所以同名文件在两个平台上是两次独立运行，而不是一份数据的两种写法。

一次跑齐（两条脚本就是全部数据的来源）：

```bash
bash scripts/run_experiments_musa.sh          # -> data/musa/（租用的 MUSA 机器上）
```
```powershell
powershell scripts\run_experiments.ps1        # -> data/（本机 CUDA）
python tools\analyze.py      --data data      --out docs/结果表格.md
python tools\analyze_musa.py --data data/musa --out docs/结果表格_MUSA.md
```

## 0. 读这些数字之前必须知道的三件事

1. 口径是「占同会话实测屋顶」，不是驱动报的理论值。屋顶一律用 `--mode roof` 实测：
   CUDA 侧 memcpy 实测约 380 GB/s；MUSA 侧驱动报的理论值（512.8 GB/s）比实测还低，
   唯一可用的分母是 SIMT 拷贝 671.3 GB/s（`data/musa/info.txt`、`roof.txt`、
   `data/roof_cuda.txt`）。
2. 跨会话的绝对值不可比：同一台 MUSA 机器两次会话差 25%（报告 7.15.11）。所有 A/B 都是
   同会话内反复交替跑出来的（`quant_ab.log`、`quant_ab_cuda.log` 里的 BEFORE/AFTER 交叉出现
   就是为了这个）。
3. `data/tests.log` 是最终一轮的记录（2026-09-18，clang-format 之后重编重跑：
   560 / 132 / 2 / 158 / 124 = 976 项 0 失败）；再早的中间轮次读数已不再保留。报告 5.10 修复之后
   在备用机上的复跑是 `data/tests_sm89.log`（1088 项 0 失败）与 `data/check.log`。
   MUSA 侧的对应文件是 `data/musa/tests.log`（781 项）与 `final_tests4.log`（连跑两遍）。

## 4. 融合量化（第二轮优化的主战场）

| 文件 | 产生方式 | 关键读数 | 引用 |
|---|---|---|---|
| `data/quant_fp8_<dim>.log`、`data/quant_int4_<dim>.log` | `--mode quant --quant {fp8,int4} --dim <64..1024> --rows 262144` | 融合 vs 非融合（旋转 + 量化）逐形状；CUDA 上 **2.38–5.09x**（dim 256：FP8 2.39x / INT4 2.64x） | 结果表格 §6 |
| `data/quant_error.log` | `python tools/quant_error.py`（CPU numpy 仿真，按内核的量化规则；不需要 GPU） | 旋转前后的量化误差：有异常值时 INT4 SQNR +9–11 dB（按行），FP8 反而 −1.3 到 −8.8 dB；高斯输入两者相同 | 报告 7.7.1 |
| `data/musa/quant_*_<dim>.log` | 同上（MUSA） | 优化后 dim=64 融合 **5.33x / 6.11x**，dim=256 **1.65x / 2.63x**，dim=1024 FP8 只有 0.81x | 结果表格_MUSA §5 |
| `data/musa/quant_tune.log` | 融合量化的 tpr × rpb **150 组**扫描（rows=262144，f16，fp8+int4） | 选出 `tpr=8 rpb=16`：各形状都在最优 1.07 倍内（旧默认最差 2.56 倍） | 报告 7.15.14(a) |
| `data/musa/quant_ab.log` | 改前/改后同会话交叉跑（四组） | 只改几何 **1.41x**、只改代码 **1.06x**、两处一起 **1.52x** | 报告 7.15.14(c) |
| `data/quant_tune_cuda.log`、`data/quant_ab_cuda.log` | 同一套扫描/A-B 在 CUDA 上重跑 | CUDA 侧几何敏感性很弱，改动中性偏正（**0.964x**） | 报告 7.15.14(d) |

这一组还有一份更早的读数（9/17、同一批形状，给出 4.23x / 2.34x / 4.39x / 2.63x 等值）。
两轮相差 ≤2%，只有 dim 64 的 INT4 例外（4.39x → 5.09x）。报告统一采用 9/18 那一轮，
也就是 `data/quant_*.log` 现在的内容；9/17 那份已判定为旧读数，不再保留。

## 9. 服务器上的构建产物

MUSA 那台租用机上还有 6 个 `mcc` 编出来的二进制（约 28 MB），本机没有 MUSA 工具链，拿回来也跑不了，
所以没有放进仓库。需要复现时按 `scripts/build_musa.sh` 在 MUSA 机器上重新编译即可。

## 10. 命名约定

- `<mode>.log` 是 `fhwt` 某个模式的完整标准输出，同名 `.csv` 是同一个模式的机器可读版本；
  `tools/analyze*.py` 只吃 `.csv`。
- `final_*` / `dbg_*` / `tail*` / `passes*` 是收尾、诊断、补跑留下的记录，不参与表格生成，
  但都对应报告里的具体结论，删掉就少了证据。
- 平台专属的差异全部放在 `data/musa/` 里，同一份数据不会出现在两个目录。
