## 摘要

目标是给 LLM 量化前的旋转（QuaRot / SpinQuant 那类用法）做一个尽量把显存带宽用满的快速
Walsh–Hadamard 变换，输入 `[batch, seq_len, num_heads, head_dim]`，`head_dim` 为 2 的幂。

最后做出来的是一个不依赖第三方 GPU 库的 CUDA 库：三套内核（寄存器 + warp shuffle、两级共享内存、
Tensor Core 块对角），旋转与 FP8 / INT4 量化的融合内核，原地变换，把旋转折进 GEMM 的 A-tile 载入，
以及用 CUDA Graph 降低发射开销的调用接口。主测机是 RTX 5060 Ti，另外在摩尔线程 MTT S4000 上
完整跑了一遍。

| 项目                                         | 结果                                                                                           |
| ------------------------------------------ | -------------------------------------------------------------------------------------------- |
| 正确性                                        | 单元检查 CUDA 976 项（5.10 修复后复跑 1088 项）、MUSA 781 项；与 `fast_hadamard_transform` 逐元素比对 80 项；全部 0 失败 |
| 误差                                         | FP16 ≤ 3.91e-3（阈值 1e-2），BF16 ≤ 3.13e-2（阈值 5e-2）                                              |
| 显存受限区吞吐                                    | 378–392 GB/s，实测 memcpy 上限的 99–100%                                                           |
| 对比 `fast_hadamard_transform` / cuBLAS GEMM | 1.00–6.45x / 1.02–11.0x                                                                      |
| Tensor Core 对比寄存器内核                        | 显存受限区 0.99–1.02x，L2 驻留区 0.34–0.86x                                                           |
| 融合量化（dim 256）                              | FP8 2.39x，INT4 2.64x                                                                         |
| 旋转对量化误差                                    | 有异常值时 INT4 SQNR +9–11 dB；FP8 反而变差                                                            |

做下来最主要的认识是：这是一个纯带宽受限的算子。Tensor Core 路径在显存受限区和寄存器路径打平，
在 L2 驻留区反而更慢，和 HadaCore（arXiv 2412.08832）报告的 1.0–1.4x 一致。真正有用的优化是
减少访存（融合量化、折进 GEMM）和改变工作集（原地变换），以及在小 shape 上减少提交次数。

`data/`（RTX 5060 Ti）和 `data/musa/`（MTT S4000）里每个文件是怎么来的、被哪一节引用，
都列在 `docs/数据索引.md`。

## 1. 问题定义与验收标准

输入：`[batch, seq_len, num_heads, head_dim]` 的 FP16/BF16 连续张量，本实现统一按
`[rows, dim]` 处理（`rows = batch * seq_len * num_heads`）。

变换：正交旋转 `x → (1/√d)·H_d·x`，`H_d` 为 Sylvester 构造的 2 的幂阶 Hadamard 矩阵，
只含 ±1。作用是压平激活/权重中的离群值动态范围，让后续的均匀量化（FP8/INT4）更准。

## 2. 调研结论提要

完整调研见 `docs/research/调研笔记.md`（基于 11 篇 arXiv 实抓摘要 + 参考实现源码）。
对设计影响最大的五条：

1. 算术强度极低 → 本质是带宽受限算子。 每元素 `0.5·log2(d)` 次加减、4 字节访存；
   `d = 256` 时约 1 op/byte。在 ~450 GB/s 带宽、~20 TFLOP/s 算力的消费级 GPU 上，
   算力不是瓶颈。
2. 稠密矩阵乘完全不可用。 `d` 阶变换稠密 matmul 每行 `d²` 次 MAC，FWHT 只要
   `(d/2)·log2(d)` 个蝶形，执行/运算比 `2d/log2(d)`，`d = 256` 时 64x。
   Tensor Core 只能利用块对角结构。
3. 数据重排常常比计算更贵。 HadaCore 明确把"共享内存数据重排"列为主要开销来源，
   其实测加速比只有 1.0–1.4x（峰值 3.5x）。
4. ±1 结构意味着只需要加减。 任何引入真正乘法的实现都不划算。
5. L2 容量效应。 HadaCore 附录 B 指出原地变换可以在 L2 容量附近带来大幅收益。
6. 存内计算路线（HTMA-Net, arXiv 2509.23103）证明该变换可以完全不用乘法，
   与本实现共享"没有一次真正乘法"的性质。

## 3. 方法：算法分解

### 3.1 寄存器主线 `kernel_reg`（dim 32..1024）

一行长度 `D = 2^k` 的向量由 `TPR`（threads per row，2 的幂 ≤ 32）个 lane 协作，
每 lane 持有 `EPT = D/TPR` 个连续元素。蝶形按二进制位分两段：

```
bit 0 .. log2(EPT)-1     -> lane 内（寄存器蝶形）
bit log2(EPT) .. k-1     -> lane 间（__shfl_xor_sync）
```

一条蝶形对打包的 2 个元素只需两条指令：

```
v' = __hfma2(v, (1,-1), PRMT_swap(v))     // PRMT 换半字 + HFMA2
```

即每 2 个元素 4 条指令（2 ALU + 1 PRMT + 1 shuffle 摊销）。跨 lane 阶段的符号是
无分支的：`v' = fma(v, ±1, partner)`，低半 lane 取 +1、高半取 -1。

关键性质：零共享内存、零 `__syncthreads()` —— 因此不存在 bank conflict，
也不存在块级同步；每 lane 的 `EPT` 个连续元素用 128-bit 访存读入/写出，访存完全合并。

### 3.2 大 head_dim：两级分治 `kernel_smem`（dim 64..16384）

`dim > 1024` 超出一个 warp 的寄存器容量，改用两级分治：

```
level 1  bits [0, log2(CHUNK))  寄存器（EPT 位 lane 内 + TPR 位 shfl_xor）
level 2  bits [log2(CHUNK), k)  共享内存中步长 2^s 的蝶形
```

`CHUNK = 32 × EPT = 256`。跨 chunk 阶段使用位分离索引映射
`i = (j/d)·2d + (j mod d)`，使同一 warp 内连续线程访问连续地址（无 bank conflict），
唯一的不连续点距离 `2d ≥ 2·CHUNK` 个元素。

### 3.3 Tensor Core 路径 `kernel_tc`（任意 2 的幂）

按 `d = 2^r · 16^L` 分解：

```
H_d = (H_16 ⊗ … ⊗ H_16) ⊗ H_{2^r}
每个 radix-16 阶段 = d/16 个独立的 16 阶 Hadamard，第 n 组的 16 个成员相距 s = 2^(r+4(l-1))
```

一个 16 阶 Hadamard 恰好是一条 `mma.m16n8k16`：

```
C(16×8) = A(16×16) · B(16×8),   A       = H_16（编译期常量，符号由 popcount 奇偶直接算出）
                                B[:, n] = 第 n 组的 16 个元素
                                C[m, n] = 第 n 组的第 m 个输出
```

行先在共享内存中暂存一次，之后每个阶段做 `gather B fragment → mma → scatter C fragment`。
残余的 `H_{2^r}`（`r = log2(d) mod 4`）用寄存器内的 2/4/8 点蝶形处理，从而支持任意
2 的幂 `dim`，而不只是 16 的幂。HadaCore 用"沿对角线铺开 2^m 阶矩阵"达到同样目的。

### 3.4 融合量化 `kernel_quant`

旋转结果不落回 DRAM，直接在寄存器里量化成 FP8(E4M3) / INT4 写回：

| 路径                                         | 每元素访存                        |
| ------------------------------------------ | ---------------------------- |
| 未融合：rotate（读 2 + 写 2）+ 量化（读 2 + 写 1 / 0.5） | FP8 7 B/elem、INT4 6.5 B/elem |
| 融合 FP8(E4M3)                               | 3 B/elem                     |
| 融合 INT4                                    | 2.5 B/elem                   |

数值一致性的处理：融合内核在量化前先把旋转结果 `round_to_storage` 回 FP16/BF16，
因此与"先写回 DRAM、再读出来量化"的参考流水线逐位一致，而不是仅近似相等
（`tests/test_fusion.cu` 验证：5.10 修复前 132 项，修复后按库默认几何扩充到 244 项，
两块卡上都逐位一致）。

### 3.5 原地变换

两个内核都满足原地（`x == y`）语义。原地变换不改变 DRAM 流量、也不改变指令数，
它唯一改变的是工作集能否留在 L2（见 7.8 节）。

## 5. 优化历程与迭代

这一节记录实际踩到的问题，因为它们比最终代码更能说明设计的约束。

### 5.1 TC kernel：PTX 的类型顺序写错

第一版 `mma` 内联汇编写成了

```
mma.sync.aligned.m16n8k16.row.col.f16.f16.f16.f16     // 错
```

`ptxas` 直接报错。PTX 的修饰符顺序是 destination、A、B、C，与操作数的书写顺序
（D, A, B, C）不同：

```
mma.sync.aligned.m16n8k16.row.col.f32.f16.f16.f32     // 对
```

即"结果 f32、A 是 f16、B 是 f16、C 是 f32"。fp16 与 bf16 输入都用 fp32 累加器，
这也正好是 `fast_hadamard_transform` 的累加精度（见 7.1 节：TC 路径因此比寄存器路径
更准）。

### 5.2 TC kernel：`tc_stage_out` 的 16x 写放大

TC 内核把每行结果从共享内存搬回全局内存时，第一版写成了逐元素标量循环：

```cpp
for (int i = 0; i < kEPT; ++i) dst[lane * kEPT + i] = buf[lane * kEPT + i] * scale;
```

编译器不会自动把它合并成向量写，于是同一个 warp 的 32 个 lane 每个都发出
32 次独立的 2 字节写、地址相隔 64 字节 —— 这是主流 DRAM 流量上的 16x 写放大。

实测后果：dim 256、rows 262144 的 TC 内核吞吐从应有的 ~371 GB/s 掉到 ~90 GB/s。

修复方式是复用寄存器内核已有的向量化存取路径：

```cpp
load_row_vec<kEPT, T, Acc>(buf + lane * kEPT, v);
store_row_vec<kEPT, T, Acc>(dst + lane * kEPT, v, scale);
```

修复后 dim 256 恢复到 385 GB/s（1.01x reg）。这个 bug 也解释了为什么"写出"路径必须
和"读入"路径用同一套向量化策略——只在读侧做向量化是不够的。

### 5.3 测量方法本身也需要优化

第一轮实验矩阵（`--iters 30`、无重复）跑出来 `dim = 1024, rows = 65536` 只有
192 GB/s，而单独重跑同一组配置稳定在 375–379 GB/s。差值 2x 且横跨全部 18 个
几何配置，不是随机噪声，而是那一段测量窗口被无关的 GPU 工作（本机 GPU 同时驱动桌面）
污染了。

处置：所有计时改为 best-of-N burst（`--reps`，默认 3；原地对比用 5）。
这是非实时 OS 上微基准的标准估计量——它对样本数单调，且拒绝报告偏慢的离群值。
`tools/bench_baseline.py` 使用同一个估计量，因此本实现与基线的对比是公平的。

修正后同类数据的对比：

| 配置                  | 修正前                  | 修正后                      |
| ------------------- | -------------------- | ------------------------ |
| 262144×1024 f16 reg | 3.5197 ms / 305 GB/s | **2.8386 ms / 378 GB/s** |
| 65536×1024 f16 reg  | 0.8511 ms / 315 GB/s | **0.7090 ms / 379 GB/s** |

### 5.4 共享内存路径静默忽略 `--acc fp32`

`--acc fp32` 在寄存器路径与量化路径上都生效，但两级共享内存路径的派发点把
`Acc` 写死成了 `Native2<T>`，导致 `--kernel smem --acc fp32` 静默地什么也不做。
已修复（`ops.cu::dispatch_smem_acc`）：dim 1024 f16 的 `|ours - exact|` 从
2.53e-3 降到 1.93e-3，可观测到了差别。

### 5.5 日志编码

Windows PowerShell 的 `>` 重定向默认写 UTF-16，Python 侧读出来全是乱码，
导致报告里的实验环境段落与量化段落一度缺失。现在所有产物统一走
`[IO.File]::WriteAllText(..., UTF8Encoding($false))` 写 BOM-less UTF-8。

### 5.6 小规模测不准：发射开销，以及 CUDA Graph

5.3 节用 best-of-N 解决了"偶发干扰"，但 rows ≤ 4096 的数据仍然几乎不可复现：同一个
shape 的读数在 7–300 GB/s 之间随桌面负载浮动（8.5 节有两次测量的对照）。把 nsys 的
sqlite 导出来、逐内核对齐之后才看清：内核中位时长恒为 2.59 µs，相邻内核间隔的
中位数只有 1.5 µs、均值却有 31 µs——被测窗口里 92% 的时间 GPU 在等提交，而不是在算。

修法不是改内核，而是改调用方式：`--graph` 把整段 burst 录成 CUDA Graph 再重放。
dim 128 / rows 4096 从 302.2 GB/s 变成 858.3 GB/s，最小的 dim 64 / rows 1024 从
41.1 GB/s 变成 227.2 GB/s，L2 驻留区 +39%~48%，
DRAM 受限区纹丝不动（1.00x）。完整分析见 8.5 节。

### 5.7 服务场景基准：归一分母写错，把三个策略一起缩小了

`--mode loop` 的第一版有一个很隐蔽的测量 bug。计时函数是这样写的：

```cpp
cudaEventRecord(st0, probe);
body();                        // body() 只跑 *一趟* forward
cudaEventRecord(st1, probe);
...
return best / (double)passes;  // 却按 passes 趟归一
```

窗口里只有一趟，分母却是 `passes`，于是 A / B / C 三个数一起被缩小了 `passes` 倍。
它不影响加速比（同一分母），但绝对数字全错，而且错得不自洽：同一个配置用
`--iters 1` 和 `--iters 10` 跑，读出的"单次变换耗时"差 5.5–9.5 倍。

发现方式：把 C 的读数换算回带宽——rows 2048、dims 64/128/256、32 层的工作集是
36.5 MiB，若真如读数所示 9.5 µs 跑完，等效带宽会是 4.0 TB/s，远超本机实测 L2 峰值
（1.72 TB/s）。物理上不可能，于是回头查分母。

修法是让计时窗口真的覆盖 `passes` 趟：`for (p = 0; p < passes; ++p) body();`。
修完 `--iters 1` 与 `--iters 10` 的读数一致（A 0.215 / 0.241 ms，C 0.100 / 0.093 ms），
且 C 的等效带宽落到 384–412 GB/s，正好贴着本机 DRAM 实测上限。§7.11 与
`docs/结果表格.md` 第 9 节的数字都是修正后重新测的。

这件事本身也是一条结论：当某个读数对应的带宽超出了硬件上限，先怀疑测量，再怀疑内核。
5.3 节和 8.5 节是同一类问题的另外两个例子。

### 5.8 fork/join 图：五个被排除的假设，和真正的那个原因

10.1 节曾把「让图内的层并行起来」列为方向，本轮实现成 `GraphSequence::add_parallel()`
（见 7.10）。`--mode loop` 相应新增第四列 D（与 C 同样的节点，但声明成互不依赖，
录成一张 fork/join 图）。实测结果与预期相反：D 相对 A 只有 1.0–1.7x，相对 C 全线
落后（C/D = 0.27–0.99x，L2 驻留规模上只有 0.27–0.32x）。如果就此写下「fork/join
无用」，那是一条错误的结论——
它量到的是别的东西。这一节按顺序记录排查过程，包括一个被推翻的假设。

① 先排除内核、归一化和 staging。

| 追问               | 怎么验的                                                       | 结果                                              |
| ---------------- | ---------------------------------------------------------- | ----------------------------------------------- |
| 是内核变慢了吗？         | nsys **节点级**剖析（`--cuda-graph-trace=node`），两次采集各 2016 条内核记录 | 排除：C 与 D 的内核逐条相同，中位都是 992 ns（8.6 节）             |
| 是归一化算错了吗？        | `--iters 2 / 20 / 200`                                     | 排除：每趟耗时与趟数无关，说明它是**每次重放**的固定量                   |
| 是节点数造成的吗？        | 节点数 1 → 2 → 4 → 8 → 16 → 32                                | 排除：1 个节点时完全没有这笔开销，≥2 个节点时立刻出现，且**不随节点数增长**（见 ③） |
| 是图的首次 staging 吗？ | 加显式 `cudaGraphUpload()`（已保留在代码里）                           | 排除：数值不变                                         |

② 把「子图」这个嫌疑犯直接消掉 —— 假设被推翻。 最可疑的是每个节点用
`cudaGraphAddChildGraphNode` 挂了一张独立捕获的子图。于是 `record_fork_join()` 被改成
先把捕获出来的单节点图拆开（`cudaGraphGetNodes()` → `cudaGraphNodeGetType()` →
`cudaGraphKernelNodeGetParams()`），再用 `cudaGraphAddKernelNode()` 挂成真正的 kernel
node；不是单节点的就回退到原来的子图路径，行为不变。`tests/test_graph.cu` 新增一条
断言核对录出来的全部节点确实都是 kernel node。结果：数字毫无变化（rows 512 /
dims 128 / layers 8：每趟 0.42 ms，改之前是 0.34 ms，同一量级）。所以问题不在子图、
也不在内核——`kernel_nodes()` 现在把这个诊断结果报出来，`--mode loop` 的 D 行会打印
`kernel nodes` 而不是 `child graphs`。

③ 换成「根节点个数」的实验，真因出现。 上面的节点数扫描里有一个反直觉的细节：
1 个节点时没有任何开销，2 个节点时开销就满了。而 1 个节点的 fork/join 图与多节点
图的唯一区别，是它只有 1 个根。于是把「层 0 改为串行入口、其余层照旧分叉」
（`--serial-entry`）与「所有层都是根」并排测。逐个数字见 `data/roots.csv`
（`tools/bench_roots.py`，两种形态交替测 5 轮取中位——交替是为了让机器漂移同时
落在两列上）：

| layers | nodes | A µs/次 | C µs/次 | D 全根 µs/次 | vs C      | D 单根 µs/次 | vs C  |
| ------ | ----- | ------ | ------ | --------- | --------- | --------- | ----- |
| 1      | 1     | 6.60   | 5.30   | 6.40      | 0.83x     | 8.80      | 0.60x |
| 2      | 2     | 6.05   | 3.25   | 15.05     | **0.22x** | 3.30      | 0.98x |
| 4      | 4     | 15.75  | 3.23   | 15.38     | **0.21x** | 2.10      | 1.54x |
| 8      | 8     | 6.90   | 1.79   | 13.09     | **0.14x** | 1.55      | 1.15x |
| 16     | 16    | 6.33   | 1.16   | 4.63      | **0.25x** | 1.18      | 0.99x |
| 32     | 32    | 6.32   | 1.15   | 4.33      | **0.27x** | 1.05      | 1.10x |

（rows 512 / dims 64,128,256 / iters 20 / reps 3 / runs 5。layers=1 那行的 0.60x 是
5 µs 量级上的噪声——1 个节点的两种形态本来就是同一张图。）

④ 用 8 轮交替对照确认，并看清收益到底有多大。 同一个配置
（rows 512 / dims 64,128,256 / layers 32）交替跑全根与单根各 8 次：

| 量                              | 结果                                               |
| ------------------------------ | ------------------------------------------------ |
| C（内部对照，`--serial-entry` 影响不到它） | 1.156 µs/次，8 轮里 7 轮读数完全相同，最大 1.194               |
| D 全根                           | 4.17–6.11 µs/次，中位 4.78                           |
| D 单根                           | 1.03–1.58 µs/次，中位 1.06                           |
| C / D 单根                       | 1.11、1.10、1.12、0.73、1.11、0.99、1.08、0.96（中位 1.10） |

结论 —— 这是本节的交付。

1. 多根图的重放惩罚是稳定且量级很大的：只要图里有 ≥2 个根，`cudaGraphLaunch`
   就比同节点数的单根图贵 3.7–7 倍（`data/loop.csv` 八个配置的 C/D 全根 =
   0.27–0.99x，L2 驻留规模上是 0.27–0.32x）。
2. 把它消掉是确定的：让第一层走 `add()`（分叉有汇合点）之后，D 立刻回到 C 的
   水平。这就是 fork/join 在这台机器上值的全部。
3. 但「fork/join 更快」的说法在这里不成立：单根 D 相对 C 的中点只有 1.10x，
   8 轮里有 3 轮落到 0.96–0.99x。量级上是打平，不是碾压。原因也说得通——这 32 个
   内核本来就只有 ~1 µs、GPU 忙占比约 8%（8.5 节），把一层从串行链上摘下来省不出多少。
4. 所以这既不是「fork/join 没用」，也不是「fork/join 有用」，而是
   「这张图里有几个根节点」——它是调用方步骤列表的性质。库的处理方式是把这条建议
   写进 `add_parallel()` 的文档（含实测数字），由调用方决定要不要留一个串行入口，
   而不是替调用方改语义：`add_parallel()` 声明的是「与前面的步骤无依赖」，
   让 `record()` 擅自给第一层加一条依赖是错的。

顺带记一条工具上的教训：第一次抓这段 nsys 用的是默认的 `--cuda-graph-trace` 粒度，
nsys 会把整张 CUDA Graph 当成一条记录，于是 `docs/profile/loop_forkjoin.txt` 里只有
184 条内核（全是策略 A 的），C 与 D 根本看不见。要看到图内部必须加
`--cuda-graph-trace=node`；8.6 节的全部数字都来自加上这个开关之后的两次采集。

### 5.9 严格别名违规：nvcc 容忍、mcc 直接编译错的 8 个 half

这条 bug 是移植到 MUSA 时才暴露出来的，但它不是 MUSA 的 bug，是一段
未定义行为（UB）在另一个编译器下露出了真面目。

症状：融合 GEMM 的回归在 MUSA 上 10 项失败，形状只在 `k = 128` / fp16 出现；
`fused` 与「先旋转再 GEMM」的相对 L2 误差是 `inf`，即 C 里出现了非有限值。
同一份源码在 nvcc / sm_120 上 124 项全过。

定位（5 个探针，都在远端跑）：

| 探针       | 做了什么                              | 结果                                                                                                             |
| -------- | --------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| `probe2` | 令 `B = I`，于是 `C` 应当逐元素等于 `A_rot`  | `-O0 / -O2 / -O3` 三个优化级别**结论完全一致**（排除编译器优化档位问题）；只在 `k=128` 复现，`k=256` 正常；非有限值只出现在 tile 行满足 `r % 4 ∈ {2,3}` 的位置 |
| `probe4` | 复刻 A-tile 的「载入 → 蝶形 → swizzle 存回」 | 变换正确、swizzle 正确、0 个非有限值                                                                                        |
| `probe5` | 在 kernel 里加 hook，把真实 A-tile 打印出来  | A-tile 完全正确                                                                                                    |
| `probe6` | 同样的 hook 扩到 B-tile                | **B-tile 里是陈旧的半精度数**                                                                                           |
| `probe7` | 按下一节的修法改掉那一行                      | `k = 128` 立刻修复                                                                                                 |

根因（`include/fhwt/kernel_gemm.cuh`）：B-tile 的载入把一个声明类型为 `uint4`
的局部变量别名成 `const T*` 去取 half：

```cpp
uint4 raw = ...;                                    // 这个对象的类型是 uint4
const T* sh = reinterpret_cast<const T*>(&raw);     // 用 T 类型去访问它
b_s[...] = sh[e];                                   // 严格别名违规（UB）
```

C++ 的严格别名规则规定：一个对象的存储只能通过其声明类型（以及 char 类）访问。
`U` 是 `uint4`，却按 `__half` 读，属于 UB；编译器有充分理由认为「写 `raw` 不会影响
按 `__half` 读出来的值」，于是把那 8 个 half 提到了循环外面——mcc 正是这么优化的，
喂进 B-tile 的是上一轮循环的旧数据。nvcc 恰好没有做这个变换，所以这段代码"看起来
是对的"。

修法：先按 `uint4` 合法地把 4 个 32 位字取出来，再用 `memcpy` 把每个 16 位片段
搬进 half——`memcpy` 是语言层面唯一保证的重解释方式：

```cpp
const uint32_t w4[4] = {raw.x, raw.y, raw.z, raw.w};
#pragma unroll
for (int e = 0; e < 8; ++e) {
  const uint16_t hbits = (uint16_t)(w4[e >> 1] >> ((e & 1) * 16));
  memcpy(&shv[e], &hbits, sizeof(uint16_t));
}
```

`memcpy` 在两边都折回寄存器搬移，nvcc 生成的机器码与改前一致（已逐项复测：
CUDA 侧 124 项仍然全过），所以这是一次纯修复、零代价的改动。

为什么要写进报告：移植到第二个编译器的价值，一半就在这里——它把一个在原始
平台上"碰巧能跑"的 UB 变成了一个必须修掉的问题。如果只在自己那块 NVIDIA 卡上做到
"测试全绿"就收工，这段代码会一直带着这个定时炸弹。

### 5.10 收尾复核：两处只在默认配置下才触发的隐患

提交前按选题书逐条复核时，又查出两处测试没有覆盖到的问题，都已修复：

1. warp shuffle 掩码的移位量越界。 `kernel_reg` / `kernel_quant` / `kernel_smem` 用
   `((1 << TPR) - 1) << (threadIdx.x & ~(TPR - 1))` 计算行组掩码，移位量用的是 block 内的线程号。
   `TPR < 32` 且 block 多于一个 warp 时，第二个 warp 起移位量 ≥ 32——C++ 里是未定义行为，硬件上
   得到 `mask = 0`，而以不含自身的掩码调用 `__shfl_xor_sync` 同样未定义。默认配置恰好会触发
   （dim 32/64 的变换 256 线程/块；融合量化 128 线程/块、所有 dim）。结果一直正确，是因为 warp
   在这里是收敛的，硬件"碰巧"放过了；而测试把 `rows_per_block` 固定为 4，每行 8 线程时整个 block
   只有 32 个线程，正好绕开。修法：移位量改用 warp 内的 lane 号 `(threadIdx.x & 31)`。
   `tests/test_fusion.cu` 新增一组按库默认几何（多 warp 的 block）运行的用例。
2. 分块量化的 `block_size` 没有范围检查。 融合内核一个 lane 只写一个 scale，所以 scale 块不能
   窄于 lane 持有的元素数；默认几何下 dim 1024 每 lane 32 个元素，`--block-size 16` 会让
   `1 << (bs - log2 EPT)` 出现负移位，输出静默错误。独立量化器在 `block_size > 256` 时 shuffle
   宽度会超过 32。现在四个入口（融合、独立量化、`Graph::capture_quant`、`GraphSequence`）都在
   发射 / 录图之前检查"2 的幂且在 [8, dim]"；默认几何下自动加宽行组，显式给了不兼容的
   `--tpr` 则直接报错。

这两处修改不改变任何已有配置的数值结果；`data/` 里的性能与测试日志是修复前跑的，修复后的复跑
记录见 `data/tests_sm89.log`（1088 项 0 失败）与 `data/check.log`（见 7.1 末尾）。

## 6. 实验环境与测量方法

```
Device        : NVIDIA GeForce RTX 5060 Ti (sm_120)
SMs           : 36
Max thr/SM    : 1536
Shared/SM     : 102400 bytes
L2            : 32.0 MiB
SM clock      : 2.57 GHz
Mem clock/bus : 14.00 GHz / 128 bit
D2D memcpy ceiling      :    380.3 GB/s (2.823 ms for 512 MiB copy)
Theoretical DRAM bandwidth:    448.0 GB/s
```

宿主为 Windows + PowerShell，CUDA Toolkit 12.x，`-arch=native`，`-O3`，
刻意禁用 `--use_fast_math`（会破坏 IEEE 语义，使误差指标失去意义）。

测量口径：

* 有效带宽 = `2 × rows × dim × sizeof(T) / 时间`，即"读一遍 + 写一遍"。
  这是任何非原地变换的物理下界，也是与 memcpy 对比的自然口径。
* 屋顶用 `--mode info` 实测的 D2D memcpy 上限（380.3 GB/s），而不是理论峰值
  （448 GB/s）——因为实测值才是这块卡真正能拿到的带宽。
* 所有计时为 best-of-N burst（`--reps`）。
* 计时只包含内核本身（`cudaEvent` 环绕纯内核循环），不含分配与初始化。
* 跨轮稳定性：同一台机器、同一条命令重跑，L2 驻留档位复现到 1–2%，而 DRAM 受限
  档位可以差到约 15%（实例与判据见 7.14 末尾的注）。因此 DRAM 区的绝对吞吐按量级读，
  跨会话的比值比绝对值可信。
* `--graph` 是另一套计时口径：把整段 burst 录成一张 CUDA Graph，计时窗口里只放
  一次 `cudaGraphLaunch`，用于把主机侧提交开销从关键路径上摘掉。不加 `--graph` 时
  仍是逐次 `cudaLaunchKernel`（8.5 节给出两者的对比）。

（c）一个意外的发现：`--acc fp32` 与参考实现逐位相同

`fast_hadamard_transform` 的最大绝对差是 0.0000e+00：不是"误差很小"，而是
逐位相同（该区间内 10/10 个配置全部如此；80 项比对中共有 14 项为逐位相同，

也反过来给"我们的实现没有引入额外数值扰动"提供了最强的证据。

误差分解也说明了精度来自哪里：

| dim 1024, FP16  | max \|ours − exact\| | max \|ref − exact\| |
| --------------- | -------------------- | ------------------- |
| reg + native 累加 | 2.53e-3              | 9.70e-4             |
| reg + fp32 累加   | **9.70e-4**          | 9.70e-4             |
| tc（fp32 累加）     | 1.25e-3              | 9.70e-4             |

精度介于两者之间。

| 4096       | 172.4      | 360.6      | 663.7  | 1010.3 | 1119.6 |
| 16384      | 591.4      | 957.5      | 1350.9 | 1548.6 | 386.5  |
| 65536      | **1592.0** | **1657.8** | 390.6  | 384.8  | 378.6  |
| 262144     | 390.2      | 392.5      | 383.3  | 381.7  | 378.3  |

单位 GB/s。两条清晰的规律：

1. 工作集能装进 L2（32 MiB）时，吞吐远超 DRAM 带宽（最高 1658 GB/s，约 4.4x
   理论峰值）——此时数据在 L2 里被反复读写，DRAM 不再是瓶颈。

2. 工作集超出 L2 后，所有配置收敛到 378–392 GB/s，即实测 memcpy 的 99–100%。
   这是该算子的真正天花板：它就是一次内存往返。

3. 上表 L2 区的数字是被发射开销低估过的下界。 用 `--graph` 重测同一区间
   （8.5 节）：dim 256 / rows 16384 从 1350.9 GB/s 升到 1719.6 GB/s。DRAM 受限区则完全不受影响
   （1.00x）。

### 7.3 Tensor Core 路径 vs 寄存器路径

| rows   | dim  | dtype | reg GB/s   | tc GB/s | TC/reg    |
| ------ | ---- | ----- | ---------- | ------- | --------- |
| 262144 | 64   | f16   | 390.2      | 397.1   | 1.02x     |
| 262144 | 128  | f16   | 392.5      | 386.9   | 0.99x     |
| 262144 | 256  | f16   | 383.3      | 385.0   | 1.00x     |
| 262144 | 512  | f16   | 381.7      | 382.3   | 1.00x     |
| 262144 | 1024 | f16   | 378.3      | 381.5   | 1.01x     |
| 65536  | 256  | f16   | 390.6      | 391.6   | 1.00x     |
| 65536  | 64   | f16   | **1592.0** | 544.1   | **0.34x** |
| 16384  | 512  | f16   | **1548.6** | 743.7   | **0.48x** |
| 16384  | 128  | f16   | 957.5      | 810.0   | 0.85x     |

结论：

* 在 DRAM 受限的规模上，TC 与 reg 完全打平（0.99–1.02x）。 这不是实现不好，而是
  物理结论：两条路径都已经把 DRAM 带宽吃满，再多算力也用不上。8x 的 Tensor Core
  算力在 1 op/byte 的算子上没有任何转化途径。
* 在工作集驻留 L2 的规模上，TC 明显更慢（0.34–0.86x）。 此时瓶颈不再是 DRAM，
  而是路径本身的访存/指令效率。TC 路径每个 radix-16 阶段都要在共享内存里
  gather 一次、scatter 一次；寄存器路径只用 `__shfl_xor_sync` 在 lane 间交换，
  连共享内存都不用碰。这正是 HadaCore 点名的主要开销来源（其论文实测加速比
  也只有 1.0–1.4x）。
* nsys 数据支持这一点：TC 内核 grid 32768×256、动态共享内存 4 KB，
  中位时长 690.1 µs；reg 内核 grid 65536×128、零共享内存，
  中位时长 689.2 µs。同样的 DRAM 流量、同样的时间，但 TC 多用了 4 KB 片上暂存。

`dim = 64`、`rows = 65536` 上扫 `(tpr, rpb)`，单位 GB/s
（完整热力图见 `docs/结果表格.md` 第 4 节）：

| tpr | rpb=1 | rpb=2 | rpb=4 | rpb=8      | rpb=16 | rpb=32 |

对照 `dim ≥ 256`：热力图几乎是平的（378–392 GB/s），任何几何都能打满带宽——
调优的价值只集中在小 dim。

| 格式        | dim  | 融合 ms  | 未融合 ms | 加速比       | 融合有效带宽     |
| --------- | ---- | ------ | ------ | --------- | ---------- |
| FP8(E4M3) | 64   | 0.1082 | 0.4522 | **4.18x** | 465.1 GB/s |
| FP8(E4M3) | 256  | 0.5198 | 1.2409 | **2.39x** | 387.3 GB/s |
| FP8(E4M3) | 1024 | 2.0935 | 5.0008 | **2.39x** | 384.7 GB/s |

| INT4      | 256  | 0.4331 | 1.1412 | **2.64x** | 387.4 GB/s |
| INT4      | 1024 | 1.6989 | 4.6024 | **2.71x** | 395.0 GB/s |

未融合路径 = 旋转（读 2 B + 写 2 B）+ 量化（再读 2 B + 写 1 / 0.5 B），即 FP8 7 B/elem、
INT4 6.5 B/elem；融合路径为 3 / 2.5 B/elem。
表中的数字取自随包的 `data/quant_*_<dim>.log`（2026-09-18 那一轮）。早一轮（9/17）在同一批形状上给出的是 4.23x / 2.34x / 4.39x / 2.63x 等值，
两条曲线相差 ≤2%，只有 dim 64 的 INT4 例外（4.39x → 5.09x）——9/17 那份已被判定为旧读数
（`docs/数据索引.md` 第 4 节），本报告统一采用 9/18 值。

dim ≥ 256 的加速比与访存量之比几乎完全吻合：理论比值 FP8 7/3 = 2.33x、INT4 6.5/2.5 = 2.6x，
实测 2.39x / 2.64–2.71x（多出的一点来自省掉的一次内核启动），这与「带宽受限」的判断一致。

> 口径更正（收尾复核）：早先的 `--mode quant` 把未融合路径记成 FP8 5 / INT4 4.5 B/elem，漏算了
> 中间张量的一写一读，报告此处据此写过「理论比值 1.67 与 2.0」。已改为 7 / 6.5 B/elem（`src/main.cu`）。
> 随包的 `data/quant_*.log` 是改动前跑的：其中的 ms 与加速比不受影响，只有 unfused 那一行的
> GB/s 和 B/elem 标注按旧口径计算（按新口径 FP8 应乘以 1.4、INT4 乘以 1.44）。

dim 64 的 4.18x / 5.09x 要打折看。 这两个数高于访存比，一半原因是下面的 L2 驻留，另一半在
对照组：独立量化器 `quantize_rows_kernel` 按"一个 warp 一行、每 lane 8 个元素"组织，dim 64 时
每个 warp 只有 8/32 个 lane 在干活，量化那一步只跑到约 189 GB/s（`data/quant_fp8_64.log`：
0.2665 ms 搬 50 MB），而 dim 256 时同一内核是 383 GB/s。所以 dim 64 的融合收益里有一部分是
「对照组偏弱」，可信的融合收益以 dim ≥ 256 的 2.39x / 2.64x 为准。

dim 64 的融合有效带宽 465.1 GB/s 甚至超过理论 DRAM 峰值 448 GB/s——因为
262144×64 的输入只有 32 MiB，恰好 L2 驻留。

作为对照，PyTorch 上的 rotate+quant 流水线在同一批形状（`rows = 262144`）上只有
39–71 GB/s，按有效带宽比本实现的融合内核慢 5.7–10x。这批读数在原始数据
`data/baseline.csv` 的 `rotate+quant_fp8` / `rotate+quant_int4` 行里（自动生成的
`docs/结果表格.md` 第 5 节只列 memcpy / 参考实现 / cuBLAS 三列，不含它）。

### 7.7.1 精度这一半：旋转对量化误差的影响

7.7 回答的是"旋转 + 量化能不能快"；选题的另一半是"在保持精度的同时"。`tools/quant_error.py`
按与内核相同的量化规则（E4M3：scale = amax/448、RNE、饱和；INT4：scale = amax/7、对称、RNE；
按行或每 32 列一个 scale；旋转结果先舍入回 FP16），在三种输入上对比「直接量化」与「旋转后量化、
反量化再逆旋转」的误差，误差在原始域里量（`H/√d` 正交，逆变换是精确的）。这是 CPU 上的
numpy 仿真：规则与内核一致，不声称逐位相同（内核侧的逐位一致性由 `--mode quant` 保证）。
4096 行，完整 48 行结果见 `data/quant_error.log`，这里摘 dim = 128 / 1024、按行 scale：

| 输入                     | 格式       | dim 128：直接 → 旋转（SQNR dB） | dim 1024：直接 → 旋转 | 旋转后 MSE 缩小     |
| ---------------------- | -------- | ------------------------ | ---------------- | -------------- |
| 高斯 N(0,1)              | INT4     | 18.61 → 18.59            | 16.92 → 16.92    | 1.00x          |
| 高斯 N(0,1)              | FP8      | 31.79 → 31.79            | 31.57 → 31.56    | 1.00x          |
| **异常值通道**（1/64 的列 ×20） | **INT4** | **10.82 → 21.64**        | **8.63 → 17.80** | **8.3–12.1x**  |
| 异常值通道                  | FP8      | 37.04 → 31.53            | 32.79 → 31.52    | 0.28–0.75x（变差） |
| 重尾 Student-t(3)        | **INT4** | **13.04 → 19.21**        | **8.05 → 17.17** | **4.1–8.2x**   |
| 重尾 Student-t(3)        | FP8      | 33.03 → 31.72            | 32.19 → 31.55    | 0.74–0.86x（变差） |

三条结论：

* INT4 是旋转真正起作用的地方。 有异常值时按行 INT4 的 SQNR 提高 9–11 dB（MSE 降到
  1/8–1/12）；每 32 列一个 scale 时收益变小但仍有 4.4–8.0 dB——分块 scale 本身就在对付异常值，
  两者部分重叠。高斯输入上两条路径完全一样，旋转不引入额外误差（FP16 舍入那一步可以忽略）。
* FP8(E4M3) 上旋转反而让误差变大（异常值输入 −1.3 到 −8.8 dB）。E4M3 是浮点格式，
  相对精度与量级无关，本来就能同时照顾大值和小值；旋转把分布"拉平"成近似高斯后，这个优势没了，
  所有元素都落到同一个相对误差上。旋转后的 FP8 在所有输入上都稳定在 ~31.5 dB，也就是说旋转
  换来的是与输入分布无关的稳定误差，而不是更小的误差。这与 QuaRot / SpinQuant 把旋转主要
  用在 INT4 上的做法一致。
* 对本项目的含义：融合内核让旋转的时间成本接近零（dim 256 时融合 0.52 ms，而单独量化一次
  就要 0.53 ms，见 7.7），所以 INT4 场景下旋转是"几乎免费的 8–12 倍 MSE 改善"；FP8 场景下
  是否旋转应由精度需求决定，本库两条路径都提供。

局限：这是合成分布上的仿真，没有在真实模型激活或端到端困惑度上验证（见 10.2）。

### 7.8 原地变换与 L2 容量效应

`--mode inplace` 扫 4 个 dim × 2 个 dtype × 6 档 rows（完整表见 `docs/结果表格.md` 第 7 节）。
以 dim = 256、FP16 为例：

| rows      | 工作集        | 非原地 GB/s  | 原地 GB/s   | 原地 / 非原地  |
| --------- | ---------- | --------- | --------- | --------- |
| 8192      | 4 MiB      | 908.0     | 937.8     | 1.03x     |
| 16384     | 8 MiB      | 1362.5    | 1349.6    | 0.99x     |
| 32768     | 16 MiB     | 1633.1    | 1635.9    | 1.00x     |
| **65536** | **32 MiB** | **384.7** | **828.6** | **2.15x** |
| 131072    | 64 MiB     | 383.3     | 382.6     | 1.00x     |
| 262144    | 128 MiB    | 381.4     | 382.0     | 1.00x     |

规律非常干净：

* 工作集小于 L2：输入输出都命中 L2，比值 1.00x。
* 工作集恰好等于 L2（32 MiB）：非原地版本要同时驻留输入 + 输出 = 64 MiB，
  被挤出 L2 退化为 DRAM 受限（384.7 GB/s）；原地版本只需要 32 MiB，正好装得下
  （828.6 GB/s）。2.15x。
* 工作集远大于 L2：两者都是 DRAM 受限，比值回到 1.00x。

这个 2.12–2.18x 的收益在全部 8 个（dim, dtype）组合上都精确出现在 32 MiB 这一点上，
且 FP16 与 BF16 两条曲线逐点一致（最大偏差 0.10）——说明这是纯粹的访存行为，
与数值格式无关。与 HadaCore 附录 B 的观察一致。

工程含义：原地变换是一个"零成本但需要选对时机"的优化。对 LLM 推理，
当 `rows × head_dim × 2` 接近目标卡的 L2 容量时应当优先选择原地路径。

### 7.10 库内 API：图重放与原地策略的验证

7.8–7.12 的结论都落在调用侧，因此被固化成公共 API
（`include/fhwt/fhwt.h`）：`fhwt::Graph`（把一段 burst 录成图，按 shape 重放）、
`fhwt::GraphSequence`（把整趟 forward 录成一张图，见 7.11；`add_parallel()` 可把步骤
声明成与前面的步骤互不依赖）、`fhwt::GraphExecCache`（按下述键缓存 `cudaGraphExec_t`）、
`fhwt::TensorView` + `fhwt::row_contiguous()`（判断一个 `[b, h, s, d]` 视图能否安全
原地变换）与 `fhwt::inplace_pays_off()`（按 L2 容量判断原地是否划算）。CLI 的
`--graph` 现在走的就是 `fhwt::Graph`，所以 8.5 节那张表度量的是这条公开路径，
而不是 bench 里的临时代码。

`tests/test_graph.cu`（158 项检查、0 失败）从十个角度验证：

| 检查                 | 内容                                                                                       | 结果           |
| ------------------ | ---------------------------------------------------------------------------------------- | ------------ |
| 图重放 == 直接启动        | dim ∈ {32,64,128,256,512,1024} × dtype ∈ {f16,bf16,f32}，逐位比较                             | 0 失败         |
| `repeats` 语义       | `repeats=2` 的双节点图 == 两次直接调用（逐位）；`reset()` 后可重新捕获                                         | 0 失败         |

| 融合量化捕获             | `capture_quant` FP8/INT4 × dim 64/128/256，量化结果与 scale 逐位一致                               | 0 失败         |
| `GraphSequence` 语义 | 4 步混合序列（不同 buffer / dtype / 融合量化）逐位一致；`add()` 作废录制；`reset()` 清空队列                        | 0 失败         |

`GraphExecCache` 的键里必须有地址。 这里记录一次被实测否定的设计：最初写的是一个
按 shape 作键的 `GraphCache`，理由是"同一个 shape 的图可以复用"。测试
（`tests/test_graph.cu` 第 9 节）直接把它否掉了——图节点里存的是当时那次调用传入的
指针，换一个 shape 相同但缓冲区不同的调用命中缓存后，重放的是旧指针，输出是错的
（不是慢，是错）。所以 `GraphExecCache` 的键包含 `x` / `y` / `scale_out` 三个地址、
全部形状与配置字段以及 `repeats`，任一项不同就是 miss。这不是保守，是正确性要求。

`TensorView` 解决的是另一个静默错误。 原地变换把"第 i 行读完写回第 i 行"当成前提；
如果传入的是 `[b, h, s, d]` 转置后的视图或按 head 切出来的切片，行与行在内存里是交错的，
原地变换会静默地把结果写到错误的位置。`row_contiguous()` 用 `stride[3] == 1` 加上
"每个非 size-1 轴的 stride 必须等于其右侧所有维度的乘积"来判定；size-1 轴不设约束，
因为它的 stride 永远不会被读到。转置视图、头切片、stride-2 的尾维一律拒绝，
`inplace_pays_off(TensorView&)` 因此只会对真正连续的行布局给出"划算"。

最后一行是重点：判据 `footprint ≤ L2 && 2·footprint > L2` 不是拟合出来的经验式，而是
与实测逐点核对过的——L2/4、L2/2、2×L2、4×L2 全部判为"不划算"（实测 1.00x），
只有恰好等于 L2 的那两档判为"划算"（实测 2.15x）。退化输入（`rows=0`、极小张量）
不返回建议。

`--mode advice` 把两个启发式加内核选择打印出来，集成时可直接查：

```
> build\fhwt.exe --mode advice --rows 65536 --dim 256 --dtype f16
shape             : rows=65536 dim=256 f16
kernel            : fhwt_reg (tpr=32 rpb=8 grid=8192 block=256)
tensor footprint  :    32.00 MiB
out-of-place ws   :    64.00 MiB (input + output)
device L2         :    32.00 MiB
in-place          : RECOMMENDED (working set halves into L2, measured ~2.1x)
batching          : single launch is fine (kernel >> launch overhead)
```

（同一命令在 `rows=1024 dim=64` 上把 batching 一行改判为
`use fhwt::Graph (submission-bound at this size, measured 1.4-29x)`；在
`rows=131072 dim=256` 上把 in-place 一行改判为 `not expected to help`。）

### 7.11 收益来自「一张图里装了多少内核」：A / B / C / D 四种提交方式

8.5 节证明了小规模是发射受限的，但有一个很容易踩错的推论：换成 CUDA Graph 这件事
本身没有价值。`--mode loop` 用一个服务场景把它测了出来——L 层，每层旋转自己的
`[rows, dim]` 激活（各自独立的 buffer），跑若干趟 forward，比较四种提交方式：

| 策略       | 提交方式                                                                            |
| -------- | ------------------------------------------------------------------------------- |
| **A**    | 每次变换一次 `cudaLaunchKernel`                                                       |
| **B**    | 每次变换重放一张只含 **1 个节点**的图                                                          |
| **C**    | **整趟 forward 的全部层录进同一张图**，每趟只提交一次                                               |
| **D 全根** | 与 C 同样的节点，但用 `GraphSequence::add_parallel()` 声明成互不依赖，录成一张 fork/join 图——每一层都是根节点 |
| **D 单根** | 与 D 同一张图，但第一层用 `add()` 排队（`--serial-entry`），于是整张图只有 1 个根 + 其余分叉                 |

计时用 `cudaEventRecord` 包住一个覆盖 `passes` 趟的窗口、取 best-of-reps：窗口里包含
"GPU 等主机提交"的时间，而这正是这里要量的东西。8 个配置（7 个 32 层 + 1 个 8 层；
工作集从 L2 驻留一路涨到远超 L2，含 FP8 / INT4 融合路径）的逐配置精确数字由
`data/loop.csv` 自动生成到 `docs/结果表格.md` 第 9 节。下面的归纳用
5 轮独立扫描的中位数（`data/loop_runs.log` 保存了全部原始轮次）：

| 档位      | 工作集 / 层布局                       | A µs/次     | B vs A     | C µs/次        | C vs A         | C / D 全根   | C / D 单根       |
| ------- | ------------------------------- | ---------- | ---------- | ------------- | -------------- | ---------- | -------------- |
| L2 驻留   | rows 512 / 1024，dims 64/128/256 | 6.1–6.7    | 0.97–1.08x | **1.16–1.29** | 5.2–5.3x       | 0.27–0.32x | **1.10–1.26x** |
| 越过 L2   | rows 2048–4096（含 FP8 / INT4）    | 7.0–8.9    | 0.94–1.00x | 2.71–5.23     | 1.7–2.8x       | 0.62–0.72x | 0.98–1.65x     |
| DRAM 受限 | rows 16384 / 65536，dims 256     | 45.2–182.6 | 0.99–1.00x | 44.9–183.3    | **1.00–1.01x** | 0.98–0.99x | 0.99–1.01x     |

* B 没有价值，而且 A 与 B 本身就不稳定。 本轮 5 轮扫描里 B vs A = 0.94–1.08x
  （中位 1.00），上一轮扫描同一列却覆盖 0.93–3.59x；根因在 A：同一份代码、同一个配置，
  A 的读数在两次扫描之间从 ~6.4 µs 跳到 ~32 µs，而 B 跟着 A 一起跳。原因不难理解——
  A 与 B 量的是主机提交速率，本机 GPU 同时在驱动桌面，主机侧一旦被抢占，读数就整段抬高。
* C 是唯一可复现的读数，也是真正的收益所在。 C 的离散度极小（rows 512：5 轮中位
  1.156 µs；另一组 8 轮交替测量里 8 轮有 7 轮读数完全相同、最大 1.194 µs，见 5.8）。
  它把整趟 forward 的 32 次提交变成 1 次，L2 驻留规模上单次变换被压到 1.16–1.29 µs；
  工作集越过 L2 后升到 2.71–5.23 µs；到 rows 16384/65536 时内核本身就够长，C 与 A 打平
  ——与 8.5 节 DRAM 受限区间的结论完全一致。要注意"C 比 A 快多少"这个比值本身不是
  可靠数字：A 在两次扫描之间从 ~6.4 µs 跳到 ~32 µs，同一个 C（1.16 µs）于是被算成
  5.2x 或 27x。可靠的是「C 让单次变换稳定在 1.16 µs」。
* D 分两列，结论完全不同（完整排查见 5.8）。 全根 D 相对 A 只有 1.2–1.7x，相对 C
  全线落后（C/D = 0.27–0.99x，L2 驻留规模上慢 3–4 倍）；而只把第一层改成串行入口之后，
  同一张图回到 C 的水平甚至略高（C/D 单根 = 1.10–1.65x 的 5 个配置，0.98–1.01x 的
  3 个 DRAM 受限配置）。这条负面结果留在表里，因为它正是定位真因的那组数据：
  多根图每次重放要多付一笔主机侧开销（8.6 节：`cudaGraphLaunch` 中位 35–58 µs，
  单根只有 11.7–12.0 µs）。修好之后 fork/join 的收益是打平——5.8 节 8 轮交替对照的
  中位数是 1.10x，而不是"更快"。唯一能明确支持的强说法是：当一趟 forward 本身已经
  DRAM 受限（≥ 1.5 ms）时，图内怎么排布没有区别（三种形状差 2% 以内）。
* 建图成本是一次性的，约 0.15 ms（一张 32 节点的图；表中 7 个同规模配置的中位数，范围 0.13–0.32 ms）。相对被移除的提交开销，跑一趟
  就已经回本——这也是 API 把录制（`record()`）与使用（`launch()`）分开的原因。

四种策略的正确性在同一模式下核对过：B、C、D 的输出与 A 逐位相同（32/32 层，
融合路径下量化结果与 scale 也逐位相同），所以这里比较的确实是同一份计算。

结论：图的价值是「把 N 次提交变成 1 次」，因此捕获的单位应当是一趟 forward（一个批次
的全部层），而不是一次变换。`fhwt::GraphSequence` 正是按这个粒度设计的；反过来说，
把 `--graph` 当作「每次变换重放一张单节点图」来用是无效的（第 10.1 节记录了这次纠正）。

这一节的场景是合成的，7.13 做了补正。 这里每层有自己的 buffer，所以录图时才能把
每一层都声明成互不依赖；真实 forward 里第 k 层的输出就是第 k+1 层的输入，可并行的
是同一层内的多个投影。7.13 用 `--tensors N` + `--group-entry` 把「每层 N 个张量」这一半
补上，同层分叉组拿到 1.40–2.23x；而这一节的 `D 全根`（把相关性最高的那批节点全摊平）
在 7.13 的数据里是 0.03–0.90x。

### 7.12 端到端融合：把旋转折进 GEMM 的 A-tile 载入

10.1 节第 1 条（端到端融合）在本轮实现并测了。QuaRot 风格的一层做两件事：

```
A_rot = A H_k        读一遍 A、写一遍 A_rot        ← 一次内核
C     = A_rot B^T    再读一遍 A_rot                ← 另一次内核
```

A 被搬了三趟。但 GEMM 本来就要读 A，于是把旋转放在写入共享内存 tile 的路上：
A 只搬两趟，`A_rot` 这个张量在 DRAM 里从不存在——省下 `2·M·K·sizeof(T)` 字节和一次
内核启动，而算术一点没变（这也是它能逐位相同的原因）。

|     |                                                                      |
| --- | -------------------------------------------------------------------- |
| 实现  | `include/fhwt/kernel_gemm.cuh`（`fhwt::hadamard_gemm()`）              |
| 对照  | A = `hadamard(A)` 后 GEMM（2 个内核）；B = 融合（1 个内核）——**同一个手写 GEMM 核**      |
| 正确性 | 14 个形状**全部逐位相同**；`tests/test_gemm.cu`，124 项检查；`compute-sanitizer` 无错 |
| 工具  | `--mode gemm`、`tools/bench_gemm.py`（每形状 5 轮独立扫描取中位，极差一并入表）           |

逐形状的完整表格见 `docs/结果表格.md` 第 10 节。归纳：

* 收益随 N 增大而消失，与算术强度的预期一致。 融合只省下 `2·M·K·sizeof(T)` 字节，
  不改变任何算力需求：M=8192、K=256 时加速比从 N=64 的 1.11x 掉到 N≥256 的
  0.86–0.97x（N=4096 时 0.95x）；省下的 8 MiB 相对总流量的占比也从 61.4% 掉到
  10.3%。这条曲线不是单调的——N=1024 反而是最低点（0.86x），因为那一刻省下的流量
  已经小到被 L2 复用和发射噪声盖住。
* 收益随 K 增大而增大。 M=8192、N=128 上，K=128 → 1.17x、K=512 → 1.28x、
  K=1024 → 1.25x：K 翻倍，省下的流量就翻倍。
* M 大而 N 小时收益最实在。 rows 32768 / 65536、N=128、K=256 分别是 1.33x / 1.27x
  （省下 32 / 64 MiB）。这正是 QuaRot 里 `head_dim` 出投影的形状。
* M=1024 那行的 3.01x 意义有限：它省掉的是两个内核里的一整个启动（总共才几十微秒），
  不是带宽。
* 一个诚实的观察：收益并没有像预期的那样在 N 很大时归零。 我们的手写 GEMM 峰值只有
  约 7.4 TFLOP/s，远低于这张卡 FP16 张量核的峰值——也就是说这个 GEMM 从来没有真正
  进入计算受限区，始终受制于 L2 带宽与发射，所以删掉 8 MiB DRAM 流量仍然看得见。
  换成一个接近峰值的 GEMM（例如 cuBLAS），融合的收益会被压得更小。
* 边界：这张表量的是融合，不是 GEMM 写得好不好（对照双方是同一个
  手写核，绝对性能与 cuBLAS 的对比在 7.6 节）。工作量上，融合需要手写 GEMM 的 tile 载入
  路径并维护一个 A-tile 的 bank-conflict-free 置换
  （`slot(u) = (u mod kUnits)·32 + u/kUnits`，写和读用同一置换，所以结果逐位不变），
  比"多调一个内核"重得多；只有当模型确实在 QuaRot 式的旋转 + 投影组合上受带宽限制时
  才值得。

### 7.13 分叉宽度：把并行度放在同一层的多个张量上

7.11 的 D 是在一个层间互不依赖的合成场景上量的：每层有自己的 buffer，所以录图时可以
把每一层都声明成互不依赖。这里先纠正 7.11 里一句不够准确的话——那一节把 D 打平的
原因写成"依赖本来就不存在"。在一趟真实的 forward 里，第 k 层的输出就是第 k+1 层的输入，
层间依赖是存在的；真正互不依赖的，是同一层内部的那几个投影（一个 attention 块
要旋转 Q、K、V，QuaRot 里还有 o_proj）。所以 7.11 的 D 应当读作「多根图的形状实验 +
驱动/调度器行为」，而不是「真实依赖场景下的并行度」。这一节把缺的那一半补上。

动机。 设一层有 `N` 个独立张量，一趟 forward 的旋转次数是 `layers × N`。7.11 测的是
`N = 1`，此时可用宽度恰好是 0：层数再多，层与层之间也是串的。这一节把 `N` 打开。

方法。 `--mode loop` 新增三个开关：

| 开关              | 含义                                                                                                              |
| --------------- | --------------------------------------------------------------------------------------------------------------- |
| `--tensors N`   | 每层有 **N 个独立的 `[rows, dim]` 张量**（同层共享 `head_dim`，`dim` 列表按**层**循环而不是按张量循环）；一趟 forward 的旋转次数变成 `layers × N`       |
| `--group-entry` | **每层的第一个张量用 `add()` 排队（当锚点），同层其余张量用 `add_parallel()`**；录出来的是「每层一个 fork 组、下一层的锚点 join 上一组」，整张图**只有一个根**（5.8 的修法） |
| `--streams N`   | 完全不用图：把 `layers × N` 次裸 `cudaLaunchKernel` 轮转铺到 N 条非阻塞流上（策略 **E**）                                              |

于是同一份节点列表能录出三种 D 形状：`D 全根`（每个节点都是根，7.11 的默认）、`D 分组`
（每层一个 fork 组 + 单根），以及不建图的 `E 多流`。E 是对照：流只搬运提交、不减少
提交，所以如果收益真的来自"这些张量互不依赖"，E 也该快；如果来自"整趟只有一次提交"，
E 会停在 A 附近。

结果。 `data/group.csv`（每配置 3 轮独立扫描取中位数；单位 µs/单次变换，一趟 =
`layers × N` 次旋转），C 是 7.11 的串行链：

| rows  | dims       | 层 × 张量 | 节点  | A     | C     | D 全根  | **D 分组**  | **D 分组 vs C** | E 多流  | E vs C |
| ----- | ---------- | ------ | --- | ----- | ----- | ----- | --------- | ------------- | ----- | ------ |
| 512   | 64/128/256 | 8 × 1  | 8   | 29.71 | 1.300 | 44.25 | 1.312     | 0.99x         | —     | —      |
| 512   | 64/128/256 | 8 × 2  | 16  | 31.49 | 1.162 | 21.81 | 1.156     | 1.01x         | 15.55 | 0.07x  |
| 512   | 64/128/256 | 8 × 3  | 24  | 31.34 | 1.204 | 14.88 | 0.862     | **1.40x**     | 11.02 | 0.11x  |
| 512   | 64/128/256 | 8 × 6  | 48  | 33.16 | 1.177 | 9.96  | **0.602** | **1.96x**     | 6.93  | 0.17x  |
| 512   | 64/128/256 | 8 × 12 | 96  | 33.34 | 1.229 | 8.45  | **0.550** | **2.23x**     | 15.08 | 0.08x  |
| 4096  | 128        | 8 × 1  | 8   | 25.01 | 2.638 | 44.41 | 2.638     | 1.00x         | —     | —      |
| 4096  | 128        | 8 × 3  | 24  | 28.91 | 4.971 | 18.40 | 5.063     | 0.98x         | 15.56 | 0.32x  |
| 4096  | 128        | 8 × 6  | 48  | 24.36 | 5.631 | 12.58 | 6.135     | 0.92x         | 12.31 | 0.46x  |
| 16384 | 256        | 8 × 1  | 8   | 46.48 | 48.78 | 74.21 | 49.31     | 0.99x         | —     | —      |
| 16384 | 256        | 8 × 3  | 24  | 52.36 | 52.76 | 58.81 | 53.46     | 0.99x         | 53.81 | 0.98x  |

（`--group-entry` 在 `tensors = 1` 时退化成串行链——第 1 行和第 6 行就是它，`forks = 0`、
走的是 linear capture，D 分组 ≈ C，正好是一组自带的对照。）

三条结论：

* 宽度必须落在同一层内部，而这是本项目里第一个稳定的正收益。 同层张量数从 1 涨到
  3 / 6 / 12，D 分组相对串行链是 1.40x / 1.96x / 2.23x，峰值 0.550 µs/次
  （rows 512、8 层 × 12 张量、96 个节点）。这个收益不是噪声：7 个 `tensors > 1` 的配置里
  4 个 ≥ 1.0（1.01–2.23x），另外 3 个 0.92–0.99x 全部落在工作集 ≥ 4096 rows 的档位。
  更有说服力的是同一批数据里的对照：同样是把 48 个节点声明成并行，扁平扇出
  （D 全根）只有 0.03–0.90x，每层分组的 fork/join 是 1.96x——差别只在锚点放在哪一层。
* E（多流）全线落后。 `E vs C` 落在 0.07–0.98x，除了 DRAM 受限的 rows 16384 档
  （0.98x，那一档三种形状本来就一样）之外，最好也只有 0.17x。而在同一个配置上 E 相对 A
  是 4.8x 快的（33.16 → 6.93 µs）——A 本来就是单流串行提交，最慢的那个。也就是说：
  把工作铺到多条流上确实让内核重叠了，但那点重叠远远补不回"提交了 48 次"。这一列
  的作用就是把"并行度"与"提交次数"两个因素分开，结论是收益来自后者。
* 收益随工作集增大而消失。 rows 4096 时 D 分组 vs C 是 0.92–1.00x，rows 16384 时
  0.99x。内核一旦长到 DRAM 受限，串行链上每个节点之间那点空隙（见下面的 nsys 数据）
  就不值一提。所以这条优化的适用面是明确的：L2 驻留 / 发射受限的小 `head_dim` 档位。

内核侧证据（nsys，节点级）。 把 `rows 512 / 8 层 × 6 张量 / 48 节点` 那次采集按
correlation id 拆开（必须 `--cuda-graph-trace=node`，否则整张 CUDA Graph 在时间线上是
一条不透明的记录），每次重放取 span（最后一个节点结束 − 第一个节点开始）、busy（节点
时长之和）与峰值并发：

| 形状                  | 重放次数 | span 中位 | busy 中位 | span/busy | 峰值并发 | 单次变换    |
| ------------------- | ---- | ------- | ------- | --------- | ---- | ------- |
| C，48 节点串行链          | 60   | 58.0 µs | 47.0 µs | 1.23      | 1    | 1.21 µs |
| D，8 × (1 锚点 + 5 并行) | 60   | 25.0 µs | 54.3 µs | 0.46      | 5    | 0.52 µs |

串行链的 span 大于 busy 10.9 µs——每个节点之间约 234 ns 的空隙——而峰值并发是 1，
说明 48 次旋转老老实实付了它们时长之和。分组图正好反过来：span 只有 busy 的 46%，
峰值并发 5（一层 6 个节点里 1 个是锚点、其余 5 个同时跑）。0.52 µs 已经低于内核自身的
中位时长 1.376 µs——单个内核都比这慢，这只可能是同层张量真的重叠了。两条独立读数
（事件计时 1.18 / 0.60 µs，nsys 1.21 / 0.52 µs）落到同一处；原始导出在
`docs/profile/loop_group_width.txt`，采集文件是 `docs/profile/loop_group_width.nsys-rep`。

一个诚实的边界：48 个节点时提交本身开始变贵。 同一次采集里 1 节点的图
`cudaGraphLaunch` 中位 5.2 µs，48 节点的图中位 39–51 µs，多 47 个节点贵约 35 µs
（≈0.7 µs/节点，与 8.6 节 8 节点单根图 11.7–12.0 µs 吻合）。这份读数被 profiler 与桌面
负载抬高了（D 自己的整趟实测是 28.9 µs，低于它的 39 µs 提交中位），所以稳的只有差值
这一项。含义是：在 48 节点这一档，提交路径和计算已经是同一个量级，再往下压要靠
"一张图里装更多趟"（把计时窗口批进一张图），而不是继续改图的形状。

### 7.14 一张图里装几趟：把趟与趟之间的空转也吃掉

7.13 结尾留了一个数字：48 节点的图 `cudaGraphLaunch` 中位 39–51 µs，而它对应的 GPU 工作
只有 25 µs——提交比计算还贵。那么下一步不是再改图的形状，而是让一次提交覆盖多趟：
`--passes-per-graph K` 把整份节点列表重复 K 次录进同一张图。每趟都是同样的计算、同一批
buffer，所以逐位不变（`--mode loop` 每次都核对）。

结果（`data/batch.csv`；8 轮交替扫描取中位，rows 512 / 8 层 × 6 张量，L2 驻留档位）。
两档形状都列出来，因为下面那条独立校验要求形状严格对齐：

`--dims 128`——这一档就是本节 nsys 采集用的形状，也是 7.13 的峰值配置：

| K（趟/图） | 节点  | 建图成本 ms | C 串行链 µs/趟 | **D 分组 µs/趟** | D vs K=1  |
| ------ | --- | ------- | ---------- | ------------- | --------- |
| 1      | 48  | 0.30    | 55.4       | 28.9          | 1.00x     |
| 2      | 96  | 0.52    | 55.5       | 25.8          | 1.12x     |
| 5      | 240 | 1.33    | 55.5       | 24.4          | 1.18x     |
| 10     | 480 | 3.05    | 55.5       | 24.0          | 1.20x     |
| 20     | 960 | 5.66    | 55.6       | **23.8**      | **1.21x** |

`--dims 64,128,256`（三种 head_dim 混合，7.13 的另一档）：

| K（趟/图） | 节点  | 建图成本 ms | C 串行链 µs/趟 | **D 分组 µs/趟** | D vs K=1  |
| ------ | --- | ------- | ---------- | ------------- | --------- |
| 1      | 48  | 0.29    | 55.4       | 28.9          | 1.00x     |
| 2      | 96  | 0.52    | 57.3       | 26.2          | 1.11x     |
| 5      | 240 | 1.34    | 55.5       | 25.2          | 1.15x     |
| 10     | 480 | 2.87    | 55.5       | 24.6          | 1.17x     |
| 20     | 960 | 5.36    | 55.4       | 24.4          | **1.18x** |

* D 分组再拿 1.18–1.21x，K ≈ 5 就基本饱和。 两档都是从 28.9 µs/趟降到 23.8 / 24.4，
  等价地 0.602 → 0.496 / 0.508 µs 单次变换；K=5 已经拿到 1.15–1.18x，K=10/20 只再多
  1–3%。两档曲线几乎重合，说明这个收益跟 head_dim 的取值无关，只跟「每趟有多长」有关。
* 串行链完全不动。 C 在 K=1..20 上是 55.4–55.6 µs/趟（两档形状都一样），与 K 无关。
  下面 nsys 那一段解释了为什么它动不了。
* 平台期的样子本身就是证据。 K=1 时 D 每趟 28.9 µs，比它的 GPU span（24.96 µs，
  nsys 用完全相同的形状独立量到）多出 4 µs——这 4 µs 就是尚未被摊掉的提交开销；
  K ≥ 10 之后秒表读数落到 24.0–23.8 µs，与 span 重合到 3–5% 以内。也就是说 K 够大时
  秒表读数已经就是纯 GPU 时间，主机侧那一部分已经完全被摊掉了——两条互相独立的测量（CUDA
  事件、GPU 时间线）落到同一处。C 停在 55.4 µs，它的 span 是 57.95 µs，同样重合。
  同一规律在 `tensors = 1` 那一档也能看到（8 节点的链每趟 11.7 → 9.3 µs），只是那一档
  本来就处在「提交 ≈ GPU 时间」的边界上，收益只有 1.26x。
* 一处自我更正。 本节初稿把 `--dims 128` 采集到的 nsys span 与 `--dims 64,128,256`
  的秒表读数放在一起比，两者形状并不严格一致；现已把与采集完全相同的形状加进扫描
  （`data/batch.csv` 里新的一档），结论不变，而且 K=1 与 span 之间的差值现在有了明确
  读法——它就是可以被摊薄的提交开销。

机理（nsys，K=1 那一半）。 在 GPU 时间线上量相邻两次重放之间的空隙：

| 形状    | 每次重放的 span | 重放之间的空隙 p50 |
| ----- | ---------- | ----------- |
| C 串行链 | 57.95 µs   | 3.52 µs     |
| D 分组  | 24.96 µs   | **9.92 µs** |

两者用的是同一种提交（同一张 48 节点的图），差别只在每趟的 GPU 工作：链是 58 µs，
比提交的开销长，主机跟得上，只留 3.5 µs；分组图只有 25 µs 的活，比提交短，于是 GPU
干完这一趟就得等下一次提交，空出 9.9 µs。这正是「批 K 趟能救 D、救不了 C」的原因，
事件计时也完全对上（D 每趟省 5.1 µs，C 省 0）。profiler 会放大主机侧空隙，所以 9.9 µs
读作「这个洞存在、且只出现在 D 上」，不要当它的绝对值。

一个负面结论：提交路径本身没有「批量折扣」。 同一次采集里 48 节点的图
`cudaGraphLaunch` 中位 41.7 µs，960 节点的图 1241.1 µs——折算到每 48 个节点反而更贵
（41.7 → 62.1 µs）。批 K 趟省下的是趟与趟之间的空转，不是提交成本的一部分。
（作为尺度：1 节点的图——几乎全是固定开销——在同一次采集里是 4.8 µs。）

收益的边界也是清楚的：只在「每趟的 GPU 时间短于提交开销」的档位成立。 同一份扫描里
rows 4096 / dim 128 / 8 层 × 6 张量（每趟约 260 µs）在 K=1..20 上完全不动（D 5.38–5.41、
C 5.16–5.18 µs/次，D vs C 0.95–0.96x），rows 16384 / dim 256 也一样（44.6–45.0 µs/次，
各 K 之间差 1% 以内）。内核一旦长到 DRAM 受限，主机侧这点开销本来就被淹没了——与 8.5 节
的结论一致。

一处必须说明的跨轮漂移（以及为什么采信这一轮）。 本节那两档「无收益」的配置在两轮扫描
之间差了约 15%：`rows 16384 / dim 256` 的每趟时间从 1.29–1.33 ms 变成 1.07–1.08 ms，
`rows 4096 / dim 128` 从约 300 µs 变成约 258 µs（上面表里就是这一轮的读数）。把流量算清楚
就能判断哪一轮可信——这两档每趟的读写量是 402 MB / 101 MB，折算 376 GB/s / 390 GB/s，
正好落在报告里 DRAM 受限区的 378–392 GB/s（= D2D memcpy 的 99–100%）上；而前一轮是
312 / 335 GB/s，够不到这个上限。所以本节采用这一轮，前一轮是被带宽拖慢的一次异常（定稿前又对这两档独立重测了三轮：386–391 GB/s 与 371–378 GB/s，仍然贴着上限，所以这一轮是可复现的，不是碰巧）。
真正的教训是测量稳定性：同一台机器、同一条命令，DRAM 受限档位可以有 15% 的跨轮漂移，
而 L2 驻留档位只差 1–2%（两轮的 512 档几乎逐位重合）。读报告里那些绝对吞吐数字时请记住这个
量级（跨会话的比值比绝对值可信）。它不影响本节的结论：两轮里各个 K 的读数都彼此相差 1% 以内，「批 K 趟在这里没有收益」
在两轮里都成立。

代价与适用面。 建图成本随 K 线性上涨：48 节点的 D 图 0.29–0.30 ms、960 节点的
5.4–5.7 ms（≈6 µs/节点，8 轮中位）。按每趟省 4.5–5.1 µs 算，一张 960 节点的图需要
同一批 buffer 重放约 1100–1200 趟才回本。所以这是服务循环的优化（一张图跑几千个
step），不是一次性调用的优化——与 `fhwt::GraphSequence` 的设计前提一致。

一个必须说明的测量边界。 `--cuda-graph-trace=node` 会放大大图：同一份工作在 K=20
时 nsys 读到的每趟 span 是 31.4 µs（D）/ 124.2 µs（C），而 K=1 是 25.0 / 58.0 µs——节点级
追踪给每个节点插入了额外工作，图执行器只能等它。所以K 这一维只能用秒表量（未采样的
读数 23.8 / 55.4 µs），nsys 在这里只负责解释 K=1 的机理。原始导出在
`docs/profile/loop_batch.txt`，采集文件 `docs/profile/loop_batch_k1.nsys-rep` 与
`loop_batch_k20.nsys-rep`。

### 7.15 第二次实测：摩尔线程 MTT S4000（MUSA 3.1）

选题书写明「每在一款国产平台上支持，额外加分」。7.15 就是这件事的实测记录：
一块 MTT S4000 上把本项目的全部内核、融合量化、原地变换、图提交与 GEMM 融合重跑
一遍。结论与 NVIDIA 上不一样，而且不一样的地方很有信息量。

#### 7.15.1 环境与迁移路径

| 项    | 值                                                                                     |
| ---- | ------------------------------------------------------------------------------------- |
| 卡    | MTT S4000，`mp_22`，56 SM，warp **128** 线程，L2 **24 MiB**，SM 1.60 GHz，48 GB               |
| 工具链  | MUSA **3.1.0**（`mcc`，clang 14），`--offload-arch=mp_22 -mtgpu`                          |
| 迁移方式 | **不改写源码**：`include/fhwt/backend.cuh` 把 55 个 `cuda*` 名字映射到 `musa*`，`mcc` 直接编译同一份 `.cu` |
| 构建   | `bash scripts/build_musa.sh all`；实验 `bash scripts/run_experiments_musa.sh`            |
| 回归   | **781 项检查，0 失败**（`data/musa/tests.log`）                                               |

厂商给的迁移方式是 `musify-text` 这类源码改写工具（把 `cudaMalloc` 写成 `musaMalloc`）。
它能把东西跑起来，但代价是仓库本身不再可编译——每次构建前都得先跑一遍改写，改完的
源码与仓库里的源码不是同一份。这里换了个做法：在包含层面做映射。MUSA 安装里
不存在任何 `cuda*` 标识符（头文件、类型、函数都没有），所以 `backend.cuh` 提供
`#define cudaMalloc musaMalloc` 这样的 55 条映射，外加两个类型别名
（`__nv_bfloat16` → `__mt_bfloat16`，MUSA 只有这一处是"换个名字的另一个类型"
而不是加前缀）。每一条映射都先在 MUSA 3.1 的头文件里核过存在性，不是猜的。

收益：`nvcc` 与 `mcc` 编译的是同一份源码，没有中间产物、没有"改过的副本"，
一次提交两个平台都能构建。

#### 7.15.3 屋顶：驱动报的理论值比实测值还低

这是本次移植里最该记住的一条。`--mode info` 报的两个数：

```
Mem clock/bus : 8.01 GHz / 256 bit
D2D memcpy ceiling        :  688.0 GB/s (async) / 687.1 GB/s (sync)
Theoretical DRAM bandwidth:  512.8 GB/s      <- 驱动算术
```

驱动按「2 次传输/时钟 × 8.01 GHz × 256 bit」算出 512.8 GB/s，而实测拷贝跑到
688 GB/s。也就是说驱动报的理论带宽不是天花板，它连实测值都不到——如果拿它当分母，
本项目的内核会"跑到理论值的 116%"（`data/musa/kernels_reg.csv` 里确有此行），
这种数字写进报告只会让人怀疑全部测量。

为此新增了 `--mode roof`：用和变换内核同一批执行资源（网格跨步、128 位访存）
去量三个方向的屋顶，而不是拿驱动的算术当真：

| 屋顶                        | GB/s          | 说明                              |
| ------------------------- | ------------- | ------------------------------- |
| `cudaMemcpy` D2D（异步 / 同步） | 687.1 / 685.0 | 驱动拷贝路径，与 SIMT 拷贝一致              |
| SIMT 拷贝（读+写）              | **671.3**     | **本算子该用的分母**（每元素 1 读 1 写）       |
| 只读（归约）                    | 688.8         |                                 |
| 只写（填充）                    | 664.5         |                                 |
| 落在 L2 里的同一拷贝（工作集 = L2/4）  | **1320.5**    | 同一块数据放进 L2 值 **2.0x**（见 7.15.6） |

该卡的真实 DRAM 能力约 671–688 GB/s，本报告所有 MUSA 百分比都以此为分母
（`docs/结果表格_MUSA.md` 顶部也写着这个数）。附带一条方法论：屋顶必须用
纯搬运内核在同一次运行里量，否则跨会话对比毫无意义——7.15.11 会看到，
连同一台 NVIDIA 机器上的两次会话都能差 25%。

同一把尺子量第二块卡。 `--mode roof` 在两个平台上跑的是同一个内核（同一份
`include/fhwt/probe.cuh`），所以下面这张表可以横着读（CUDA 侧原始输出：
`data/roof_cuda.txt`）：

| 屋顶                      | RTX 5060 Ti（sm_120）       | MTT S4000（mp_22）     | 备注                |
| ----------------------- | ------------------------- | -------------------- | ----------------- |
| 驱动报的理论带宽                | 448.0 GB/s（与实测吻合）         | 512.8 GB/s（**低于**实测） | 只有 NVIDIA 侧能拿它当参考 |
| D2D `memcpy`（异步 / 同步）   | 366.4–380.8 / 368.7–375.1 | 685.5 / 684.8        |                   |
| SIMT 拷贝（读+写）            | 361.3–371.5               | **671.3**            | 两个平台的百分比都用它做分母    |
| 只读 / 只写                 | 396.0–406.4 / 397.2–424.0 | 686.1 / 681.7        |                   |
| L2 驻留拷贝（工作集 = L2/4）     | 1942.8–1995.2             | 1320.5               |                   |
| **L2 倍率（对各自的 DRAM 拷贝）** | **≈5.2–5.5x**             | **2.0x**             | 原地变换收益的上限         |

读这张表要注意跨会话效应：CUDA 侧这三次抓取互相就差 2–3%（SIMT 拷贝 361–372 GB/s），
而 7.2 节那些变换内核的读数来自 `cudaMemcpy` ≈380 GB/s 的另一次会话——不要跨表相除，
这张表只用来看两个平台各自的 L2/DRAM 比值（三次抓取分别是 5.52 / 5.28 / 5.23）。

两块卡的 L2 倍率差约 2.7 倍，这正是 7.15.6 里原地变换收益差一档的直接原因。
CUDA 侧的 L2 数字同样是用「一次发射里跑 reps 次」摊销发射开销量出来的（`src/ops.cu`
里 `reps = 32`）——不摊销的话，6 MiB 的工作集量到的是发射开销，会得出「L2 比 DRAM
还慢」的错误结论（这块卡上第一次量就掉进过这个坑，见 7.15.6）。

两点结论：

1. NVIDIA 上调出来的几何（`tpr=32, rpb=8`，就是 `src/ops.cu` 里
   `default_log_tpr()` / `default_rows_per_block()` 的返回值）在 MUSA 上不是最优。
   dim=1024 用这个几何是 487.5 GB/s（对驱动理论值 95.1%、对实测屋顶 72.6%），
   MUSA 重扫后是 495.1 GB/s（96.6% / 73.8%）——只差 1.6%；小 dim 上差得多：
   dim=64 用这个几何只有 194.4 GB/s（屋顶的 29.0%），重扫后 313.7 GB/s（46.7%），
   1.61x。跨平台必须重扫，这一条是可以直接写进移植清单的。
2. 在 MUSA 上，主导变量是"每个 block 领多少行"（rpb），而不是"每行派多少线程"（tpr）。
   dim=1024 时 tpr 从 8 到 32 几乎不动（495 / 495 / 495），rpb 从 1 到 4 是
   182 → 334 → 495 GB/s；rpb 再大反而略降（8 → 488、32 → 470）。rpb=1 时一个 block
   只有 8–32 个线程，占用的是一个 128 宽的 warp 槽——这是 warp 宽度差异在
   几何搜索里的直接体现。

| 4096       | 48.9 (7%)   | 83.1 (12%)  | 133.2 (20%) | 166.5 (25%)     | 203.2 (30%) |
| 16384      | 145.8 (22%) | 207.9 (31%) | 270.0 (40%) | 292.2 (44%)     | 327.2 (49%) |
| 65536      | 318.7 (47%) | 353.9 (53%) | 421.3 (63%) | 492.3 (73%)     | 495.7 (74%) |
| 262144     | 501.0 (75%) | 533.0 (79%) | 588.1 (88%) | **596.9 (89%)** | 561.5 (84%) |

单位 GB/s，括号内是占实测屋顶 671.3 的百分比；每个格子取该 (rows, dim) 下所有 dtype
与 `tpr × rpb` 组合里的最优值。峰值 596.9 GB/s 出现在 rows=262144、dim=512、bf16
（`tpr=8, rpb=4`）。

和 NVIDIA 的差别在这里：在 RTX 5060 Ti 上，DRAM 受限区间的内核可以跑到实测
memcpy 的 99–100%（7.2 节），"带宽吃满"这个论断是成立的；在 MUSA 上只有
rows=262144 那一档能到 75–89%，rows=65536 是 47–74%，中等规模（16384 行）
只有 22–49%，rows=4096 更是只有 7–30%。也就是说这个算子在 MUSA 上
还有明显的带宽余量，见 7.15.10 的清单。

#### 7.15.6 原地变换：L2 仍然值 2x，但收益比 NVIDIA 小一档

先看 L2 本身值多少。`--mode roof` 用同一个拷贝内核、只换工作集大小
（256 MiB → L2/4 = 6 MiB），并且把 32 次拷贝放进一次发射里——这一步是必须的：
在这块卡上，一次 6 MiB 拷贝的搬运时间约 18 µs，与一次发射的代价相当，
不摊销的话量到的是发射开销（第一次量就掉进了这个坑：394 GB/s，看起来"L2 比 DRAM 还慢"）。

| 工作集           | 拷贝带宽            | 相对 DRAM 拷贝 |
| ------------- | --------------- | ---------- |
| 256 MiB（DRAM） | 671.3 GB/s      | 1.00x      |
| 6 MiB（L2 驻留）  | **1320.5 GB/s** | **1.97x**  |

所以 MUSA 的 L2 是有倍率的，约 2.0x。NVIDIA 那块卡上，同一把 `--mode roof`
的纯拷贝尺子量到 ≈5.2–5.5x（1942.8–1995.2 GB/s ÷ 361.3–371.5 GB/s，三次抓取，
`data/roof_cuda.txt`）；7.2 节里的 4.4x 是另一个口径——变换内核在 L2 里的吞吐
（1658 GB/s）除以 DRAM 吞吐（380 GB/s）。两个数不矛盾，但只有纯拷贝口径能在这两块卡之间直接横比（7.15.3 的对照表）。

那为什么 `--mode inplace` 的 60 个配置里几乎没有收益？

| 原地工作集             | 原地/非原地          | 配置数 |
| ----------------- | --------------- | --- |
| 1 – 8 MiB         | 0.97 – 1.01     | 10  |
| 8 – 24 MiB（落进 L2） | **1.10 – 1.17** | 6   |
| 32 MiB（刚好超出 L2）   | 0.97 – 1.11     | 4   |
| > 32 MiB          | 0.97 – 0.99     | 其余  |

收益确实出现在窗口里（原地工作集 16 MiB、L2 24 MiB 那一档：1.10 / 1.17 / 1.15 / 1.10），
只是幅度只有 1.1–1.2x，而不是 NVIDIA 上的 2.12–2.18x。原因是窗口太窄：
L2 只有 24 MiB，原地工作集必须 ≤ 24 MiB 才谈得上命中，而扫描的尺寸是
2/4/8/16/32/64 MiB 的整数倍跳档，只有一个档位落在里面；NVIDIA 那边 L2 是 32 MiB，
同一个扫描里有更多档位落进去，而且 L2 的倍率本身高一倍多。结论应表述为：
"原地变换的收益 = L2 倍率 × 命中比例"，两个因子在 MUSA 上都更小。
（另外这一组扫描用的是库的默认几何 `tpr=32/rpb=8`，在 MUSA 上不是最优几何，
所以两列的绝对值偏低；但原地与非原地用的是同一几何，比值仍然可比。）

#### 7.15.7 融合量化：收益上限由量化那一步决定

dim=256、rows=262144（`data/musa/quant_*.log`；括号里是 7.15.14 优化后的读数）：

| 量化       | 融合                  | 非融合                              | 加速比                | NVIDIA 同项 |
| -------- | ------------------- | -------------------------------- | ------------------ | --------- |
| FP8 E4M3 | 1.3952 ms（原 1.5728） | 2.2974 ms（旋转 0.6016 + 量化 1.6957） | **1.65x**（原 1.46x） | 2.39x     |
| INT4     | 0.5999 ms（原 1.0218） | 1.5765 ms（旋转 0.6016 + 量化 0.9749） | **2.63x**（原 1.62x） | 2.64x     |

拆开看就清楚了：融合省下的是"写一遍 + 读一遍"，省不掉量化本身的代价。
而 MUSA 上量化那一步远低于带宽：FP8 输出 262144×256×1 B + 读 128 MiB，1.70 ms
只折合 118 GB/s（实测屋顶 671.3 的 17.6%）——反倒是融合后的同一个形状
在 7.15.14 之后拿到了 144 GB/s（21.5%）；INT4 从 164 GB/s 抬到 280 GB/s（24.5% → 41.7%）。
融合的收益上限被最慢的那一步卡住了，所以在 MUSA 上"把量化内核做快"比"把旋转
融合掉"更值钱——这和 NVIDIA 上"量化那一步已经贴着带宽、只能靠省流量"的局面正好
相反。7.15.14 就是照着这一条做的。

#### 7.15.8 CUDA Graph 在 MUSA 上是负优化

在 NVIDIA 上，"还剩最后一个优化：CUDA Graph"（8.5 节）是成立的：小 shape 5–29x。
在 MUSA 上同一份代码给出的是相反的结果（`data/musa/graph.csv`，单节点图 vs 裸启动）：

| rows   | dim | 裸启动 ms/次 | 图重放 ms/次 | 图/裸       | 等效带宽           |
| ------ | --- | -------- | -------- | --------- | -------------- |
| 1024   | 64  | 0.0218   | 0.2434   | **0.09x** | 12 → 1.1 GB/s  |
| 16384  | 128 | 0.0452   | 0.1478   | 0.31x     | 185 → 57 GB/s  |
| 16384  | 256 | 0.0607   | 0.1560   | 0.39x     | 276 → 108 GB/s |
| 65536  | 256 | 0.1763   | 0.1779   | 0.99x     | 381 → 377 GB/s |
| 262144 | 256 | 0.6014   | 0.6028   | 1.00x     | 446 → 445 GB/s |

重放一次只有 1 个节点的图要花 0.24 ms——其中没有任何计算，全是 MUSA 3.1
图重放的固定开销。服务场景（`--mode loop`，rows=2048、dims 64/128/256、8 层）里
这个开销的表现是：

| 策略                         | 每趟        | 每变换      | 相对 A      |
| -------------------------- | --------- | -------- | --------- |
| A 裸启动（8 次/趟）               | 0.9864 ms | 123.3 µs | 1.00x     |
| B 每步一张单节点图                 | 0.7561 ms | 94.5 µs  | 1.30x     |
| C 一趟一张图（8 节点）              | 0.2643 ms | 33.0 µs  | **3.73x** |
| D 分叉图（8 节点、child graph、全根） | 2.2198 ms | 277.5 µs | **0.44x** |

这张表的原始文件没有落盘——它是全文唯一一处无法从 `data/` 复算的数字。
四行读数是租用机上手工跑 `--mode loop` 的输出；同一批 shape 的自动化采集
`tools/bench_loop.py` 在这台机器上 8 个 shape 全部 `run failed`（`data/musa/sweep.log`
第 649–658 行），于是 `data/musa/loop.csv` 只写了表头、`loop_runs.log` / `loop.log`
都是空文件。本节其余两张表不受影响（分别来自 `data/musa/graph.csv` 与
`data/musa/passes.log`）；这条缺口记在 10.2 节。

把规模放大到 48 节点（8 层 × 6 张量、`--group-entry`）后 B 和 D 一起塌掉：
A 1.1220 ms/趟、C 1.1352（0.99x）、B 12.78（0.09x）、D 17.65（0.06x）。

值得注意的是 A 本身：8 层那个形状里是 123 µs 一次变换，一次变换只搬约 1 MiB，
按屋顶算该是 3 µs 的事。用 `--mode bench` 单独量发射代价（同一 shape 重复 100 次
裸启动）得到的数字是 15–20 µs 一次（rows=1024/dim=64 时 0.019 ms 一次、
rows=4096/dim=64 时 0.011 ms 一次）——两种量法差了一个数量级，但都指向同一件事：
MUSA 的提交路径比 NVIDIA 贵一到两个数量级（CUDA 上是 2–5 µs），
所以本报告在 MUSA 上所有小 shape 的读数都是"发射受限"。

给调用方的结论：在 MUSA 3.1 上，图的正确用法是"把多节点录进一张普通的图"
（C 策略，8 个节点拿到 3.73x）；不要用单节点图逐次重放（B），更不要用
fork/join / child graph 拓扑（D，慢 2–16 倍）。NVIDIA 上恰好反过来（8.6 节：根节点
少、图内节点多是好事，但单节点图重放便宜）。

`--passes-per-graph K`（7.14 在 NVIDIA 上再拿到 1.18–1.21x）在 MUSA 上没有收益：
48 节点那张图 K=1 / K=2 的 C 列分别是 1.1299 / 1.1352 ms 每趟（0.99x 对 A），
因为 A 本身已经不再是"每趟一次提交"的瓶颈（48 次发射 1.12 ms，≈23 µs 一次），
而图重放的开销与节点数成正比。同一条优化，在一个平台上有效、在另一个平台上
恰好抵消，这是跨平台实测才能给出的一类结论。

| ----- | ---- | --- | ------- | ------- | ----- | ---------- | -------------- |
| 8192  | 64   | 256 | 4.3135  | 4.3141  | 1.00x | 62.2       | 8.0 MiB (61%)  |
| 8192  | 128  | 256 | 4.2959  | 4.3276  | 0.99x | 124.1      | 8.0 MiB (57%)  |

#### 7.15.10 MUSA 上还能优化什么（本轮实测给出的清单）

1. ~~量化内核：FP8 113 GB/s、INT4 183 GB/s，只有屋顶的 17–27%。~~ 已在
   7.15.14 做了一轮：只改默认几何 + 换一条取整指令，同一会话 A/B 下 10 个形状的
   几何均值快了 1.52x（dim=64 达到 2.55–2.83x），现在 FP8 是屋顶的 14–23%、INT4 是
   29–42%。仍然没有贴顶：编码器还是软件 E4M3（`mp_22` 没有硬件 `cvt`），
   dim=1024 的 FP8 只有 91.7 GB/s（13.7%），这是下一轮的第一顺位。
2. 发射开销：每次裸发射 ~120 µs。库内已经提供 `GraphSequence`，在 MUSA 上应按
   7.15.8 的规则用（多节点单图），而不是单节点图重放。
3. 中等规模的带宽余量：16384 行的读数只有屋顶的 49%（NVIDIA 上同一区间是 99–100%），
   说明网格/分块在这个区间还没有喂满访存；MUSA 上 rpb 是最有效的那把旋钮（7.15.4）。
4. `--mode advice` 的原地判据：现在只看"工作集 vs L2 容量"，也就是隐含假设
   "命中就能拿到平台的 L2 倍率"。这个假设本身没错，但倍率是平台相关的
   （同口径纯拷贝：NVIDIA ≈5.2–5.5x、S4000 ≈2.0x，见 7.15.3 的对照表与 7.15.6），所以同一句"RECOMMENDED"在两块卡上
   对应的收益差一倍。判据应当改用量到的倍率来换算收益。
5. bf16 打包算术：mp_22 上没有可用的 packed bf16 内建，`types.cuh` 展开成 fp32
   （结果正确，指令数翻倍）。在带宽受限区间无影响，在量化那一步可能是上面第 1 条的成因之一。

#### 7.15.11 顺带发现：同一台机器，两次会话差 25%

复核 CUDA 侧数据时发现，同一块 RTX 5060 Ti、同一份代码，不同会话的实测搬运带宽
差了约 25%（记录数据时 memcpy 380 GB/s，复核时 295–315 GB/s；GPU 无降频、无报错、
P1 状态、温度 56 ℃）。这不改变任何结论——本报告的所有结论都是"同一次运行内 kernel
与屋顶的比值"——但它说明跨会话比较绝对带宽是无效的，也说明"跑一次留个数字"
这种做法在共享桌面卡上不可靠。`--mode roof` 就是为了消除这个变量而加的。

#### 7.15.13 这一轮移植真正的产出：一个被隐藏的 UB

移植的价值不止"多一个平台"。7.15.2 里那份差异清单中，有一项直接导致了一个
真实 bug 的暴露：`kernel_gemm.cuh` 里一段严格别名违规（把一个 `uint4` 局部变量
按 `__half*` 读）在 nvcc 下恰好正确、在 mcc 下被优化成读陈旧数据，`k=128` 的
fp16 融合 GEMM 因此产出 `inf`。定位过程与修法见 5.9 节。

这类问题只有换编译器才会现形。它也是本项目"平台适配"这一项最实在的收获：
在第二块卡上把 781 项检查跑绿的过程中，修掉了原始平台上一直存在的一个 UB。

#### 7.15.14 第二轮：把量化内核从"屋顶的 17–27%"抬起来

7.15.10 的第 1 条把量化内核列为 MUSA 上最值钱的一块，这一轮就动它。没有改算法，
只动了两处：默认启动几何，和量化那一步的取整指令。所有对比都是同一个会话里交替跑
出来的（`data/musa/quant_ab.log`：改前默认 / 改后默认 / 改后强制旧几何 / 改前强制新几何
四组交叉），这样才是可比的——跨会话的绝对值会差 25%（7.15.11）。

（a）融合量化有自己的最优几何：8 线程/行、16 行/块

原来 `--mode quant` 用的是旋转内核的几何（32 线程/行、4 行/块，即 `QuantLauncher`
里的 `rpb = 4`）。在 MUSA 上把 `--tpr × --rpb` 的 150 组全扫了一遍
（`data/musa/quant_tune.log`），表里是每个形状相对扫描出的最好几何的倍率
（fp8 / int4 取较差者）：

| 几何                 | dim=64    | dim=128   | dim=256   | dim=512   | dim=1024  | 几何均值       | 最差    |
| ------------------ | --------- | --------- | --------- | --------- | --------- | ---------- | ----- |
| **tpr=8, rpb=16**  | **1.00x** | **1.00x** | **1.07x** | **1.07x** | **1.02x** | **1.016x** | 1.07x |
| tpr=16, rpb=16     | 1.00x     | 1.27x     | 1.01x     | 1.23x     | 1.02x     | 1.066x     | 1.27x |
| tpr=32, rpb=16     | 1.00x     | 1.27x     | 1.36x     | 1.06x     | 1.02x     | 1.101x     | 1.36x |
| tpr=32, rpb=4（旧默认） | 2.56x     | 1.87x     | 1.35x     | 1.05x     | 1.01x     | 1.429x     | 2.56x |
| tpr=32, rpb=2      | 5.00x     | 3.06x     | 1.77x     | 1.53x     | 1.26x     | 2.351x     | 5.00x |

（本小节的扫描日志 `data/musa/quant_tune.log` 打印的百分比以驱动报的 513 GB/s 为分母，
本报告统一换算成实测屋顶 671.3 GB/s——同一个读数 91.7 GB/s 在前者是 17.9%、在后者是
13.7%，见 7.15.3。）

规律和 7.15.4 是同一条、但方向相反：旋转内核在 MUSA 上要"每个 block 多领行"，
量化内核还要更进一步——每个 lane 少拿元素（8 个，正好是一次 128 位访存的宽度），
因为量化比旋转多了一步逐元素编码，寄存器压力和指令吞吐在这里才是瓶颈。于是把
`default_log_tpr_quant()`（8 线程/行）和 `default_rows_per_block_quant()`（16 行/块）
写进库里，作为融合量化的默认；同一个默认在两块卡上都不亏（见下面的 CUDA 复核）。

（b）量化那一步本身：一条取整指令 + 只舍入一次

两处都是位精确的改写，不是近似：

| 改动          | 原来                             | 现在                       | 依据                                                                  |
| ----------- | ------------------------------ | ------------------------ | ------------------------------------------------------------------- |
| int4 的取整    | `(int)rintf(v)`                | `__float2int_rn(v)`      | 值已被夹到 `[-(qmax+1), qmax]`，两者逐位相同；MUSA 的头文件把 `rintf` 标为 *slow round* |
| 融合内核的存储类型舍入 | amax 循环舍入 2 次/元素 + 打包循环再舍入 1 次 | 舍入一次存进 `rv[]`，amax 与打包共用 | `Acc::to_float2()` 一条指令取回两半，省掉 2 次 fp32→fp16→fp32 往返                |

（c）结果（同一会话 A/B，10 个形状）

| 拆解                    | 几何均值                       | 范围            |
| --------------------- | -------------------------- | ------------- |
| 只改几何（同代码，32/4 → 8/16） | **0.711x**（即 1.41x 加速）     | 0.391x–1.018x |
| 只改代码（同几何 32/4）        | **0.941x**（即 1.06x 加速）     | 0.850x–1.008x |
| 两处一起（旧默认 → 新默认）       | **0.656x**（即 **1.52x** 加速） | 0.354x–1.021x |

逐形状（融合内核 ms，rows=262144、f16）：

| dim  | fp8 改前 → 改后                | int4 改前 → 改后               |
| ---- | -------------------------- | -------------------------- |
| 64   | 0.9610 → **0.3773（2.55x）** | 0.6014 → **0.2127（2.83x）** |
| 128  | 1.1164 → **0.6595（1.69x）** | 0.7054 → **0.3196（2.21x）** |
| 256  | 1.5726 → 1.3970（1.13x）     | 1.0211 → **0.5992（1.70x）** |
| 512  | 2.7209 → 2.7778（0.98x）     | 1.6146 → 1.4654（1.10x）     |
| 1024 | 9.1652 → 8.7813（1.04x）     | 3.2321 → 2.7753（1.16x）     |

融合相对非融合的加速比也跟着涨（`docs/结果表格_MUSA.md` 第 5 节）：dim=64 的
FP8 从 2.09x 到 5.33x、INT4 从 2.28x 到 6.11x；dim=256 的 INT4 从 1.62x
到 2.63x。dim=512/1024 基本不动，因为那两个形状本来就被 `dispatch_quant_dim`
固定成 32 线程/行的特化（几何没得选），只剩代码改动的那 1.0–1.16x。

（d）CUDA 侧复核：同一改动在那里是中性偏正的

同一台 5060 Ti、同一会话、两个二进制交替跑（`data/quant_ab_cuda.log`）：

| dim  | fp8 改后/改前  | int4 改后/改前 |
| ---- | ---------- | ---------- |
| 64   | **0.880x** | **0.835x** |
| 128  | 1.010x     | 0.965x     |
| 256  | 0.983x     | 1.011x     |
| 512  | 0.991x     | 0.997x     |
| 1024 | 0.997x     | 0.991x     |

几何均值 0.964x（快 3.6%）。CUDA 上这个内核本来就在实测 memcpy 的 99–100%
（7.2 节），所以"几何"在那儿没有腾挪空间——几何敏感性是 MUSA 特有的，
把默认值改过去的代价是 dim=128/256 上各 1% 左右，收益是 dim=64 上的 12–17%。

（e）正确性

改动是位精确的，所以判据很硬：`test_fusion`（融合 == "先旋转再量化"，逐位）
在两块卡上都全过，MUSA 上 781 项回归重跑仍是 0 失败
（`data/musa/final_tests3.log`）。CUDA 侧 `test_correctness` 560 项 + `test_fusion`
132 项同样全过。

（f）这一轮的边界

* 编码器仍然是纯软件 E4M3（`mp_22` 没有 `sm_89` 那种硬件 `cvt`），FP8 路径的
  每元素成本没变；把它向量化或改成分支更少的实现是下一轮的第一顺位。
* dim=1024 的 FP8 只有 91.7 GB/s（屋顶的 13.7%）——`dispatch_quant_dim` 把它
  锁在 32 线程/行，每个 lane 要处理 32 个元素（16 个寄存器对），寄存器压力已经很大。
* FP8 的有效带宽（133–153 GB/s）仍然低于 INT4（197–280 GB/s），差距来自
  "写 1 B/元素"与"写 0.5 B/元素"之外的那部分固定成本。

#### 7.15.15 收尾复核时抓到的一个偶发失败：默认流和自建流之间没有隐式同步

把五个套件连续跑（前一个套件的进程退出后紧接着下一个）时，`test_graph` 会偶发一条
失败：`a repeats=3 graph equals three chained direct launches`；同一份二进制单独跑 2/2
通过，整套连跑 2/2 失败（`data/musa/final_rerun.log`、`final_rerun2.log`）。

给这条断言加上逐元素位模式诊断（原始输出 `data/musa/dbg_run.log`）之后，现象很干净：
`twice` 全是 NaN（`scale=1.0` 是 raw 变换，走两趟就溢出 fp16），而 `z` 全是 `0x0000`——也就是 x→z 那次重放的结果没留下，
留在地板上的是 memset 的零。问题不在图，在流：

```cpp
cudaMemset(z, 0, bytes);      // 默认流（legacy）
cache.launch(x, z, ...);      // 内部用的是 cudaStreamCreate 建出来的流
```

CUDA 的 legacy 默认流会和所有阻塞流做隐式同步，所以这条写法在 5060 Ti 上一直是对的；
MUSA 3.1 上不是——memset 落到了重放之后，`z` 被清成了 0。把清零点挪到同一条流上
（`cudaMemsetAsync(z, 0, bytes, cache.stream())` 再同步）之后，同一套连跑 3/3 全绿
（`data/musa/dbg_fix.log`），随后整套 781 项连跑两遍全绿
（`data/musa/final_tests4.log`：380 + 132 + 2 + 143 + 124 = 781 项，两遍都是 0 失败）。

两点值得记下来：

* 这是测试写法的问题，不是库的问题——库内所有入口都用调用方传进来的流，从不自己
  使用默认流。但结论对使用者成立：在 MUSA 上不要把 NULL 流当作隐式同步点。这条已经
  并进 `docs/国产平台适配.md` 8.2 的差异清单（第 6 条）。
* 那条断言本身也偏脆：`scale=1.0` 是 raw 变换，1 趟和 3 趟的结果都只剩 NaN，比的是溢出
  之后的位模式。改完仍然是逐位 memcmp，只是不再依赖跨流顺序。

同一份改动在 CUDA 上重编重跑 `test_graph` 是 158 项 0 失败（CUDA 侧不跳过图边查询与
32 MiB L2 那几条），所以这条修法两边都成立。

## 8. Nsight 剖析

原始输出与摘要见 `docs/profile/`（`README.md` 为摘要，`*.txt` 为 `nsys stats` 原始报告，
`*.nsys-rep` 为可在 Nsight Systems GUI 中打开的时间线）。

### 8.1 内核时间线：几乎没有空隙

| 用例             | 内核                | 启动次数 | 中位时长     | 相邻内核中位间隔 | 间隔 / 时长   |
| -------------- | ----------------- | ---- | -------- | -------- | --------- |
| dim256_dram    | `fhwt_reg_kernel` | 60   | 689.2 µs | 2.40 µs  | **0.35%** |
| dim1024_dram   | `fhwt_reg_kernel` | 60   | 698.6 µs | 2.62 µs  | **0.38%** |
| dim256_tc      | `fhwt_tc_kernel`  | 60   | 690.1 µs | 2.26 µs  | **0.33%** |
| dim256_inplace | `fhwt_reg_kernel` | 60   | 78.6 µs  | 2.48 µs  | 3.16%     |
| dim256_l2      | `fhwt_reg_kernel` | 60   | 19.4 µs  | 2.88 µs  | 14.88%    |

稳态下 GPU 在内核之间几乎没有空隙（0.33–0.38%），说明瓶颈完全在内核内部，
不存在启动开销、同步或流水线气泡问题。这也排除了"多 launch 一个 kernel 就能更快"
的可能性——每次调用只有一个内核。

注意最后两行的对比本身就是证据：dim256_l2 的内核只有 19.4 µs，此时 2.88 µs 的
启动间隔已经占到时长的 14.88%——当内核短到几十微秒时，主机侧开销才变得不可忽略。
这解释了为什么小规模（rows ≤ 4096）的测量值总是偏低。

### 8.2 网格几何与资源占用

| 用例               | grid  | block | 动态共享内存 |
| ---------------- | ----- | ----- | ------ |
| dim256_dram（reg） | 65536 | 128   | **0**  |
| dim256_tc        | 32768 | 256   | 4 KB   |
| dim256 融合量化      | 65536 | 128   | **0**  |

寄存器主线确实一个字节的共享内存都没用——这是设计目标之一，nsys 数据直接证实。

### 8.3 融合量化：少一次内核、少一个中间张量

| 内核                             | 中位时长         |
| ------------------------------ | ------------ |
| `fhwt_reg_kernel`（未融合的 rotate） | 689.7 µs     |
| `quantize_rows_kernel`（未融合的量化） | 506.4 µs     |
| **`fhwt_quant_kernel`（融合）**    | **505.2 µs** |

未融合 = 689.7 + 506.4 = 1196.1 µs，融合 = 505.2 µs，比值 2.37x，
与 7.7 节的 2.39x 一致。融合内核的耗时几乎正好等于"独立量化"那一步——因为
融合把旋转的写回与量化的读入合并掉了，只剩下一次读 + 一次低比特写。

### 8.4 ncu：从拿不到计数器，到「DRAM 87–93% / SM 20–24%」

一开始 Nsight Compute 在这台机器上根本用不了：

```
ncu --metrics gpu__time_duration.sum --launch-count 1 ./fhwt.exe ...
==ERROR== ERR_NVGPUCTRPERM - The user does not have permission to access
          NVIDIA GPU Performance Counters on the target device 0.
```

当时的记录写的是「当前用户不是管理员」，后来查清这句话不准确，而且注册表那条路
也不是写完就生效：

* 该账户本来就在管理员组里，只是 shell 用的是 UAC 过滤后的普通令牌
  （`whoami /groups` 里 BUILTIN\Administrators 标着 "Group used for deny only"）——
  问题不是「没有权限」，而是「没有提权」；
* 把 `HKLM\...\Nvtweak\RmProfilingAdminOnly` 置 0 是必要不充分的：驱动在加载时
  读这个值，写完必须重启才生效。所以置 0 之后立刻重试仍然报同一个错。

生效路径两条，任选其一：管理员窗口里直接跑采集脚本（本次数据就是这样采的），
或者置 0 后重启。采集脚本是 `scripts/collect_ncu.ps1`（6 条用例，形状与 nsys 那一批逐字相同，
先做权限自检，拿不到权限就直接停下）。

结果（RTX 5060 Ti，ncu 2025.2.0，原始输出 `docs/profile/ncu/*.txt`）：

| 用例               | 内核    | 寄存器/线程 | DRAM 吞吐   | SM 吞吐 | L1/TEX | 占用率       | No Eligible | 主 stall                   | 时长       |
| ---------------- | ----- | ------ | --------- | ----- | ------ | --------- | ----------- | ------------------------- | -------- |
| `dim256_dram`    | reg   | 27     | **88.5%** | 22.0% | 21.1%  | 86.4%     | 87.2%       | Long Scoreboard 90.9%     | 640.3 µs |
| `dim1024_dram`   | reg   | 48     | **86.8%** | 20.1% | 23.6%  | 71.7%     | 89.6%       | **MIO Throttle 55.6%**    | 676.3 µs |
| `dim256_tc`      | tc    | 32     | **88.4%** | 24.0% | 27.4%  | 80.7%     | 82.6%       | Long Scoreboard 90.3%     | 641.8 µs |
| `quant_fp8_256`  | quant | 58     | **90.1%** | 24.0% | 26.0%  | **57.9%** | 74.2%       | Long Sb 66.4% + MIO 11.0% | 497.6 µs |
| `dim256_inplace` | reg   | 27     | 90.8%     | 31.3% | 24.7%  | 66.3%     | 81.3%       | Long Scoreboard 92.9%     | 116.3 µs |
| `dim256_l2`      | reg   | 27     | 93.2%     | 41.9% | 43.5%  | 82.2%     | 80.8%       | Long Scoreboard 88.7%     | 43.3 µs  |

（表中百分比一律四舍五入到一位小数，如 `dim256_inplace` 的 SM 吞吐原始值 31.25% 写作 31.3%；
未取整的读数在 `docs/profile/ncu/汇总.md` 与原始 `*.txt` 里。）

三条读数最要紧：

1. 算力只用了 20–24%，内存用了 87–93%。 这是「加算力没有用」最直接的证据，
   也把 7.3 节 Tensor Core 的结论从「我们实现得不够快」升级成物理结论。
2. TC 与寄存器路径在计数器上同构：DRAM 88.4% vs 88.5%、SM 24.0% vs 22.0%、
   时长 641.8 vs 640.3 µs（比值 1.002，端到端测到的是 0.99–1.02x，两个口径对上了），
   但 L1/TEX 吞吐 27.4% vs 21.1%（+30%） —— TC 每个 radix-16 阶段多做的
   共享内存 gather/scatter 是真实存在的开销，只是被 DRAM 瓶颈掩盖了。
3. stall 的绝对主因是 `Long Scoreboard`（88.7–92.9%），配合 No Eligible 74–90%
   （调度器绝大多数周期没有能发射的 warp），是教科书式的访存延迟受限画像。
   唯一例外是 `dim1024_dram`：head_dim 变大后 48 寄存器/线程、占用率掉到 71.7%，
   主 stall 换成 `MIO Throttle`（55.6%）——这解释了 7.2 节里 dim=1024 档位吞吐略低
   （378 vs 392 GB/s）不是带宽不够，而是指令队列跟不上。
   另外 `quant_fp8_256` 的 DRAM 90.1% 是全组最高、占用率 57.9% 是全组最低：
   融合量化已经把带宽兑现到极限，剩下的空间在寄存器压力上（与 10.1 节一致）。

与 nsys 的交叉验证。 ncu 在重放前会清空缓存，所以「靠缓存驻留挣钱」的用例
在 ncu 里会变慢 —— 这不是误差，是一组现成的对照实验：

| 用例                                                             | nsys 中位时长                        | ncu 时长                           | ncu / nsys                    |
| -------------------------------------------------------------- | -------------------------------- | -------------------------------- | ----------------------------- |
| `dim256_dram` / `dim1024_dram` / `dim256_tc` / `quant_fp8_256` | 689.2 / 698.6 / 690.1 / 505.2 µs | 640.3 / 676.3 / 641.8 / 497.6 µs | **0.93 / 0.97 / 0.93 / 0.98** |
| `dim256_inplace`                                               | 78.6 µs                          | 116.3 µs                         | **1.48**                      |
| `dim256_l2`                                                    | 19.4 µs                          | 43.3 µs                          | **2.24**                      |

四个 DRAM 受限用例两个工具互相印证（0.93–0.98，偏快来自 ncu 重放时时钟稳定、
没有桌面负载抢 DRAM），两个缓存型用例的读数就回落了。这反过来证明 7.8 节的原地变换
2.12–2.18x 与 L2 驻留区的 1720 GB/s 确实来自缓存驻留，而不是测量口径。

逐条读数、stall 分布与全部原始 sections 见 `docs/profile/ncu/README.md`。

### 8.5 小内核：发射受限，以及 CUDA Graph 为什么是这里唯一还剩下的优化

8.1 节末尾留了一个伏笔：内核只有几十微秒时，2.4 µs 的启动间隔已经占到时长的 15%。
把规模再往下一档（dim 128 / rows 4096，内核只有 2.6 µs），这个效应就完全主导了测量。

现象。 这个 shape 的读数极不稳定——不稳定本身就是这里最重要的观测。
同一套参数、同一台机器，隔一段时间再测，连趋势都会变：

| iters | 第一次测量                          | 第二次测量（稍后，桌面负载不同）    |
| ----- | ------------------------------ | ------------------- |
| 20    | 0.0150–0.0157 ms（133–140 GB/s） | 0.0117 ms（179 GB/s） |
| 200   | 0.0325–0.0348 ms（60 GB/s）      | 0.0071 ms（295 GB/s） |
| 2000  | 0.0352–0.0369 ms（57–60 GB/s）   | 0.0114 ms（185 GB/s） |
| 20000 | 0.0361–0.0380 ms（55 GB/s）      | 0.0071 ms（297 GB/s） |

第一次测量里"`--iters` 越大越慢"，第二次测量里这个规律消失了（而且同一套参数
`--iters 2000` 连跑三次可以读到 294 / 180 / 174 GB/s）。也就是说，在这个规模上调参
是没有意义的：读数由测量时机器在做什么决定，而不是由参数决定。
（旁证：整个调查期间，`--mode info` 的 512 MiB D2D memcpy 探针读到过 380 GB/s，
也读到过 91 GB/s——后者说明确有其它 GPU 工作在同一块卡上抢带宽。）

那内核到底有多快？下面这张表才是能复现的部分。

根因：从 nsys 的 sqlite 导出逐内核 start/end。 对 dim 128 / rows 4096 抓两次剖面
（`--iters 20` 与 `--iters 2000`），把 `CUPTI_ACTIVITY_KIND_KERNEL` 与
`CUPTI_ACTIVITY_KIND_RUNTIME` 按 correlationId 对齐后：

| 量                       | `small_iters20` | `small_iters2000` |
| ----------------------- | --------------- | ----------------- |
| 内核个数（含 warmup）          | 70              | 2050              |
| 内核中位时长                  | **2.59 µs**     | **2.59 µs**       |
| 内核合计时长                  | 0.187 ms        | 5.87 ms           |
| 捕获窗口                    | 2.31 ms         | 82.0 ms           |
| **GPU 忙占比**             | **8.1%**        | **7.2%**          |
| 相邻内核间隔中位数               | 1.54 µs         | 1.54 µs           |
| 相邻内核间隔**均值**            | **30.8 µs**     | **37.1 µs**       |
| 相邻内核间隔最大值               | 596 µs          | 3413 µs           |
| `cudaLaunchKernel` 中位耗时 | 6.66 µs         | 8.11 µs           |
| `cudaLaunchKernel` 最大耗时 | 13.7 ms         | 18.2 ms           |

（原始剖面与生成脚本：`docs/profile/small_iters20.nsys-rep`、`small_iters2000.nsys-rep`、
`docs/profile/launch_bound_analysis.md`、`tools/gap_analysis.py`。）

两个结论可以直接从表里读出来：

1. 内核本身没有变慢。 两种 `iters` 下内核中位时长都是 2.59 µs，对应
   `2 MiB / 2.59 µs ≈ 810 GB/s`（张量 1 MiB；读 + 写 2 MiB，全部驻留 L2）。也就是说被测窗口里
   GPU 只有 8% 的时间在跑内核，其余 92% 在等提交。
2. 间隔分布是双峰的。 中位数 1.54 µs（下一条命令已经在驱动里），均值却是 31–37 µs
   ——少数间隔落在几百微秒到几毫秒，均值被这一小撮完全支配。窗口越长、机器越忙，
   撞上这些停顿的次数就越多，这就是上面读数大幅浮动（且两次测量趋势不同）的原因。

把 `--warmup` 从 10 加到 500 不改变结果，所以这不是预热不足；它是 Windows/WDDM 下
小内核提交路径的固有代价（本机 GPU 同时要驱动桌面，存在其它 GPU 上下文）。

处置：`--graph`。 用 `cudaStreamBeginCapture` 把整段 burst 录成一张图，计时窗口里
就只剩一次 `cudaGraphLaunch`。`--iters` 按规模选取，使每个 burst 的墙钟时长都落在
20–40 ms 量级（避免"长 burst 更容易被桌面负载污染"这个混杂因素），raw / graph 各取
5 次最快（`tools/bench_graph.py`）：

| rows   | dim | 张量      | 裸启动                     | CUDA Graph                  | 加速比       |
| ------ | --- | ------- | ----------------------- | --------------------------- | --------- |
| 1024   | 64  | 0.1 MiB | 0.0064 ms / 41.1 GB/s   | 0.0012 ms / **227.2 GB/s**  | **5.33x** |
| 4096   | 128 | 1 MiB   | 0.0069 ms / 302.2 GB/s  | 0.0024 ms / **858.3 GB/s**  | **2.88x** |
| 16384  | 128 | 4 MiB   | 0.0111 ms / 754.1 GB/s  | 0.0075 ms / **1123.3 GB/s** | 1.48x     |
| 16384  | 256 | 8 MiB   | 0.0136 ms / 1231.1 GB/s | 0.0098 ms / **1719.6 GB/s** | 1.39x     |
| 65536  | 256 | 32 MiB  | 0.1787 ms / 375.5 GB/s  | 0.1797 ms / 373.5 GB/s      | 0.99x     |
| 131072 | 256 | 64 MiB  | 0.3599 ms / 372.9 GB/s  | 0.3612 ms / 371.6 GB/s      | 1.00x     |
| 262144 | 256 | 128 MiB | 0.7181 ms / 373.8 GB/s  | 0.7212 ms / 372.2 GB/s      | 1.00x     |

这张表回答了两个问题：

* DRAM 受限区（1.00x）：内核几百微秒，发射开销早就被淹没，CUDA Graph 无功可立。
  两边的 370–375 GB/s 也正是 `--mode info` 的 memcpy 上限。
* L2 驻留区（1.39–1.48x）：此前 7.2 节在这个区间量到的带宽，被发射开销系统性地
  低估了。移走发射开销后 dim 256 / rows 16384 打到 1719.6 GB/s——也就是说在这个
  区间内核同样已经到顶，"L2 区还有余量"是测量假象，不是内核余量。
  附带地，本机真实 L2 上限比 7.2 节用裸启动量到的 1658 GB/s 还要高一些。

一个必须说明的不稳定性。 表里 Graph 一侧是稳的（跨运行复现性好，是内核的真实速度），
裸启动一侧则随桌面负载大幅浮动：最小那个 shape 在不同时间的 best-of-N 读数在
7.6 与 41.1 GB/s 之间（对应加速比 28.8x 与 5.33x）——因为它量的是提交路径，
而提交路径正是被桌面负载影响的那一条。所以加速比一列应当读作"量级"而不是精确值：
小规模 5–29x，L2 区 ~1.4–1.6x，DRAM 区 1.00x。

真正剩下的空间在小规模那一端：`dim = 64/128` 恰好是 LLM 里 `head_dim` 最常见的取值，
此时一次变换的耗时由提交路径而不是内核决定。正确的方向因此是把旋转融进相邻算子
（GEMM 的 A/B 载入阶段）或者把多次旋转合并成一次提交，而不是继续雕琢内核指令。

### 8.6 一张图的两种形状：根节点个数才是那笔开销

7.11 的 D 策略在 nsys 里留下了直接的证据。先记一个工具上的坑：nsys 默认把一张 CUDA
Graph 当成一条记录，所以用默认粒度抓的那一段（`docs/profile/loop_forkjoin.txt` /
`loop_forkjoin.nsys-rep`）里只有 184 条内核记录、全是策略 A 的，C 与 D 完全看不见。
要看图内部必须加 `--cuda-graph-trace=node`。加上之后重抓的命令是

```
nsys profile --force-overwrite true --cuda-event-trace=false --cuda-graph-trace=node \
    -o p_nodes_all -- .\build\fhwt.exe --mode loop --rows 512 --dims 128 \
       --layers 8 --iters 20 --reps 3
```

原始输出见 `docs/profile/loop_forkjoin_nodes.txt`，时间线
`loop_forkjoin_nodes_multiroot.nsys-rep`；把最后一条命令再加一个 `--serial-entry`
就得到单根的那一份，存为 `loop_forkjoin_nodes_singleroot.nsys-rep`。

内核侧：两种形状逐条相同。 两次采集都只有一种内核，
`fhwt_reg_kernel<f16, Native2, 7, 5>`，各 2016 条，中位都是 992 ns
（全根：最小 896 / 最大 2080 ns；单根：最小 832 / 最大 3488 ns）。fork/join 图里的
内核与串行链里的内核是同一批、同样快，所以 C 与 D 的差别不可能在内核侧——这既是 8.5 节
「发射受限」的直接测量，也是 5.8 节判定那笔开销来自主机侧的依据。

主机侧：怎么把 C 和 D 分开。 `--mode loop` 按 A、B、C、D 的顺序各跑 `--reps` 轮；
`cudaGraphLaunch` 的 correlation id 上挂着几个内核是已知的（B 的单步图 = 1 个，
C 与 D = 8 个），据此可以把最后 120 次 8 节点重放切成 C（每轮 20 次 ×3）与 D（同样）。
于是 `cudaGraphLaunch` 自身的耗时可以分开统计：

| 组                  | 次数  | p50                       | p90       | 最大         |
| ------------------ | --- | ------------------------- | --------- | ---------- |
| B 单步图              | 504 | 4.9 µs                    | 8.5       | 116 µs     |
| C 8 节点串行链（全根那次采集）  | 60  | 9.9 / 10.0 / 9.9 µs       | 10.5–12.7 | 23 µs      |
| **D 8 节点分叉图，8 个根** | 60  | **35.5 / 58.3 / 35.0 µs** | 67–122    | **295 µs** |
| C 8 节点串行链（单根那次采集）  | 60  | 10.0 / 9.8 / 9.8 µs       | 18.9–21.9 | 29 µs      |
| **D 8 节点分叉图，1 个根** | 60  | **11.7 / 12.0 / 11.6 µs** | 19.4–26.6 | 58.5 µs    |

（斜杠分隔的三个数是三次 `--reps` 各自的读数。）

C 是这两次采集之间的内部对照：它不调用 `add_parallel()`，`--serial-entry` 不可能
影响它，而它在两次采集里都落在 9.8–10.2 µs——是同一个数。D 则差 3 倍：8 个根时中位
35–58 µs、最坏 295 µs，1 个根时 11.7–12.0 µs、最坏 58.5 µs。同一批节点、同一批内核、
同一个驱动、同一条流，唯一的差别是根节点的个数。

再往细看，两列的形状也不同：全根那一列 60 次重放的最小值是 33.2 µs、p90 到 122 µs，
而且三轮之间会跳（35.5 → 58.3 → 35.0 µs）；单根那一列是 9.6–58.5 µs、p90 只有
19–27 µs，三轮之间是平的（11.7 → 12.0 → 11.6 µs）。

这就是 5.8 的全部机制：不是 fork/join 的形状贵，也不是
`cudaGraphAddChildGraphNode`（5.8 把每个节点都换成真正的 kernel node，数字没动），
而是图里有多少个根节点在 Windows/WDDM 上决定了每次重放的提交代价。它不影响交付的
结论（DRAM 受限时三种形状本来就无差别），但它把 5.8 那条「没查清」的尾巴补上了。

一个环境上的小技巧，值得记下来：本项目的路径含中文，`nsys` 在
`Agent.ConfigureRequest` 里传 `working_directory` / `output_path` 时会因 protobuf
要求 UTF-8 而失败（`Message parsing failed`）。用目录联接做一个纯 ASCII 别名
（`mklink /J C:\fhwt "D:\…\cuda项目_XLD"`）、在该别名目录下运行 `nsys`，即可绕开；
文件仍是同一份，不需要复制任何东西。

## 9. 结论

1. 这个算子是纯带宽受限的，而且已经打到了物理上限。
   DRAM 受限区间稳定在 378–392 GB/s = 理论峰值的 84–87%、实测 memcpy 的 99–100%。
   与 `fast_hadamard_transform` 在这一区间完全打平（1.00x）——不是我们没优化好，
   而是两者都已经到达天花板。

2. Tensor Core 在这个算子上没有收益。
   DRAM 受限区间与寄存器路径打平（0.99–1.02x），L2 驻留区间反而更慢（0.34–0.86x）。
   原因是执行/运算比 `2d/log2(d)`（d=256 时 64x）——MMA 的算力无处可花，而块对角
   结构迫使每个 radix-16 阶段多一次共享内存 gather/scatter。这与 HadaCore
   1.0–1.4x 的实测一致。

3. 真正有效的优化在"访存量"和"工作集"上，不在算力上。

   | 手段  | 收益  | 机制  |
   | --- | --- | --- |

| 融合量化 | **2.38–5.09x** | 7 / 6.5 B/elem → 3 / 2.5 B/elem |
   | 原地变换 | **2.12–2.18x**（工作集 = L2 时） | 工作集减半，留住 L2 |
   | 启动几何（小 dim） | **最高 6.7x** | 修正"一块一行"的占用率陷阱 |
   | Tensor Core | 1.00x（DRAM 区）/ 更差（L2 区） | 算力不是瓶颈 |
   | 图内 fork/join 并行 | 同层多张量 **1.01–2.23x**；层间**打平**（中位 1.10x） | 宽度必须落在同一层内部；多根图会先吃掉这笔收益 |
   | 一次提交覆盖多趟 | 在分组图之上再 **1.18–1.21x**（K≈5 饱和） | 消掉趟与趟之间 9.9 µs 的 GPU 空转；提交路径本身无批量折扣 |

4. 正确性有多重独立证据：976 项（CUDA；5.10 修复后复跑 1088 项）/ 781 项（MUSA）单元检查（对比 double
   精度 CPU 参考）、80 项与 `fast_hadamard_transform` 的逐元素比对、以及 fp32 累加下
   与其逐位相同的结果。

5. 精度与性能可以按需取舍：`--acc fp32` 在大 dim 上把 bf16 误差从 3.13e-2 降到
   1.95e-2，而这条路径不占用额外带宽（只影响寄存器内累加宽度），
   所以在大 `dim` 上应当默认开启。

6. 小规模是发射受限，不是内核慢；CUDA Graph 在这一端最高值 29x。
   dim 128 / rows 4096 的内核只有 2.59 µs（≈810 GB/s，读+写 2 MiB 全部驻留 L2），
   但裸启动的计时窗口里 GPU 只有 8% 的时间在跑内核。录成 CUDA Graph 后该配置从
   302.2 GB/s 升到 858.3 GB/s，L2 驻留区 +39%~48%，DRAM 受限区完全不受影响（1.00x）。
   因为 `head_dim = 64/128` 是 LLM 最常见的取值，这一步是纯内核优化之外唯一还有
   显著收益的方向（第 10.1 节的第 2、5 条已在本轮实现）。

7. 关键不是“用了图”，而是“一张图里装了多少个内核”。 服务场景下把整趟
   forward 的 32 层录成一张图，L2 驻留规模上单次变换从 6.1–6.7 µs 压到
   1.16–1.29 µs；而每次变换重放一张单节点图只有约 1.0x。
   收益正好等于省下的提交开销占比——工作集远超 L2 后内核算得够久，C 回落到 1.00x。
   这条差异直接决定了 API 的粒度（`fhwt::GraphSequence`，见 7.10 / 7.11）：把它误用成
   “每次变换一张图”会得到零收益。

8. 图内 fork/join 并行：真因是「图里有几个根节点」；层间打平，同层多张量才拿到收益。
   把每一层都声明成互不依赖（全根图）会让每次重放的 `cudaGraphLaunch` 从约 10 µs 涨到
   35–58 µs（最坏 295 µs），整趟比串行链慢 3–7 倍；只把第一层改成串行入口（单根）就回到
   串行链的水平——8 轮交替对照的中位数是 1.10x，最差 0.96x，量级上是打平。把每个节点从
   `cudaGraphAddChildGraphNode` 换成真 kernel node 之后数字毫无变化，所以这与子图内联
   无关（5.8 / 8.6）。这条也纠正了上一轮的写法：不是「fork/join 没有收益」，
   而是「不该造多根图」。7.13 又补了一刀：修好多根之后仍然只是打平，是因为 7.11
   那个场景里层与层之间本来就没有可用的宽度；把宽度换成同一层内的多个张量
   （`--tensors N` + `--group-entry`），同一套 `add_parallel()` 立刻给出
   1.01–2.23x（7 个 `tensors > 1` 的配置里 4 个 ≥ 1.0），峰值 0.550 µs/次。

9. 图上还能再压一层：一次提交覆盖多趟（`--passes-per-graph K`）。 批 K 趟再拿
   1.18–1.21x（D 分组每趟 28.9 → 23.8 µs），K ≈ 5 饱和，而饱和后的读数正好落在
   nsys 独立量到的同形状 GPU span 上（23.8 vs 24.96 µs）——K=1 时多出来的那 4 µs
   提交开销已经完全被摊掉。串行链不动（55.4 vs span 57.95 µs），因为它的每趟 GPU 工作本来
   就比提交长，不存在空转。机理是把 K=1 时 D 图上那 9.9 µs 的重放间空隙（C 只有
   3.5 µs）消掉；提交路径本身没有「批量折扣」（960 节点折算到每 48 节点反而更贵）。
   代价是建图 ≈6 µs/节点（960 节点 = 5.4–5.7 ms），要重放约 1100–1200 趟才回本；
   工作集大到每趟几百 µs 以上时收益归零。所以这是服务循环的优化（7.14）。

10. 同一份源码在国产卡（摩尔线程 MTT S4000 / MUSA 3.1）上跑通了，而且结论会变。
       781 项回归 0 失败；迁移不改写源码（`backend.cuh` 在包含层做映射）。但三条在 NVIDIA 上
       成立的结论在这块卡上不成立，而且原因都能指到具体的平台特性：

| 结论                | NVIDIA              | MTT S4000                      | 原因                                                  |
| ----------------- | ------------------- | ------------------------------ | --------------------------------------------------- |
| 内核打满带宽            | 实测 memcpy 的 99–100% | 实测屋顶的 **47–89%**（rows ≥ 65536） | MUSA 上中等规模还没喂满访存                                    |
| 原地变换 2.12–2.18x   | 成立                  | **1.10–1.17x，且窗口很窄**           | L2 倍率 4.4x（同口径纯拷贝 5.2–5.5x）→ 2.0x，L2 容量 32 → 24 MiB |
| CUDA Graph 是剩下的优化 | 小规模 5–29x           | **单节点图重放 0.09–0.39x**          | 图重放固定开销 ~0.24 ms                                    |
| 融合旋转进 GEMM        | 1.02–11.0x          | **0.97–1.03x**                 | 该卡手写 GEMM 只有 258–295 GFLOP/s，全程算力受限                 |
| 驱动报的理论带宽可作分母      | 可用（与实测吻合）           | **不可用**（512.8 < 实测 676–688）    | 加 `--mode roof` 用纯搬运内核量屋顶                           |

   而且这一轮移植修掉了一个真实 bug：`kernel_gemm.cuh` 里一处严格别名违规
   （nvcc 下恰好正确、mcc 下被优化成读陈旧数据，导致 `k=128` fp16 融合 GEMM 产出 `inf`），
   详见 5.9 节。换编译器是发现 UB 最便宜的手段。

## 10. 未来工作

### 10.1 可继续优化的方向

1. 端到端融合。 目前融合了"旋转 + 量化"，下一步是把旋转直接吞进消费它的 GEMM
   的 A/B 载入阶段（QuaRot 的旋转在权重侧可以离线吸收；激活侧则可以在加载 tile 时
   顺势旋转），做到旋转零额外访存。SAW-INT4（arXiv 2604.19157）报告的
   "零开销旋转"就是这个形态。

2. 原地变换的自动选择 —— 本轮已完成。 已实现 `fhwt::inplace_pays_off()`（判据
   `footprint ≤ L2 && 2·footprint > L2`），并与 `data/inplace.csv` 的 12 个测点逐点核对，见 7.10。
   仍可继续的是策略覆盖面：目前只按“单张量连续布局”判断，真实模型里
   `[batch, heads, seq, dim]` 的转置 / 切片视图能否原地，还需要一层 alias 检查。

3. 小 dim 的合并访存。 `dim = 64` 时一行只有 128 字节，一个 128-bit 访存只覆盖
   8 个元素。可以考虑让一个线程处理两行的同一段，把访存粒度从 128-bit 提到
   256-bit 级别（在支持的前提下）。

4. `dim` 非 2 的幂。 当前要求 `dim` 是 2 的幂。真实模型里偶见 `head_dim = 96 / 192`，
   但这里要修正一个我们自己写过的想法：并不存在“radix-3 快速变换”——
   快速蝶形依赖 Sylvester 结构 `H_2^{⊗k}`，而 96 = 2^5·3 不是 2 的幂，它的
   Hadamard 矩阵（如 Paley 构造）虽然存在，却没有对应的快速分解，
   不能拆成 `H_96 = H_32 ⊗ H_3`。所以对这类 `head_dim` 的可行做法是
   pad 到下一个 2 的幂（零填充后旋转，再截回），或者在模型侧直接
   避免这种 `head_dim`。这一点我们在实现前发现并放弃了原计划。

5. 把 CUDA Graph 从"计时开关"变成"执行路径" —— 本轮已完成。 `--graph` 已改走
   `fhwt::Graph`，并新增了 `fhwt::GraphSequence`（把整趟 forward 录成一张图）。
   这里记录一次自己的纠正： 我们最初实现的是一个“按 shape 缓存单步图”的
   `GraphCache`，但实测（7.11 策略 B）显示单节点图与直接启动等价（0.73–1.11x，中位 1.01），
   于是改为按“整趟 forward”粒度捕获。仍未做的是按 shape 组合缓存
   `cudaGraphExec_t` 的注册表：现在需要调用方自己保持 `GraphSequence` 对象。
   它与第 1 条的端到端融合互补（融合消除这次访存，图消除这次提交）。

6. 图内并行度 —— 本轮已闭环：真因是「图里有几个根节点」，不是 fork/join 本身。
   `GraphSequence::add_parallel()` 把步骤声明成互不依赖，`record()` 相应产出 fork/join 图
   （7.10）。实测（7.11 的 D 列）全部层都用 `add_parallel()` 时没有收益，L2 驻留规模
   上每趟是 C 的 3–7 倍。这里记录一次自己的纠错：上一轮把嫌疑放在
   `cudaGraphAddChildGraphNode`（子图内联）上，并写下了「下一步该做的实验是用
   `cudaGraphAddKernelNode` 建真 kernel node」。这一步做完了，假设被推翻：所有节点
   换成真正的 kernel node 之后数字毫无变化。真因是根节点个数——全根图每次重放的
   `cudaGraphLaunch` 中位 35–58 µs，只让第一层走 `add()` 变成单根后回落到
   11.7–12.0 µs，而同一张图的这几种形状内核逐条相同（8.6 节的节点级剖析）。
   修好之后 fork/join 也只是打平（8 轮交替对照中位 1.10x），因为这一档本来就只有
   ~1 µs 的内核、约 8% 的 GPU 忙占比。当时留下的两条"别的形状"本轮都做了，结论一正一负
   （7.13）： `--tensors N` + `--group-entry` 让同一层的 N 个张量（Q / K / V 各自的旋转）
   并成一个分叉组，7 个 `tensors > 1` 的配置里 4 个拿到 1.01–2.23x，峰值
   0.550 µs/次（rows 512、8 层 × 12 张量、96 节点）；另外 3 个（0.92–0.99x）都在
   工作集 ≥ 4096 rows 的档位。多流（`--streams N`，策略 E）则是负结果：
   0.07–0.98x vs C，因为在 48 个节点那一档，流只搬运提交、不减少提交。余下的两件是
   「多流与图混用」（目前 E 是纯裸启动，没有 `Graph` 版本）和跨层的真实依赖形状
   （7.13 的层间仍是无依赖的合成假设，见 10.2）。

7. 一张图里装几趟 —— 本轮已完成（7.14）。 `--passes-per-graph K` 把 K 趟旋转换成一次
   提交，在分组图之上再拿 1.18–1.21x（每趟 28.9 → 23.8 µs），K ≈ 5 饱和，而饱和值正好
   落在 nsys 独立量到的同形状 GPU span 上（24.96 µs）。仍余下两件：(a) K 的最优取值应该由库来
   选——它取决于「每趟的 GPU 时间 / 一次提交的开销」这个比值，而这两者 `--mode advice`
   与 `--mode loop` 都已经能测出来，目前却仍要调用方自己算；(b) 多流与图混用：策略 E
   至今是纯裸启动，没有 `Graph` 版本，而"每层一个分叉组 + 多条流"这种混合形状没有测过
   （7.13 只测了「图 + 单流」与「裸启动 + 多流」两个角）。

8. 要真正用上 Tensor Core，得把 radix-16 阶段的共享内存 gather/scatter 消掉。
   本项目的 TC 路径每级都要把 16 点变换的成员从共享内存里 gather 成 fragment、算完
   再 scatter 回去（3.3 节），这正是 HadaCore 点名的主要开销，也是它在 L2 驻留区反而
   比寄存器路径慢的原因。把这一进一出改成寄存器内/warp shuffle 完成（`ldmatrix`
   只接受固定布局，所以需要自己设计置换）能提高 TC 路径本身的效率；但第 9 节已经
   说明这个算子执行/运算比高、算力不是瓶颈，所以上限是打平而不是超过寄存器路径
   （HadaCore 自己也只报 1.0–1.4x）。属于"可以做，但期望收益有限"。

### 10.2 未完成与局限

* 国产平台已经实测（7.15），但"跑通"不等于"跑好"。 MTT S4000 上 781 项回归全绿、
  全量性能与图实验都重做了（`data/musa/`、`docs/结果表格_MUSA.md`）。仍然存在的缺口：
  MUSA 上 Tensor Core 路径不可用（该工具链下没有 `mma.sync.m16n8k16`），
  所以 7.3 那组"TC vs 寄存器"对照无法在国产卡上复现；融合旋转进 GEMM 在 MUSA 上
  无收益（0.97–1.03x），因为那边的手写 SIMT GEMM 全程算力受限；MUSA 上量化内核
  已按 7.15.14 优化过一轮（几何 + 取整指令，几何均值 1.52x），但仍只有屋顶的
  14–42%——`mp_22` 没有硬件 E4M3 `cvt`，编码器是纯软件实现，dim=1024 的 FP8
  只有 91.7 GB/s，这是下一轮该动的地方。
  另外 `-arch=sm_80` 重编译（没有 sm_89 的 FP8 `cvt`）后完整测试套件仍全部通过
  （用当前源码重编重跑：976 项、0 失败，`docs/portability_sm80.log` [5]），
  FP8 自动走软件回退分支（`docs/portability_sm80.log`）。
* 量化精度只在合成分布上验证过（7.7.1）。 旋转对 INT4 / FP8 误差的影响用 CPU 仿真在高斯、
  异常值通道、Student-t 三种输入上量过，没有在真实模型激活或端到端困惑度上验证。
* 7.15.8 里那四行 MUSA 的 A/B/C/D 读数没有原始文件。 `tools/bench_loop.py` 在这台
  机器上 8 个 shape 全部 `run failed`（`data/musa/sweep.log` 第 649–658 行），
  `data/musa/loop.csv` 只写了表头，`loop.log` / `loop_runs.log` 是空文件，所以那张表是
  手工运行的读数，本仓库无法复算。全文其余数字都能从 `data/` 里的文件重新生成
  （两份结果表格已用 `tools/analyze.py` / `tools/analyze_musa.py` 逐行校验：重新生成与
  入库版本 diff 为 0 行）。
* `-arch=sm_75` 无法编译，原因是 bf16 输入格式需要 sm_80 的原生 bf16 算术。
  这是输入格式的要求，不是算法的要求。
* ncu 计数器已经拿到（8.4 节）。此前记录的「权限不足」是判断错误：账户本就在
  管理员组，需要的是提权；而注册表置 0 那条路必须重启才生效。仍没做的是
  国产平台上的计数器级采集——MUSA 侧没有与 ncu 对应的公开硬件计数器工具，
  所以 7.15 的 MUSA 剖析仍然只有时间线一级的证据，这是两边的证据强度不对等的地方。
* 桌面负载造成的双状态读数：本机 GPU 同时驱动桌面（含一个持续渲染的动态壁纸）。
  同一份代码、同一套参数在 DRAM 受限区会读出 300–385 GB/s 两个状态；而同一时刻
  `--mode info` 的 D2D memcpy 探针稳定在 380 GB/s，说明 300 GB/s 那一侧是桌面负载
  抢占 DRAM/L2，不是内核问题。表中数字取 best-of-N，即机器让出的最好窗口。
* 小规模（rows ≤ 4096）的裸启动数据应视为下界：计时窗口里 92% 的时间在等提交。
  要量到内核的真实速度必须加 `--graph`（见 8.5 节）。同理，7.11 里 A 与 B 两列的
  绝对值在不同轮次之间会跳 3x 以上，只有 C 列可以当作稳定读数。
* fork/join 那笔固定开销是在本轮才查清的（5.8 / 8.6）。真因是图里的根节点
  个数：nsys 节点级剖析里同一张 8 节点图，8 个根时 `cudaGraphLaunch` 中位 35–58 µs
  （最坏 295 µs），1 个根时 11.7–12.0 µs（最坏 58.5 µs），而两次采集里 C 都是
  9.8–10.2 µs。仍然没有查清的是它为什么会发生：`cudaGraphLaunch` 内部的哪一步变慢，
  `cuda_api_trace` 只给到调用级，而 ncu 采的是内核计数器、回答不了主机侧 API 内部的
  实现细节（8.4 节），我们手里只有「与根节点
  个数强相关、且在同一张图上反复重放时会抖到 295 µs」这一层级的事实。多根图在这条
  驱动路径上走了另一次提交编排——这是推测，不是结论。
* 修好之后的收益也很小，不应夸大。 单根 fork/join 相对串行链的中点只有 1.10x，
  8 轮交替对照里有 3 轮落在 0.96–0.99x（5.8 节）。量级上是打平，而且它只在 L2 驻留的
  规模上才看得见（DRAM 受限时三种形状本来就是 0.98–1.01x）。
* 7.13 的「层间独立」仍然是合成假设。 `--mode loop` 里每层有自己的 buffer，所以层与
  层之间没有数据依赖；真实 forward 是链式的，能并行的是同层内的多个张量。7.13 量的
  正是后者（1.01–2.23x），但「层间真依赖 + 层内分叉」同时出现在一张图上的形状还没有做。
  另外 7.13 的收益只在 L2 驻留 / 发射受限档位成立，rows ≥ 4096 就落到 0.92–1.00x。
* 48 个节点时提交本身开始变贵，这是 7.13 顺带量到的。 同一次 nsys 采集里 1 节点的图
  `cudaGraphLaunch` 中位 5.2 µs，48 节点的图 39–51 µs：多 47 个节点贵约 35 µs
  （≈0.7 µs/节点，与 8.6 节的 8 节点 11.7–12.0 µs 吻合）。这份读数被 profiler 与桌面负载
  整体抬高（D 自己的整趟实测 28.9 µs 低于它的 39 µs 提交中位），因此可信的只有差值。
  这个"下一级"本轮做了（7.14）：批 K 趟进一张图再拿 1.17x（28.9 → 24.8 µs/趟，
  K≈10 饱和）。但它不是免费的：建图成本 ~6.7 µs/节点（960 节点 = 6.6 ms），按每趟
  省 4.1 µs 算要重放约 1600 趟才回本；而且提交路径本身没有批量折扣（960 节点折算
  到每 48 节点反而更贵），省下的是趟与趟之间那段 GPU 空转。所以它只适用于一张图反复
  重放的服务循环，对一次性调用是净亏。
* `--mode advice` 的原地判据是"容量型"的，在 MUSA 上会误判。 库内判断"原地是否值得"
  用的是工作集 vs L2 容量（`inplace_pays_off()`），这个判据隐含假设"命中 L2 就能换到更高
  带宽"。RTX 5060 Ti 上成立（L2 驻留 1658 GB/s vs DRAM 380），MTT S4000 上不成立
  （7.15.3：同一份拷贝放进 L2 反而更慢），于是同一份建议会在国产卡上给出错误的
  "RECOMMENDED"。正确的修法是让判据使用实测的 L2 带宽倍率（`--mode roof` 已经把这个
  数测出来了），本轮只把数据补上，判据本身留到下一轮。
* `tools/analyze.py` 在本轮被误清空过一次。它是纯派生工具（输入 `data/*.csv`、
  输出 `docs/结果表格.md`），本轮从会话记录重建并逐行校验：重建版与原版在第 1–224 行
  完全一致（section 0–8），其后的差异都是本轮新增的 D 列与第 10 节。教训很直接：
  这个目录不是 git 仓库，不要用"先截断再读"的方式改写文件
  （`io.open(p, "w")` 会立刻清空目标）。

## 11. 复现方式

```powershell
# 0. 代码格式（可复现，不依赖本机的 ~/.clang-format）
#    clang-format -i <src/ include/ tests/ 下的 .cu .cuh .h>
#    配置见仓库根目录 .clang-format；本次用的是 clang-format 23.1.1，格式化后再跑一次
#    无差异（幂等），且 19 个文件逐个做了"去注释去空白后 token 完全相同"的校验。
#
# 1. 构建（Windows；Linux 用 make -j）
powershell -ExecutionPolicy Bypass -File scripts\build.ps1 -Target all

# 2. 正确性（随提交包提供的那条路）：程序自带的 --mode verify
#    与 double 精度 CPU 参考逐元素比对，按选题书阈值直接判 PASS（fp16 1e-2 / bf16 5e-2）。
#    这就是仓库里 `make check` 跑的全部内容。
cmd /c build\fhwt.exe --mode verify --dim 256 --rows 4096
cmd /c build\fhwt.exe --mode verify --dim 128 --rows 4096 --kernel tc --dtype bf16
cmd /c build\fhwt.exe --mode verify --dim 4096 --rows 512 --kernel smem --acc fp32

# 2'. 开发树里的 1088 项单元检查（5.10 修复前为 976 项）（**tests/ 不随提交包提交**：通用「项目代码要求」
#     第 1 条要求无测试代码，而选题三要求包含测试，两条冲突——本提交按通用条款执行）。
#     在完整开发树里 `make check-tests` 或逐个跑：
cmd /c build\test_correctness.exe     # 560 项
cmd /c build\test_fusion.exe          # 244 项（5.10 修复前为 132 项）
cmd /c build\test_fp8.exe             #   2 项
cmd /c build\test_graph.exe           # 158 项（图重放 / GraphSequence / fork-join /
                                      #         GraphExecCache / TensorView / 原地策略）
cmd /c build\test_gemm.exe            # 124 项（旋转折进 GEMM 的 A-tile 载入）

# 2b. 屋顶：分母必须是同一次运行里实测的纯搬运带宽（7.15.3 的横比表用它）
cmd /c build\fhwt.exe --mode roof > data\roof_cuda.txt

# 2c. 调用侧建议（内存还是原地、是否需要图批量）
cmd /c build\fhwt.exe --mode advice --rows 65536 --dim 256 --dtype f16

# 3. 验收标准：与 fast_hadamard_transform 逐元素比对
$env:PYTHONPATH="$env:TEMP\fhwt_ref"    # 编译好的参考实现
python tools\check_against_ref.py --bin build\fhwt.exe `
    --dims 64,128,256,512,1024 --rows 1024 --kernels reg,tc,smem --accs native,fp32

# 4. 全部性能实验 -> data/
powershell -ExecutionPolicy Bypass -File scripts\run_experiments.ps1

# 4b. CUDA Graph 对比（也包含在上一步里；单独跑一条看效果）
cmd /c build\fhwt.exe --mode bench --kernel reg --dim 128 --rows 4096 ^
    --dtype f16 --iters 1000 --warmup 30 --reps 3 --graph

# 4c. 服务场景：一整趟 forward 的四种提交方式（A / B / C / D，见 7.11）
#     A/B 量的是主机提交速率，本机桌面负载会让它们跳 3x 以上；-runs 5 取中位数，
#     并且只有 C 一列可以当作稳定读数。
cmd /c build\fhwt.exe --mode loop --rows 2048 --dims 64,128,256 ^
    --layers 32 --iters 10 --dtype f16 --reps 3
python tools\bench_loop.py --bin build\fhwt.exe --out data --reps 3 --runs 5

# 4c'. 图里有几个根节点这件事本身（layers 1..32；全根 / 单根交替测 5 轮取中位，见 5.8）
python tools\bench_roots.py --bin build\fhwt.exe --out data --reps 3 --runs 5

# 4c''. 单根形态：第一层走 add()，其余层照旧分叉（唯一的差别，见 5.8）
cmd /c build\fhwt.exe --mode loop --rows 512 --dims 64,128,256 ^
    --layers 32 --iters 20 --dtype f16 --reps 3 --serial-entry

# 4c'''. 分叉宽度放在同一层的多个张量上（见 7.13）。--tensors N 让每层有 N 个独立张量，
#       --group-entry 让每层的第一个张量当锚点、其余 add_parallel()，整张图仍是单根。
#       对照：不加 --group-entry 就是 7.11 的"D 全根"（扁平扇出）。
cmd /c build\fhwt.exe --mode loop --rows 512 --dims 64,128,256 ^
    --layers 8 --tensors 6 --iters 20 --dtype f16 --reps 3 --group-entry
#       --streams N 是纯裸启动的多流对照（策略 E）：不建图，只把提交铺到 N 条流上。
python tools\bench_group.py --bin build\fhwt.exe --out data --reps 3 --runs 3

# 4c''''. 一次提交覆盖多趟（见 7.14）：--passes-per-graph K 把整份节点列表录 K 遍。
#         K 必须整除 --iters，否则窗口的尾巴会被丢掉（不参与计时，也不会算错）。
cmd /c build\fhwt.exe --mode loop --rows 512 --dims 64,128,256 ^
    --layers 8 --tensors 6 --group-entry --passes-per-graph 10 ^
    --iters 20 --dtype f16 --reps 3
python tools\bench_batch.py --bin build\fhwt.exe --out data --reps 3 --runs 8

# 4d. 端到端融合：旋转折进 GEMM 的 A-tile 载入（见 7.12）
python tools\bench_gemm.py --bin build\fhwt.exe --out data --reps 3 --runs 5

# 5. baseline（PyTorch / cuBLAS / 参考实现 / memcpy）
$env:PYTHONUTF8="1"; $env:KMP_DUPLICATE_LIB_OK="TRUE"
python tools\bench_baseline.py --csv data\baseline.csv

# 6. 出表与剖析摘要
python tools\analyze.py         --data data --out docs\结果表格.md
python tools\profile_summary.py --dir docs\profile

# 7. Nsight Systems 剖析
powershell -ExecutionPolicy Bypass -File scripts\collect_profiles.ps1

# 7d. Nsight Compute 计数器采集（8.4 节）。需要管理员权限：
#     右键 PowerShell -> 以管理员身份运行，再执行下面这条；
#     或者把 RmProfilingAdminOnly 置 0 后重启。脚本会先做权限自检。
powershell -ExecutionPolicy Bypass -File scripts\collect_ncu.ps1
#     输出 -> docs/profile/ncu/*.txt 与 _run.log

# 7b. 图内节点级采集（默认粒度会把整张 CUDA Graph 当成一条记录，见 8.6）。
#     nsys 需要纯 ASCII 路径，中文路径会让 protobuf 的 working_directory 解析失败，
#     所以先用目录联接做一个别名，在别名下运行。
cmd /c mklink /J C:\fhwt "D:\学习\大模型\InfiniTensor\cuda项目_XLD"
cd C:\fhwt
$nsys = "$env:ProgramFiles\NVIDIA Corporation\Nsight Systems 2025.1.3\target-windows-x64\nsys.exe"
& $nsys profile --force-overwrite true --cuda-event-trace=false --cuda-graph-trace=node `
    -o C:\fhwt_tmp\p_nodes_all -- .\build\fhwt.exe --mode loop --rows 512 --dims 128 `
       --layers 8 --iters 20 --reps 3
& $nsys profile --force-overwrite true --cuda-event-trace=false --cuda-graph-trace=node `
    -o C:\fhwt_tmp\p_nodes_sr  -- .\build\fhwt.exe --mode loop --rows 512 --dims 128 `
       --layers 8 --iters 20 --reps 3 --serial-entry
& $nsys profile --force-overwrite true --cuda-event-trace=false --cuda-graph-trace=node `
    -o C:\fhwt_tmp\g_w6 -- .\build\fhwt.exe --mode loop --rows 512 --dims 128 `
       --layers 8 --tensors 6 --group-entry --streams 6 --iters 20 --reps 3
# 每趟一次提交 vs 一次提交覆盖多趟（7.14）：一张 48 节点的图，和一张 960 节点的图。
& $nsys profile --force-overwrite true --cuda-event-trace=false --cuda-graph-trace=node `
    -o C:\fhwt_tmp\g_b1  -- .\build\fhwt.exe --mode loop --rows 512 --dims 128 `
```
