# 作业 03：Hadamard 变换加速（Tensor Core）实现报告

## 摘要

实现沿最后一维的 Hadamard 旋转 `y = H_d·x/√d`（输入 `[B,S,H,D]` 的 fp16/bf16，d 为 2 的幂），
并把旋转与 FP8 E4M3 per-token 量化融合进同一个 kernel。三条实现路径：

- **M2 寄存器蝶形 + warp shuffle**（`launch_fwht_baseline`）：一行的数据完全驻留在 32 个线程的
  寄存器里，`len < 8` 的蝶形级用寄存器异或、`len ≥ 8` 用 `__shfl_xor_sync`，全程不碰 shared
  memory、不需要 `__syncthreads()`。DRAM 受限的 256 MiB shape 跑到 943 GB/s（1008 GB/s 峰值的
  93.6%，而同 footprint 的一次读 + 一次写拷贝上限是 925 GB/s）；与官方 `fast_hadamard_transform`
  在 d = 2…512 上**逐元素 bit-exact**（max|diff| = 0）。
- **M3 Tensor Core（WMMA）**（`launch_hadamard_tc`）：把 `Y = X·H_d` 写成 tiled GEMM，靠 Sylvester
  的 Kronecker 分块只常驻 ±H_16（不存 d×d 矩阵，smem 用量与 d 无关），累加器全程 FP32。
- **M4 FP8 融合**（`fwht_fp8_kernel` / `tc_fwht_fp8_kernel`）：直接输出 E4M3 码字 + 每行一个 scale，
  与「先变换后量化」两段式**逐字节一致**（20 个用例 0 个不同码字、scale 逐位相等）；DRAM 行
  0.2138 ms vs 两段式 0.4996 ms（2.34×，与 7/3 的流量账吻合）。

三条主要结论（细节见 §4）：

1. **这个问题在 DRAM 上是拷贝受限的**（一读一写，上限就是 memcpy），Tensor Core 不可能带来
   数量级收益：M2 已经贴在搬运上限上，M3 的价值在于把「FWHT 写成 GEMM」这条路走通、并定量
   解释它与 M2 的差距。
2. **M3 的差距来自算法本身的 MAC 数，不是工程实现**：d ≥ 256 时 M3 已达裸 mma 峰值的 84~90%
   （`-Xptxas -v` 显示全部 instantiation 无 spill，占用率 25~42%，瓶颈不在发射也不在访存），
   但 `D²` 对 `D·log2 D` 的 MAC 差在 d = 256 / 1024 时是 32× / 100×。实测
   `M3/M2 ≈ D·BW_M2/(2P)` 在 d ≥ 256 上误差 ≤ 5%，交叉点落在 **d ≈ 110**——本作业的
   D = 64/128/256 正在这一档，Tensor Core 路线没有胜算。
3. **融合量化上蝶形版全面优于 TC 版**（d ≥ 16 快 2.0~6.8×）：省下的流量只在访存受限时才变成
   时间，而 TC 在这些 shape 上本来就是计算受限；融合只在流量收益大于 epilogue 串行链的代价时
   才划算（d = 16 的融合 TC 比它自己的两段式还慢 2.3×，就是反例）。

验收：`hw_tests` 57 项检查 0 failed / 0 skipped（其中 45 项涉及 GPU），`ctest` 2/2（0.57 s），逐项
输出见 `docs/logs/ctest_rtx4090d.txt`；fp16 最大绝对误差 ≤ 7.4e-4（门槛 1e-2）、bf16 ≤ 7.7e-3
（门槛 5e-2）。本文所有性能数字取自未插桩的一次运行，stdout 原文见 `docs/logs/bench_rtx4090d.txt`；
占用率与 profiler 依据见 `docs/logs/ptxas_v_hadamard_gpu.txt` 与 `docs/logs/nsys_stats.txt`（附录 A）。

## 2. 实现思路

### 2.1 变换约定（已与参考实现对齐）

做法：clone `Dao-AILab/fast-hadamard-transform`，先读源码把口径定下来，再编译安装它的 CUDA
扩展做数值对拍。

结论：

- 该库把缩放作为参数传入 kernel（`params.scale`），在写回时统一相乘；其 README 与自带测试
  统一取 `scale = 1/sqrt(dim)`，并声明等价于 `F.linear(x, scipy.linalg.hadamard(dim)) * scale`。
- 所以本项目的 `y = H_d x / sqrt(d)`（Sylvester 构造、自然顺序输出）与参考实现一致，不需要
  额外的归一化修正或输出置换。
- 该库对非 2 的幂尺寸内部补零到下一个 2 的幂；本项目按题面只支持 2 的幂。

### 2.2 非 Tensor Core baseline（M2）

实现位于 `src/hadamard_gpu.cu`，核心是把 `[B,S,H,D]` 展平成 `M = B·S·H` 行、行长 `D` 的二维
数组，再做蝶形 FWHT。

- **线程映射**：一行由同一 warp 内的 T 个线程协作，线程 `lane` 连续持有 `E = D / T` 个元素。
  E 以 8 为优选值（fp16/bf16 下正好一个 128-bit 向量）；`D > 8·32` 时改为增大 E 而不是 T，
  因为 shuffle 的分组不能跨 warp。`d = 2` 退化为 T = 1、E = 2。
- **蝶形**：第 `s` 级步长 `len = 2^s`。`len < E` 时配对的两个下标落在同一线程的寄存器里
  （线程持有的块按 E 对齐，异或不会跨块），直接寄存器加减；`len >= E` 时配对线程为
  `lane ^ (len / E)`、元素下标不变，用一次 `__shfl_xor_sync` 交换即可，符号折进求和
  （`v = sign·v + other`）。
- **零 shared memory**：上面两级合起来覆盖全部 `log2(D)` 级，所以 kernel 不碰 shared memory、
  不需要 `__syncthreads()`，一行只过一遍显存（一次读、一次写），理论上限就是 memcpy。
- **精度**：全程 FP32，仅在写回时按目标精度舍入一次；`1/sqrt(D)` 折进 epilogue，避免每级都
  引入舍入误差（否则半精度中间量的误差会直接吃掉 1e-2 的容差预算）。
- **访存**：按每线程 run 宽度选择 16/8/4/2 字节向量；行内 T 个线程连续访存，天然完全合并。
- **尾部处理**：最后一块中越界的线程不提前 return（否则 shuffle 的 mask 与配对会失效），
  而是钳到最后一个有效行继续计算、只跳过写回。
- **launch 粒度**：以每 SM 约 8 个 block 为目标反推 block 持有多少行，向上取整到整 warp，
  上限 256 线程，兼顾小 shape（行数少）与大 shape 的并行度。
- **支持范围**：`head_dim` 为 2 的幂且不超过 1024；其余尺寸返回 `false`，harness 报 SKIP。

### 2.3 Tensor Core 主实现（M3）

同样在 `src/hadamard_gpu.cu`（`tc_fwht_kernel`），把问题写成

```
Y (M×D) = X (M×D) · H_D (D×D)
```

的 tiled WMMA GEMM：A 操作数是激活，B 操作数是 ±1 常量矩阵，K = D 按 16 切分，
累加器全程 FP32，`1/sqrt(D)` 放在 epilogue。

**不存 D×D 矩阵。** Sylvester 构造满足

```
H_d[(i1,i0),(j1,j0)] = H_{d/16}[i1,j1] · H_16[i0,j0],   i = 16·i1 + i0
```

因为 `H_n[i,j] = (-1)^popcount(i&j)`，而 `i1` 与 `i0` 的比特不重叠。于是任意
(K tile, N tile) 需要的 B 分块只可能是 `+H_16` 或 `-H_16`，符号由
`(-1)^popcount(k_tile & n_tile)` 决定。收益：

- shared memory 只需要常驻两个 16×16 的 tile（共 1 KiB），**与 D 无关**。D = 512 若直接
  存 `H_d` 要 512 KiB，远超单 SM 的 100 KiB，所以这个技巧是必需的而不是可选优化。
- 每个 mma 都是满密度的 `m16n16k16`，没有为稀疏结构浪费算力。
- 两个符号变体都常驻寄存器，B 在 K 循环里零访存。
- d 的适用范围顺带放宽（smem 只需 16 行 × D，M2 的寄存器方案受限于每线程能装多少）。

写 kernel 之前先用一个仓库外的 host 程序验证了这条分块公式：d = 16…1024 逐元素与递归
构造的 `H_d` 比对（1,398,016 次检查全部相等），并用分块累加复算 `H_d x`，与显式 matmul
完全一致。这一步不能省——公式错了 kernel 里的 bug 会非常难查。

**线程映射与 tile 循环。** 一个 block 负责 16 行 × `kCols = min(D, 256)` 列，每个 warp
负责其中 `kCols / kWarps` 列并跑完整的 K = D 循环；D > 256 时再按列切成 2~4 个 block。
16 行 × D 的激活块先 staging 进 shared memory，行距取 `D + 8`：若行距正好是 128 B 的整数
倍，16 行会落在同一组 bank 上，`load_matrix_sync` 会退化。

**epilogue。** WMMA 的累加器片段是 FP32，而 `store_matrix_sync` 只能写与片段同类型的
buffer，输出却是 fp16/bf16，所以片段先落到 FP32 shared memory（与 A staging 共用同一块
buffer，中间用 `__syncthreads()` 隔开），再由线程按 16 B 向量读回、乘 `1/sqrt(D)`、舍入到
目标精度写出。行方向的越界线程在 staging 阶段钳到最后一个有效行、在写回阶段被掩掉，
因此 `rows = 1` 这类用例不需要特判。

**支持范围。** `D ≥ 16` 走 TC；`D ∈ {2,4,8}` 无法满足 `m16n16k16` 的 K ≥ 16，直接转调
M2 的蝶形实现（两条路径的精度口径一致，回落不影响对拍结论）。

### 2.4 FP8 E4M3 per-token 量化融合（M4）

把「旋转 → 量化」压成一个 kernel：输入 fp16/bf16 激活，直接输出 FP8 E4M3 码字（每元素 1 B）
与每行一个 FP32 scale，中间结果不落显存。

**量化口径。** per-token，即每行一个 scale：`amax = max|y[row][:]|`，`scale = amax / 448`，
`rscale = 1 / scale`，`q = cvt(v · rscale)`。全零行的 `amax = 0` 直接取倒数会得到 `inf`，而
`0 · inf = NaN`，所以约定全零行 `scale = 1`、码字全 0。舍入统一走
`__nv_cvt_float_to_fp8(v, __NV_SATFINITE, __NV_E4M3)`（round-to-nearest-even + 饱和），host
参考与两个 kernel 用同一个入口。写 kernel 之前先测过这个函数在 host 与 device 上的结果**逐字节
一致**（1528 个探针值：全部有限码字、±1 ulp、相邻码字中点、次正规数、±inf、饱和点，0 处不一致），
否则「逐字节对拍」这个验收口径根本无从谈起。

**三个 kernel。**

| kernel | 说明 |
|---|---|
| `quantize_fp8_kernel` | 两段式流水线的第二段：读激活、写码字；线程映射与 M2 相同（一行 2^kLogT 条 lane，行内归约用 shuffle） |
| `fwht_fp8_kernel` | M2 蝶形 + 量化 epilogue：行的最大绝对值由共享该行的 lane 做 shuffle 蝶形得到，不需要 smem 与 block 级同步；覆盖 d = 2…1024 全部尺寸 |
| `tc_fwht_fp8_kernel` | M3 的 WMMA GEMM + 量化 epilogue：d ∈ [16, 512] |

**为什么融合结果能逐字节复现。** 两段式里第二段读回的是第一段**已经舍入到目标精度**的输出，
因此融合 kernel 也必须对「先舍入到 fp16/bf16 的那个值」求 amax 并量化，而不是对 FP32 累加器求；
做法是每处用到累加值的地方都套一次 `TypeTraits<T>::from_float(v * scale)` 再取回浮点。
省掉这一步，融合结果就会在两段式累加顺序跨越舍入边界的那些元素上差一个码字——而融合的意义恰恰是
「量化结果不依赖于由哪个 kernel 产生旋转」。

**TC 融合 kernel 的 epilogue。** 与 M3 最大的区别是 scale 是整行的量，所以**一个 block 必须独占
整行**，不能像 M3 那样把列切给多个 block：

1. 累加器片段用 `store_matrix_sync` 落进一块 16 × (d + 8) 的 FP32 smem tile（每个 warp 写自己的
   列切片，`ldm` 取 padding 后的行距），与 A staging 复用同一块 buffer，中间用 `__syncthreads()`
   隔开；
2. 从 **smem tile** 而不是从累加器片段求行最大绝对值：片段元素到矩阵下标的映射不属于 WMMA 的
   接口约定，按约定编程的代码不该去猜它。求的仍然是舍入到目标精度后的值；
3. 行最大绝对值 → `rscale` → 按 16 B / 8 元素的向量做第二遍 scale + 转换 + 写出，最后写 `scales[]`。

`kWarps = max(2, d / 64)`（上限 8），即每个 warp 尽量负责 64 列（4 个 n tile）。d = 64 若只给
1 个 warp，行归约会退化成 16 次串行、每次只有 8 条 lane 干活，比融合省下的流量还贵（见 §3.8）。
d > 512 不支持：16 × (d + 8) × 4 B 的 FP32 tile 在 d = 1024 时是 66 KiB，超过 48 KiB 的静态
smem 上限；d < 16 无法满足 `m16n16k16` 的 K ≥ 16，转调蝶形融合版。

## 3. 优化历程与踩坑

### 3.1 设计取舍：直接落地寄存器方案

原计划按「v0 逐级 shared memory 蝶形 → v1 向量化访存 → v2 shuffle 换 len < 32 → v3 每线程多元素」
的阶梯实现。读了参考实现的源码后确认：对本作业的 `D ≤ 512`，一行的全部数据在 32 个线程的
寄存器里就能装下（`32 × 8 × 2 B = 512 B`），于是 `len < E` 用寄存器加减、`len ≥ E` 用 warp
shuffle 的组合可以覆盖全部蝶形级次，根本不需要 shared memory。因此直接落地了这一版，
把 smem 版本留给 M3 里可能出现的跨 warp 交换场景。收益体现在实测上：DRAM 受限的大 shape
达到 943 GB/s（理论峰值的 93.6%），kernel 时间已经贴近 memcpy 这一上限（见第 4 节）。

### 3.2 踩坑 1：参考实现的越界 bug（M1）

CPU 参考里的 `build_sylvester` 用元素个数 `n·n` 当作矩阵维度来判断何时退出展开循环，
`d > 2` 时索引远远越过 buffer：`d = 128` 的最大误差 > 1e17、`d = 256` 直接段错误，而蝶形
参考实现却是对的。定位手法：利用解析性质「全 1 输入经 `y = H x / sqrt(d)` 应只有第 0 个
元素为 `sqrt(d)`、其余为 0」，一次就断定问题出在 matmul 参考而不是蝶形实现。修复后
`d = 2 … 512` 的两套参考实现互相吻合到 1e-6。

### 3.3 踩坑 2：host-only 的转换函数

`TypeTraits::to_float/from_float` 原本只在 host 侧（WMMA 探针）使用，kernel 里调用后报
`calling a __host__ function from a __device__ function`。补上 `__host__ __device__` 后
host/device 两侧共用同一套 fp16/bf16 转换。

### 3.4 踩坑 3：benchmark 带宽超过 HBM 峰值

首次实测小 shape 得到 1383–2694 GB/s，超过 4090 D 的 1008 GB/s 理论峰值。原因是 benchmark
对同一块 0.4–16 MiB 的张量重复 50 次迭代，输入输出全部落在 72 MiB 的 L2 里，测到的是 L2
带宽。核实手段：另写一个仓库外的临时程序，用 256 MiB 流量的大 shape 复测，得到 DRAM 受限的
943 GB/s；随后把该大 shape 加进 `bench_hadamard.cu`，让 benchmark 同时覆盖 L2 与 DRAM 两种
情形，并在输出里注明哪一行是 DRAM-bound。

### 3.5 踩坑 4：常量矩阵只被填了一半

`H_16` 的 256 个元素最初写成 `if (tid < 256) { ... }`，但 block 只有 32~128 个线程，
于是只有前 `blockDim.x` 个元素被写入，其余保持 shared memory 的初值 0。d = 16 时只有
`H_16` 的前 2 行非零，结果退化成「只对前两个输入做变换」，输出列呈现周期 2 的假象；
d = 64/128 时是周期 8，正是前 8 行非零。

定位手法值得记下来：不要盯误差量级，而是**把 kernel 实际作用的矩阵读出来**——用
one-hot 输入 `e_i` 跑 `rows = 1` 的用例，输出就是该矩阵的第 i 行。一次运行就看清楚
第 0、1 行正确、第 2 行起全 0，直接指向常量填充而不是 tiling/符号逻辑。改成
`for (v = tid; v < 256; v += blockDim.x)` 后所有尺寸回到 fp16 舍入水平（≤ 5e-4）。

### 3.6 踩坑 5：分支 vs 选择——fp16 被谓词化 HMMA 拖慢 1.5×

符号选择最初写成带分支的形式：

```
if (sign) mma(acc, fa, fb_neg, acc);
else      mma(acc, fa, fb_pos, acc);
```

结果是同一个 kernel、同样的 shape，bf16 比 fp16 快 1.5 倍，而且多次运行稳定（不是时钟
假象）。先排除了硬件差异：仓库外的纯 mma 微基准（fragment 常驻寄存器、无访存）测得两种
精度的裸吞吐相同（147.0 vs 146.7 TFLOPS，见第 4 节）。

dump SASS 后原因很清楚：bf16 实例编译出 8 条无谓词的 `HMMA.16816.F32.BF16`，fp16 实例
却是**两套被 `@!P0` 谓词化的 HMMA（共 16 条）加 10 条 WARPSYNC**——nvcc 把两个分支都
发射出来，并在每次谓词化 mma 后插入 warp 同步，MMA 的发射槽因此直接翻倍。

把分支改成分支无关的选择（先 `fb = sign ? fb_pos : fb_neg` 再 mma）后，fp16 与 bf16 的
数字并齐，L2 受限的 shape 提升 1.5~1.7×（621 → 914 GB/s、946 → 1581 GB/s）。这也是本
里程碑里性价比最高的一个改动。

### 3.7 踩坑 6：FP8 的「半个量化步长」不是一个数

写量化验证时最自然的直觉是「误差不超过半个量化步长」，但 FP8 E4M3 的格点**不均匀**：3 位尾数
使得每个二进制区间（binade）内分 8 档，步长每过一个 2 的幂就翻倍，顶格（416 → 448）的步长是
32 = `448 / 14`。于是「半个步长」至少有两种说法：绝对形式是 `448/28 = 16`（顶格的半个步长），
相对形式是 `ulp(v)/2 ≤ v/16 ≤ amax/16 = 0.0625·amax`（v 略高于某个 binade 下界时取到最坏）。
两者都正确，但相差 1.75 倍；若随口拿「某个典型步长」去算，能差出 50 倍，检验要么虚设要么永远
失败。

最终两种写法都用上：测试断言用相对形式 `err / (amax/16) ≤ 1`，报告里给绝对形式 `16 = 448/28`。
实测 1527 个探针（每个码字、其两侧相邻浮点值、相邻码字的中点、饱和点）的最坏比值是 **0.571**
——正是顶格中点 432 那个平局舍入点，与上面的推导一致。

### 3.8 踩坑 7：融合 epilogue 的两处浪费

bench 里 TC 融合版一度比两段式还慢（d = 64 的小 shape 上 5.3 µs vs 4.5 µs）。排查出的两个问题
都在 epilogue，不在 GEMM 本体：

- **写回只按 lane 跨步**。第二遍写回的循环写成 `for (v = lane; v < 16·kVecsPerRow; v += 32)`，
  意味着 block 里**每个 warp 都把整个 tile 转换并重写一遍**：结果正确（写的是同一份数据），
  但做了 kWarps 倍的无用功。改成跨 `tid / blockDim.x` 跨步后：d = 512 的 L2 行 10.9 → 9.3 µs，
  16 MiB 行 15.5 → 14.2 µs，DRAM 行 225.1 → 218.2 µs。
- **d = 64 只有 1 个 warp**。`kWarps = max(1, d/64)` 在 d = 64 时只给 1 个 warp，行归约变成 16 次
  串行（每次 5 级 shuffle，且只有 8 条 lane 有活），单个 block 内没有任何并行度可以掩盖它。
  改成 `max(2, d/64)` 后，d = 64 的两个 shape 分别 5.3 → 3.6 µs、 13.4 → 10.1 µs，反超两段式。

教训：融合 kernel 的收益来自省流量，但 epilogue 是一条**串行依赖链**（store → sync → 归约 →
sync → 写回），它的固定开销只有在访存受限的行里才能被隐藏；在 L2 常驻、计算受限的行里它是纯开销。

### 3.9 踩坑 8：benchmark 自己的两个方法论错误

M5 补「全 shape + head_dim 扫描」时，先跑出来的两张表本身是错的，而且错误都在测量口径上，
不在 kernel 里：

- **表 2 的工作集取小了**。扫描最初设成 `kSweepElems = 256 · 1024`（0.5 MiB 流量），于是每一行
  都落在 ~2.2 µs 的 launch 地板上：copy、M2、M3 三条曲线被压成一条 2.1~2.3 µs 的直线，d 的差别
  被完全吃掉，GB/s 列算出来没有意义。放大到 `4 · 1024 · 1024`（16 MiB 流量，仍在 72 MiB L2 内）
  之后，M2 与 M3 才分开（见 §4.2）。
- **CPU 参考的门限用错了复杂度**。bench 计时的是 `hadamard::ref_fwht_fp32`，仓库里这条参考是
  `O(d·log2 d)` 的蝶形实现（实测约 3.4 ns/元素，与 d 无关），但门限写的是 `rows · d² ≤ 1e9`，
  按 `O(d²)` 的显式 matmul 估的。后果是最大的 shape 被静默跳过 CPU 一行，而它实际只要 0.23 s/次。
  改成按元素数门限（`kCpuElemLimit = 64 · 1024 · 1024`）后，256 MiB 那一行也有了 CPU 基准。
- **搬运上限那句话写反了**。文件头原先写「任何 3 B/elem 的融合行都不可能超过 copy 的 GB/s 的
  四分之三」。因为每一行都按自己真实搬动的字节数折算，融合行是**可以**达到同一个 GB/s 上限的；
  只有它的**时间**下界是 copy 的 3/4。按原措辞读，会把「已经贴着上限的融合行」误判成「离上限
  还差 25%」。

教训：benchmark 的对手不是 kernel，而是自己的口径。工作集大小、参考复杂度、单位这三处各错一次，
都会产出一张看起来合理、实际在骗人的表。

## 4. 性能指标与分析

RTX 4090 D（sm_89，114 SM，1008 GB/s HBM 峰值，72 MiB L2），`hw_bench`，50 次迭代取均值、
CUDA event 计时（含一次预热）；fp16 与 bf16 的耗时差异在 1% 以内，下表以 fp16 列 ms、bf16 只列
带宽。L2 常驻的几行逐次运行有 2~3% 抖动。本节所有数字来自同一次 `./build/hw_bench`，stdout 原文
见 `docs/logs/bench_rtx4090d.txt`（含每个 shape 的 copy 搬运上限行）。

**没有硬件计数器时用什么当对照物。** 这台机器上 `ncu` 不可用（原因见 §4.3），所以每个 shape 都先
用一个 uint4 的 grid-stride `copy_kernel` 测出「同样 footprint 的一次读 + 一次写」要多久，作为该
尺寸下这台机器的访存上限。所有行都按**各自真实搬动的字节数**折带宽：`copy_kernel` 与两条变换
路径 4 B/元素，两段式量化 7 B/元素，融合量化 3 B/元素另加每行 4 B。于是各行之间可以直接比较，
某一行报出的带宽与同一 shape 的搬运上限相同时，它就是贴在访存上限上，而不是「慢」。

先给出两条路线的算术强度。M2 每行 `D·log2(D)` 次加减、每元素读一个、写一个，
算术强度约 `log2(D)/2 ≈ 3.5 flops/byte`；M3 每行 `2D²` 次 MAC，强度为 `D/2`。平台的机器
平衡点由实测的裸 mma 峰值给出：仓库外的微基准（fragment 常驻寄存器、无访存、4 条独立
累加器链）测得 **147.0 TFLOPS（fp16 → fp32 累加）** 与 **146.7 TFLOPS（bf16 → fp32 累加）**
——两种精度的 Tensor Core 吞吐实际上相同。对 1008 GB/s 的 HBM 就是 **146 flops/byte**，
对实测 2.5–2.7 TB/s 的 L2 只有 **~50 flops/byte**。

- **L2 常驻的行 M3 反而慢 1.5~2.4×**：这些 shape 的算术强度高于 L2 的 ~50 flops/byte，

  数据量相同。
- **D = 64 的两行（强度 32 < L2 的 50）按理应该是访存受限，实测仍慢 1.7~1.8×**，这是每 block
  固定开销在作祟：16 行 × 64 列的 tile 只有 4 KiB 流量，却要做 prologue（`H_16` 构造、A
  staging、两次 `__syncthreads()`）与 epilogue，这部分开销摊不薄；表 2 的 d 扫描把这档的达峰率
  定在 35%（修正后 45%），是整张表里除 d = 16 之外最低的。
- **fp16 与 bf16 一致**（差异 < 1%），与微基准的裸吞吐结论一致；早期 fp16 慢 1.5× 的
  现象见 §3.6，是代码生成问题而不是数据格式问题。
- **最小的 shape（0.4 MiB）三行（copy、M2、M3）都是 2.2 µs**：全部是 kernel 启动与尾部
  延迟，与访存、蝶形、Tensor Core 都无关；这类 shape 的优化方向是减少 launch 与尾部开销
  （见 §6），而不是改访存或蝶形。

分析：

- **蝶形（M2）几乎永远贴在搬运上限上**：d ≤ 16 时与 copy 持平（3091 vs 3103 GB/s），d = 64 时
  3012（97%），一直涨到 d = 1024 才降到 1974（64%）。它的时间从 0.0054 到 0.0085 ms 只涨 57%，
  而每行的加减次数涨了 7 倍——多出来的算力被访存完全掩藏，这是「蝶形在寄存器里做」的直接结果。
- **M3 的带宽一路掉到 258 GB/s，而达峰一路涨到 90%，这两件事是同一件事**。M3 的算术强度是
  `D/2`，D ≥ 128 后超过 L2 的 ~50 flops/byte，kernel 进入计算受限区，于是「按搬动字节数折的
  带宽」必然下降、「按 MAC 数折的达峰」上升。看 M3 该看达峰列，看 M2 该看带宽列。
- **交叉点可以用一个两行的模型预测**。M2 的时间是 `4E / BW_M2`，计算受限区里 M3 的时间是
  `2E·D / P`（E 为元素数，P 为达到的 mma 吞吐），相除得 `M3/M2 ≈ D·BW_M2 / (2P)`。把平台期
  实测的 P = 132 TF 与各行的 BW_M2 代入：d = 256 / 512 / 1024 得 2.41 / 4.62 / 7.66，对应实测
  2.54 / 4.66 / 7.65，误差 ≤ 5%。令比值等于 1 得交叉点 `D* ≈ 2P / BW_M2 ≈ 110`——在这台机器的
  L2 口径下，只要 `D` 小于约 110，M3 就该输给 M2。
- **本作业的 shape 都落在交叉点附近或右侧，Tensor Core 路线没有胜算**：表 1 的 D 只有
  64/128/256。D = 64 按模型本该是 M3 略快（0.73×），实测却是 1.84×，因为一个 block 只有 16 行，
  prologue/epilogue 摊不薄——表 1 里那两行也只有 4% 与 31% 达峰；D = 128/256 连模型都判定 M3 更
  慢（表 2 在 d = 128 处实测 M2 快 1.69×）。
- **融合量化上蝶形版全面优于 TC 版**：d ≥ 16 时快 2.0~6.8×，而且省流量的收益恰好落在 TC 最弱的
  档位——d = 16 时 fwht+fp8 只要 0.0048 ms，TC 融合版要 0.0324 ms。
- **d = 16 的 TC 融合行是整张表最差的一格**（421 GB/s，0.0324 ms）：比同一行的非融合 TC 版
  （0.0097 ms）还慢 3.3×，比同一行的两段式（0.0141 ms）慢 2.3×。原因是 `tc_fp8_warps_for(16) = 1`
  ——一个 block 只有 1 个 warp（32 线程）、16384 个 block，而 SM 的 block 数上限是 24，每 SM 只能
  有 24 × 32 = 768 线程（50%），行归约还要 16 次串行。同一列里 d = 8 的融合 TC 行只要 0.0048 ms
  （它走蝶形回落），比 d = 16 这一格快 6.8×——所以问题不是「d 太小算力不够」，而是块粒度与
  epilogue 结构（见 §6 的「扩大块粒度」）。

| `tc_fp8_kernel<half,9>` (d = 512) | 62 | 34 KiB | 256 | 2（smem） | 512 | 33% |

读法：M2 是纯寄存器 kernel（零静态 smem、寄存器少），占用率 83~100%，所以它能贴在带宽上；M3 的
smem 用量（A staging + `H_16` + epilogue tile，随 d 涨到 19~34 KiB）把它压到 25~42%，配合它本身
的计算受限属性，解释了为什么它到不了裸 mma 峰值（d ≥ 512 停在 90%）；d = 16 的融合 TC kernel
是被 block 数上限（24）截住的，32 线程的 block 天生填不满 SM，与 §4.2 那一格 421 GB/s 的观测一致。

**（2）profiler 权限：`ncu` 不行，`nsys` 行。** `ncu` 的任何 profile 都在初始化时失败：

```
==ERROR== ERR_NVGPUCTRPERM - The user does not have permission to access NVIDIA GPU Performance Counters
```

原因在容器外面、且不可从容器内改变：`/proc/driver/nvidia/params` 里 `RmProfilingAdminOnly: 1`
（该文件只读，权限 `-r--r--r--`），而当前进程的 capability 集
`CapEff = 00000000a80425fb` 不含 `CAP_SYS_ADMIN`(21) 与 `CAP_SYS_MODULE`(16)，既改不了这个参数
也重载不了驱动。这是环境限制，不是用法问题；在有权限的机器上补一次 `ncu` 就能直接拿到 DRAM
吞吐 / occupancy / stall 三张表。

`nsys` 可用，`nsys profile --stats=true ./build/hw_bench` 正常产出报告，它给出两条侧证：
9650 次 `cudaLaunchKernel` 的 host 侧耗时中位数 3.0 µs、最小 2.66 µs，与各行实测的 ~2.0 µs 底部
同一量级，坐实了「小 shape 的行由 launch 与尾部延迟主导」；442 次 `cudaMalloc` 合计 138.5 ms
（单次最大 101 ms）——这部分是 benchmark 自己的缓冲区分配，不在被计时的区间内，但它解释了为什么
计时区间里必须只留 kernel 与一次 memcpy。另有 166 次 memset 合计 1.47 ms（单次最大 132 µs），
是每个 case 之间清输出缓冲的开销。nsys 插桩会把最小的几行从 2.2 µs 抬到 3.4~3.8 µs，所以
§4.1 / §4.2 的所有数字都取自未插桩的那次运行。

### 4.4 融合量化的流量账（M4）

量化路径的流量口径：融合版读 1 次激活、写 1 次 FP8 码字（每元素 3 B）再加每行 4 B 的 scale；
两段式是「变换（2+2 B/elem）+ 量化（2+1 B/elem + scale）」共 7 B/elem。若两条路线都贴住带宽上限，
融合相对两段式应得 7/3 ≈ 2.33×。下表为 fp16 激活（bf16 的流量完全相同），与 §4.1 同一次运行：

| shape (B,S,H,D) | D | 融合流量 | fp8 只量化 | fwht+fp8 融合 | tc+fp8 融合 | tc → fp8 两段式 | TC 融合加速 | 蝶形融合加速 |
|---|---|---|---|---|---|---|---|---|
| [1,128,12,64] | 64 | 0.29 MiB | 0.0022 ms (137) | 0.0023 ms (134) | 0.0036 ms (84) | 0.0044 ms (158) | 1.22× | 1.91× |
| [2,256,16,128] | 128 | 3.0 MiB | 0.0024 ms (1350) | 0.0033 ms (976) | 0.0070 ms (452) | 0.0070 ms (1056) | 1.00× | 2.12× |
| [1,512,8,256] | 256 | 3.0 MiB | 0.0024 ms (1331) | 0.0035 ms (892) | 0.0093 ms (339) | 0.0103 ms (717) | 1.11× | 2.94× |
| [4,512,16,128] | 128 | 12.1 MiB | 0.0045 ms (2822) | 0.0071 ms (1799) | 0.0143 ms (888) | 0.0152 ms (1938) | 1.06× | 2.14× |
| [1,4096,12,64] | 64 | 9.2 MiB | 0.0039 ms (2489) | 0.0050 ms (1928) | 0.0102 ms (947) | 0.0128 ms (1733) | 1.25× | 2.56× |
| [8,4096,16,128] | 128 | 194 MiB | 0.2139 ms (951) | 0.2138 ms (951) | 0.2186 ms (931) | 0.4996 ms (944) | 2.29× | **2.34×** |

两个加速比都以「tc → fp8 两段式」为分母（它是同一批 shape 下唯一既完整又统一的两段式口径）。

分析：

- **DRAM 行是唯一能验证流量账的地方**（表内「两段式」列的带宽按 7 B/elem 计，其余三列按 3 B/elem）：
  两段式 0.4996 ms 恰好等于「M3 变换 0.2872 + 量化 0.2139」之和（0.5011，差 0.3%），说明两段式
  既没有重叠也没有额外开销；融合后的蝶形版 0.2138 ms 与**纯量化**的 0.2139 ms 几乎逐位相同
  （都是 951 GB/s），即变换的算力被完全藏进流量里，而它只多搬了 3 B/elem 的账；相对两段式 2.34×，
  与 7/3 = 2.33 的预测吻合（TC 融合版 2.29×，差的 2% 是它自身的计算开销）。
- **融合版甚至比单独的 M2 变换更快**：0.2138 ms vs 0.2846 ms，因为输出从 2 B/elem 降到 1 B/elem，
  `0.2846 × 3/4 = 0.2135 ms`，与实测一致。
- **L2 常驻的行增益小得多**，TC 版只有 1.00~1.25×：这些行本来就是计算受限（算术强度 `D/2` 已经
  高于 L2 的 ~50 flops/byte），省下的流量不构成瓶颈，而 epilogue 的固定开销照付。蝶形融合版在这些
  行仍有 1.9~2.9×，因为 M2 即使在 L2 里也是访存受限（§4.2 的 d 扫描给出同样的结论），省下的 4/3
  流量直接变成时间。
- **d = 16 的 TC 融合是负收益**：0.0324 ms（§4.2），比它自己的两段式还慢 2.3×，而同一档的蝶形
  融合只要 0.0048 ms。融合只有在流量的收益大于 epilogue 串行链的代价时才划算，d = 16 的块粒度让
  这条链彻底暴露在外。
- **小 shape（0.29 MiB）由 launch 与尾部延迟主导**：四行都在 2.2~4.4 µs，带宽数字没有意义。

## 5. 正确性验证

- **对拍口径**：输入先量化到目标精度，参考值在该量化输入上计算，因此误差只反映 kernel 误差，
  不混入输入量化误差。
- **CPU 参考自洽**：Sylvester 显式 matmul 与蝶形 FWHT 两条独立实现互相吻合，
  `d = 2/64/128/256/512` 最大差 2e-6；正交性检查（连续做两次变换应回到原值）对全部尺寸
  通过，可捕获符号、顺序与归一化错误。
- **GPU 对拍**：`hw_tests` 中 20 个 GPU 用例（fp16/bf16 × `d = 2/64/128/256/512` × M2/TC 两条路径，
  其中 `d = 2` 由 TC 路径转调 M2）全部 PASS。实测最大绝对误差：fp16 ≤ 7.4e-4（门槛 1e-2，余量
  13×），bf16 ≤ 7.7e-3（门槛 5e-2，余量 6.5×）；逐项输出见 `docs/logs/ctest_rtx4090d.txt`
  （fp16 最大 0.000738、bf16 最大 0.007638，都出现在 d = 256）。
- **两条路径相互印证**：TC 用例与 M2 用例的最大误差逐位相同，说明两者都是 FP32 累加、
  只在写回时舍入一次；B 操作数的 ±1 在 fp16/bf16 下精确，所以差异只来自累加顺序，
  完全落在最后一次舍入之内。
- **TC 路径的额外自查**：用 one-hot 输入把 kernel 实际作用的矩阵读出来与 `H_16` 逐元素比对
  （做法见 §3.5）。这比只看误差量级更容易发现结构性错误，建议保留为回归手段。
- **与官方实现对拍**：把官方 `fast_hadamard_transform` kernel 消费的同一份 fp16/bf16 输入喂给
  我们的 kernel，`d = 2/64/128/256/512` 全部逐元素 **bit-exact（max|diff| = 0）**。这说明两者的
  中间精度与舍入方式也完全一致（双方都是 FP32 累加、只在写回时舍入一次）。

M4 的验证沿用同一口径（输入先按目标精度取整、参考值在该输入上计算），另外加了两条针对量化的检验：

- **舍入规则本身**：1527 个探针值（`0x00`–`0x7E` 每个码字的解码值、其两侧相邻浮点值、相邻码字的
  中点即舍入边界、±448 / ±449 / ±1e10 饱和点、±0、最小次正规数）逐一与**独立实现的
  round-to-nearest-even**（对解码出的格点做最近邻扫描，平局取偶尾数）比对码字：
  `mismatches = 0 / 1527`。这类断言能抓到「差一个码字」的错误，而误差量级类断言抓不到。
- **半 ulp 上界**：同一批探针组成的行（amax = 448.000031）走完 per-token 流程后
  `err / (amax/16) = 0.571`，与 §3.7 的推导一致。
- **融合 vs 两段式逐字节一致**：(M3, TC 融合) 与 (M2, 蝶形融合) 两条路线 × d = 2/64/128/256/512
  × fp16/bf16 共 20 个用例，全部 `codes differing = 0`、`|scale diff| = 0`（scale 逐位相等），
  同时 `err / (amax/16) ≤ 0.5715`。TC 路径在 d = 2 时转调蝶形，因此那一组比的是「蝶形融合」与
  「蝶形 + 量化」，结论同样成立。
- **全零行**：host 参考与两个融合 kernel 都给出 `scale = 1`、全部码字 `0x00`。
- **host/device 舍入一致**：见 §2.4，1528 个探针 0 处不一致——这是「逐字节对拍」成立的前提。
- **不回归**：M5 改完 benchmark 后重跑，M2/M3/M4 的 20 个 GPU 用例仍全部 PASS（`hw_tests`
  共 57 项断言，0 failed、0 skipped），`ctest` 2/2、用时 0.57 s；这次运行的完整记录归档在
  `docs/logs/ctest_rtx4090d.txt`。

## 6. 未来工作

- **radix-16 hybrid（下一步最有价值的方向）**：M3 现在做的是**完整** GEMM，每行 `D²` 次 MAC；
  若只把「16 点 radix 级」交给 Tensor Core（该级在 16×16×16 上就是满密度的 H_16），
  剩下的 `D/16` 点变换仍用 M2 的蝶形（需要 strided 版本或经 smem 转置），算术强度可以从
  `D/2` 压回 ~5 flops/byte，即回到与 M2 相同的访存受限区间。这是目前看来唯一能让 Tensor Core
  路线在计算受限档位（D ≥ 128 的 L2 场景、D ≥ 512 的 DRAM 场景）追平或反超蝶形的方案。
  表 2 支持这个判断：d ≥ 256 时 M3 已经跑到裸 mma 峰值的 84~90%（占用率侧证见 §4.3，无
  spill、瓶颈不在发射或访存），剩下的差距来自算法本身——`D²` 对 `D·log2 D` 是 18×（d = 128）、
  32×（d = 256）、100×（d = 1024）的 MAC 差，做满 GEMM 就注定多花这些算力。
- **扩大块粒度**：现在一个 block 只有 16 行，prologue 与 epilogue 的固定开销摊不薄。表 1 的达峰
  只到 31~68%，但表 2 显示大 d 时已达 84~90%，所以块粒度真正拖累的是小 d 那一档（d = 64 停在
  35% 达峰、M3/M2 = 1.84×）与 d = 16 的融合行（1 warp/block，占 SM 上限的一半）。改成 32/64 行
  一块、A staging 双缓冲，是收窄这两档差距的直接手段。
- **列块的重复 staging**：D > 256 时每个列块都会重新 staging 整行激活，D 较大时可以改成
  按 K 分块或让同一 block 覆盖全部列。
- **INT4 对称量化**：同一套 epilogue 骨架可以做 `scale = amax/7`、8 个值打包进 int32；行尺度与
  两遍写回的结构不变，只是写回从「每元素 1 B」变成「每 8 元素 1 个 int32」。
- **更细的 scale 粒度**：per-tile（例如每 128 个元素一个 scale）精度更好，代价是一个 block 只需要
  部分行，行归约要变成跨 warp 的树；现在选 per-token 是刻意的简单口径。
- **d = 1024 的融合**：FP32 的 16 × (d+8) epilogue tile 超过静态 smem，需要动态 smem，或者拆成
  「先算 amax、再转换」两遍（后者基本等价于两段式，除非中间结果能留在寄存器里）。
- **更大的 head_dim**：超过 1024 后每线程寄存器装不下一行，需要跨 warp 的 shared memory
  交换（参考实现的做法）或分块策略。
- **非 2 的幂**：按参考实现补零到下一个 2 的幂。
- **小 shape 的 launch 开销**：`[1,128,12,64]` 这类只有 2 µs 的场景，可考虑合并多行/多次调用、
  持久化 kernel 或 CUDA Graph。
- **profiling**：M5 已把能用上的两条侧证做掉——`-Xptxas -v` 的寄存器/占用率表与 `nsys` 时间线
  （§4.3），并确认本容器的 `ncu` 不可用是权限问题（`ERR_NVGPUCTRPERM`、`RmProfilingAdminOnly: 1`、
  容器内无 `CAP_SYS_ADMIN`）而不是用法问题。有权限的机器上按优先级补三组计数：DRAM 吞吐（验证
  「贴在搬运上限上」）、mma 发射槽与 `smsp__inst_executed`（定位 d ≥ 512 停在 90% 的那 10%）、
  以及长依赖链的 stall 原因（验证融合 epilogue 是否真被流量隐藏）。代码级的 `clock64()` 阶段
  分解本轮未做：融合 kernel 的 epilogue 依赖整行归约，分段计时要给每个 block 分配时钟槽位并处理
  跨 warp 读回，成本超过它能回答的问题（§4.3 已经用占用率与延迟探针覆盖了同一结论）。

## 7. 结论

**作业要求与实测对照**：

| 要求 | 门槛 / 目标 | 实测 | 结论 |
|---|---|---|---|
| fp16 精度 | 绝对误差 < 1e-2 | ≤ 7.4e-4 | 达标，余量 13× |
| bf16 精度 | 绝对误差 < 5e-2 | ≤ 7.7e-3 | 达标，余量 6.5× |
| 非 TC baseline | 自定目标：有效带宽 ≥ 50% 峰值 | DRAM 行 943 GB/s = 93.6% | 达标 |
| Tensor Core 路径 | 「最好基于 Tensor Core」 | 10 个 TC 用例全部 PASS（从 SKIP 变 PASS）；DRAM 行与 M2 打平（935 vs 943 GB/s） | 达标 |
| 与量化融合 | 融合且不损精度 | 与两段式逐字节一致；DRAM 行 2.34× | 达标 |
| 与参考实现对拍 | 与 `fast_hadamard_transform` 一致 | d = 2…512 逐元素 bit-exact（max\|diff\| = 0） | 达标 |
| 输入：一系列张量形状与类型 | `[B,S,H,D]`，fp16 / bf16，`head_dim` 为 2 的幂 | 形状与类型以内置表给出：`bench/bench_hadamard.cu` 的表 1（6 个 shape × fp16 / bf16）与表 2（`d = 8…1024` 扫描），`tests/test_correctness.cu` 的对拍用例（`d = 2/64/128/256/512` × fp16 / bf16）；性能日志即 `hw_bench` 的 stdout（`./build/hw_bench > perf.log`） | 以内置形状表覆盖 |
| 执行时间日志 | 提供 | `docs/logs/bench_rtx4090d.txt`：表 1 的 6 个访存档位各 10 行（fp16/bf16 × 两条变换路径 + copy 上限 + CPU 参考 + 量化三行）；表 2 的 8 个 head_dim × 2 个工作集（4 Mi 元素 + `rows = 1` 延迟探针）各 8 行。逐行带 ms 与按各自流量折算的有效带宽 | 已提供 |

**四条结论**：

1. **瓶颈由访存决定，而本问题的访存下限就是一读一写**。256 MiB shape 上 M2 跑到 943 GB/s，
   而同 footprint 的 copy 上限是 925 GB/s——已经没有优化空间；M3 也只做到 935 GB/s。所以
   Tensor Core 在这个问题上的意义不是「更快」，而是「不变慢」并把 GEMM 路线走通。
2. **M3 慢于 M2 是算法性的，不是工程性的**：d ≥ 256 时它已达裸 mma 峰值的 84~90%，`-Xptxas -v`
   显示无 spill、占用率 25~42%，`M3/M2 ≈ D·BW_M2/(2P)` 在 d ≥ 256 上误差 ≤ 5%；差距来自
   `D²` 对 `D·log2 D` 的 MAC 数，交叉点 d ≈ 110。要赢只能改算法（radix-16 hybrid，见 §6）。
3. **量化融合的收益是流量，不是算力**：7 B/elem → 3 B/elem + 4 B/row 只在访存受限时兑现。
   蝶形融合在 DRAM 行把变换完全藏进流量（0.2138 ms ≈ 纯量化 0.2139 ms，而 0.2846 × 3/4 = 0.2135
   也对得上），TC 融合则被 epilogue 的串行链拖住（2.29× vs 2.34×），并且在 d = 16 这种块粒度
   下变成负收益。
4. **「逐字节一致」是设计出来的，不是测出来的**：只有先把累加值舍入到目标精度、再对那个值求 amax
   与量化（§2.4），并且 host 参考与 device kernel 共用同一个舍入入口（1528 个探针 0 处不一致，
   §2.4 / §5），验收标准才能写成「融合 = 两段式」。从 FP32 累加器直接量化会让两者在极少数
   边界上差一个码字，那就只剩下误差量级可测了。

方法学上也值得一提：M5 发现 benchmark 自身的三个口径错误（工作集落在 launch 地板上、CPU 参考
的复杂度用错、搬运上限的措辞写反，见 §3.9）。在没有硬件计数器的容器里，「同 footprint 的搬运
上限 + `-Xptxas -v` 的占用率 + `nsys` 时间线」三件套足以支撑 §4 的全部结论，但它们能成立的前提
是口径先对。

大小（4 Mi 元素），换一个工作集可能就又回到 launch 地板——这正是 §3.9 记录的第一个坑。
