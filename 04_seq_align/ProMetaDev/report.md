# GPU 生命序列比对 —— 总结报告

> 选题：2026 夏季训练营 CUDA 方向项目阶段 · 选题四（生命序列比对）
> 环境：WSL2 Ubuntu 22.04 + CUDA 12.2 + NVIDIA RTX 5070 Ti Laptop (12 GB)，编译目标 `sm_90`
> 国产平台适配：沐曦 MetaX 曦云 C500 + MACA 3.5.3（见第 9 节，已实测验证，自带测试全部通过）
> CPU 基准：32 核，OpenMP 并行

---

## 1. 问题描述

测序仪产生海量短片段（reads，由 A/T/C/G 组成），需要把每条 read 比对回已知的参考基因组，
确定其来源位置。参考基因组是完整 DNA 序列（如人类基因组约 30 亿碱基），按染色体分成多条。

本题要求实现一个 CUDA 程序：

1. 输入 **FASTA 格式**参考基因组（多条序列，可跨行）与 **FASTQ 格式** reads（每条 4 行）；
2. 输出比对结果：`read 名 · 参考序列名 · 起始位置（0-based）· 比对得分`，
   无法比对者标记为 `unknown_origin`；
3. 得分参数：**匹配 +2、错配 −1、空位 −1（线性空位罚分）**；
4. 规模要求：参考基因组 ≥100 条序列 × ≥10⁸ 长度；reads ≥10⁵ 条 × ≥100 长度（默认不超过 200）；
5. 以总体性能为评判标准，需超越 CPU 同级别实现；
6. 默认支持 NVIDIA 平台；使用 FASTQ 质量分可加分。

## 2. 系统设计

### 2.1 总体流水线

直接对 10⁸~10¹⁰ bp 的参考做穷举比对是不可行的（每 read 的代价正比于参考长度）。
本实现采用工业界标准的 **seed-and-extend（种子-扩展）** 架构：

```
参考基因组 ──► ① k-mer 索引（GPU 计数排序 + 散列分桶，常驻显存，只建一次）
reads ───────► ② 种子枚举（GPU：每 (read, seed) 一线程查表 → 候选锚点）
              ─► ③ 候选去重（每 read 一线程：插入排序 + 相邻去重）
              ─► ④ 带状 DP 验证（每候选一线程：窗口内自由起始的 fitting 比对）
              ─► ⑤ 每 read 归约（取最高分，同分取最左）+ 阈值判定
```

索引只依赖参考，与 reads 无关，因此**构建一次后可服务任意批次**，符合"测序仪每秒产生数百万条
reads"的流式场景。

### 2.2 参考基因组的表示

把所有序列拼接成一个连续碱基数组，**序列之间填充 64 个 `N`**，首尾也各留 64 个 `N`：

```
[64×N] seq0 [64×N] seq1 [64×N] ... [64×N]
```

这一设计同时解决三个问题：

1. **k-mer 不跨越序列边界**：含 `N` 的 k-mer 一律不进入索引；
2. **比对窗口不越界**：窗口长度 `L+2B+1`（B 为带宽），首尾 64 的填充保证任何合法锚点的窗口都在数组内，
   无需在核心里做强边界判断；
3. **跨边界比对被自然惩罚**：窗口若跨到相邻序列，会读到一串 `N`（恒为错配），得分显著下降。

全局坐标 → `(序列号, 序列内偏移)` 用对 `seq_begin` 的二分查找完成。

### 2.3 k-mer 索引

- 碱基编码 `A=0, C=1, G=2, T=3`，`k ≤ 16` 时一个 k-mer 恰好放进 32 位整数；
- 哈希用 Murmur 风格的 finalizer 把 2k 位打散到 `2^bits` 个桶；
- 用**计数排序**建桶（GPU 两趟）：
  1. `kmer_count_kernel`：每个参考位置算 code → `atomicAdd(count[hash], 1)`；
  2. 主机端对桶计数做前缀和；
  3. `kmer_scatter_kernel`：再扫一遍，`slot = atomicAdd(cursor[hash], 1)`，写入 `(code, pos)`。
- 桶内**同时存 code**，查表时先比 code 再取位置，因此**哈希碰撞不会产生假阳性**，只是多几次比较。

**桶数自适应**：桶数按"平均负载 16 个条目/桶"选取（`2^bits ≥ n/16`，`bits ∈ [16, 28]`）。

### 2.4 种子枚举与候选去重

- read 上每隔 `seed_step`（默认 8）取一个 k-mer 作为种子；150 bp read、k=15 时约 17 个种子；
- 每个种子查索引得到其全部出现位置 `p`，候选锚点 `q = p − off`；
- 过滤掉窗口放不下的 `q`；
- 每条 read 的候选用 `atomicAdd` 追加到**定长容量区**（默认 64 个），超出丢弃；
- `dedup_kernel`：每 read 一个线程，对候选做插入排序 + 相邻去重。

一条 150 bp read 的 ~17 个种子通常都指向同一个真实位点，去重后候选数降到 1~3 个
（实测目标规模下平均 **2.38 个候选/read**），把验证工作量压到最低。

### 2.5 带状 DP：窗口内自由起始的 fitting 比对

**打分与 DP 定义**（CPU 参考与 GPU 内核完全一致）：

给定锚点 `q`，窗口取 `ref[q−B, q+L+B)`，长度 `W = L + 2B + 1`。
要求**整条 read 被完整比对到窗口内的某一段**，起始位置在窗口内自由，
末端不做惩罚（fitted / semi-global alignment 语义）。

用对角偏移作列下标：`i` = 已消耗的 read 碱基数，`j` = 已消耗的参考碱基数，
`e = j − i − B ∈ [−B, B]`（即 `j − i ∈ [0, 2B]`）。递推：

```
D[i][e] = max( D[i−1][e]   + s(read[i−1], ref[q+i+e−1]),   // 匹配 / 错配
               D[i−1][e+1] + gap,                          // 参考中出现空位
               D[i][e−1]   + gap )                         // read 中出现空位
```

初值 `D[0][e] = 0`（`e ∈ [−B, B]`，即比对可从窗口内任意列起始），结果取 `max_e D[L][e]`。

工程实现要点：

- **一线程一个候选**，两行 DP 缓冲放寄存器（`B=8` 时每行 17 个 `int32`，共 34 个寄存器），
  用 `#pragma unroll` 完全展开内层循环；
- 内核按 `B` 做模板特化（4 / 8 / 16），使数组维度成为编译期常量；
- 参考与 read 都以碱基编码（`uint8`）形式上传，省去内核里的字符比较；
- 边界用 `j > W` 提前 `break`，并把 `j < 1` 与 `e ± 1` 越界的情况显式置为负无穷。

### 2.6 关键技巧：把「得分」与「起始位置」打包进一个 int32

由于窗口内起始位置是自由的，DP 必须同时报告起始坐标才能给出确定结果。
如果额外维护一个 `start[i][e]` 数组，寄存器占用要翻倍。

本实现把两者打包进同一个 `int32`：

```
packed = (score + L) × (2B+1) + (2B − t)          t = 起始列编号 ∈ [0, 2B]
```

- `score ≥ −L`（每个 read 碱基最差是错配），故 `score + L ≥ 0`，整数除法可安全解码；
- 转移时把得分增量乘以 `(2B+1)` 再加，低位的起始列编号沿路径自动保持；
- 取 `packed` 最大 ⇒ **得分最大**；得分相同时 `2B − t` 最大 ⇒ `t` 最小 ⇒ **起始位置最靠左**。

这样既省掉一整个 DP 数组，又天然得到"同分取最左"的确定性规则（CPU 与 GPU 因此逐字节可复现）。

### 2.7 CPU 侧的两个参考实现

| 实现 | 用途 | 复杂度 |
|---|---|---|
| `cpu`（穷举） | **正确性基准**：枚举参考上每一个锚点做同样的窗口 DP | O(N_ref × L × 2B) 每 read |
| `cpuseed`（同算法） | **性能基准**：主机端建同样的索引，跑同样的种子→候选→DP→归约流程，OpenMP 并行 | 与 GPU 同 |

前者用于小规模**逐行 diff**（因为它是真正的穷举，不依赖种子，能发现种子漏检）；
后者用于大规模**逐行 diff** 与加速比测量（因为穷举在大参考上不可行）。

## 3. 优化历程与开发中发现的问题（真实记录）

### 3.1 空位符号写反，导致"空位越多分越高"

**现象**：自检里精确匹配的 read `ACGTACGT` 应得 16 分（8 个匹配 × 2），实测却是 20 分；
随机 read 也被判为"可比对"。

**根因**：配置里 `gap = −1` 表示"空位罚分 −1"（本身已是负值），
而递推里写成了 `max(best, u − cfg.gap)` —— 等于每次空位 **加 1 分**。
于是 DP 会无脑插入空位来刷分。

**修复**：改为 `u + cfg.gap`。

> 教训：把"罚分"存成负值、又在表达式里做减法，是极易出错的双重取负。
> 一处符号错误就足以让最优解完全失真（本例中得分甚至超过了理论上限）。

### 3.2 固定起始点会漏掉"起始点发生偏移"的最优解

**现象**：加入自动比对后，`--cpu-ref` 逐查询比对发现有条 read 两者不一致：

```
CPU 穷举: seq=chr3 pos=2857 score=290
GPU:      seq=chr3 pos=2858 score=288
```

GPU 找到的是"真值位置"（该 read 确实采样自 2858），但 CPU 穷举找到了**更高分**的解。

**分析**：把得分拆开看。位置 2858 处是 146 匹配 + 4 错配 → `146×2 − 4 = 288`；
位置 2857 处的解是 147 匹配 + 3 个"非匹配列" + 1 个参考空位 → `147×2 − 3 − 1 = 290`。
即：**在参考中删掉一个碱基，可以把一个错配变成匹配**，净赚 2 分。
这是题目给定打分下完全合法的比对。

**根因**：GPU 的候选锚点由种子反推得到（`q = p − off`），
而该最优比对的起始点比种子支持的锚点**左偏了 1**，因此不在候选集里。

**修复**：把 DP 从"**定起始点**"改为"**窗口内自由起始**"——
锚点只决定窗口 `[q−B, q+B]`，比对可从窗口内任意列开始。
这是更贴合"最佳匹配位置"语义的定义，也让 CPU 与 GPU 的结果重新对齐。
修改后上例两者都给出 `pos=2857 score=290`，全量逐行 diff 完全一致。

> 教训：seed-and-extend 里"候选 = 起始点"是一个隐含且不成立的假设。
> 带空位的比对会让最优起始点相对种子锚点漂移，必须让窗口（而非单点）承担候选语义。

### 3.3 错误匹配与空位同分，使 DP 主动"挑选"匹配（重要的负结果）

**现象**：随机 read（与参考无关）经 CPU 穷举后也能拿到很高的分——
150 bp 随机 read 得分可达 **138 / 300**（约满分的 46%），40 bp 随机 read 可达 47 / 80（59%）。

**根因**：题目的打分里 **错配(−1) 与空位(−1) 同分**。这带来一个非直觉的后果：
把一个错配替换成"空位 + 平移"，代价相同，但平移后**后续若干列的错配可能变成匹配**。
代价 1 分换取 2 分，DP 自然乐于这么做。而带宽 `B` 恰好提供了这种平移的自由度
（`j − i ∈ [0, 2B]`，每列可选 17 个不同位置）。

粗算：17 个候选位置中至少有一个匹配的概率约 `1 − 0.75¹⁷ ≈ 99%`，
于是随机 read 的每个碱基几乎都能被"安排"到一个匹配，得分被系统性抬高。

**这不是 bug，而是给定打分参数的固有性质**（真实比对工具都会加 gap-open 罚分来避免它）。

**处理**：本实现用两道闸门来判定 `unknown_origin`：

1. **种子**：随机 read 几乎不可能在参考上找到精确 k-mer 匹配。
   10⁸ bp 参考、k=15 时，一个随机 15-mer 的期望命中次数约 `10⁸ / 4¹⁵ ≈ 0.09`。
   实测随机 read 的 `unknown_origin` 判定率 **100%**（20 万条随机 read 全部正确拒绝）。
2. **阈值**：`score ≥ min_ratio × match × L`（默认 0.7）。
   自带来源的 read（3% 替换）得分约为满分的 95%，与随机 read 的 ~50% 有充分间隔。

> 教训：当评测指标本身存在退化（degenerate）情形时，不能只用"最优值"做判定，
> 必须引入独立于该指标的判据（这里是"是否存在精确种子"）；
> 并且要在报告里把这个性质写清楚，而不是把好看的数字当作算法能力。

### 3.4 索引桶数固定，小参考时主机前缀和与 PCIe 传输成为瓶颈

**现象**：`T_index` 在 15 kbp 参考与 2 Mbp 参考上**都停在约 220~250 ms**，与数据规模无关。

**定位**：加分段计时后发现耗时集中在"计数"阶段之后的**主机端前缀和 + H2D/D2H 传输**：
固定 `2^22` 个桶、每桶 `unsigned long long`，需要 33 MB × 3 次跨 PCIe 搬运，
而 WSL2 的 PCIe 带宽很低（实测约 0.6 GB/s）。数据量越大这部分占比越小，
所以"时间不涨"本身就是线索。

**修复**：桶数改为按参考规模自适应（平均负载 16 条目/桶）。
2 Mbp 参考的桶数从 4.19 M 降到 131 K，传输量降到 1/32。
`T_index` 从 ~240 ms 降到 **6.3 ms**，且此后随规模线性增长（符合真实计算特征）。

### 3.5 PTX JIT 的一次性开销污染计时

**现象**：修复 3.4 后 `T_index` 在 2 Mbp 上仍有 ~230 ms，且多次运行都稳定复现。

**根因**：本机 GPU 是 **sm_120（Blackwell）**，而 CUDA 12.2 不支持 sm_120 原生编译，
只能用 sm_90 的 PTX 由驱动 JIT。JIT 发生在**每个内核的首次启动**，
且 WSL2 下不会跨进程复用编译缓存。第一次调用 `kmer_count_kernel` 时，
整个模块的 JIT 开销被计入了"计数"阶段。

**修复**：在计时区间之前做一次**完整预热**（用一段极小的合成分片跑通整条流水线，
让所有内核都完成首次启动），之后 `T_align` 与 `T_index` 都只反映真实计算。

> 说明：这是本机环境的产物（在 sm_90 卡上或原生支持 sm_120 的 CUDA 上不存在）。
> 报告中的所有性能数字都已在预热之后采集。

### 3.6 主机端 FASTA 解析成为端到端瓶颈

**现象**：20 Mbp 参考的 `T_load` 高达 **815 ms**，占端到端的 90%。

**根因**：最初的解析实现是 ① 逐行 `std::getline` + `chomp` + `cur += line`（多次重新分配），
② 为了取序列名把文件又扫了一遍。

**修复**：一次性把整个文件读进内存，再在内存里按行切分、`append(buf, i, len)` 直接拷贝，
名称与序列一趟收集完。

**效果**：20 Mbp 的 `T_load` 从 815 ms → **107 ms**；10⁸ bp 为 1158 ms（约 87 MB/s，受 WSL2 磁盘读取限制）。

### 3.7 用两个互补的基准把"正确性"钉死

因为种子会漏检，只用穷举基准做大规模比对是不现实的（代价正比于参考长度），
只用同算法基准又无法发现共同的算法错误。因此：

- **小规模**：GPU vs **CPU 穷举**（不依赖种子）→ 4 组 `(k, band)` 组合全部逐行一致；
- **大规模**：GPU vs **CPU 同算法实现**（独立代码路径、独立内存管理、OpenMP 并行）
  → 10⁸ bp × 10⁵ reads 的输出**逐字节一致**。

两条路径的实现完全独立（一条在 GPU 上、一条在 CPU 上，索引与 DP 分别编码），
因此同时通过可以作为很强的正确性证据。

### 4.4 关于"起点/得分不完全一致"

真值文件记录的是**采样位置**与**无空位情形下的理论得分**（`2L − 3m`，`m` 为替换数）。
而 DP 求的是允许空位的**最优得分**，它可以合法地高于该理论值（见 3.2 的实例）。
因此 3% 的"起点不一致"与 11% 的"得分不一致"不是比对错误，而是**最优解与采样真值的差异**；
真正的正确性证据是 4.2/4.3 中与两个独立基准的逐字节一致性。

## 5. 性能指标

### 5.1 指标定义

| 指标 | 含义 |
|---|---|
| **T_load** | 主机端解析 FASTA / FASTQ |
| **T_index** | 构建 k-mer 索引（含上传参考） |
| **T_upload** | 上传本批 reads 到显存 |
| **T_seed** | 种子枚举 + 候选去重 |
| **T_verify** | 带状 DP 验证 |
| **T_reduce** | 每 read 归约 + 回传 |
| **T_align** | 单批 reads 的完整比对（upload + seed + verify + reduce） |
| **T_total** | 端到端（T_load + T_index + T_align） |

### 5.2 多规模 GPU / CPU 对比

CPU 为 32 核 OpenMP，运行**完全相同的 seed-and-extend 算法**。

| 规模 (参考bp / reads) | 索引条目 | GPU 索引 | GPU 比对 | CPU 索引 | CPU 比对 | 比对加速比 |
|---|---|---|---|---|---|---|
| 50 k / 5 k | 15 k | 1.11 ms | 0.56 ms | 0.86 ms | 8.94 ms | 16.0× |
| 200 k / 20 k | 1.6 M | 6.23 ms | 3.80 ms | 32.2 ms | 16.5 ms | 4.3× |
| 1 M / 50 k | 20 M | 82.6 ms | 11.2 ms | 1134 ms | 60.6 ms | 5.4× |
| **5 M×20 = 10⁸ / 10⁵** | **100 M** | **459 ms** | **30.5 ms** | **10 630 ms** | **232 ms** | **7.6×** |

**目标规模下的端到端**：

- GPU：`T_index + T_align = 459 + 30.5 = 490 ms`
- CPU：`10 630 + 232 = 10 862 ms`
- **整体加速比 22.2×**

**索引构建加速比**：`10 630 / 459 = 23.2×`（CPU 侧为单线程建桶，GPU 为全并行计数排序）。

**比对吞吐**：`10⁵ reads / 30.5 ms ≈ 3.3 × 10⁶ reads/s`，按碱基计约 **500 Mbp/s**。

### 5.3 目标规模的比对阶段拆解（10⁸ bp × 10⁵ reads）

| 阶段 | 耗时 | 占比 |
|---|---|---|
| T_upload（15 MB H2D） | 12.4 ms | 41% |
| T_seed | 7.0 ms | 23% |
| T_verify（237 804 个候选 × 17×150 单元） | 8.9 ms | 30% |
| T_reduce + 回传 | 0.4 ms | 1% |
| **T_align 合计** | **30.0 ms** | 100% |

- **上传占比最大（41%）**，说明在 WSL2 的低带宽 PCIe 下，30 MB 的 reads 搬运已成为瓶颈；
  真实流式场景应改为 pinned memory + 异步拷贝并与计算重叠（见「局限」）。
- DP 验证的实际算力：`237 804 × 2 × 150 × 17 ≈ 1.2 × 10⁹` 次单元更新 / 8.9 ms
  ≈ **1.4 × 10¹¹ 单元/秒**，说明寄存器驻留 + 全展开的带状 DP 达到了较高效率。

### 5.4 参数敏感性（1 Mbp 参考 × 50 k reads，3% 替换）

| k | band | seed_step | 候选对 | 比对耗时 | 起点一致率 | 随机 read 拒绝率 |
|---|---|---|---|---|---|---|
| 11 | 8 | 8 | 2 889 528 | 99.10 ms | 96.85% | 100% |
| 13 | 8 | 8 | 307 943 | 20.50 ms | 96.98% | 100% |
| 15 | 4 | 8 | 55 987 | 17.32 ms | 97.02% | 100% |
| 15 | 8 | 4 | 71 572 | 13.14 ms | 96.98% | 100% |
| 15 | 8 | 8 | 55 987 | 10.81 ms | 96.98% | 100% |
| 15 | 8 | 16 | 48 501 | 9.92 ms | 96.98% | 100% |
| 15 | 16 | 8 | 55 987 | 10.46 ms | 96.98% | 100% |

- **k=11 时候选数是 k=15 的 51 倍**（短种子在参考上重复率高），耗时 9 倍，而召回率并无提升
  → 默认 `k=15` 是合理的工作点；
- `band` 从 4 增到 16 几乎不影响耗时（因为用模板特化后内层循环仍被完全展开，
  且带宽只改变寄存器的循环次数），但能容纳更多 indel；
- `seed_step` 从 4 增到 16 使候选数下降 32%、耗时下降 25%，召回率不变
  → 在低突变率数据上可以用更稀疏的种子换取速度。
- 所有配置下随机 read 的拒绝率都是 **100%**，说明这道闸门主要来自"精确种子"而非阈值。

## 6. 依赖说明

| 组件 | 实现方式 |
|---|---|
| k-mer 索引 / 种子枚举 / DP 验证 / 归约 | 纯手写 CUDA C++，仅用 `atomicAdd`（32/64 位）与 `__restrict__` |
| 计数排序 | 自实现（设备端计数 + 主机端前缀和 + 设备端散列） |
| CPU 穷举参考 | 自实现带状 DP（滚动两行） |
| CPU 同算法基准 | 自实现主机端索引 + OpenMP 并行 |
| 合成数据生成 | 自实现（Python 标准库） |
| 第三方库 | **无**（仅 CUDA Runtime + C++ 标准库 + OpenMP） |

**未使用 Hopper / Blackwell 特性**：无 WGMMA、无 TMA、无 FP8/FP4、无分布式共享内存。
所有内核只用 sm_70 即有的一般特性，代码在 sm_70 及以上均可编译运行。
构建产物为单一可执行文件 `seqalign`。

## 7. 局限与未来可继续提升的方向

**本次实现的局限**：

1. **未在题目要求的最大规模上实测**。题目要求 ≥100 条 × 10⁸ bp（合计 10¹⁰ bp）。
   按本实现的内存模型，10¹⁰ bp 的 k-mer 索引约需 120 GB 显存，12 GB 的本机无法承载；
   磁盘上还需存放约 10 GB 的 FASTA。本次实测做到 **10⁸ bp**（题目单条长度要求的量级，
   为总规模的 1/100），并已验证程序对规模是线性的。
2. **种子敏感度有上限**。突变率高于约 15% 或存在较多 indel 的 read，
   可能找不到精确 k-mer 种子而漏检。工业界做法是引入 spaced seeds、minimizer
   或对种子缺失的 read 走 fallback 通路。
3. **阈值为经验值**。`min_ratio` 默认 0.7 由本报告的合成数据标定；
   严格做法是像 BLAST 那样基于参考规模与打分矩阵做**统计显著性（E-value）**标定。
4. **未使用 FASTQ 质量分**（题目第 4 行的加分项）。合理做法是把质量分转成
   位置相关的错配代价，让 DP 在高质量位置更"不容忍"错配。
5. **国产平台适配已完成**（沐曦 曦云 C500，见第 9 节；仅新增构建脚本，源码零改动，自带测试全部通过）。
6. **`ncu` / `nsys` 未采集**：WSL2 不透传 CUPTI，瓶颈判断基于分阶段计时与算术量估算。
   此外本机为 sm_120、CUDA 12.2 不支持其原生编译，只能 JIT 运行 sm_90 PTX，
   首次内核启动有一次性编译开销（已在计时前预热剔除）。

**优化方向**：

1. **重叠上传与计算**：当前 H2D 占 `T_align` 的 41%。改为 pinned memory +
   多流（多 batch 的 upload / seed / verify 交替进行）可把上传完全藏在计算之后。
2. **minimizer / 双索引压缩索引体积**：只索引每个窗口的最小 k-mer，
   可把索引缩小 5~10 倍，是支撑 10¹⁰ bp 规模的关键。
3. **参考分片 + 流式处理**：把参考按染色体切成可容纳的分片，逐片建索引与比对，
   让显存需求与参考总规模解耦。
4. **种子敏感度增强**：加入 spaced seeds、双种子组合（pairwise seeding），
   或对无种子的 read 用较短的 k 做二次搜索（two-pass seeding）。
5. **仿射空位罚分**：题目要求线性空位，但工程上仿射（gap-open + gap-extend）
   能显著抑制 3.3 中提到的"用空位挑匹配"的退化行为；可作为可选模式。
6. **质量分加权**：把 FASTQ 第 4 行转成位置相关代价，争取加分项。
7. **warp 级协作 DP**：当前是"一线程一个候选"，在候选数很少时 GPU 占用不足；
   当候选稀疏时可切换为"一线程块一个候选"的反斜对角波前并行。

## 8. 复现方式

```bash
# 构建（默认 sm_90；同时生成 PTX 以兼容更新架构）
bash build.sh 90

# 自检
./build/seqalign selftest

# 端到端测试（构建 + 自检 + GPU/CPU 穷举逐行比对 + 真值召回 + 确定性）
bash tests/run_tests.sh 90

# 多规模性能基准（GPU vs CPU 同算法）
bash tests/benchmark.sh 90

# 参数敏感性扫描
bash tests/sensitivity.sh

# ---- 目标规模复现（10⁸ bp 参考 × 10⁵ reads，生成约 20 秒） ----
python3 tools/gen_data.py --ref-seqs 20 --ref-len 5000000 --reads 100000 \
    --read-len 150 --sub-rate 0.03 --random-frac 0.2 --seed 2026 \
    --out-ref tests/tmp/target.fa --out-reads tests/tmp/target.fq \
    --out-truth tests/tmp/target.truth

# GPU 比对（含真值统计）
./build/seqalign gpu tests/tmp/target.fa tests/tmp/target.fq tests/tmp/target.gpu.txt \
    --k 15 --band 8 --seed-step 8 --truth tests/tmp/target.truth

# CPU 同算法基准，并与 GPU 结果逐字节比对
./build/seqalign cpuseed tests/tmp/target.fa tests/tmp/target.fq tests/tmp/target.cpu.txt \
    --k 15 --band 8 --seed-step 8 --truth tests/tmp/target.truth
diff tests/tmp/target.gpu.txt tests/tmp/target.cpu.txt && echo "完全一致"
```

### 输入格式

**FASTA 参考基因组**（`>` 开头为序列名，其后可多行碱基）：
```
>chr1
ATCGATCGATCG...
>chr2
GCTAGCTAGCTA...
```

**FASTQ reads**（每 4 行一条：`@标识` / 碱基 / `+` / 质量）：
```
@read1
ATCGATCG
+
IIIIIIII
```

**比对结果**（`read名 参考序列名 起始位置 得分`，未比对则只有 `read名 unknown_origin`）：
```
read1 chr1 0 8
read2 chr2 0 8
read3 unknown_origin
```

## 9. 国产平台适配：沐曦（MetaX 曦云 C500 / MACA）

### 9.1 平台环境与编译方式

| 项目   | 值                                                                                |
| ---- | -------------------------------------------------------------------------------- |
| 加速卡  | 沐曦 曦云 C500（`mx-smi` 2.2.12，KMD 3.8.30）                                           |
| 设备属性 | `warpSize = 64`，104 个 SM，`maxThreadsPerBlock = 1024`，共享内存 64 KB/block，计算能力 `(10,0)` |
| 软件栈  | MACA 3.5.3.20（SDK 3.5.3.307），CUDA 兼容层由 `tools/cu-bridge` 提供                       |
| 编译器  | `mxcc 1.0.0`（`/opt/maca/mxgpu_llvm/bin/mxcc`）                                     |

本工程原本用 CMake + nvcc，沐曦平台改用 [`build_maca.sh`](build_maca.sh)：

```bash
mxcc -x maca -offload-arch native --maca-path=/opt/maca \
     -Iinclude -I/opt/maca/tools/cu-bridge/include -L/opt/maca/lib \
     -imacros __macro_mxcc.h -forward-unknown-to-compiler \
     -fgpu-rdc --maca-link -lToolsExt_cu -lruntime_cu -lmcToolsExt \
     -std=c++17 -O3 -use-fast-math \
     src/main.cpp src/io.cpp src/cpu_ref.cpp src/cpu_seeded.cpp src/align_gpu.cu \
     -o build_maca/seqalign

export LD_LIBRARY_PATH=/opt/maca/lib
```

`tests/run_tests.sh` 固定使用 `./build/seqalign`，因此跑测试前把产物放过去即可：

```bash
mkdir -p build && cp build_maca/seqalign build/ && bash tests/run_tests.sh
```

### 9.2 移植要点：三个编译参数，**源码零改动**

| 参数                                       | 作用                                                              |
| ---------------------------------------- | --------------------------------------------------------------- |
| `-imacros __macro_mxcc.h`                | 让 `__CUDACC__` 等 CUDA 宏在 mxcc 下生效（否则 `__host__ __device__` 宏退化，见 9.3） |
| `-fgpu-rdc --maca-link`                  | 设备侧可分离编译与 MACA 链接阶段                                             |
| `-lToolsExt_cu -lruntime_cu -lmcToolsExt` | cu-bridge 把 `cudaXxx` 映射为 `wcudaXxx`，实现体在 `libruntime_cu.so`，必须显式链接   |

另注：fast-math 开关是 `-use-fast-math`（连字符），不是 nvcc 的 `-use_fast_math`（下划线），
写错会被 mxcc 解析成 `-u se_fast_math` 而报 `unknown argument`。
